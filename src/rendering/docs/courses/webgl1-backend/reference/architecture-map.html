1. 四层与依赖方向

来源：HW2 架构设计 §4（codex-workspace/…/2026-08-26-hw2-complete-webgl1-architecture-design.md）。高层描述「画什么」，Backend 决定「在当前这个 WebGL1 context 上怎么画」。

第一层 · 场景与逻辑资源（CPU，没有任何 GL handle）· 已实现
scene/ SceneNode、Group、Scene、Mesh、Transform、cameras/ · resources/ Geometry、VertexAttribute、ShaderModule、Material、Texture2D、CubeTexture、RenderTarget · core/ Resource、errors、requireNonNull
↓ 数据：第二层读取第一层（只借用，不持有设备）
第二层 · 帧提取与编排 · 只有类型
已有：RenderItem、ViewState（一帧的值快照）。未实现：RenderList、RenderListBuilder、RenderPass、ForwardPass、RenderPipeline、Renderer（Task 16–18）
↓ 调用：只通过 RenderBackend 接口
第三层 · 设备后端 · 基础设施已实现，编排类 2026-09-26 有了初版
RenderBackend（接口：ready、resizeDrawingBuffer、withRenderSurface、draw、dispose；清除改成进入 withRenderSurface 时的一项描述）、RenderSurface · webgl1/ 下 13 个文件（第 3 节；Task 15 又加了 WebGL1SurfaceScope、WebGL1Uniforms）· WebGL1Backend Task 15
↓ 调用：唯一持有 gl 的一层
第四层 · 平台与设备
HTMLCanvasElement · WebGLRenderingContext · 浏览器（ANGLE）· 驱动 · GPU

两种方向。调用（谁调用谁、谁持有谁）只沿 Engine → Renderer → Pipeline → Pass → Backend → GL 往下走；类型的 import 则指向数据：处理数据的机器都可以读第一层的资源和第二层的值类型，这些数据不知道任何读它的机器。原则是被依赖的一方更稳定、更通用。禁止的反向依赖包括：Backend 知道 Pass、Scene 或 HW2；Mesh 知道 framebuffer 或 GL；Resource 知道具体 Manager（Resource 只提供 onDispose 通知，不知道谁在听）；Pass 自己调用 gl.clear、gl.useProgram 或 gl.draw*。

Backend 独占它的 context。后端之外的任何代码都不能直接改同一个 context 的 program、VAO、buffer、framebuffer、viewport 或渲染状态；否则 WebGL1State 的缓存就不可信了（HW2 设计 §18）。

2. 一次 draw 的目标顺序 Task 15

2026-09-26 初版的实际顺序：先解析资源（programs.get、geometries.get），再做 uniform 预检（uniforms.prepare：验证所有 active uniform，cubemap 第一次用到时会在这里上传）；然后才 useProgram、应用渲染状态、上传 uniform，最后绑定顶点输入并发出 draw（WebGL1Backend.ts:183–231）。和上表的差别在于「预检提前」：资源的冷路径可能让 State 缓存失效，所以要先把资源都解析完，再应用这一次 draw 的状态。

4. GPU 对象所有权

核心规则：CPU Resource 决定逻辑生命周期；Manager 只管理「这个 context」里的 GPU 表示。Manager 从不调用 CPU 资源的 dispose()，只订阅它的 onDispose 通知。

GPU 对象谁创建谁删除、何时删除缓存 key
WebGLShaderProgramManager.compile同一次 get 的 finally 里就删（链接成功后先 detach）不缓存
WebGLProgramProgramManager.getProgramManager.release：ShaderModule dispose 或 Manager dispose 时；如果正在使用，先 useProgram(null)ShaderModule 对象身份
WebGLBuffer（属性、索引）GeometryManager.uploadGeometryManager.release：Geometry dispose 时；删之前先释放依赖它的 VAOGeometry 对象身份
WebGLVertexArrayObjectOESOESVertexInputManager.bind（首次组合时）releaseGeometry、releaseProgram（经 beforeDelete，先于 buffer 和 program）或 disposeGeometry → WebGLProgram 两层 Map
WebGLTexture（cube）CubeTextureManager.getCubeTextureManager.release：CubeTexture dispose 时CubeTexture 对象身份
FBO、颜色纹理、深度 renderbufferRenderTargetManager.createrelease（RenderTarget dispose 时），或者 revision 变化时：新的一套建完整后，再删旧的RenderTarget 对象身份 + revision
（无）WebGL1State—只记「上次设成了什么」；undefined = 不知道，null = 明确没有绑定

context 丢失时，所有 Manager 走 invalidateForContextLoss()：只丢记录、取消订阅，不对已经失效的 context 调用任何 delete，而且这一代 Manager 永远不再复用。恢复后由 Backend 重新探测能力、创建新的一代。

5. 接线：ResourceManager 怎样组装

来源：WebGL1ResourceManager 构造函数。

WebGL1Backend（Task 15）
 ├─ WebGL1State ◀──────────── hooks.invalidateState（凡是 Manager 直接改过 GL 状态，都会调用它）
 ├─ WebGLContextLifecycle     onLost → 整批失效；restore → 新 capabilities + 新 State + 新 ResourceManager
 └─ WebGL1ResourceManager
     ├─ vertexInputs  = createWebGL1VertexInputManager(gl, caps, hooks)   → 有 VAO 扩展选 OES，否则选 Manual
     ├─ geometries    beforeDelete: geometry => vertexInputs.releaseGeometry(geometry)
     ├─ programs      beforeDelete: program  => vertexInputs.releaseProgram(program)
     ├─ cubeTextures
     └─ renderTargets

 dispose 顺序：vertexInputs → renderTargets → cubeTextures → geometries → programs
            （先结束借用方，再结束被借用的资源的所有者；某一步失败就停在那一步，下次 dispose 从那里重试）

为什么用显式的 beforeDelete 回调，而不是让 VertexInputManager 也去订阅 Geometry 的 onDispose？因为几个 listener 的执行先后取决于注册顺序，而「先删 VAO、再删 buffer」这个顺序必须由代码结构来保证，不能靠运气（HW2 设计 §22.1）。

为什么只传 invalidateState 回调，而不把整个 State 传进去？Manager 只需要「让缓存失效」这一项能力，不应该顺带获得改 viewport、剔除方式的能力。这就是窄接口 (narrow interface) 和依赖注入。

6. 三种容易混淆的生命周期

谁的状态转换由什么触发源码
CPU Resource可用 → disposed（单向）dispose()/tryDispose()，或者最后一个 Scene 引用释放；先通知 listener，再清 CPU 数据Resource.finalizeDisposal
一代 Manager可用 → lost（只丢记录）/ disposed（按顺序删 GPU 对象）context 丢失通知，或者入口处发现 isContextLost()；Backend disposeinvalidateForContextLoss、dispose
context 状态机ready → lost → restoring → ready 或 restore-failed；任何状态 → disposed浏览器事件；transitionVersion 防止旧调用栈覆盖新状态handleLost、handleRestored

另外还有两个名字里带 restore、但与 context 恢复无关的东西：State.restoreSurfaceState() 恢复的是临时切换过的 framebuffer 和 viewport；GeometryManager、RenderTargetManager、TextureUploadSupport 在 finally 里恢复的是它们临时改动过的绑定。

7. 校验的四个维度

来源：src/rendering/docs/design-reading-guide.zh-CN.md，讲解顺序第 4 条。遇到任何一处校验，先问它属于哪一类，再问它挡住了哪个反例。

维度什么时候知道项目里的例子
输入（类型、范围、形状）CPU 构造时就能判断，只判一次VertexAttribute 的 itemSize 必须能整除数据长度（VertexAttribute.ts:86）；索引不能超出 vertexCount，drawCount 要和拓扑匹配（Geometry.ts:212）；Material 参数要是有限数、int32 范围内（materialParameters.ts:156–174）；RenderTarget 尺寸是正的安全整数；fovY ∈ (0, π)
设备能力（扩展、上限）只有拿到具体 context 才知道；每个 context 的每一代都要重新判断MAX_VERTEX_ATTRIBS；Uint32 索引需要扩展，或者最大值 ≤ 65535（GeometryManager.prepareIndices）；cube 尺寸上限、NPOT 规则、浮点纹理扩展（validateStorage）；MRT 扩展和附件数量上限（RenderTargetManager.validate）
组合兼容（两份各自合法的资源相遇）program 与 geometry 第一次组合时shader 用到的每个 active attribute，Geometry 里都要有同名数据；itemSize 在 1..4；location 唯一且小于上限；拒绝矩阵 attribute（VertexInputSupport.resolve、readInputs）
生命周期（会变的状态）每个入口都要查；跨过一次 GL 查询或外部回调之后还要再查一次Resource.disposed；Manager 是否已 disposed；isContextLost()（后端里共 34 处）；releasing 集合防止重入；transitionVersion

把校验放在哪一层，取决于最早能在哪里知道答案：不可变的输入在构造时判一次就够；设备能力要等拿到 context；会变的生命周期每次都得重新确认。每个 GL 调用失败时各自通过哪条通道报告，见 API 速查 · 五种失败通道。

8. 与 three.js r177 的对应

three.js 自 r163 起不再支持 WebGL1（WebGLRenderer.js:101），所以对照看的是它的 WebGL2 内部实现。模块的切分几乎一一对应，差别在于具体取舍。

本项目three.js r177相同不同
WebGL1State WebGLState.useProgram、enable 用 JS 缓存省略重复的 GL 调用 three.js 的 reset() 会真的把 GL 重置成默认值，再把缓存同步成这些默认值；本项目的 invalidate() 只遗忘缓存（全部置为 undefined），不发任何 GL 命令
VertexInputManager（OES / Manual） WebGLBindingStates.getBindingState VAO 按 geometry × program 缓存 three.js 只用 WebGL2 原生 VAO，key 里还多一层 wireframe；本项目多了一条「没有扩展时手动接线」的策略
ProgramManager getProgramCacheKey、acquireProgram、releaseProgram 懒编译并缓存 three.js 用「材质参数拼出的字符串」作 key，用 usedTimes 引用计数；本项目用 ShaderModule 对象身份，释放跟随 Resource 的生命周期
GeometryManager WebGLGeometries.onGeometryDispose、WebGLAttributes.updateBuffer 监听 dispose：删除 buffer，并清理这个 geometry 相关的 VAO 状态 顺序正好相反：three.js 先删 buffer、后调用 releaseStatesOfGeometry（第 13–38 行）；本项目用 beforeDelete 保证先删 VAO、再删 buffer。另外，three.js 按单个 BufferAttribute 管 buffer，支持用 bufferSubData 局部更新；本项目整份 Geometry 静态上传（STATIC_DRAW），没有更新接口
CubeTextureManager、RenderTargetManager uploadCubeTexture、setupRenderTarget 上传、设置 sampler 参数、建 FBO three.js 用一个 WebGLTextures 包办 2D、cube、3D 纹理和 FBO；本项目按资源类型拆成几个 Manager；pixelStorei 的处理，three.js 是每次按纹理属性直接设置，本项目是「保存 → 设成确定值 → 恢复」
Capabilities WebGLCapabilities、WebGLExtensions 探测上限和扩展 本项目返回冻结的快照，每一代 context 重新探测一次
ContextLifecycle onContextLost、onContextRestore 都调用 preventDefault()；恢复时重建全部内部模块（three.js 是重跑 initGLContext） 本项目有显式的状态机、用 transitionVersion 防重入、保留失败诊断；three.js 只有一个 _isContextLost 标志
Resource.onDispose、Manager 里的 Map<CPU 对象, …> EventDispatcher 的 'dispose' 事件、WebGLProperties 的 WeakMap 都用「CPU 对象 → GPU 记录」的映射，CPU 对象里不存 handle 本项目用 Map，配合显式的 unsubscribe 和 Scene 引用计数；three.js 用 WeakMap，释放完全靠用户手动调用 dispose()
