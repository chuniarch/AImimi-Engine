系列「带阴影的三角形：从一个函数到 src/rendering」5/7 · 约 25 分钟

两遍变成两个 Pass：画到哪是进门出门，画几遍由场景说了算

第 43 课的 renderFrame 写死了「先画阴影图，再画屏幕」。可是 HW2 没有阴影，FFT 要画十几遍。这一课把每一遍做成一个 Pass 对象，按顺序装进 Pipeline，由场景交出自己要的那一组。顺手解决两件手写时容易出错的事：「画到哪」变成进门、出门，出错也一定换回来；每次 draw 自己设好要的状态，不靠前一遍留下。

和你的目标的关系 —— HW1 设计里的 ShadowMapPass、Engine.setScene({ scene, camera, passes }) 就是这一课的两样东西。真实代码现在还在 Engine 里写死了一个 ForwardPass（engine.ts:404–405），HW1 要加阴影，第一步就是让场景交出 Pass。
默认你已经会的：① 第 43 课的 buildFrame、shadowPass、mainPass、renderFrame；② 第 27 课：framebuffer 绑定以后，之后的 draw 和 clear 都写进它，直到换绑；③ 第 39 课：进门时要问两次 GL（framebuffer 和 viewport）。
这一课讲的：一遍一个对象；手写「画到哪」的两个坑和进门出门；只有第一遍开了深度测试的坑和「每次 draw 自己设状态」；场景交出 Pass、引擎照单安装；对照 src/rendering 和 three.js。
在一帧里的位置和寿命：Pass 对象由场景建、交给引擎以后归 Pipeline 所有，活到下一次换场景；每帧被调用一次 execute，只读快照和后端。进门出门只活一个回调那么长。

1. renderFrame 写死了画几遍

第 43 课一帧是这样的：

function renderFrame(gl, managers, scene, camera) {
  const frame = buildFrame(scene, camera, aspect)
  shadowPass(gl, managers, frame)
  mainPass(gl, managers, frame)
}

需求：同一个程序还要显示一个没有阴影的场景（HW2 那样：一个 shader、只画一遍）。按这个写法只有两条路：再写一个 renderFrameWithoutShadow；或者在 renderFrame 里加 if (有阴影) shadowPass(…)，mainPass 里再加「有阴影才绑阴影图」。FFT 来了又要再加十几个 if。「这个场景要画哪几遍」是场景的事，却写在了每帧的代码里。

要把它交出去，每一遍得先变成一个能放进列表的东西：一个对象，有名字、能执行、能释放自己拥有的资源。

2. 一遍一个对象

每个 Pass 只有三样：name、execute(context)、dispose()。context 是这一帧的快照加一个后端：{ frame, backend }。Pass 拿不到 gl，也拿不到 Manager——它只能对后端说两句话：「我要画到哪」（withRenderSurface）和「画这个物体」（draw）。

几处要点：

  • ShadowMapPass 拥有自己画深度的 shader，dispose 时释放它；ForwardPass 什么都不拥有。Pipeline 拥有这组 Pass：Pipeline 释放时，挨个调用它们的 dispose。
  • ShadowMapPass 遍历 frame.lights：哪盏灯有阴影设置就画哪盏的阴影图。第 43 课的 shadowPass 只看第一盏灯。
  • ForwardPass 里还有三行和阴影有关（点「ForwardPass 里的阴影」）：它得知道阴影图在哪、灯的矩阵是多少、bias 是多少。画屏幕的那一遍为什么要懂阴影？这是第 45 课的问题。

3. 画到哪：进门、出门

第 43 课每一遍开头都手写四行：bindFramebuffer、viewport、clearColor、clear。手写有两个坑，两张卡片各演示一个：

把这四行收进后端的 withRenderSurface(目的地, 回调)：

  1. 进门：先记下现在绑的 framebuffer 和 viewport（两次 GL 查询，就是第 39 课数过的那两次）；再绑目的地，viewport 照目的地的尺寸设，按描述清屏。
  2. 回调：Pass 在里面调用 draw。
  3. 出门：在 finally 里把 framebuffer 和 viewport 换回进门前的样子——回调正常结束要换，抛错也要换。

写 Pass 的人只说「画进这盏灯的阴影图、先清成白色」，不再碰 viewport，卡片 A 的错就写不出来；出门一定换回来，卡片 B 的事也不会发生。进门出门可以套：在屏幕的门里再进阴影图的门，出来以后自动回到屏幕和 480 × 300 的 viewport（备课时实测：里面 512 × 512，出来 480 × 300，绑定回到屏幕）。FFT 一层套一层地切换目标，靠的就是这一点。

后端还顺手挡住了一种错：在写阴影图的门里，又拿这张阴影图当纹理去采样。GPU 不能同时读写同一张纹理，draw 会直接抛「uShadowMap：不能采样正在写的目标 shadow map」。

这里的检查（第 ③ 层，每次进门）：目的地还在、读的不是正在写的目标、draw 一定在某扇门里。之后可以放心：出门时一定绑回进门前的目标和 viewport。见 校验地图「WebGL1SurfaceScope」一行。

代价：每帧多了 4 次 GL 查询（两扇门各问两次）。实测第 43 课每帧 48 条命令、0 次查询，这一课 58 条、4 次——多出的 10 条命令是出门的换绑和每次 draw 设深度测试（下一节）。

4. 画一个物体：状态自己设

回头看第 43 课：gl.enable(gl.DEPTH_TEST) 只在 shadowPass 里出现过一次，mainPass 一直沾着它的光。两遍总是一起跑，所以从来没出过问题。现在场景可以只要 ForwardPass 了：

办法不是让 ForwardPass 也去开一下深度测试——那只是把依赖换了个方向。办法是：每次 draw 自己设好这次要的状态（小引擎的 Backend.draw 里那一行 gl.enable(gl.DEPTH_TEST)）。于是 GL 状态分成两类，各有各的规矩：

哪类状态例子谁管规矩
画到哪framebuffer 绑定、viewport进门出门进门时换，出门时换回来
怎么画深度测试、深度写入、剔除每次 draw每次 draw 照自己的需要设，不管之前是什么

真实代码也是这样分的：SurfaceScope 只存、只恢复 framebuffer 和 viewport（WebGL1SurfaceScope.ts:160–163）；深度、剔除这些由每个 Material 的 state 描述，Backend 每次 draw 照它设（WebGL1Backend.ts:215 的 applyDrawState），WebGL1State 记住当前值，没变就不重发（第 14 课）。

5. 场景交出自己要的 Pass

现在一帧变成：先抄一份，再把同一个 context 依次交给 Pipeline 里的每个 Pass。Pipeline 里装什么，由场景交给引擎：engine.setScene({ scene, camera, passes })。

setScene 分三段，这个顺序是 HW1 设计文档 §3.9 定的（设计 §3.9）：

  1. 准备：会失败的检查都放在这里（passes 不能为空、每个都要有 execute 和 dispose、同一个对象不能出现两次）。这一段抛错时，什么都没换，Pass 仍归调用者。
  2. 提交：换上新的 Pipeline，记下新场景。从这一行起，新的场景和 Pass 归引擎。
  3. 清理旧的：释放旧 Pipeline 和旧场景的资源。新场景已经装好了，这里失败只记进 diagnostics，不能再对调用者说「安装失败」。
