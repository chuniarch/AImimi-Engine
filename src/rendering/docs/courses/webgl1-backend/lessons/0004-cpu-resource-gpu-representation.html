架构决策一：一份 CPU 资源，每个 context 一份 GPU 表示

GPU 句柄 (handle) 应该放在哪里？这一课先用实测说明为什么不能放在 Geometry 身上，再精读 CPU 资源和 Manager 之间的协作协议：第一次用到时创建，之后复用；CPU 资源释放、context 丢失、Backend 关闭时，各自发生什么。读完你应该能说出 Manager 缓存表的三条不变量，并能预测一次 get、dispose 或 context 丢失会触发哪些 GL 调用。

和你的目标的关系 —— 第 15–18 课精读的每一个 Manager，都是这一课这个模式的一个实例；Task 15 的 WebGL1Backend 也只是「借用」这些 Manager。记住这一课的协议，后面读任何一个 Manager，都只需要看它和这个模板哪里不一样。

1. 设计问题：句柄放在谁身上？

第 3 课看过旧引擎的做法：旧 Mesh 自己拿着 gl、VBO 和按 program 分的 VAO。直觉上这很自然：数据和它在 GPU 上的副本放在一起。新架构偏偏不这么做，原因是下面三个力 (force)。前两个我在浏览器里实测过（Chrome 152）：

  1. 句柄只属于创建它的那个 context。把 context A 创建的 buffer 绑到 context B 上，B 记下 INVALID_OPERATION，B.isBuffer(它) 是 false。同一份几何体要画进两个 canvas（主视图加调试视图，或者离屏预计算），就需要两份句柄。句柄放在 Geometry 身上，就得改成「按 context 分的表」——又是第 3 课说的「共享一加入，就得给数据对象加维度」。
  2. context 丢失会让所有句柄同时作废，而且从外表看不出来。丢失再恢复之后，你拿到的还是同一个 gl 对象；但旧 buffer 的 isBuffer 是 false，绑定它报 INVALID_OPERATION，只有新建的才能用。所以「同一个 gl」不等于「同一代」。句柄散在各个 CPU 对象上时，恢复就要找到每一个对象去清理、重建——可是没有任何地方知道「有哪些对象」。Manager 的缓存表本身就是这份清单：整张表丢掉就行。
  3. 第一层不能知道 gl（第 3 课的判据）。CPU 资源因此可以脱离 GL 测试。更重要的是，CPU 数据是恢复时重建的唯一来源，它必须比任何一代 GPU 表示活得都长。

2. 决策：一对多，以对象身份为 key

新架构的回答是：CPU 逻辑资源 (logical resource) 只描述数据；每个 context 有一组 Manager，各自用一张 Map<CPU 对象, 这一代的 GPU 表示> 保存句柄。于是一份 CPU 资源可以同时有好几份 GPU 表示 (GPU representation)，每个 context 一份： 

第一层（不知道 gl）    Geometry g：不可变快照（position、uv……）
                        onDispose 监听器：[ A 的 release, B 的 release ]
                                │
              ┌─────────────────┴──────────────────┐
              ▼                                    ▼
第三层  context A 的 GeometryManager         context B 的 GeometryManager
        Map { g → { resource, unsubscribe } }  Map { g → { resource, unsubscribe } }
              │                                    │
              ▼                                    ▼
        A 这一代的 buffers                     B 这一代的 buffers

四个 Manager 都是这个形状，只是 GPU 表示不同，「什么时候需要重建」也不同：

CPU 资源（第一层）Manager（第三层）GPU 表示什么时候需要重建
GeometryGeometryManager每个属性一个 VBO，外加可选的 EBO永远不需要：CPU 快照不可变
ShaderModuleProgramManager链接好的 program，以及 attribute / uniform 的 location永远不需要：源码不可变
CubeTextureCubeTextureManager一个 cubemap 纹理不重建：内容要变，就新建一个 CubeTexture（:38）
RenderTargetRenderTargetManagerFBO、颜色纹理、深度 renderbufferresize() 让 revision 加一之后
Geometry × program（派生）VertexInputManagerVAO两者之一被释放，或者 Geometry 的 GPU 表示换了一份

key 是对象身份 (object identity)，不是名字，也不是内容。源码里反复写着这一点：ShaderModule 的 name「不充当 GPU cache key」（ShaderModule.ts:19–20）；ProgramManager 的「cache key 是完整 CPU 对象身份，不是 name」（:52）；CubeTextureManager 的「相同 label 的两个 CPU 对象不会合并」（:79）。反例：两个同名但源码不同的 ShaderModule，如果按名字共用一个 program，其中一个就会画错。代价是内容完全相同的两个对象也会各编译一次（第 7 节卡片 D）；想共享，就共享同一个对象。

3. 精读 ①：Resource 这一侧只负责「通知」

Resource 的类注释写得很直白：它「不持有 WebGL context 或 GPU handle」。它对 Manager 一无所知，只维护一个监听器集合。和协作有关的代码只有两段： 

// src/rendering/core/Resource.ts:104-112（行尾注释是我加的）
onDispose(listener: DisposeListener): () => void {
  this.assertUsable()                              // ① 已经释放了还来订阅：抛 ResourceDisposedError
  this.disposeListeners.add(listener)              // ② 存进 Set，保持注册顺序
  return () => {                                   // ③ 返回「退订」函数
    this.disposeListeners.delete(listener)         //    Set.delete 调两次也无害：幂等 (idempotent)
  }
}

// src/rendering/core/Resource.ts:204-216
private finalizeDisposal(): void {
  if (this.disposedValue) return
  this.disposedValue = true                        // ④ 先标记：监听器里再想读这个资源，会被 assertUsable 拒绝
  for (const listener of this.disposeListeners) {  // ⑤ 按注册顺序通知：每个 context 的 Manager 删掉自己的 GPU 表示
    listener()
  }
  this.disposeListeners.clear()                    // ⑥ 清空监听器
  this.disposeCPUData()                            // ⑦ 最后才丢 CPU 数据（例如 Geometry.ts:345 清空属性和索引）
}
  • 术语：从 API 看，Manager 调用 onDispose(listener) 是注册监听器；从语义看，它因此订阅了这个资源的释放事件——两个说法指同一个动作（代码自己两个词都用：Resource.ts:98「注册一个同步释放监听器」，:101「取消订阅函数」）。被订阅的是「释放」这个事件（disposed 从 false 变成 true 的那一次跳变，由 Resource 推送），不是 disposed 这个状态：状态随时可以去读，但读它不会通知你。本课说「订阅」，都是指订阅释放事件。
  • ① 挡住的反例：给已经释放的资源订阅释放事件，得到的是一个永远不会触发的订阅。Manager 那条 entry 就再也没人来删，句柄一直泄漏到 Backend 关闭。（10 月 10 日以前这里写的是 if (this.disposedValue) throw new ResourceDisposedError(…)；现在改调 assertUsable()，行为一样。assertUsable 为什么从 protected 改成 public，见第 7 课的更新。）
  • ③ 为什么必须幂等：下一节会看到，Manager 关闭时会对同一条 entry 退订两次。
  • ④ 的后果：监听器运行的时候，资源已经是 disposed，任何 CPU getter 都会抛错。所以 Manager 的 release 故意不读 CPU 数据，只按对象身份查自己的表（OESVertexInputManager.ts:160 和 RenderTargetManager.ts:363 都写明了这一点）。删除 GPU 对象需要的一切，都事先存在 entry 里。
  • 这是观察者模式 (observer pattern)，也是依赖倒置 (dependency inversion)：第一层只暴露一个「我要被释放了」的回调口，第三层来订阅。运行时，通知从第一层发给第三层；代码里，却是第三层 import 第一层的类型——第一层连一个 Manager 的名字都不知道。数据不知道消费它的机器，这正是第 3 课说的「知识方向」。

4. 精读 ②：Manager 这一侧——一张表，三条出路

拿 GeometryManager 当代表（另外三个 Manager 结构相同，第 15–17 课逐个讲差异）。先看表里存的是什么：

// src/rendering/backend/webgl1/WebGL1GeometryManager.ts:54-57、73
interface GeometryEntry {
  readonly resource: WebGL1GeometryResource   // 交给调用者借用的 GPU 表示（冻结对象）
  readonly unsubscribe: () => void            // 撤销对这个 CPU 资源释放事件的订阅
}
private readonly entries = new Map<Geometry, GeometryEntry>()   // key：CPU 对象本身

再看入口：第一次用到才创建（懒创建 lazy creation），之后直接复用。

// WebGL1GeometryManager.ts:104-114、185-188（省略了创建、上传、保存与恢复绑定——第 16 课细讲）
get(geometry: Geometry): WebGL1GeometryResource {
  this.assertAvailable('get geometry')             // Manager 没关闭、context 没丢失（一次 isContextLost）
  if (geometry.disposed) throw new ResourceDisposedError('Geometry')
  if (this.releasing.has(geometry)) throw …         // 正在释放它的途中又来要：拒绝
  const cached = this.entries.get(geometry)
  if (cached !== undefined) return cached.resource  // 命中：不发任何创建或上传命令，返回同一个冻结对象
  // … preflight、createBuffer、bufferData、恢复绑定、错误检查——全部成功才往下走 …
  const unsubscribe = geometry.onDispose(() => this.release(geometry))   // 先订阅
  this.entries.set(geometry, { resource, unsubscribe })                  // 再发布
  return resource
}

然后是三条出路。一条 entry 离开这张表，只有这三种方式：

事件Manager 做什么GL 调用CPU 资源之后
CPU 资源被释放
（应用调用 dispose，或 Scene 引用归零）		 release：先让依赖它的顶点输入放手（beforeDelete，:225），再退订、移出表（:232–233），最后 deleteBuffer（:235–241） 有：deleteBuffer 已经 disposed（这正是起因）
context 丢失 invalidateForContextLoss：标记 lost，退订全部，清空表 没有：句柄已经随 context 作废 不变；下一代 Manager 从它重建
Backend 关闭 dispose：先退订全部（:273），再逐个 release（:275） 有：deleteBuffer 不变：Manager 从不释放 CPU 资源（测试断言见 ResourceManager.test.ts:306）

dispose 先退订一遍，release 里又退订一遍——这就是上一节说的「退订两次」，幂等让它无害。

把这些代码压缩成三条不变量 (invariant)。这是本课最重要的收获：

  1. 这张表是本 context 里这些句柄的唯一所有者。调用者拿到的 resource 只是借用（GeometryManager.ts:33–34：「所有 buffer 均由 GeometryManager 拥有，调用者只借用」），谁也不许自己去 deleteBuffer。
  2. 表里有一条 entry，就恰好有一个活着的订阅；entry 离开表，订阅同时撤销。三条出路都遵守它。反例一：entry 还在、订阅没了——CPU 资源释放时没人删 GPU 对象，泄漏。反例二：entry 没了、订阅还在——CPU 资源的监听器集合一直拽着一个已经作废的 Manager（连同它的 gl 和整张表），内存泄漏；等 CPU 资源终于释放，还会调进这个死掉的 Manager。
  3. 只发布完整的结果。全部创建、上传成功之后，才订阅、才放进表；中途失败，只清理这一次新建的对象（:195），表里什么都不留。这叫事务式发布 (transactional publish)，第 15、16 课细讲。

5. 精读 ③：缓存什么时候过期

缓存最难的问题永远是失效。这套代码按 CPU 资源的性质，用了三种办法：

5.1 不可变快照：永不过期

Geometry、ShaderModule 构造时复制输入，之后没有任何修改方法；读取时也只给副本（copyIndices()、copyData()）。内容永远不变，所以 GPU 表示永远不会过期，命中时不需要任何版本比较（GeometryManager.ts:113–114 只查了一次 Map）。CubeTexture 借用的图片对象是可变的，所以它等到第一次真正上传时才读尺寸；上传成功之后按静态资源缓存，内容要变就新建一个 CubeTexture（CubeTextureManager.ts:37–38）。

这就是第一层坚持「不可变快照」的真正理由：不可变，让缓存失效这个难题直接消失。

5.2 版本号：RenderTarget 的 revision

RenderTarget 必须能改尺寸（窗口会缩放）。resize() 验证成功后让 revision 加一（:492）；Manager 每次 get 都比较版本：

// src/rendering/backend/webgl1/WebGL1RenderTargetManager.ts:76-78、103-109、121（节选）
const old = this.entries.get(target)
const revision = target.revision
if (old?.resource.revision === revision) return old.resource           // 版本相同：直接复用
next = this.create(target.descriptor, revision, label)                 // ① 先建好一整套新的
const unsubscribe = old?.unsubscribe ?? target.onDispose(() => this.release(target))   // 沿用旧订阅
this.entries.set(target, { resource: next, unsubscribe })              // ② 发布新的
if (old !== undefined) this.deleteResource(old.resource)              // ③ 最后才删旧的

两个细节。顺序是「建新 → 发布 → 删旧」（类注释 :42–45）：新的建失败时，旧 entry 原样留着，调用者收到异常。替换时沿用旧的订阅，不再订阅第二次——不变量 2 在替换时也成立。

5.3 派生缓存：核对「用哪一份 GPU 表示建的」

VAO 是从「某一份 Geometry 的 GPU 表示 + 某个 program」派生出来的。OES 策略在缓存里记下建 VAO 时用的那一份 GPU 表示，命中要求对象完全相同（OESVertexInputManager.ts:66–73）；不同就重建，并删掉旧 VAO（:116–119：「同一 CPU Geometry 的 GPU 表示若被重新创建，不能复用旧 buffers 的 VAO」）。GeometryManager 返回的冻结对象身份稳定，于是它自己就充当了版本号。

6. 「一代」：context 丢失以后

context 丢失时，Manager 不修补自己，而是整个作废：「一旦失效，不允许此实例在 context 恢复后重新使用旧记录」（GeometryManager.ts:79–80）。恢复之后，Backend 重新探测能力，组装一个新的 ResourceManager（ResourceManager.ts:38）。CPU 资源一个字节都没动，新一代第一次 get 时从快照重建。测试「新一代可从仍存活的 CPU 数据重建，旧一代仍拒绝工作」验证的就是这件事。

为什么不让旧 Manager「复活」？第一，旧句柄全死了（第 1 节的实测），表里没有一条还能用。第二，恢复后设备的能力可能变了（例如换了一块 GPU），而好几处决定依赖能力：用 OES VAO 还是手动接线、Uint32 索引能不能直接用。重新探测、重新组装，是最简单、也最不容易错的规则。丢失时退订全部，正是为了让旧一代和 CPU 资源彻底断开（不变量 2）。

9. 架构视角

9.1 对照 three.js：同一个决策，几处不同的取舍

决策本身和 three.js 一致。three.js 的 BufferGeometry、Texture 也不持有 GL 句柄，渲染器内部按对象保存 GPU 数据：旧渲染器用 WebGLProperties（一个 WeakMap），新渲染器用 DataMap 和 Backend.data（也是 WeakMap）。释放通知靠 CPU 对象派发的 'dispose' 事件，渲染器在第一次用到时才订阅：纹理见 WebGLTextures.js:666–670，几何体见 WebGLGeometries.js:52–56，新渲染器见 common/Geometries.js:194。context 恢复时，旧渲染器调用 initGLContext()，把 properties、textures、geometries、bindingStates 等子系统全部新建一遍（:401–425）——和本项目「整代丢弃、重新组装」是同一个思路。

本项目three.js r177
缓存表 Map：强引用，可以遍历 WeakMap：CPU 对象没人用了，条目跟着被回收；但不能遍历
「全部删除 / 全部退订」 遍历表，逐项处理（第 4 节的三条出路） 没法逐项处理，只能换一张新表：WebGLProperties.dispose() 就是 properties = new WeakMap()，换表本身不删除任何 GL 对象
context 丢失时的旧订阅 主动退订，旧一代立刻和 CPU 资源断开 onContextLost 只设一个标志。旧一代的监听器还挂在 CPU 对象上，要等对象被 dispose 时才运行一次、摘掉自己（WebGLTextures.js:301–305），拿旧表里的旧句柄去删
program 的 key ShaderModule 的对象身份，不去重 由材质参数拼成的字符串（getProgramCacheKey）：内容相同就共用，再用 usedTimes 引用计数防止误删（acquireProgram、releaseProgram）

两边的取舍都说得通。three.js 的 shader 是由材质参数生成的，许多材质会生成同一份源码，所以必须按内容去重；本项目的 ShaderModule 是用户显式写的，共享用「同一个对象」来表达就够了。WeakMap 的好处是：CPU 对象忘了 dispose，也不会被渲染器一直拽着；Map 换来的是可枚举，关闭和丢失时能精确地删除、退订每一项。本项目为此付出的代价是：忘了释放的 CPU 资源，会被 Manager 的表一直拽着，直到 Backend 关闭——所以生命周期必须显式管理，这正是下一课 Scene 引用计数要解决的事。

9.2 审查视角：「一对多」留下的一个未决问题

一对多的通知有一个代码自己承认的缺口。TODOList.md 记着：Resource 的监听器抛错时怎么办，还没有定（Resource.ts:56–58 的注释也指向它）。现在的循环不 catch，所以只要有一个监听器抛错，释放就当场中断：后面的监听器收不到通知，监听器集合没清空，disposeCPUData() 也没执行——但 disposed 已经是 true 了。

放到本课的图里看：Geometry 被两个 context 共用，A 的 release 抛错，B 的 Manager 就永远收不到通知。再调一次 geometry.dispose() 也没用：它一进门就因为已经 disposed 而返回。B 的 buffers 只能等 B 整体关闭时才删。

TODO 里列了几个要做的决定：一个监听器失败后，要不要继续通知其余的？CPU 清理还做不做？报第一个错、最后一个错，还是用 AggregateError 汇总？或者干脆规定 Manager 的监听器不许抛错？先想一想你会选哪一种、为什么。第 7 课精读 Resource 时，我们拿你的选择去对照 TODO 里的约束。
