前面几十课读的都是「代码为什么这样写」。这一课换一个角度：拿你接下来真要用它做的事——把 FLIP 的结果画出来——去审它。哪些地方接得住，哪些接不住，接不住的是缺陷还是当初有意没做，最后写成一份审查意见。

和你的目标的关系 —— 10 月 19 日起渲染引擎的定位是仿真可视化工具。FLIP 课的目标是 3D CPU 实现：32³ 网格、约 6 万个粒子的溃坝（dam break），v1 用粒子和切片可视化，验收里有「投影后 max|div| < 1e-5」（FLIP 课的 MISSION.md；那是你的个人学习文件，不放进发布副本，这里只引它的数字）。这一课的审查结论，就是动手画 FLIP 之前，渲染这边要先补什么、可以不管什么。

1. 怎样审：五步，和意见的写法

Google 的代码审查指南（code review guide）把「设计」放在第一位，其次是「功能」，问的是这段代码对它的使用者好不好用。它说的使用者有两种：受到改动影响的最终用户，以及以后要「使用」这段代码的开发者（What to look for in a code review · Functionality）。这一课里，你就是后一种：以后拿 src/rendering 画仿真结果的人。所以审查从你的需求出发，不从代码出发。

步骤做什么这一课里的例子
① 写下需求和数字写清要做什么、每帧多少数据、能容忍多大误差。没有数字就判断不了严重程度。6 万个粒子，画成点每帧 703 KiB
② 找到接住它的代码顺着第 47 课那条调用链，找到真正处理这条需求的那几行。Geometry 构造、GeometryManager.get
③ 跑真实代码量一量不靠读代码猜，把真实的类跑起来，数调用、数对象、看画面。每帧新建 Geometry：多 14 条命令、12 次查询
④ 分类先读设计文档再分类，下面的表是四类。「Geometry 不能改」是有意的范围
⑤ 写意见贴标签、写位置、写现象和理由、给建议。question (blocking): 没有 points

第 ④ 步最容易出错。同一个「做不到」可能属于四类中的任意一类，处理方式完全不同：

类别怎么认意见应该怎样写
缺陷 (bug)代码没做到它自己承诺的事（注释、类型、文档、测试说了 A，跑出来是 B）。issue：指出承诺和现象，建议修法。
有意的范围 (scope)设计文档、注释或 TODO 写明「这一版不做」。note：说明它挡住了新需求，不要求「修」。
新需求下的缺口 (gap)当初的范围合理，但新需求要它。question 或 suggestion：要设计，列出设计要回答的问题。
取舍 (trade-off)两种写法各有代价，当初选了一种。thought 或 suggestion：写清两边的代价，用数字说哪边更重。

例子：Geometry 不能改，粒子每帧换位置只能整个重建。读代码时很像缺陷，可是类的注释写了「初版 Geometry 是完全静态的，不提供 revision、usage 或 updateAttribute()」（Geometry.ts:135），FLIP 交接文档也写了「不假设静态 Geometry 已经支持动态粒子数据」「不……在未设计生命周期、dirty range、版本和恢复语义前直接修改 Geometry」（交接文档 §9）。所以它是有意的范围；对 FLIP 来说是缺口，意见要写成「需要设计，设计要回答这四个问题」，不能写成「这是 bug，改成可变的」。

第 ⑤ 步用 Conventional Comments 的格式：<标签> [修饰]: <一句话>，下面再写讨论（conventionalcomments.org）。这一课用到的标签： praise真心觉得好的地方（规范建议每次审查至少写一条，不要写假的）； issue具体的问题，最好配一条建议； suggestion改进提议； question有顾虑但不确定，请作者确认； note不挡路，只提醒注意； nitpick小的偏好问题，天然不挡路。 修饰用 (blocking)（不解决不能接受）、(non-blocking)、(if-minor)（改动小就顺手改）。

3. 需求一：6 万个粒子每帧换位置

现在的引擎能怎样画？没有 points，所以每个粒子只能画成一个小三角形（3 个顶点）。Geometry 不能改，Mesh 的 geometry 也不能换（Mesh.ts:24 是 readonly），所以位置一变，应用每帧要做四件事： 

// 课程写的（assets/build/review-course.ts 的 createParticleDemo），引擎现在只能这样用
scene.remove(oldMesh)                    // 1. 旧 Mesh 拿出场景
scene.release(oldGeometry)               // 2. 最后一个引用 → dispose → 各 Manager 删 buffer、VAO
const geometry = scene.retain(new Geometry({ attributes: { position: new VertexAttribute({ data, itemSize: 3 }) } }))
scene.add(new Mesh(geometry, material))  // 3、4. 新建、登记、放进场景

3.2 实验台：每帧要花多少

选一种写法和粒子数，跑 30 帧（6 万个粒子跑 10 帧），数第 2 帧起每帧的调用。「什么都不变」是对照：粒子不动，只看引擎每帧的底数。最后两项是课程直接用原生 GL 写的对照，不经过引擎：一个 buffer 只分配一次，之后每帧 bufferSubData 改内容。

我在这台 Mac 的无界面 Chrome（SwiftShader）上测到（1 000 个粒子，有 VAO 扩展）：

什么都不变（对照）3471 / 1

6 万个粒子时每帧顶点数据 2.06 MiB（2 160 000 字节，画成三角形，是画成点的 3 倍）。引擎在 CPU 上整份复制两次（VertexAttribute.ts:100 构造时、GeometryManager.ts:145 上传前），再用 bufferData 整块重新分配、上传一次。光构造 VertexAttribute 和 Geometry，这台机器上每帧约 2–3 ms，占 60 fps 一帧预算（16.7 ms）的八分之一到六分之一。命令和查询的条数与粒子数无关，1 000 和 60 000 都是 48 和 19。没有 VAO 扩展时（Manual 路径）每次 draw 还要多 2 次 getError，这是找茬题 18。

4. 需求二：一张散度切片每帧更新

切片用 DataTexture2D 存，片元着色器按值上色：红是正，蓝是负，白是 0，乘上 uScale = 1 / amplitude 把 ±1e-5 放大到 ±1。场是课程写的 1e-5 · sin(2πx) · sin(2πy)，四个象限正负交替，样子像一张散度图。

4.1 实验台：纹理要过的几道关

改尺寸、格式、类型、过滤、环绕，或者假装设备没有 OES_texture_float_linear（课程把扩展藏起来，模拟别的设备），看在哪一步被拦、拦下的是什么错误。「每帧换新纹理」模式按 32 × 32、rgba float 跑 20 帧，数每帧的调用。

我测到的几组：

  • 30 × 30、rgba、float32、linear、clamp：画得出来。左下象限 (217, 52, 39) 是红，右下 (39, 90, 217) 是蓝，正中接近白。30 不是 2 的幂，用 clamp、不要 mipmap 就能过 NPOT 那道关。
  • 换成 uint8：整张都是 (245, 245, 245) 的白。1e-5 × 255 取整是 0，数据在上传之前就没了。这就是 R2 必须用浮点的原因。
  • 藏起 OES_texture_float_linear：第一次 draw 抛 UnsupportedRenderFeatureError（OES_texture_float_linear is required）；同样设置改成 nearest 就画得出来。
  • 30 × 30 加 repeat：第一次 draw 抛 NPOT 的错；32 × 32 加 repeat 能画。
  • 每帧换新纹理：每帧 53 条命令、18 次查询；纹理不变时是 35 和 7。多出来的是 createTexture、texImage2D（整张重新分配）、4 次 texParameteri、8 次 pixelStorei（上传前后各设一遍）、deleteTexture，以及 4 次 getError、7 次 getParameter。

5. 需求三：跑很久

FLIP v1 在 CPU 上算，画面的原料全是 CPU 数据。设备丢失以后，引擎照着 CPU 原件重建就行（第 46、47 课）。可是将来 GPU 上算的版本（Stable Fluids 的速度场、时间累积……）把状态存在 RenderTarget 里，这些状态在 CPU 上没有原件。下面这张卡片用一个最简单的例子代表它们：两张 RenderTarget 轮流读写（ping-pong），每帧把上一帧的值加 1。

6. 纯渲染的条目（少讲，不跳过）

这些条目和仿真可视化关系不大，大多在前面的课里讲过。每条先给提示，答案折叠着，想自己找就先别展开。

  • issuesRGB 纹理配 mipmapPolicy: 'generate'：看 Texture2DManager.ts:141 和 CubeTextureManager.ts:161，事前的 validateStorage 少检查了什么？
    答案（第 17 课讲过，找茬题 1）

    EXT_sRGB 规定对 sRGB 纹理调用 generateMipmap 产生 INVALID_OPERATION。两个 validateStorage 都没拦这个组合，错误在上传以后才以笼统的 WebGLOperationError 报出来，而不是事前的 UnsupportedRenderFeatureError。修法：两处各加一行；以后合并 validateStorage 时只加一处（找茬题 20）。

  • issue镜像的物体：WebGL1Backend.ts:337 每次 draw 都设 frontFace(CCW)。世界矩阵行列式小于 0（比如 scale.x = −1）时会怎样？
    答案（第 11 课讲过，找茬题 10 ②）

    镜像以后三角形的绕向反了，剔除背面会剔掉正面。three.js 每次 draw 按 object.matrixWorld.determinant() < 0 算 frontFaceCW（WebGLRenderer.js:1100）。本项目的 RenderItem 已经有 worldMatrix 快照，可以在 draw 里同样算一次。

  • issue旧引擎的阴影打包：rgbaPack.frag:7–8 按 256 进位。8 位通道存的是什么？
    答案（第 27 课附注讲过，找茬题 21）

    8 位通道存的是 k/255，按 256 进位再按 256 解，0.3 解出 0.30116。按 255 进位才能精确还原（第 40、47 课的深度着色器已经按 255 写）。和仿真的关系：有了浮点 RenderTarget，就不用再把一个数拆进四个 8 位通道。

  • suggestionState 缓存：同一个 Pass 里连着两次 draw，第二次的 useProgram、enable、depthFunc 有没有被缓存省掉？看 OESVertexInputManager.ts:138。
    答案（第 31、47 课讲过，找茬题 29）

    没有。OES 顶点输入的 bind 在 finally 里调 invalidateState，把 program、深度、剔除的缓存全清了，可它真正要作废的只有 ELEMENT_ARRAY_BUFFER。每次 draw 多 6 条左右的调用。仿真可视化如果要画很多个小物体（比如几千个箭头），这条会变要紧。

  • suggestiongetError 怎样收：卡片 C 里，Manual 路径的错误信息是「GL error 1280」，OES 路径是「GL errors: 1280」。为什么不一样？
    答案（找茬题 6、17）

    ProgramManager 和 GeometryManager 的 checkError 是有界循环（最多 32 次，一次报出全部错误码，GeometryManager.ts:416）；VertexInputSupport（:168）和 TextureUploadSupport（:27）只取一次。四处行为不一致，建议抽成一个共用函数。

  • nitpick不进门就 draw 时，错误信息说「enter surface scope failed for draw」。看 SurfaceScope.ts:39–40。
    答案（第 47 课卡片 B，找茬题 32）

    helper invalid 把操作名写死成 enter surface scope，可这次根本没人进门。给 invalid 加一个操作名参数就行。

  • nitpick文档和注释漂移，四处：program-and-geometry-managers.zh-CN.md:102、static-geometry.zh-CN.md:8、shader-and-material.zh-CN.md:40、WebGL1State.ts:235。每处和现码哪里对不上？
    答案（第 15、10、11、14 课布置过，找茬题 2、8、9、15）

    ① 文档说 Program「没有 detachShader」，ProgramManager.ts:136 起已经在链接成功后 detach；② 示例写 new VertexAttribute(array, 3)，构造函数收的是 { data, itemSize }；③ 写的是 Material.renderState，代码里叫 state；④ 注释说 restoreSurfaceState 只在单元测试里被调用，生产路径 SurfaceScope.run 早就在调用它。

  • nitpickWebGL1Capabilities.ts:34 的函数名。
    答案（第 13 课布置过，找茬题 4）

    reqiurePositiveLimit 拼错了，应为 require。

three.js r177 的 WebGLRenderer 从 r163 起只支持 WebGL 2（WebGLRenderer.js:101），所以下面只比「怎样表达这件事」，不比扩展。

three.js r177本项目
顶点数据会变BufferAttribute.setUsage(DynamicDrawUsage)（BufferAttribute.js:164）；改完设 needsUpdate = true，version 加一（:152–154）；可以只标一段 addUpdateRange（:178）。WebGLAttributes 比 version，不一样就 bufferSubData（WebGLAttributes.js:76、:86）；尺寸变了直接抛错，不支持改大小（:210）不能变；每帧新建 Geometry（R1-③），R1-⑥ 的方向和 three.js 一样

10. 延伸阅读

首选（约 15 分钟）：Google Engineering Practices 的 What to look for in a code review。按顺序列了设计、功能、复杂度、测试、命名、注释、风格、一致性、文档、每一行、上下文、好的地方。对照这一课：第 2 节的需求是「功能」里说的使用者；R3-⑦ 是「测试」；第 6 节的漂移是「文档」；R2-①、R3-①② 是「好的地方」。

补充：① Conventional Comments，标签和修饰的完整列表，第 1 节只用了其中一部分；② MDN 的 WebGL best practices，「Don't assume you can render into float textures」一节说很多移动设备能建 RGBA32F 纹理，挂到 framebuffer 上却不完整（R3-②），「Avoid blocking API calls in production」一节说 getError、getParameter 会让调用线程同步等待（R1-③、R2-④ 里多出来的查询）；③ WebGL 1.0 规范 texImage2D：pixels 为 null 时传入一块全 0 的缓冲区，这就是卡片 E 恢复后累加值从 0 重来的原因；④ OES_texture_float 的格式表里有 LUMINANCE + FLOAT，这是 R2-③ 的依据。

做完告诉我：检查题错了哪几题、五张卡片哪张和你猜的不一样。还有两件事想听你的：① 汇总表里有没有你不同意的分类或严重程度；② 你想先处理哪一条，我按那一条准备下一步（设计还是课）。
