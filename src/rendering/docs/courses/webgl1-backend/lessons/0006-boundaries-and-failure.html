架构决策三：边界上传什么，失败怎样跨过边界

前三课讲了分层、GPU 表示、所有权。这一课看第二层和第三层之间那条边界：上面交给后端的是什么，后端怎样保证「临时改的绑定一定改回来」，出了错怎样告诉上面，以及 context 丢失为什么不按「一次调用失败」来处理。读完你应该能说出 RenderBackend 每个成员背后的约束，并能判断一次失败之后哪些状态保持、哪些回滚、哪些整代作废。

和你的目标的关系 —— Task 15 要实现的正是这条边界：withRenderSurface、clear（Task 15 已把它并入 withRenderSurface，见第 2 节的更新说明）、draw、ready。这一课是它的「验收标准」；详细设计篇（第 7–18 课）之后，第 19 课再回来讲编排。

0. 热身：前几课还记得吗

1. 设计问题：边界上该传什么？

后端画一个物体，需要几何体、材质、模型矩阵、视图和投影矩阵、相机位置。最省事的办法是把 Mesh 和 Camera 直接交给后端。本项目偏不这样做，draw 只收一个 DrawSubmission：{ item: RenderItem, view: ViewState }。原因有三条：

  1. 后端不能知道场景。收 Mesh、Camera，后端就得 import scene，违反「Backend 不知道 Scene」（第 3 课）。
  2. 同一批 draw 要看到同一帧。提取阶段把可变的场景读一次，复制成值：RenderItem 带着 worldMatrix 的副本（RenderItem.ts:11），ViewState 带着相机矩阵的副本。「Backend 不接收 Camera，因此不能在同一批 draw 中重新读取可变相机状态」（ViewState.ts:11）。否则，两次 draw 之间有人动了相机，同一帧就会一半用旧矩阵、一半用新矩阵。
  3. 类型把边界钉死。RenderBackend.test.ts:41–44 用 @ts-expect-error 证明：draw 不接受零散的 geometry、material 字段，Mat4Tuple 少一个数都编译不过。

快照有一个诚实的缺口：RenderItem 复制了矩阵，Geometry、Material 却只是借用身份。Geometry 不可变，没问题；Material 可以 setParameter，而源码写明了它的读取结果「不是整帧快照协议；后续帧提取若要求参数在一帧内固定，需要在那里显式捕获」（Material.ts:175–176）。这是留给 Task 16 的决定。

2. 精读 ①：RenderBackend 的六个成员（Task 15 后是五个），每个都是「意图」

// src/rendering/backend/RenderBackend.ts（Task 15 改动之前的版本，节选，注释是我加的）
export interface RenderBackend {
  readonly ready: boolean                                             // 设备现在能不能画（未丢失、未关闭）
  resizeDrawingBuffer(cssWidth: number, cssHeight: number, pixelRatio: number): void
  withRenderSurface(surface: RenderSurface, callback: () => undefined): void   // 在某个输出目标上执行一段同步代码
  clear(descriptor: ClearDescriptor): void                            // 清除当前目标的哪些缓冲
  draw(submission: DrawSubmission): void                              // 画一个物体
  dispose(): void
}
2026-09-26 更新：Task 15 改了这份契约，现在是五个成员。独立的 clear() 取消了，清除变成进入作用域时的一项描述：withRenderSurface 的第一个参数是 { surface, clear? }（RenderSurface.ts:37–40），绑定目标之后、执行回调之前清除一次；嵌套作用域退出时只恢复外层的绑定，不会再清一次外层（:28–36）。形状上和 WebGPU 的 render pass 一样：清除是「开始画这个目标」时的一个选项，而不是随时可以插进来的命令。上面的节选保留改动前的样子，读新代码以 RenderBackend.ts:18–44 为准；正式实现在 WebGL1SurfaceScope.ts:191–244。

对照重构方案的三条接口规则（PLAN.md §5.8）：① 方法名表达意图，不用 GL 术语——这里没有 bindFramebuffer、useProgram，只有「在哪画、清什么、画什么」；③ 签名里不出现任何 GL 类型——只有逻辑资源和值类型。第 ② 条（能力差异走 hasFeature）目前还没有对应的成员：只有一个后端时用不上，接 WebGL2 时要补上。

这条边界还有两条「反向」的约束：Pass 不能自己调用 gl.clear、gl.useProgram 或 gl.draw*（HW2 设计 §18）；后端独占它的 context，任何外部代码都不能直接改同一个 context 的状态（:1191）。后一条正是 State 缓存可信的前提——上次答疑讲 invalidateState 时说的就是它。

3. 精读 ②：输出目标用「作用域」，不用全局开关

一次离屏绘制要临时绑定另一个 framebuffer 和 viewport，画完必须改回去。改回去有两种写法：

全局开关（three.js 的 setRenderTarget）作用域（本项目的 withRenderSurface）
写法setRenderTarget(rt) → 画 → setRenderTarget(旧的)withRenderSurface(surface, () => { 画 })
谁负责改回去每个调用者自己记住后端在 finally 里改回去
中途抛错改回去的那一行被跳过，之后的绘制都画进了离屏目标照样恢复
嵌套调用者得自己保存每一层的旧值每一层都恢复到自己进入之前的样子

契约写在 RenderBackend.ts:25–37：先捕获真实的 FRAMEBUFFER_BINDING 和 VIEWPORT，再在 try 里解析并绑定目标、执行回调，最后在 finally 里恢复。捕获真实值而不是假设「进来之前是画布」，是因为外层可能本身就是另一个离屏目标（WebGL1State.ts:228）。三块零件已经在 State 里：captureSurfaceState、bindSurface、restoreSurfaceState；把它们组装成作用域，是 Task 15 的事（卡片 D 演示了这个骨架）。

两处细节：

  • 目的地是显式的联合类型。RenderSurface 只有 default-framebuffer 和 render-target 两种，不允许用 null 表示画布。设计文档说明了原因：「不能把 disposed RenderTarget 的 null framebuffer 静默当作默认 framebuffer，否则像素会写进 canvas」（§28）。
  • 回调必须同步，而且类型只挡得住一半。回调类型是 () => undefined——和上次答疑讲的 hook 是同一个手法，async 函数和 () => 1 都编译不过（RenderBackend.test.ts:35–38）。但它挡不住回调内部启动一个不等待的异步任务，比如 () => { void loadAndDraw() }：那个任务会在 finally 恢复之后才去画，画到错误的目标上。所以契约写明「禁止跨 await 或启动稍后再次 draw 的任务」，这部分要靠 lint 和审查（:34）。

4. 精读 ③：失败怎样跨过边界——分类，要么完整、要么不变

第 2 课按「GL 从哪条通道报错」分过类；这里换一个角度：上层拿到错误之后该做什么。设计文档说得很直白：窄错误的意义不是增加类的数量，而是让调用者区分这几种情况（§28）：

情况错误类（都继承 RenderingError）上层该怎么办
数据非法Invalid*Error（Geometry、Material、RenderTarget……）、SceneGraphCycleError修调用方的数据或代码；重试没有用
对象已释放 / 记账错误ResourceDisposedError、ResourceHasSceneReferencesError、WebGLBackendDisposedError调用方的 bug：用了已经释放的东西（第 5 课）
功能不支持UnsupportedRenderFeatureError、UnsupportedShaderLanguageError、UnsupportedIndexTypeError换一种方案，或者关掉这个功能
构建失败ShaderCompilationError、ProgramLinkError（带 infoLog）、IncompleteFramebufferErrorshader 写错了就报告开发者；FBO 不完整就换附件格式
设备暂时不可用WebGLContextLostError暂停绘制，等恢复（第 5 节）
GL 操作失败WebGLOperationError、WebGLResourceCreationError多半是代码 bug；OUT_OF_MEMORY 可以试着降低分辨率

「功能不支持」的检查放在创建任何 GPU 对象之前：「能力检查必须先于任何 create*，避免已知不支持的请求产生半成品」（RenderTargetManager.ts:190）；ProgramManager 也是先看 shader 语言，再碰 GL（ProgramManager.ts:92–94，卡片 B）。

而一旦开始创建，失败时就要做到要么完整成功，要么什么都没变。这句话在三个粒度上各执行一次：

  • CPU 资源：先验证，再提交。Material.setParameter 验证失败时旧值不变（Material.ts:337–349）；RenderTarget.resize「先验证两个尺寸，再准备完整新快照，最后提交」（RenderTarget.ts:465–470）；Scene 的账本（第 5 课）。
  • GPU 资源：事务式发布 (transactional publish)。全部成功才放进缓存；失败只删这一次新建的对象（RenderTargetManager.ts:341–347），缓存里不留半成品，下次 get 会从头再来（卡片 A）。
  • 作用域：恢复绑定。finally 恢复的是 framebuffer 和 viewport。它不回滚已经写进附件的像素，也不恢复 program、深度状态（WebGL1State.ts:229–230）。「原子」指的是状态，不是已经发生的效果。

5. 精读 ④：context 丢失是一个状态，不是一次调用的失败

context 可能在任意两个 GL 调用之间丢失。如果把它当成「某次调用失败」，就得在每个 gl.* 外面包 try/catch。设计文档明确拒绝了这种做法：「不需要在每个 gl.* 周围 try/catch。Renderer 在帧入口检查 backend.ready；Backend 公开方法仍执行 assertReady() 作为误用防线」（§20）。 

ready ──webglcontextlost──→ lost ──webglcontextrestored──→ restoring ──成功──→ ready
                                                               └──失败──→ restore-failed
任何状态 ──dispose()──→ disposed                         （WebGLContextLifecycle.ts:2）
  • 丢失时：状态先变成 lost（所以回调里看到的 isReady 已经是 false），再通知后端让这一代的缓存整体作废（第 4 课）。浏览器的 DOM 事件回调里「所有业务回调异常均不逃出 DOM listener」（Lifecycle.ts:70）：失败记进 lastFailure，不往浏览器里抛。
  • 恢复时：重新探测能力、重新组装 State 和 Manager，最后才变回 ready；之后第一次 draw 从 CPU 资源懒上传。
  • 边界上：第二层只看一个布尔值 ready（RenderBackend.ts:20）。实施计划里 Renderer 的测试要求：「backend not ready 时 Builder/Pipeline 都不调用」。

生命周期里还有一个 transitionVersion，用来防止旧的回调覆盖新的状态。它是第 13 课的主题，这里先知道它存在就行。

8. 架构视角

8.1 对照 three.js：它选择「软失败」

  • 边界上传的是活对象。新渲染器的 Backend.draw(renderObject, info) 收到的 RenderObject 直接引用 object、material、scene、camera（RenderObject.js:105–126），没有值快照这一层；它靠版本号和缓存来判断哪些东西变了。
  • 输出目标是全局开关。setRenderTarget 直接改渲染器的当前目标（:2685），恢复靠调用者自觉（卡片 D 的解析里有它自己的例子）。
  • 出错不抛异常。shader 编译、链接失败时，它调用 debug.onShaderError 或者在控制台打印错误，然后继续运行（WebGLProgram.js:919–950）；context 丢失时，render() 开头直接返回（WebGLRenderer.js:1533）。

取舍：three.js 面向的是终端用户的页面，一个 shader 写错不该让整页崩掉，所以它选「软失败、继续跑」。本项目是要反复重构、要教学、要逐像素对比两个后端的代码库，更需要「在哪一步、因为什么失败」一目了然，所以选「大声失败、按类型分类」。代价是应用边界上必须有人接住这些异常，并决定报告、暂停还是降级——分好类的错误，正是让这个决定能做出来的前提。

8.2 审查视角：一个会误导人的字段

所有渲染错误都继承自 RenderingError，而 RenderingError 把基类 EngineError 的 recoverable 一律写死为 false（RenderingError.ts:40）——连 WebGLContextLostError 也是，可它明明有恢复路径。旧引擎的做法恰好相反：MeshVBOCreationError.ts:23 因为「可能是 WebGL 上下文丢失」而标了 recoverable: true。目前没有任何代码读取这个字段（只在序列化时输出，BaseError.ts:98），所以它暂时无害；但只要将来有人写一个「recoverable 为 false 就弹出致命错误」的全局处理器，context 丢失就会被当成致命错误。

想一想（不用写代码）：两种约定——「按错误类判断」和「按 recoverable 字段判断」——应该留哪一种？如果留字段，WebGLContextLostError 该怎样设置；如果不留，要不要在 RenderingError 的注释里写明「不要用 recoverable 判断能否恢复」？一个会误导人的字段，往往比没有这个字段更糟。
