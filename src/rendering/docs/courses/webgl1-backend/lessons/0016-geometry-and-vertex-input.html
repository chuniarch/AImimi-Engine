backend ④：把顶点数据交给 GPU——GeometryManager 与顶点输入

一个 Geometry 在 CPU 上只是几个 TypedArray。要画出来，得做两件事：把数字拷进 GPU 的 buffer（GeometryManager），再告诉 shader 的每个 attribute 从哪个 buffer、按什么格式读（顶点输入）。这一课先用背景盒子的 96 个字节把 GL 调用看明白，再从教程写法出发一版一版补上缺的东西，最后读真实代码：GeometryManager，以及顶点输入的三个文件。

和你的目标的关系 —— HW2 每帧画两样东西：背景盒子和 Mary。Mary 有 4 个属性、30522 个顶点，约 1.40 MiB 的顶点数据；它在哪里上传、上传几次、换预设时怎样删干净，都在这一课。FFT 海面的网格、HW1 的阴影 pass 也走同一条路。
默认你已经会的：第 15 课 2.4 节，链接后反射出「属性名 → location」；钩子 (hook) 就是构造 Manager 时从外面递进去的一个函数，Manager 在固定时刻调用它（第 15 课 2.6 节；那一节里 VAO 缓存的那张图，这一课 4.4 节讲完 VAO 以后一步一步重讲）；VAO 里记着 EBO 绑定、ARRAY_BUFFER 是整个 context 共用的（第 14 课 2.4 节，以及上次对话里的五步实测，2.4 节会再给一次）。Geometry 的字段（第 10 课）这一课 1.1 节会连同 HW2 的数再列一遍。如果其中哪一条其实没懂，告诉我，我先补那一块。

1.3 需求：要应付哪些情况

  1. 同一个 Geometry 只上传一次。每帧都画 Mary，两个 Mesh 也可能共用一个 Geometry；1.40 MiB 不能每帧拷一遍。
  2. 上传不能弄乱别人的绑定。尤其是索引 buffer：它的绑定记在当前 VAO 里，上传时改了它，别的物体就会用错索引。
  3. 失败不留半成品。四个属性传到第三个时显存不够，前两个 buffer 要删掉，缓存里也不能出现这个 Geometry。
  4. 老设备上的大索引。Uint32 索引要 OES_element_index_uint 扩展；没有时，能无损转成 Uint16 就转，转不了就在建任何 buffer 之前报错。
  5. shader 要的属性必须都有。缺了就报错，而且要在改任何 GL 状态之前报；Geometry 多出来的属性忽略。
  6. 换 program，location 就可能变。同一个 Geometry 配不同 shader，接线要按各自的 location 来。
  7. 没有 VAO 扩展也要能画。而且上一个物体打开的 location，这次不用就要关掉，否则 draw 可能出错（4.2 节实测）。
  8. 释放时删干净。Geometry 释放要删 buffer，但要先让顶点输入放掉借用这些 buffer 的接线；context 丢了不乱发命令。

2. 先把 GL 调用看明白

2.1 buffer：三步

const buffer = gl.createBuffer()               // ① 在 GPU 上建一个空的 buffer 对象
gl.bindBuffer(gl.ARRAY_BUFFER, buffer)         // ② 让 ARRAY_BUFFER 这个「绑定点」指向它
// ③ 把 data 的字节拷进「绑定点指向的那个 buffer」
gl.bufferData(gl.ARRAY_BUFFER, data, gl.STATIC_DRAW)
// data = 背景盒子的 Float32Array(24)：每个 Float32 占 4 字节，一共 96 字节
// 第 ③ 步不接收 buffer 参数——它操作的是第 ② 步绑上的那个。GL 的调用大多是这样：先绑，再操作。
// STATIC_DRAW 是提示：写一次、画很多次。GPU 可以把它放在读得最快的地方。

拷进去的 96 个字节是这样排的（每个顶点 12 字节，x、y、z 各 4 字节）：

2.2 vertexAttribPointer：告诉 shader 怎样读

gl.bindBuffer(gl.ARRAY_BUFFER, positionBuffer) // 先绑上要读的 buffer
gl.vertexAttribPointer(
  0,          // location：shader 的第 0 号输入（PRT 的 position，反射得到）
  3,          // size：每个顶点读 3 个分量（= itemSize），不足 4 个时 w 补 1
  gl.FLOAT,   // type：每个分量按 Float32 读（= GeometryManager 记下的 type）
  false,      // normalized：整数类型时才有意义，true 会把 0..255 映射到 0..1
  0,          // stride：相邻两个顶点隔多少字节；0 表示「紧挨着」，等于 3 × 4 = 12
  0           // offset：从第几个字节开始
)
gl.enableVertexAttribArray(0) // 打开第 0 号：从数组读。不打开时，它读的是一个固定值
// 读第 i 个顶点时，从 offset + i × 12 字节开始取 12 字节。i = 5：字节 60～71 → (1, −1, 1)
// 关键：pointer 把「此刻 ARRAY_BUFFER 绑的是谁」抄下来存好。之后改绑 ARRAY_BUFFER，不影响它。

项目里所有属性都是紧挨着排的（stride、offset 固定为 0），所以 GeometryManager 只要交出 buffer、type、itemSize、normalized 四样。

2.4 两个绑定点，和 VAO

上次对话里的实测（无界面 Chrome）再放一次，卡片可以在你的浏览器里重跑：

步骤                                      ARRAY_BUFFER  EBO   location 0 读
1 VAO1 里：绑 B1、pointer、绑 I                B1        I     B1
2 还在 VAO1：ARRAY_BUFFER 改绑 B2              B2        I     B1    ← pointer 已经抄下了 B1
3 切到 VAO2（新建，什么都没配）                B2        null  null  ← EBO 跟着 VAO 走
4 在 VAO2 里 pointer                           B2        null  B2    ← 此刻抄的是 B2
5 切回 VAO1                                    B2        I     B1    ← I、B1 都回来了

反过来，如果第 2 步改绑 B2 以后（还在 VAO1 里）再调用一次 pointer，location 0 就改读 B2：pointer 每调用一次，就把此刻 ARRAY_BUFFER 上的 buffer 重新抄一次。卡片记录的最后一行实测了这一点。

记住两句话：ARRAY_BUFFER 是整个 context 共用的，它只是 pointer 和 bufferData 的「操作对象」；每个 location 读哪个 buffer、EBO 是哪个，记在当前 VAO 里（没有绑任何 VAO 时，记在 context 自带的那个默认 VAO 里）。第 3 节的「上传会弄乱别人的索引」，和第 4 节的「为什么按 program 缓存 VAO」，都从这两句来。

3. GeometryManager 一版一版写

3.1 第 1 版：照教程写

// 第 1 版：照教程写——每个属性建一个 buffer，有索引再建一个
function uploadGeometryV1(gl: WebGLRenderingContext, geometry: GeometryLike): GpuGeometryV1 {
  // 这一次上传的结果：属性名 → 这次新建的 buffer。每次调用都新建一张、交给调用者；
  // 它不是缓存：下次再传同一个 Geometry，没有人会先查它
  const attributes = new Map<string, WebGLBuffer>()

  for (const name of geometry.getAttributeNames()) {
    const data = geometry.getAttribute(name)!.copyData() // 背景盒子的 position：24 个 Float32
    const buffer = gl.createBuffer()!
    gl.bindBuffer(gl.ARRAY_BUFFER, buffer) // 改了整个 context 共用的 ARRAY_BUFFER
    gl.bufferData(gl.ARRAY_BUFFER, data, gl.STATIC_DRAW) // 96 字节拷进 GPU
    attributes.set(name, buffer)
  }

  let indexBuffer: WebGLBuffer | null = null
  const indices = geometry.copyIndices() // 背景盒子：36 个 Uint8，Mary：null

  if (indices !== null) {
    indexBuffer = gl.createBuffer()!
    gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, indexBuffer) // 改的是「当前 VAO」里的 EBO
    gl.bufferData(gl.ELEMENT_ARRAY_BUFFER, indices, gl.STATIC_DRAW)
  }

  // 用完不把绑定还回去；也没有缓存，每次调用都重新上传一遍
  return { attributes, indexBuffer }
}

第 1 版有两个问题。

一是没有缓存。代码里的 attributes 是一张 Map，但它不是缓存：每次调用都新建一张，装的是「这一次」新建的 buffer，交给调用者就完了，下次调用不会去查它。缓存得是调用结束以后还留着、下次调用先去查的东西，比如 3.2 节第 2 版里作为类字段的 entries。第 1 版没有这样的东西，同一个 Geometry 每要一次，就新建一套 buffer、重拷一遍数据：Mary 每帧 1.40 MiB，而且旧的那套没人记得，删不掉。

二是用完不还绑定，会换掉别人的索引。上传时绑着哪个 VAO，取决于上传之前最后发生了什么。比如上一次 draw 画的是物体 A，画完 A 的 VAO（VAO_A）还绑着，这时上传背景盒子。第 1 版依次发出这四条命令，注意每一条对 VAO_A 有没有影响： 

// 上传前：当前 VAO 是 VAO_A，它的 EBO 是 A 自己的索引 I_A
gl.bindBuffer(gl.ARRAY_BUFFER, B)             // ARRAY_BUFFER 不在 VAO 里：VAO_A 不变
gl.bufferData(gl.ARRAY_BUFFER, position)      // 数据拷进 B：VAO_A 不变
gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, I_盒子) // EBO 绑定点就在当前 VAO 里：
                                              //   VAO_A 的 EBO 在这一刻变成 I_盒子
gl.bufferData(gl.ELEMENT_ARRAY_BUFFER, indices) // 数据拷进 I_盒子
// 上传结束不还：下次画 A，bindVertexArrayOES(VAO_A) 带回来的 EBO 是 I_盒子

为什么只换掉 EBO，碰不到 location 读的 buffer？回到 2.4 节的表：location 读哪个 buffer，只在调用 vertexAttribPointer 的那一刻从 ARRAY_BUFFER 抄一次。第 1 版只调用 bindBuffer、不调用 pointer（pointer 是第 4 节顶点输入的事），所以 ARRAY_BUFFER 怎么改都碰不到任何 location。EBO 没有「抄」这一步：ELEMENT_ARRAY_BUFFER 这个绑定点本身就存在当前 VAO 里，bindBuffer 一调用就写进去了。下次画 A，按盒子的编号去取 A 的顶点，画错了，也不报错。

下面两张卡片只跑第 1 版，把这两个问题跑出来。第 2 版怎样解决，在 3.2 节。

3.2 第 2 版：缓存，加上「先记下、再还回」

// 第 2 版：按 Geometry 对象缓存；上传前记下两个绑定，上传完绑回去，再告诉 State
class GeometryCacheV2 {
  private readonly entries = new Map<GeometryLike, GpuGeometryV1>()

  constructor(
    private readonly gl: WebGLRenderingContext,
    private readonly invalidateState: () => void // 第 14 课：State 记的绑定可能已经过时
  ) {}

  get(geometry: GeometryLike): GpuGeometryV1 {
    const cached = this.entries.get(geometry)
    if (cached !== undefined) return cached // 第二次起：一条 GL 命令也不发

    const gl = this.gl
    // 上传会改这两个绑定点，先查出现在绑的是谁
    const previousArray = gl.getParameter(gl.ARRAY_BUFFER_BINDING) as WebGLBuffer | null
    const previousElements = gl.getParameter(
      gl.ELEMENT_ARRAY_BUFFER_BINDING
    ) as WebGLBuffer | null

    try {
      const result = uploadGeometryV1(gl, geometry)
      this.entries.set(geometry, result)
      return result
    } finally {
      gl.bindBuffer(gl.ARRAY_BUFFER, previousArray)
      gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, previousElements) // 把当前 VAO 的 EBO 还回去
      this.invalidateState()
    }
  }
}

缓存的 key 是 Geometry 对象本身（第 4 课：每个 CPU 资源在每个 context 里一份 GPU 表示）。两个 Mesh 共用一个 Geometry 时，第二次 get 直接拿到同一份 buffer。上传前用 getParameter 查出两个绑定点现在是谁，上传完绑回去，当前 VAO 的 EBO 就还原了。最后调用 invalidateState：GeometryManager 绕过 State 直接改过绑定，要告诉 State 它记的可能不对了（第 14 课）。

注意第 2 版并没有让 VAO_A「不被碰」：上传过程中，第 3 条命令照样把 VAO_A 的 EBO 换成了 I_盒子。区别在 finally：上传前查出的 previousElements 是 I_A，最后再 bindBuffer(ELEMENT_ARRAY_BUFFER, I_A) 一次，又写回了 VAO_A。也就是「改了，再还原」。用 3.1 节的两个场景，换成第 2 版再跑一次：

第 2 版还缺一样：bufferData 失败时不会抛异常。显存不够时，GL 只是记下一个错误码（OUT_OF_MEMORY，1285），bufferData 照常返回。第 2 版不问 getError，会把一个空的 buffer 当成成功、放进缓存，以后每帧都画不出来，也不报错。下一节的真实代码补上了这一条，以及需求 3、4、8。

3.3 真实代码：get

// WebGL1GeometryManager.ts:104–201（去掉了原注释块；注释是课程加的）
get(geometry: Geometry): WebGL1GeometryResource {
  this.assertAvailable('get geometry') // Manager 还开着、context 没丢
  if (geometry.disposed) throw new ResourceDisposedError('Geometry')
  if (this.releasing.has(geometry)) {
    throw new WebGLOperationError('get geometry', 'Geometry', 'release is in progress')
  }

  const cached = this.entries.get(geometry)
  if (cached !== undefined) return cached.resource // 第 2 版的缓存

  // 先在 CPU 上查完能查的：Uint32 索引降不了级，就一个 buffer 都不建（3.4 节）
  const indices = this.prepareIndices(geometry.copyIndices())
  const mode = this.primitiveMode(geometry.topology) // 'triangles' → gl.TRIANGLES
  const gl = this.gl
  const owned: WebGLBuffer[] = [] // 这一次新建了哪些 buffer：失败时照单删除

  // 别人留下的 GL 错误，不算到自己头上（第 15 课）
  this.checkError('preflight', 'Geometry')

  // 第 2 版：先记下两个绑定点现在是谁
  const previousArray = gl.getParameter(gl.ARRAY_BUFFER_BINDING) as WebGLBuffer | null
  const previousElements = gl.getParameter(
    gl.ELEMENT_ARRAY_BUFFER_BINDING
  ) as WebGLBuffer | null
  this.checkError('capture buffer bindings', 'Geometry')

  try {
    const attributes = new Map<string, WebGL1AttributeResource>()
    let indexBuffer: WebGLBuffer | null = null

    try {
      for (const name of geometry.getAttributeNames()) {
        const attribute = geometry.getAttribute(name)!
        const data = attribute.copyData()
        const type = this.attributeType(data) // Float32Array → gl.FLOAT
        const buffer = this.upload(
          gl.ARRAY_BUFFER,
          data,
          `Geometry.attribute:${name}`,
          owned
        )
        // 交给顶点输入的「怎样读」：buffer、分量类型、几个分量、要不要归一化
        attributes.set(
          name,
          Object.freeze({
            buffer,
            type,
            itemSize: attribute.itemSize,
            normalized: attribute.normalized
          })
        )
      }
      if (indices !== null) {
        indexBuffer = this.upload(
          gl.ELEMENT_ARRAY_BUFFER,
          indices,
          'Geometry.indices',
          owned
        )
      }
    } finally {
      // 不管成功失败都绑回去；context 丢了就不发命令
      if (!gl.isContextLost() && !this.lostValue) {
        gl.bindBuffer(gl.ARRAY_BUFFER, previousArray)
        gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, previousElements)
      }
      this.hooks.invalidateState()
    }

    this.checkError('restore buffer bindings', 'Geometry')

    // Uint8Array → UNSIGNED_BYTE
    const indexType = indices === null ? null : this.indexType(indices)
    const resource: WebGL1GeometryResource = Object.freeze({
      attributes,
      indexBuffer,
      indexType,
      drawCount: geometry.drawCount,  // 背景盒子 36，Mary 30522
      primitiveMode: mode
    })

    // 全部成功才订阅、才进缓存：缓存里不会出现半成品
    const unsubscribe = geometry.onDispose(() => this.release(geometry))
    this.entries.set(geometry, { resource, unsubscribe })
    return resource
  } catch (error) {
    if (gl.isContextLost() || this.lostValue) {
      this.invalidateForContextLoss() // 丢了：不发 delete，只丢记录
      throw new WebGLContextLostError('create geometry')
    }
    for (const buffer of owned) gl.deleteBuffer(buffer) // 照清单删掉这次建的
    this.hooks.invalidateState()
    throw error
  }
}

和第 2 版比，多了四样：上传后用 getError 检查（upload 里）；一张 owned 清单，失败时照单删掉这次建的 buffer；全部成功才进缓存、才订阅 onDispose；context 丢了就只丢记录、不发 delete。upload 和索引预检在下面：

// WebGL1GeometryManager.ts:290–305、:314–336（注释是课程加的）
private prepareIndices(indices: IndexData | null): IndexData | null {
  // 不是 Uint32，或者设备有 OES_element_index_uint：原样交回
  if (!(indices instanceof Uint32Array) || this.capabilities.elementIndexUint !== null) {
    return indices
  }
  // 查的是「最大的那个编号」，不是索引个数，也不是顶点个数
  for (const index of indices) {
    if (index > 65535) {
      throw new UnsupportedIndexTypeError(
        'Uint32Array',
        'OES_element_index_uint is unavailable and an index exceeds 65535'
      )
    }
  }
  return new Uint16Array(indices) // 每个编号都放得进 16 位：复制一份，CPU 上的原数组不动
}

private upload(
  target: number,
  data: VertexAttributeData | IndexData,
  label: string,
  owned: WebGLBuffer[]
): WebGLBuffer {
  const gl = this.gl
  const candidate = gl.createBuffer()
  this.assertAvailable('create buffer')
  const buffer = requireNonNull(
    candidate,
    () => new WebGLResourceCreationError('buffer', label)
  )
  owned.push(buffer) // 一拿到就记进清单：后面 bufferData 失败也找得到它
  gl.bindBuffer(target, buffer)
  gl.bufferData(target, data, gl.STATIC_DRAW)
  // bufferData 失败不会抛异常（比如显存不够），要自己问 getError
  this.checkError('upload buffer', label)
  return buffer
}

3.4 Uint32 索引：能降就降

WebGL1 原生只支持 Uint8、Uint16 两种索引，Uint32 要靠 OES_element_index_uint 扩展（第 13 课探测的能力之一，现在的桌面浏览器基本都有）。没有扩展时，一个 Uint16 最大存 65535。真实代码的做法（上面 prepareIndices）：逐个看编号，全都 ≤ 65535 就复制成 Uint16Array；有一个超过就报 UnsupportedIndexTypeError，而且这时一个 buffer 都还没建。查的是「最大编号」而不是「索引个数」：Mary 如果改成带索引的版本，有 30522 个角、7905 个不同的顶点，最大编号 7904，放得进 Uint16；索引个数再多也没关系。

3.5 释放：先让顶点输入放手

// WebGL1GeometryManager.ts:212–247（注释是课程加的）
release(geometry: Geometry): void {
  const entry = this.entries.get(geometry)
  if (entry === undefined || this.releasing.has(geometry)) return // 没建过，或者正在删

  if (this.gl.isContextLost() || this.lostValue) {
    this.invalidateForContextLoss()
    return
  }

  this.releasing.add(geometry)
  try {
    // ① 先让顶点输入放掉借用这些 buffer 的 VAO、当前接线（和第 15 课 2.6 节同一个套路）
    this.hooks.beforeDelete?.(geometry)
    if (this.gl.isContextLost() || this.lostValue) {
      this.invalidateForContextLoss()
      return
    }
    // ② 退订、移出缓存
    entry.unsubscribe()
    this.entries.delete(geometry)
    // ③ 删除自己拥有的 buffer
    for (const attribute of entry.resource.attributes.values()) {
      this.gl.deleteBuffer(attribute.buffer)
    }
    if (entry.resource.indexBuffer !== null) {
      this.gl.deleteBuffer(entry.resource.indexBuffer)
    }
    this.hooks.invalidateState()
  } finally {
    this.releasing.delete(geometry)
  }
}

和第 15 课 2.6 节是同一个套路：删除之前先调用 beforeDelete，ResourceManager 往里填的是「请顶点输入放掉这个 Geometry」（WebGL1ResourceManager.ts:93–98）。这里多一个理由：WebGL 规定，某个 location 打开着、却已经没有 buffer 可读（buffer 被删了，绑定就清空了），draw 会报 INVALID_OPERATION，哪怕 shader 根本不用这个 location（WebGL 1.0 规范「No Client Side Arrays」一节）。4.2 节的卡片实测了这一点。

4. 顶点输入：把 buffer 接到 location 上

4.1 两份结果按名字配对

// ProgramManager 交回（PRT program）：            GeometryManager 交回（Mary）：
//   position → 0                             position      → { buffer P,  FLOAT, 3, false }
//   aTransportSH0 → 1                        aTransportSH0 → { buffer T0, FLOAT, 3, false }
//   aTransportSH1 → 2                        aTransportSH1 → { buffer T1, FLOAT, 3, false }
//   aTransportSH2 → 3                        aTransportSH2 → { buffer T2, FLOAT, 3, false }
//
// resolve 按名字配成：
//   [{ location 0, buffer P },  { location 1, buffer T0 },
//    { location 2, buffer T1 }, { location 3, buffer T2 }]
// apply 对每一条做 2.2 节那三行：bindBuffer、vertexAttribPointer、enableVertexAttribArray，
// 最后绑 EBO
// WebGL1VertexInputSupport.ts:80–103、:112–134（注释是课程加的）
resolve(
  geometry: WebGL1GeometryResource,
  program: WebGL1ProgramResource
): readonly VertexBinding[] {
  // program 用到的属性：
  //   [{ name: 'position', location: 0 }, { name: 'aTransportSH0', location: 1 }, …]
  const inputs = this.readInputs(program)

  return inputs.map(({ name, location }) => {
    const attribute = geometry.attributes.get(name) // 按名字配对，不猜别名
    if (attribute === undefined) {
      // shader 要、Geometry 没有：在改任何 GL 状态之前就报错
      throw new UnsupportedRenderFeatureError(
        'vertex input',
        `missing active attribute ${name}`
      )
    }
    if (
      !Number.isInteger(attribute.itemSize) ||
      attribute.itemSize < 1 ||
      attribute.itemSize > 4
    ) {
      throw new UnsupportedRenderFeatureError(
        'vertex input',
        `${name}: itemSize must be 1..4`
      )
    }
    return { location, attribute } // Geometry 多出来的属性不会出现在这里
  })
}

apply(bindings: readonly VertexBinding[], indexBuffer: WebGLBuffer | null): void {
  const gl = this.gl
  for (const { location, attribute } of bindings) {
    // pointer 记下的是「此刻」的 ARRAY_BUFFER
    gl.bindBuffer(gl.ARRAY_BUFFER, attribute.buffer)
    gl.vertexAttribPointer(
      location,
      attribute.itemSize,
      attribute.type,
      attribute.normalized,
      0,
      0
    )
    gl.enableVertexAttribArray(location)
  }
  // 没有索引也要显式绑 null：不能留着上一个物体的 EBO
  gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, indexBuffer)
  this.checkError('configure vertex input')
}

resolve 只读不写：缺属性、itemSize 不在 1～4、location 不合法，都在这里抛错，这时 GL 状态还没动过（需求 5）。它用到的 readInputs 会对每个 program 再反射一次属性的类型，只收 float、vec2、vec3、vec4：mat4 属性要占 4 个连续 location，现在的接线方式一条 pointer 只接一个 location，所以明确拒绝，而不是悄悄画错（WebGL1VertexInputSupport.ts:216–223 的 TODO）。

location 由 program 决定，而且和声明顺序有关：同样两个属性，在 SwiftShader 上先声明 position 时它是 0，先声明 aOther 时它是 1。所以同一个 Geometry 配两个 shader，接线可能完全不同（需求 6）。下面的卡片在你的浏览器里查。

4.2 没有 VAO：每次 draw 前接一遍线

先看 GL 里有什么。没有 VAO 扩展时，顶点输入的状态只有一份，整个 context 共用（就是 2.4 节说的 context 自带的那个默认 VAO）。可以把它想成一张 16 行的表（MAX_VERTEX_ATTRIBS：规范只保证至少 8 行，常见设备和 SwiftShader 上实测是 16，下面按 16 说），每一行对应一个 location，记三样东西：开没开、读哪个 buffer、按什么格式读。表外还有一格：EBO。draw 的时候，GPU 只看这张表取顶点。 

// 默认的这张表（整个 context 只有一份）。刚建好 context 时：
// location   开着？   读哪个 buffer
//    0         关        null
//    1         关        null
//    …
//   15         关        null
// EBO：null

// 开一行要三条命令（2.2 节）：
gl.bindBuffer(gl.ARRAY_BUFFER, P)                      // 选中 buffer
gl.vertexAttribPointer(0, 3, gl.FLOAT, false, 0, 0)    // 第 0 行抄下「读 P、每顶点 3 个 float」
gl.enableVertexAttribArray(0)                          // 第 0 行打开
// 关一行只要一条：
gl.disableVertexAttribArray(1)

所以没有 VAO 时，顶点输入的工作就是：每次 draw 之前，把这张表改成这次 draw 要的样子。HW2 每帧画两样东西，要的样子分别是：

  • 画背景盒子（背景 shader 只要 position，在 location 0）：第 0 行开着、读盒子的 position buffer（下面叫 P盒子）；其余行关；EBO 是盒子的索引 I盒子。
  • 画 Mary（PRT shader 要 4 个属性，在 location 0～3）：第 0～3 行开着，分别读 P、T0、T1、T2；其余行关；EBO 是 null（Mary 没有索引）。

第 1 版：只管这次要用的行。按 4.1 节 resolve 配好的结果，一行一行接上，最后绑 EBO：

// 没有 VAO 时的第 1 版：每次 draw 前，把这次要用的 location 接好；用不到的不管
function bindManualV1(
  gl: WebGLRenderingContext,
  bindings: readonly BindingLike[],
  indexBuffer: WebGLBuffer | null
): void {
  for (const binding of bindings) {
    gl.bindBuffer(gl.ARRAY_BUFFER, binding.buffer)
    gl.vertexAttribPointer(
      binding.location,
      binding.itemSize,
      binding.type,
      binding.normalized,
      0,
      0
    )
    gl.enableVertexAttribArray(binding.location) // 打开以后，下一次 draw 不会自动关掉
  }

  gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, indexBuffer)
}

第 ③ 步画背景时，第 1～3 行还开着、读着 Mary 的 buffer。背景 shader 不用这三行，所以这一帧还画得对。问题出在第 ④ 步：buffer 删掉时，读它的行被清成「没有 buffer」，可行本身还开着。WebGL 规定，只要有一行开着却没有 buffer 可读，draw 就报 INVALID_OPERATION（1282），不管 shader 用不用这一行（3.5 节）。于是第 ⑤ 步背景画不出来。

结论：这次不用的行，要关掉。可「哪些行开着」GL 不会主动告诉你，只能自己记。

第 2 版：记下上次开了哪些，这次不用的关掉。

// 没有 VAO 时的第 2 版：多记一样东西——上一次 bind 打开了哪些 location
class ManualInputV2 {
  // 上一次打开的 location，比如画完 Mary 是 {0, 1, 2, 3}
  private readonly enabled = new Set<number>()

  constructor(private readonly gl: WebGLRenderingContext) {}

  bind(bindings: readonly BindingLike[], indexBuffer: WebGLBuffer | null): void {
    const gl = this.gl
    // 这次要开的 location，比如画背景是 {0}
    const next = new Set(bindings.map((binding) => binding.location))

    for (const location of this.enabled) {
      // 上次开、这次不用：关掉。画完 Mary 再画背景，这里关掉 1、2、3
      if (!next.has(location)) gl.disableVertexAttribArray(location)
    }

    bindManualV1(gl, bindings, indexBuffer) // 这次要用的，照第 1 版接好

    // 记下这次开了哪些，留给下一次 bind 用
    this.enabled.clear()
    for (const location of next) this.enabled.add(location)
  }
}

第 2 版还漏了两种情况。

  1. 第一次 bind 之前，表里已经有东西。第 2 版的 enabled 一开始是空集合，等于假设表是全关的。可同一个 canvas 的 context 也许被别的代码用过（比如旧引擎的代码、一个第三方库），留下了开着的行。第 2 版不知道这些行，也就永远不会去关。真实代码的做法：还没接管过（initialized 为 false）时，不知道之前开了什么，就把 0～15 全部当成「可能开着」，这次不用的全关一遍。之后才靠 enabled 记录。
  2. 接到一半失败。比如接到第 3 行时 context 丢了，或者某条命令报了错。这时表里一部分是新的、一部分是旧的，enabled 记录也对不上。真实代码的做法：只要已经开始改 GL（changed 为 true），失败时就把 0～15 全关、两个绑定点清空（resetBindings），记录清空，再把错误抛给调用者；调用者跳过这次 draw，下次 bind 从一张干净的表开始。反过来，如果是 resolve 发现缺属性，这时还没动过 GL，就什么都不用收拾。

真实代码就是第 2 版加上这两条：

// WebGL1ManualVertexInputManager.ts:50–104（注释是课程加的）
bind(
  geometry: Geometry,
  gpuGeometry: WebGL1GeometryResource,
  program: WebGL1ProgramResource
): void {
  let changed = false // 只有开始改 GL 以后失败，才需要收拾
  try {
    this.support.assertBindable(geometry)
    this.support.checkError('prepare manual vertex input')

    const bindings = this.support.resolve(gpuGeometry, program) // 先查完：缺属性就在这里抛
    const nextEnabled = new Set(bindings.map((binding) => binding.location)) // 这次要用 {0}

    changed = true
    // 上次打开了哪些：第一次不知道，就把 0～15 全部当成「可能开着」
    const previous = this.initialized
      ? this.enabled
      : Array.from({ length: this.support.maxAttributes }, (_, index) => index)

    for (const location of previous) {
      if (!nextEnabled.has(location)) {
        this.gl.disableVertexAttribArray(location) // 上次用、这次不用：关掉
      }
    }

    this.support.apply(bindings, gpuGeometry.indexBuffer)

    // 全部成功才更新记录
    this.enabled.clear()
    for (const location of nextEnabled) {
      this.enabled.add(location)
    }
    this.initialized = true
    this.currentGeometry = geometry
    this.currentProgram = program.program
  } catch (error) {
    if (!this.support.disposed && this.support.contextLost) {
      this.invalidateForContextLoss()
      throw new WebGLContextLostError('bind vertex input')
    }
    if (changed) {
      this.resetBindings(true) // 改到一半失败：0～15 全关、两个绑定点清空，调用者跳过这次 draw
    }
    throw error
  } finally {
    this.hooks.invalidateState()
  }
}

最后看一下代价：没有 VAO 时，画一次 Mary，光是接线就要发 4 × 3 + 1 = 13 条 GL 命令（每个属性三条，加上绑 EBO），每帧每次 draw 都重来一遍；另外，真实代码每次还调用两次 getError（进门检查一次、接完检查一次）。下一节的 VAO 把这 13 条变成 1 条。

4.3 有 VAO：接好一次，以后一条命令

VAO 是什么，再说一次。一个 VAO 就是一张自己的「16 行表 + EBO」，和 4.2 节那张默认的表结构一样。bindVertexArrayOES(vao) 把「当前的表」换成它；之后的 pointer、enable、绑 EBO，全都写进这张表。所以思路是：每种要画的组合，录一张表；以后再画这种组合，换上它就行。换表只要 1 条命令，代替 4.2 节的 13 条。新建的 VAO 是一张全关的表，只开录进去的那几行，所以 4.2 节「关掉不用的行」的问题，在 VAO 这里自然就没有了。

第 1 版：每个 Geometry 录一张表。第一次画某个 Geometry 时，建一个 VAO、换上它、照 4.2 节第 1 版接一遍线，接线就录进去了；以后再画它，直接换上：

// 有 VAO 的第 1 版：每个 Geometry 录一张表
class VaoCacheV1 {
  private readonly vaos = new Map<object, WebGLVertexArrayObjectOES>() // Geometry → VAO

  constructor(
    private readonly gl: WebGLRenderingContext,
    private readonly ext: OES_vertex_array_object
  ) {}

  bind(
    geometry: object,
    bindings: readonly BindingLike[], // 按这次 draw 的 program 算出的接线（4.1 节）
    indexBuffer: WebGLBuffer | null
  ): void {
    const cached = this.vaos.get(geometry)
    if (cached !== undefined) {
      // 命中：换上录好的表，一条命令。
      // 注意 bindings 在这里没用上：表是按「第一次画它时的 program」录的
      this.ext.bindVertexArrayOES(cached)
      return
    }

    const vao = this.ext.createVertexArrayOES()! // 一张新表：16 行全关，EBO 是 null
    this.ext.bindVertexArrayOES(vao) // 换上它：之后的 pointer、enable、绑 EBO 都写进这张表
    bindManualV1(this.gl, bindings, indexBuffer) // 录：和 4.2 节第 1 版一样的命令
    this.vaos.set(geometry, vao)
  }
}

问题在「录的是哪个 program 的 location」。4.1 节说过：location 由 program 决定，换个 shader 就可能变。设想调试时 Mary 换了一个 shader，它只用 position 和 aTransportSH0，而且链接出来 aTransportSH0 在 0、position 在 1。第 1 版命中了 Mary 的那张表，可那张表是按 PRT program 录的： 

// Mary 的表（第一次画 Mary 时按 PRT program 录的）：
//   0 → P（position）  1 → T0  2 → T1  3 → T2
// 调试 shader 要的：
//   position 从 1 读    → 表里第 1 行是 T0：position 读到的是传输系数
//   aTransportSH0 从 0 读 → 表里第 0 行是 P：系数读到的是位置
// 不报任何错，只是画错

所以 key 里必须有 program：同一个 Geometry，配不同的 program，各录各的表。

第 2 版：两层 key，先按 Geometry，再按 program。

// 有 VAO 的第 2 版：两层 key，先按 Geometry，再按 program
class VaoCacheV2 {
  // 外层表：Geometry → 小表；小表：program → VAO
  private readonly vaos = new Map<object, Map<WebGLProgram, WebGLVertexArrayObjectOES>>()

  constructor(
    private readonly gl: WebGLRenderingContext,
    private readonly ext: OES_vertex_array_object
  ) {}

  bind(
    geometry: object,
    program: WebGLProgram, // 多了这个参数：这次 draw 用的 program
    bindings: readonly BindingLike[],
    indexBuffer: WebGLBuffer | null
  ): void {
    // 查两次：先拿 Geometry 查外层表，得到它的小表；再拿 program 查小表
    const cached = this.vaos.get(geometry)?.get(program)
    if (cached !== undefined) {
      this.ext.bindVertexArrayOES(cached) // 命中：这张表就是按这个 program 录的
      return
    }

    const vao = this.ext.createVertexArrayOES()!
    this.ext.bindVertexArrayOES(vao)
    bindManualV1(this.gl, bindings, indexBuffer) // 按这个 program 的 location 录

    // 这个 Geometry 第一次出现时，先给它建一张空的小表
    const programs =
      this.vaos.get(geometry) ?? new Map<WebGLProgram, WebGLVertexArrayObjectOES>()
    programs.set(program, vao)
    this.vaos.set(geometry, programs)
  }
}

Map<Geometry, Map<program, VAO>> 是 Map 里套 Map，查的时候分两步：先拿 Geometry 查外层表，得到这个 Geometry 自己的小表；再拿 program 查小表，得到 VAO。画完背景、Mary（PRT），再画 Mary（调试 shader）以后，表里是这样： 

// 外层表（key 是 Geometry）
//   盒子 → 小表（key 是 program）
//            program#背景 → VAO#1
//   Mary → 小表
//            program#PRT  → VAO#2
//            program#调试 → VAO#3   ← 换 shader 时新录的一张
// 下一帧再画 Mary（调试）：get(Mary) 得到 Mary 的小表，.get(program#调试) 得到 VAO#3，命中

真实代码在第 2 版上还多做了五件事（对照下面代码里的注释）：

  1. 先 resolve，再建 VAO。缺属性时在建 VAO 之前就抛错，不会留下半张表（需求 5）。
  2. 录完把 ARRAY_BUFFER 还回去，但新 VAO 留着绑定。录的时候改过 ARRAY_BUFFER，它不在 VAO 里，是整个 context 共用的，要还原；新 VAO 不还原，因为紧接着就要 draw。
  3. 录到一半失败，就还原进入前的 VAO 和 ARRAY_BUFFER，删掉这张半成品表。它不进缓存。
  4. 同一个 Geometry 重新上传过，就重录。缓存里除了 VAO 还记着录表时的 gpuGeometry。GeometryManager 如果给这个 Geometry 建了新的 buffer，旧表里抄的还是旧 buffer，cached.gpuGeometry === gpuGeometry 不成立，就重录一张、删掉旧的。
  5. finally 里通知 State。换 VAO 等于换了 EBO（第 14 课），录表时还改过 ARRAY_BUFFER，State 记的这两样都可能不对了。
// WebGL1OESVertexInputManager.ts:58–140（注释是课程加的；报错文案用 … 代替）
bind(
  geometry: Geometry,
  gpuGeometry: WebGL1GeometryResource,
  program: WebGL1ProgramResource
): void {
  try {
    this.support.assertBindable(geometry)

    // 两层 key：先按 Geometry，再按 program（第 15 课 2.6 节）
    const cached = this.entries.get(geometry)?.get(program.program)
    if (cached?.gpuGeometry === gpuGeometry) {
      this.extension.bindVertexArrayOES(cached.vao) // 命中：一条命令就接好了全部输入
      this.support.assertReady('bind cached VAO')
      this.currentVAO = cached.vao
      return
    }

    this.support.checkError('prepare VAO')
    const bindings = this.support.resolve(gpuGeometry, program) // 先查完再动手

    // 记下现在的 VAO 和 ARRAY_BUFFER，失败时还原
    const previousVAO = this.gl.getParameter(
      this.extension.VERTEX_ARRAY_BINDING_OES
    ) as WebGLVertexArrayObjectOES | null
    const previousArray = this.gl.getParameter(
      this.gl.ARRAY_BUFFER_BINDING
    ) as WebGLBuffer | null
    this.support.checkError('capture vertex input')

    const candidate = this.extension.createVertexArrayOES()
    this.support.assertReady('create VAO')
    const vao = requireNonNull(
      candidate,
      () => new WebGLResourceCreationError('vertex-array', …)
    )

    try {
      this.extension.bindVertexArrayOES(vao) // 之后的 pointer、enable、EBO 都录进这个 VAO
      this.support.apply(bindings, gpuGeometry.indexBuffer)
      // ARRAY_BUFFER 不属于 VAO：还回去
      this.gl.bindBuffer(this.gl.ARRAY_BUFFER, previousArray)
      this.support.checkError('finish VAO')

      const programs =
        this.entries.get(geometry) ?? new Map<WebGLProgram, VertexArrayEntry>()
      programs.set(program.program, { vao, gpuGeometry })
      this.entries.set(geometry, programs)
      this.currentVAO = vao // 新 VAO 保持绑定：接下来就要 draw

      // 同一个 Geometry 重新上传过（buffer 换了）：旧 VAO 指着旧 buffer，删掉
      if (cached !== undefined) {
        this.extension.deleteVertexArrayOES(cached.vao)
      }
    } catch (error) {
      if (!this.support.contextLost) {
        this.extension.bindVertexArrayOES(previousVAO)
        this.gl.bindBuffer(this.gl.ARRAY_BUFFER, previousArray)
        this.extension.deleteVertexArrayOES(vao) // 半成品不进缓存
      }
      throw error
    }
  } catch (error) {
    if (!this.support.disposed && this.support.contextLost) {
      this.invalidateForContextLoss()
      throw new WebGLContextLostError('bind vertex input')
    }
    throw error
  } finally {
    this.hooks.invalidateState() // 第 14 课：切 VAO 换掉了 EBO，State 要忘掉
  }
}

  • 查不到。要命中 program#1 这一行，得有人拿 program#1 调用 bind。而 bind 的 program 只来自 programs.get(材质的 ShaderModule)：材质现在用 v3；v1 已经释放，再 get(v1) 会直接抛 ResourceDisposedError（WebGL1ProgramManager.ts:83），ProgramManager 自己的记录也删了。除了小表里的这个 key，再没有代码拿着 program#1。
  • 没人删。没有钩子时，顶点输入只在两种时候删 VAO：Mary 这个 Geometry 释放（releaseGeometry 把 Mary 下面的行全删），或者顶点输入自己 dispose。调 shader 的时候 Mary 一直留着，这两件事都不会发生。
  • 一直占着。VAO 是 GPU 对象。program 删了，GL 不会跟着删 VAO：VAO 里记的是「哪个 location 读哪个 buffer、什么格式」，不记 program（4.3 节）。不调用 deleteVertexArrayOES，它就一直在。

// WebGL1OESVertexInputManager.ts:183–205（注释是课程加的）
releaseProgram(program: WebGLProgram): void {
  if (this.support.disposed) return // 顶点输入自己已经 dispose 了：VAO 早就删光了

  if (this.support.contextLost) {
    this.invalidateForContextLoss() // context 丢了：不发 delete，只丢记录
    return
  }

  // 外层表的每个 Geometry 都翻一遍：一个 program 可能画过好几个 Geometry
  for (const [geometry, programs] of this.entries) {
    const entry = programs.get(program) // 这个 Geometry 的小表里有这个 program 吗
    if (entry === undefined) continue // 没有（比如盒子的小表）：跳过

    this.deleteEntry(entry) // deleteVertexArrayOES；它正绑着的话先 unbind
    programs.delete(program) // 删掉小表里这一行

    if (programs.size === 0) {
      // 小表空了，把这个 Geometry 从外层表拿掉，不留空表
      // （边遍历边删当前这一项，JS 的 Map 允许）
      this.entries.delete(geometry)
    }
  }

  this.support.forgetProgram(program) // 再清掉按 program 缓存的属性类型（4.1 节）
}

它要把外层表的每个 Geometry 都翻一遍，因为一个 program 可以画好几个 Geometry（比如两个 Mesh 共用一个材质），每个 Geometry 下面都可能有一个按它建的 VAO。小表删空了，就把这个 Geometry 从外层表里拿掉，不留空表。

为什么一定在 deleteProgram 之前：releaseProgram 如果抛错，ProgramManager 就停在这里，program 没删，记录还在，以后还能再 release 一次。反过来，先删 program、丢掉记录，再去通知，通知一失败，就再也没人记得还有 VAO 要删（第 15 课 2.6 节的第二张卡片实测过）。下面两张卡片在你的浏览器里跑真实代码，把每一步的表打印出来。

4.5 三个文件怎样分工

// WebGL1VertexInputManager.ts:61–74（注释是课程加的）
export function createWebGL1VertexInputManager(
  gl: WebGLRenderingContext,
  capabilities: Pick<WebGL1Capabilities, 'vertexArrayObject' | 'maxVertexAttributes'>,
  hooks: WebGL1VertexInputHooks
): WebGL1VertexInputManager {
  // 探测时 getExtension('OES_vertex_array_object') 的结果（第 13 课）；没有就是 null
  const extension = capabilities.vertexArrayObject
  if (extension !== null) {
    return new WebGL1OESVertexInputManager(
      gl,
      extension,
      capabilities.maxVertexAttributes,
      hooks
    )
  }
  return new WebGL1ManualVertexInputManager(gl, capabilities.maxVertexAttributes, hooks)
}
文件是什么拥有什么
WebGL1VertexInputManager.ts两种做法共同实现的接口（bind、unbind、releaseGeometry、releaseProgram、invalidateForContextLoss、dispose），外加按能力选哪种的工厂什么都不拥有
WebGL1VertexInputSupport.ts两种做法共用的零件：resolve（配对和验证）、apply（真正接线）、每个 program 的属性类型缓存只有元数据
WebGL1OESVertexInputManager.ts有 VAO 的做法：按两层 key 缓存 VAO自己建的 VAO
WebGL1ManualVertexInputManager.ts没有 VAO 的做法：每次接线，记住打开了哪些 location只有 enabled 集合等记录

两种做法实现同一个接口，Backend 只认接口，不知道用的是哪种（策略模式）。共用的部分放进 Support，两种做法各持有一个 Support 实例，而不是继承同一个父类（组合）。buffer 和 program 都是借来的：两种做法的 release、dispose 只删自己建的 VAO 或清自己的记录，从不删 buffer、program。

4.6 和 Lifecycle 的关系

第 13 课第 2 节说，context 丢了以后，Backend 要把旧的一代作废、再建新的一代。GeometryManager 和顶点输入在这两件事里做的事：

  • 一代一份。createGeneration 新建 ResourceManager（WebGL1Backend.ts:259–267），它再新建顶点输入（WebGL1ResourceManager.ts:83，工厂按这一代探测到的能力选 OES 或 Manual）和 GeometryManager（:93–98）。buffer 缓存、VAO 缓存、Manual 的 enabled 记录，都跟着各自的 Manager 走，也是一代一份。
  • lost 事件到达：丢记录、退订，不 delete。ResourceManager 按「先借用方、后所有者」的顺序逐个通知（:171–179），顶点输入排在 GeometryManager 前面。GeometryManager（WebGL1GeometryManager.ts:250 起）记下 lost、退订所有 Geometry、清空缓存，不调用 deleteBuffer。OES 顶点输入（WebGL1OESVertexInputManager.ts:208–213）清空两层表、忘掉当前 VAO，不调用 deleteVertexArrayOES。Manual（WebGL1ManualVertexInputManager.ts:140–147）清空 enabled，并把 initialized 改回 false。buffer 和 VAO 已经随 context 一起失效了，删不删都一样，发命令反而是在对一个死掉的 context 说话。
  • 事件还在排队、context 已经丢了：先发现，不乱删。GeometryManager.get 开头的 assertAvailable 问 isContextLost（:447–454）；上传到一半丢了，catch 先判断丢失，作废并抛 WebGLContextLostError，不去删 owned 里已经失效的 buffer（3.3 节）。顶点输入的 bind 一开头就由 Support 检查（assertBindable → assertReady），catch 里同样先判断丢失。
  • 恢复以后：新 Manager，空缓存，从 CPU 数据重建。第 2 代的 GeometryManager 什么都没有；第一次画 Mary 时 get 重新建 4 个 buffer，数据来自 CPU 的 Geometry：VertexAttribute 一直存着自己的那份数组（第 10 课），所以不用重新下载 OBJ 和 PRT 文件。新的 OES 顶点输入在第一次 bind 时重录 VAO。新的 Manual 因为 initialized 是 false，第一次 bind 会把 0～15 全关一遍：4.2 节「接手之前别人开着的行」那条规则，在恢复以后又用上了一次。

5. 架构视角：对照 three.js r177

  • VAO 的 key：三层。three.js 的 WebGLBindingStates 按 geometry.id → program.id → wireframe 缓存（WebGLBindingStates.js:70–100）。多出来的 wireframe 一层，是因为线框模式要换一份索引（每条边两个编号）。前两层和本项目相同，理由也相同：location 跟着 program 走。
  • 上传不还绑定，靠的是顺序。three.js 的 createBuffer 绑上就传，不查也不还（WebGLAttributes.js:5–14）。它不怕弄乱 EBO，是因为 setup 先绑好这个物体自己的 VAO，再上传它的索引（WebGLBindingStates.js:13–35）：就算改了当前 VAO 的 EBO，改的也正是要用它的那个 VAO。本项目的 GeometryManager 不知道顶点输入的存在，上传时绑着的可能是任何 VAO，所以只能先记下、再还回。这是「谁依赖谁」换来的代价。
  • 什么时候重建。three.js 每次 setup 都比较「这个 VAO 当初接的属性对象、数据对象、索引」和现在的是否相同（needsUpdate，:137–180），不同就重新接线；本项目只比一个 gpuGeometry 引用，因为 Geometry 是不可变的快照（第 10 课），只有重新上传才会变。three.js 的属性可以改（needsUpdate、version），所以要比得更细。
  • 关掉用不到的 location。three.js 的 disableUnusedAttributes（:271–287）和 Manual 版的「这次不用就关」是同一件事；r163 起 three.js 不再支持 WebGL1，VAO 总是有；它在一个 VAO 需要重新接线时（比如几何体增删了属性）用这一步关掉不再用的 location。
