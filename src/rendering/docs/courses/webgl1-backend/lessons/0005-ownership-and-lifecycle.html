架构决策二：谁拥有，谁借用，谁负责释放

上一课讲的是 GPU 表示归谁（每个 context 的 Manager）。这一课往上走一层：CPU 资源本身归谁？一个 Geometry 被两个 Mesh、两个 Scene 共用时，该由谁、在什么时候释放它？读完你应该能区分「挂在树上」「借用」「拥有」三种关系，说出 Resource 的三个释放出口各用在什么场合，并能解释 Scene 账本里三处顺序各自挡住了什么反例。

和你的目标的关系 —— 第 4 课的 Manager 何时删除 GPU 对象，取决于这一课的 CPU 资源何时释放。HW2 切换预设时新旧两个 Scene 怎样交接资源，靠的也是这一课的机制；写 Task 15 和审查 HW2 的场景工厂时都会用到。

1. 设计问题：共享的资源该由谁释放？

一个具体场景：HW2 切换预设时，Engine.setScene()「先完成新 scene/camera 的原子替换，再 dispose 旧 Scene」（HW2 设计 §26）。假设新旧两个 Scene 共用同一个背景立方体 Geometry 和同一个 cubemap。四种分配释放责任的方案：

方案谁负责释放在这个场景里会怎样
Mesh 拥有资源每个 Mesh 释放自己的 Geometry两个 Mesh 共用一个 Geometry，先走的那个把另一个的也释放了。Mesh 还能摘下再挂回去，摘下时根本不知道该不该释放。
Scene 独占（设计文档最初的 own()）Scene.dispose() 直接 dispose 它登记过的每个资源（§9.3 末尾的修订说明）旧 Scene 一 dispose，就把新 Scene 正在用的背景和 cubemap 一起释放了。
不管（three.js 的做法）应用自己记账，手动 dispose能做对，但每一个共享点都要自己数。忘了就泄漏，数错就提前释放。
Scene 级引用计数（本项目）每个 Scene 对一个资源最多贡献一份引用；最后一份交还时自动释放旧 Scene 交还后，还剩新 Scene 那一份，资源继续活着。新 Scene 将来释放时，它才真正被释放。

设计文档最初写的是第二种，实现改成了第四种（设计文档已在 2026-09-24 按实现修订；第 8.2 节讲这次改动当时留下的旧说法）。

2. 三种关系要分开：挂在树上、借用、拥有

关系API谁对谁影响资源寿命吗
挂在树上scene.add(mesh)、mesh.removeFromParent()Scene → 节点不影响。节点可以摘下来再挂回去。
借用new Mesh(geometry, material)；Material 的 shaderModule 与纹理参数；RenderItemMesh → Geometry、Material；Material → ShaderModule、纹理不影响。借用方在使用时检查对方是否已经释放。
拥有scene.retain(r)、scene.release(r)、scene.dispose()Scene → 资源影响。引用数归零，资源自动释放。

Mesh 的类注释把前两种分得很清楚：「Scene.add(mesh) 只登记父子关系；资源存活由 Scene.retain(resource) 单独登记」（Mesh.ts:13）。所以正确的建场景写法是：每创建一个资源就立刻 retain，再把节点挂上树。retain 原样返回传入的资源，正好可以写成一行（Scene.ts:72–75 的示例）： 

const scene = new Scene()
const shader = scene.retain(new ShaderModule({ … }))
const material = scene.retain(new Material({ shaderModule: shader }))   // Material 借用 shader，但 shader 也要 retain
const geometry = scene.retain(new Geometry({ … }))
scene.add(new Mesh(geometry, material), new Mesh(geometry, material))   // 两个 Mesh 借用同一份资源

还有两种所有权不经过 Scene：RenderTarget 归创建它的 Pass 或功能模块，由它直接 dispose（HW2 设计 §6 核心规则）；GPU 对象归每个 context 的 Manager（第 4 课）。

3. 精读 ①：Resource 的计数与三个释放出口

// src/rendering/core/Resource.ts:124-190（节选，行尾注释是我加的）
retainSceneReference(): void {
  this.assertUsable()                       // ① 已释放的资源不能复活
  this.sceneReferenceCountValue += 1
}
releaseSceneReference(): void {
  if (this.sceneReferenceCountValue === 0)  // ② 先验证，再修改：不能先减成 -1 再补救
    throw new ResourceSceneReferenceUnderflowError(this.resourceType)
  this.sceneReferenceCountValue -= 1
  if (this.sceneReferenceCountValue === 0) this.finalizeDisposal()   // ③ 最后一份交还：自动真正释放
}
tryDispose(): boolean {
  if (this.disposedValue) return true
  if (this.sceneReferenceCountValue > 0) return false   // ④ 还有人持有：返回 false，什么都不改
  this.finalizeDisposal()
  return true
}
dispose(): void {
  if (this.disposedValue) return
  if (this.sceneReferenceCountValue > 0) {              // ⑤ 还有人持有：抛错，什么都不改
    throw new ResourceHasSceneReferencesError(this.resourceType, this.sceneReferenceCountValue)
  }
  this.finalizeDisposal()
}

计的是 Scene 的个数，不是 JavaScript 引用数，也不统计 Mesh 或 context（Resource.ts:31–38）。不数 Mesh，是因为 Mesh 会摘下又挂回，按它来数，资源会在节点暂时摘下时被误释放；不数 JavaScript 引用，是因为根本数不到（JS 没有析构函数，垃圾回收的时机也不可预测）。

三个出口，各用在一种场合：

出口什么时候用还有 Scene 持有时
scene.release(r) / scene.dispose()正常路径：所有者交还自己那一份，最后一份交还时自动清理只减一份，资源继续活着
r.tryDispose()「没人用了就释放」：资源可能仍被共享，这是正常分支返回 false，状态不变
r.dispose()断言「我确定没人持有它」。断言错了就是 bug，要大声失败，不能悄悄弄坏另一个 Scene抛 ResourceHasSceneReferencesError，状态不变

错误类的注释写明了这条分工：对于「资源可能仍在使用」的正常分支，应该调用 tryDispose()，「而不是依赖异常控制流程」（RenderingError.ts:58–65）。②④⑤ 有同一个模式：先验证，验证失败就什么都不改——测试逐一守着这一点（Resource.test.ts:149、:166、:215）。

4. 精读 ②：Scene 的账本，三处顺序

Scene 有两项职责：作为 Group 保存节点树，以及为每个 retain 过的资源持有一份引用（Scene.ts:11–14）。账本是一个 Set<Resource>（:38），同一个 Scene 对同一个资源最多记一次。难点全在顺序上：

// src/rendering/scene/Scene.ts:77-86、102-110、131-143（行尾注释是我加的）
retain<T extends Resource>(resource: T): T {
  if (this.disposedValue) throw new ResourceDisposedError('Scene')
  if (this.retainedResources.has(resource)) return resource   // 已记过：不重复加引用
  resource.retainSceneReference()                             // ① 先让资源同意（已释放的会在这里抛错）
  this.retainedResources.add(resource)                        //    再记账
  return resource
}
release(resource: Resource): boolean {
  if (this.disposedValue) return false                        // ③ 释放期间不接受单独的 release
  if (!this.retainedResources.delete(resource)) return false  // ② 先销账
  resource.releaseSceneReference()                            //    再交还（可能触发同步的监听器）
  return true
}
dispose(): void {
  if (this.disposedValue) return
  this.disposedValue = true                                   // ③ 先标记
  this.removeAllChildren()                                    //    断开整棵树
  for (const resource of this.retainedResources) {
    resource.releaseSceneReference()                          //    逐个交还，不是 dispose
  }
  this.retainedResources.clear()
}
  1. retain：先让资源同意，再记账。资源已经释放时，retainSceneReference 会抛错；这时 Set 里还什么都没记，账本不会留下一条假记录（:69–70）。
  2. release：先销账，再交还。交还最后一份引用会同步触发监听器。如果某个监听器又回过头来调用 scene.release(同一个资源)——这叫重入 (re-entrancy)——它会发现账已经销了，直接返回 false，不会把引用数减成负数（测试 Scene.test.ts:331）。通用规则：先改好自己的账，再通知别人。
  3. dispose：先标记，而且标记之后 release 一律返回 false。标记在前，监听器里看到的 scene.disposed 已经是 true，这时再想 retain 新资源会被拒绝（:208）。release 返回 false，是防止一个资源的监听器把另一个资源从这一轮里「截走」：那个资源会留下一份永远不会被交还的引用（:242）。

注意 dispose 里调用的是 releaseSceneReference()，不是 resource.dispose()：「如果其他 Scene 仍持有同一 Resource，引用数只会减少」（:125–126）。这正是第 1 节里新旧 Scene 能安全交接的原因。

5. 精读 ③：借用方不拥有，但在使用时检查

借用方不 retain，也不订阅释放事件。它们在每次使用时检查对方是否还活着：

  • Mesh：构造时拒绝已释放的依赖（Mesh.ts:40–41）；每次读 geometry、material 都再检查一次（:56–59、:66–69），因为「构造完成后外部仍可能释放依赖」（mesh-and-camera.zh-CN.md:19）。
  • Material：构造时检查 shader，读取纹理参数时检查纹理（cubemap 见 materialParameters.ts:118–129 的 requireCubeTexture，二维纹理和附件见 Texture2DSamplingSource.ts:53；10 月 10 日起，两处都调用资源自己的 assertUsable()，原来的 requireAlive 已删）；「替换纹理参数不负责释放旧纹理，也不负责登记新纹理的 Scene 引用」（Material.ts:340）；Material 自己释放时，只断开引用（:351–357）。
  • 参数块（10 月 19 日新增）：借用链多了一环。Material 借用 ParameterBlock，块再借用纹理或 RenderTarget 附件，两层都不 retain、不级联释放（ParameterBlock.ts:132–141），都在用的时候查：Material 每次读 blocks 都查每个块还活着（Material.ts:286–290），块读到纹理项时查那张纹理还活着（ParameterBlock.ts:80–91）。所以建场景时，块和它借的阴影图也要各自 retain（第 45 课）。

为什么借用方不订阅释放事件？它们没有东西要删：Mesh 和 Material 手里只有一个引用，发现对方死了，报错就够了。订阅反而有害：Mesh 远比资源多，每个 Mesh 挂一个监听器，Mesh 被丢弃时又没有 dispose 可以退订，监听器就会一直堆在资源身上。只有 Manager 订阅，因为它手里有必须及时删除的 GPU 副本（第 4 课）。

代价是：用了已经释放的资源，要到下一次使用才会发现，但那时一定会明确地抛出 ResourceDisposedError，而不是变成 GL 错误或者悄悄画错（卡片 E）。对建场景的人来说，规则只有一条：「Scene 必须分别 retain 每个实际需要的资源」（Material.ts:172）。漏掉一个会怎样，见卡片 F。

8. 架构视角

8.1 对照 three.js：它的 dispose 释放的是 GPU 副本

  • CPU 侧没有所有权模型。three.js 的 Object3D 和 Scene 都没有 dispose；scene.remove(mesh) 不释放任何东西；geometry.dispose() 只是派发一个 'dispose' 事件（BufferGeometry.js:1438–1442），Material、Texture 也一样（Material.js:974、Texture.js:635）。共享多少、什么时候释放，都由应用自己记。
  • dispose 的含义不同。three.js 的 dispose 释放的是 GPU 副本，CPU 对象仍然有效：渲染器删掉自己的记录（WebGLGeometries.js:27），下次再画它时重新登记、重新上传（:52–58；纹理见 WebGLTextures.js:363 与 :666–670）。本项目的 dispose 结束的是逻辑资源本身：CPU 数据被丢掉，之后再用就抛 ResourceDisposedError。
  • three.js 也有引用计数，但在 GPU 侧。多个材质共用一个 program（WebGLPrograms.js:591 的 usedTimes）、多个 Texture 共用同一份图像源时共用一个 GPU 纹理（WebGLTextures.js:700–723），都靠计数决定何时删除。本项目的计数在 CPU 侧、按 Scene 计；它的 GPU 侧是「一个 CPU 对象在每个 context 里一份表示」，没有跨对象共享，也就不需要 GPU 侧的计数。

取舍：three.js 的模型对不跨场景共享的应用更省心，「dispose 之后还能再用」也很宽容；代价是共享要应用自己数，而且用了已经 dispose 的对象不会报错，只会悄悄地重新上传一次。本项目要多学几个概念（retain、release、tryDispose 与 dispose），换来的是所有权只有一个答案，出错时大声失败。

8.2 审查视角：设计改了，旧说法还留着

设计文档原来的方案是 Scene 独占：Scene.own() 登记，Scene.dispose() 直接 dispose 每个资源（§9.3）；所有权矩阵（§6）里也写着「Scene.own() 登记」。实现改成了引用计数，Resource.dispose() 也从「总是释放」变成了「还有人持有就抛错」。备课时有两处没跟着改：

  • Group.ts:12–13 的注释写着「资源的显式所有权由 Scene.own() 管理」——Scene 已经没有 own() 了。
  • HW2 设计文档的 §6、§9.3，以及 §27.3 的时间线（原来写的是「Scene.dispose Geometry」），都还是独占模型。

照着旧文档写代码的人，会以为 Scene.dispose() 一定会释放资源，或者在另一个 Scene 还持有时直接调用 resource.dispose()（现在会抛错）。想一想（不用写代码）：Group.ts 这句注释你会怎样改？设计文档除了改成新 API，要不要再记下为什么把 own 换成了引用计数？记下改动的理由，正是架构决策记录 (Architecture Decision Record, ADR) 的用处。

2026-09-25 更新：这两处都已按实现改好。设计文档在 2026-09-24 修订了 §6、§9.3、§27.3 等节，并在 9.3 节末尾记下了为什么把 own 换成引用计数；Group.ts:13 和实施计划在 2026-09-25 同步。可以拿它们对照你对上面两个问题的答案：注释改成了什么？9.3 节末尾那段说明算不算一条 ADR？对照 ADR 常见的几个部分（背景、决策、后果、状态），它写了哪些、缺了哪些？
