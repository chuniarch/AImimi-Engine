帧编排：从 Scene 到一次次 draw——RenderListBuilder、RenderPipeline、ForwardPass 与 Renderer

前面二十多课讲的都在「一次 draw 之下」：资源怎样上传、状态怎样缓存、FBO 怎样建。可 Backend 每帧收到的那几次 draw 是从哪来的？HW2 的画面每帧只有两次 draw：先画背景盒，再画 Mary。这两次调用之上有四个类、约 670 行代码：RenderListBuilder 把会变的场景树抄成这一帧的值，RenderPipeline 按顺序执行各个 Pass，ForwardPass 说明画到哪里、先画谁，Renderer 把它们串起来并管释放顺序。这一课从 Engine 交来的原始输入出发，先写一个「边遍历边画」的第 1 版，看它错在哪里，再一版一版推到真实代码。

和你的目标的关系 —— HW1 的阴影要两个 Pass（先画阴影贴图，再正常画），HW3 要 GBuffer Pass，FFT 海面要好几个计算 Pass。它们都是往 RenderPipeline 里加 Pass，拿到的不是 Scene，而是这一课讲的 RenderPassContext。第 19 课重写时也从这一课接着讲。
默认你已经会的：① 第 6 课：RenderBackend 只收「意图」，withRenderSurface 开一个作用域（入口清屏、退出恢复），draw 只能在作用域里提交 { item, view }；② 第 8、9 课：copyWorldMatrixTo 先更新自己和祖先再复制，traverseVisible 遇到 visible = false 跳过整个子树，Mesh 的 geometry、material getter 每次先检查资源有没有释放；③ 第 25 课：视图矩阵 V = C⁻¹（C 是相机的世界矩阵），RenderListBuilder.ts:54–95 那一段你读过；④ 第 11 课：Material.queue 只有 'background' 和 'opaque'；⑤ 第 13 课：backend.ready 回答「现在能不能画」。如果其中哪一条其实没懂，告诉我，我先补那一块。第 19 课不是前置。
这一课从零讲的：Engine 每帧交来的三样东西；Backend 要的两种值（RenderItem、ViewState）；第 1 版、第 2 版各错在哪里；RenderListBuilder 的五步、copyMat4Snapshot、RenderList 为什么再复制一次、哪些复制哪些借用；RenderPass 接口为什么返回 undefined；ForwardPass 做什么、不做什么；RenderPipeline 的所有权和三个状态；Renderer 的 render 与 dispose 顺序；和 Lifecycle 的关系。

1. 原始输入

1.1 Engine 每帧交来什么

浏览器每次刷新屏幕前调用一次 requestAnimationFrame 的回调（rAF），Engine 在这个回调里推进一帧（engine.ts:505–525，工作区版本）：

// engine.ts:505–525（节选，注释是课程加的；工作区版本，未提交）
private readonly loop = (): void => {
  // …
    const oldFrame = this.frameClock.tick() // 旧引擎的计时器：帧号、累计时间、步长
    if (this.session !== null) {            // HW2 走新链路
      if (!this.hw2Closing) {
        // 抄出六个数，冻结
        const frame: FrameSnapshot = Object.freeze({
          frameNumber: oldFrame.frame,
          timeSeconds: oldFrame.elapsedTime,
          deltaSeconds: oldFrame.deltaTime,
          drawingBufferWidth: this.gl.drawingBufferWidth,
          drawingBufferHeight: this.gl.drawingBufferHeight,
          pixelRatio: this.appliedPixelRatio
        })
        this.update(frame) // HW2 是静态场景，现在什么都不做
        this.render(frame) // → :300 renderer.render({ ...binding, frame })
      }
    }
  // …
}

binding 是当前装进 Engine 的那一对 { scene, camera }。所以 Renderer 每帧收到一个 RenderView（RenderView.ts:6–10），里面三样东西：

字段是什么举例（CSS 尺寸 800 × 450 的画布，第 10 秒）
scene整棵场景树，会变：轨道控制每次拖动都改相机（第 26 课）见 1.2 节
camera树里的一个节点，也会变位置 (0, 20, 50)
frame六个数（FrameSnapshot.ts:5–21）：帧号、累计秒数、这一帧的秒数、drawing buffer 的像素宽高、像素倍率600、10、0.0167、1600、900、2

HW2 现在用不到 frame 里的任何一个数（没有动画），但 Renderer 照样复制它往下传：FFT 海面要 timeSeconds，后处理要 drawing buffer 的尺寸。

1.3 Backend 要什么

第 6 课读过 RenderBackend：一次 draw 只收两样值（RenderBackend.ts:6–9）。把它们的字段摊开：

// RenderBackend.ts:6–9、RenderItem.ts:15–20、ViewState.ts:13–20
//（三处合在一起，注释是课程加的）
interface DrawSubmission {
  readonly item: RenderItem // 画什么
  readonly view: ViewState  // 从哪里看
}
interface RenderItem {
  readonly geometry: Geometry     // 借来的资源（同一个对象）
  readonly material: Material     // 借来的资源（同一个对象）
  readonly worldMatrix: Mat4Tuple // local → world，16 个数，列主序
}
interface ViewState {
  readonly viewMatrix: Mat4Tuple          // world → view，V = C⁻¹
  readonly projectionMatrix: Mat4Tuple    // view → clip，P
  readonly cameraWorldPosition: Vec3Tuple // 相机在世界里的位置
}

Backend 拿到以后，Uniforms 按 ShaderModule 的 builtInUniforms 把它们对到 shader 的变量上（WebGL1Uniforms.ts:273–290）：modelMatrix ← item.worldMatrix，viewMatrix ← view.viewMatrix，projectionMatrix ← view.projectionMatrix，cameraPosition ← view.cameraWorldPosition。HW2 的 shader 里就是 uModelMatrix、uViewMatrix、uProjectionMatrix（第 11 课）。

注意 Backend 收不到 Scene，也收不到 Camera：它只认值（第 6 课「DrawSubmission 是值快照」）。Mat4Tuple 的注释写着「它只是数值，不是对任何矩阵存储（例如 Float32Array）的引用」（tuples.ts:22）。

2. 需求

五件事听起来一个函数就能做完。难的是下面这些要求，每一条都来自一个具体场景（实施计划的 Task 16–18 写了验收条件，实施计划 :764–797）：

#需求具体场景谁来管
①背景先画，不管它在树里排第几HW2 先加 Mary、后加背景；背景如果关掉深度测试（常见的天空写法），后画就会盖住 MaryMaterial.queue、ForwardPass
②一帧只读一次场景，几个 Pass 看到同一份HW1 阴影要两个 Pass，两个都要 Mary 的世界矩阵RenderListBuilder、Renderer
③交出去的是值：Pass 之间互不干扰，之后改场景也不影响已经交出去的一个 Pass 想按远近排自己的绘制顺序RenderList 的复制与冻结
④坏输入在第一个 draw 之前拒绝，不留半帧背景的 Geometry 被提前释放；相机缩放成 0RenderListBuilder 的检查
⑤Pass 有主人：谁加进来、谁释放、按什么顺序阴影 Pass 拥有自己的 RenderTarget，删 FBO 时 Backend 必须还活着RenderPipeline、Renderer.dispose
⑥context 丢了就跳过这一帧；render 里不能再 render第 13 课：丢失到恢复之间Renderer

3. 第 1 版：边遍历边画

3.1 旧引擎怎样画一帧

旧引擎的 WebGLRenderer 每帧清屏，然后把同一个活的相机交给每个 Pass：

// 旧引擎 src/renderers/WebGLRenderer.ts:198–217（节选，注释是课程加的）
render(context: FrameContext): void {
  this.withRenderTarget(null, () => { // null 表示画到屏幕
    const gl = this.gl
    gl.clearColor(0.0, 0.0, 0.0, 1.0)
    // …
    gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT)

    for (const pass of this.renderPasses) {
      // …
      pass.execute(context, this.camera, this) // 每个 Pass 拿到同一个活的相机
    }

    this.overlayRenderPass.execute(context, this.camera, this)
  })
}

ForwardRenderPass 自己存着「要画哪些 renderer」，逐个往共享的材质里写 uniform，然后 draw：

// 旧引擎 src/renderers/passes/forward/ForwardRenderPass.ts:56–89（节选）
execute(
  context: FrameContext,
  camera: PerspectiveCamera,
  _renderTargets: RenderTargetScope
): void {
  // …
  for (const meshRenderer of this.meshRenderers) { // Pass 自己的列表，不是场景树
    // …
    this.lightSystem?.applyPerFrameLightUniforms(meshRenderer)

    if ('uCameraPos' in meshRenderer.material.uniforms) {
      meshRenderer.updateMaterialUniforms({ // 往共享的材质里写
        uCameraPos: {
          type: UniformType.THREE_FV,
          value: camera.position.toArray()
        }
      })
    }
    // …
    meshRenderer.draw(context, camera)
  }
}

每个 draw 里，BaseRenderer 都重新读一次相机、求一次逆：

// 旧引擎 src/renderers/BaseRenderer.ts:166–179（节选）
protected bindCameraParameters(camera: PerspectiveCamera): void {
  // …
  const modelMatrix = this.mesh.getModelMatrix()

  // …
  const viewMatrix = mat4.create()
  camera.updateMatrix()                                // 每个 draw 都更新一次相机
  mat4.invert(viewMatrix, camera.matrixWorld.elements) // 每个 draw 都求一次逆

  // …
  const projectionMatrix = mat4.create()
  mat4.copy(projectionMatrix, camera.projectionMatrix.elements)
  // …
}

四个特点：「要画谁」存在每个 Pass 自己的列表里（阴影 Pass 另有 casters、receivers），没有一棵统一的树；绘制顺序就是登记顺序；相机每个 draw 现读现算；Pass 往共享的材质里写东西。

3.2 课程写的第 1 版

把旧引擎的思路搬到新接口上：Pass 拿着 scene 和 camera，自己遍历，遇到一个 Mesh 就交给 Backend。这段是课程写的，项目里没有（下面卡片跑的就是这份代码）：

// 课程写的第 1 版（assets/build/frame-course.ts）
const SCREEN: RenderSurfaceScopeDescriptor = {
  surface: { kind: 'default-framebuffer' },
  clear: { color: [0, 0, 0, 1], depth: 1 }
}

export function renderFrameV1(
  passes: readonly PassV1[],
  scene: Scene,
  camera: Camera,
  backend: RenderBackend
): void {
  for (const pass of passes) pass.execute(scene, camera, backend)
}

export class ForwardPassV1 implements PassV1 {
  execute(scene: Scene, camera: Camera, backend: RenderBackend): void {
    backend.withRenderSurface(SCREEN, () => {
      // 先清屏（scope 入口），再按树的顺序遍历
      scene.traverseVisible((node) => {
        if (!(node instanceof Mesh)) return

        // 每画一个 Mesh 都重读一次相机、求一次逆
        const cameraWorld = mat4.create()
        camera.copyWorldMatrixTo(cameraWorld)
        const view = mat4.create()
        mat4.invert(view, cameraWorld)
        const projection = mat4.create()
        camera.copyProjectionMatrixTo(projection)

        const world = mat4.create()
        node.copyWorldMatrixTo(world)

        // node.geometry 是 getter，资源已释放时在这里抛错；
        // 这时前面的 Mesh 已经画了
        backend.draw({
          item: {
            geometry: node.geometry,
            material: node.material,
            worldMatrix: toTuple(world)
          },
          view: {
            viewMatrix: toTuple(view),
            projectionMatrix: toTuple(projection),
            cameraWorldPosition: [cameraWorld[12]!, cameraWorld[13]!, cameraWorld[14]!]
          }
        })
      })
      return undefined
    })
  }
}

toTuple 也是课程写的：把 mat4 的 16 个数抄进普通数组，不检查、不冻结。下面两张卡片用一个和 HW2 形状相同的场景（Mary、背景、相机），Backend 换成只记录调用的替身。

3.3 第 1 版错在哪

需求第 1 版原因
① 背景先画✗ 先画 Mary遇到一个画一个，没有机会看 queue；要按 queue 排，就得先把 Mesh 收齐
② 只读一次✗ 每个 Pass 遍历一次，每个 draw 读一次相机实测：一个 Pass 读相机 2 次，两个 Pass 读 4 次（HW2 有两个 Mesh）
③ 交出去的是值✗ Pass 手里是活的 scene、camera哪个 Pass 改了相机，后面的 Pass 就看到改过的
④ 不留半帧✗ 清屏、画完 Mary 以后才发现背景坏了检查（getter）和绘制交错进行

四个问题的根源是同一个：读场景和发命令混在一起。把它们拆成两步，就是第 2 版。

4. 第 2 版：先提取，再画

4.1 代码

// 课程写的第 2 版（assets/build/frame-course.ts）
export interface FrameV2 {
  readonly view: ViewState
  readonly background: RenderItem[]
  readonly opaque: RenderItem[]
}

/** 读一遍场景，相机只算一次，按 material.queue 分成两队。 */
export function buildFrameV2(scene: Scene, camera: Camera): FrameV2 {
  const cameraWorld = mat4.create()
  camera.copyWorldMatrixTo(cameraWorld)
  const view = mat4.create()     // create() 给的是单位矩阵
  mat4.invert(view, cameraWorld) // 不可逆时返回 null，view 原样不动
  const projection = mat4.create()
  camera.copyProjectionMatrixTo(projection)

  const frame: FrameV2 = {
    view: {
      viewMatrix: toTuple(view),
      projectionMatrix: toTuple(projection),
      cameraWorldPosition: [cameraWorld[12]!, cameraWorld[13]!, cameraWorld[14]!]
    },
    background: [],
    opaque: []
  }

  scene.traverseVisible((node) => {
    if (!(node instanceof Mesh)) return
    const world = mat4.create()
    node.copyWorldMatrixTo(world)
    // 资源已释放时 getter 在这里抛错：还没开始画，不会留下半帧
    const item: RenderItem = {
      geometry: node.geometry,
      material: node.material,
      worldMatrix: toTuple(world)
    }
    if (item.material.queue === 'background') frame.background.push(item)
    else frame.opaque.push(item)
  })

  return frame
}

/** 第 2 版的 ForwardPass：先 background，再 opaque。 */
export class ForwardPassV2 implements PassV2 {
  execute(frame: FrameV2, backend: RenderBackend): void {
    backend.withRenderSurface(SCREEN, () => {
      for (const item of frame.background) backend.draw({ item, view: frame.view })
      for (const item of frame.opaque) backend.draw({ item, view: frame.view })
      return undefined
    })
  }
}

/** 提取一次，所有 Pass 共用同一份结果。 */
export function renderFrameV2(
  passes: readonly PassV2[],
  scene: Scene,
  camera: Camera,
  backend: RenderBackend
): void {
  const frame = buildFrameV2(scene, camera)
  for (const pass of passes) pass.execute(frame, backend)
}

第 1 版的四个问题，第 2 版解决了三个半：背景先画了；两个 Pass 时相机只读 1 次（实测）；背景坏了在提取时就抛错，Backend 一次调用都没收到（实测）；Pass 拿不到 scene、camera 了。剩下的半个是③：Pass 拿到的数组和矩阵还是可以改的。下面两张卡片看第 2 版还会出什么事。第二张卡片里的「小球」是另加的一个 opaque Mesh，放在 (0, 0, 30)，离相机 28.3；Mary 在原点，离相机 53.9。

5. 真实代码 ①：提取

5.1 RenderListBuilder.build 的五步

第 25 课读过相机那一段，这里把整个函数读完。源码里每一步都有很长的注释，下面换成了短的：

// RenderListBuilder.ts:42–125（注释是课程加的）
build(view: RenderView): RenderListBuildResult {
  // 0. 入口检查：类型对不对、Scene 释放了没有
  if (view === null || typeof view !== 'object')
    throw new InvalidRenderViewError('view', 'must be an object')

  const { scene, camera } = view

  if (!(scene instanceof Scene))
    throw new InvalidRenderViewError('scene', 'must be a Scene')

  if (!(camera instanceof Camera))
    throw new InvalidRenderViewError('camera', 'must be a Camera')

  if (scene.disposed) throw new ResourceDisposedError('Scene')

  // 三块临时缓冲，每次 build 新建，不会交出去
  const cameraWorld = new Float32Array(16)
  const viewMatrix = new Float32Array(16)
  const projection = new Float32Array(16)

  // 1. 相机：先更新相机和它的祖先，再复制世界矩阵 C
  camera.copyWorldMatrixTo(cameraWorld)

  // 验证 16 个分量都是有限数，得到冻结的普通数组
  const world = copyMat4Snapshot(cameraWorld, 'camera.worldMatrix')

  // V = C⁻¹；不可逆（比如缩放为 0）就拒绝，不用单位矩阵顶替
  if (mat4.invert(viewMatrix, world) === null)
    throw new InvalidRenderViewError('camera.worldMatrix', 'must be invertible')

  camera.copyProjectionMatrixTo(projection)

  // 相机位置就是 C 的平移列（第 25 课）
  const position: Vec3Tuple = Object.freeze([world[12], world[13], world[14]])

  const viewState: ViewState = Object.freeze({
    viewMatrix: copyMat4Snapshot(viewMatrix, 'camera.viewMatrix'),
    projectionMatrix: copyMat4Snapshot(projection, 'camera.projectionMatrix'),
    cameraWorldPosition: position
  })

  // 2. 更新根节点（只更新它自己；后代在第 3 步按需更新）
  scene.updateWorldMatrix()

  const background: RenderItem[] = []
  const opaque: RenderItem[] = []
  const scratch = new Float32Array(16) // 所有 Mesh 共用的临时缓冲

  // 3. 可见遍历：visible = false 的节点连同整个子树跳过
  scene.traverseVisible((node) => {
    if (!(node instanceof Mesh)) return

    // 先按需更新这个 Mesh 和它的祖先，再复制进 scratch
    node.copyWorldMatrixTo(scratch)

    const renderItem: RenderItem = {
      geometry: node.geometry, // getter：资源释放了就在这里抛错
      material: node.material,
      // 从 scratch 抄出一份自己的、冻结的（scratch 下一个 Mesh 还要用）
      worldMatrix: copyMat4Snapshot(scratch, 'mesh.worldMatrix')
    }

    // 4. 分类：只看 queue，保持树里的先后
    if (renderItem.material.queue === 'background') {
      background.push(renderItem)
    } else {
      opaque.push(renderItem)
    }
  })

  // 5. 冻结：RenderList 构造时再复制、冻结一遍
  return Object.freeze({
    viewState,
    renderList: new RenderList(background, opaque)
  })
}
步做什么为什么在这个位置
0查 view、scene、camera 的类型，scene 没有释放RenderView 来自 Engine，类型只是约定；最便宜的检查放最前
1相机：C → 验证 → V → P → 位置，冻结成 ViewState相机坏了（不可逆、NaN）就不用再遍历；所有 Mesh 共用这一份
2更新根节点计划里的「每次 build 更新一次 Scene」；实际效果见第 12 节
3可见遍历，复制每个 Mesh 的世界矩阵copyWorldMatrixTo 只更新这个 Mesh 和它的祖先；共享的祖先靠 worldVersion 缓存，每次变化只重算一次（测试 RenderListBuilder.test.ts:157）
4按 queue 分两队同一队里保持树的顺序，不排序（计划不做 renderOrder、透明）
5RenderList 冻结5.3 节

和第 9 课第 4 节那段「示意」比一下：示意里写的是 scene.traverse((node) => node.updateWorldMatrix())，先把整棵树更新一遍，再遍历一遍。真实代码只更新根节点，更新后代的事交给第 3 步里每个 Mesh 的 copyWorldMatrixTo，这样整棵树只走一遍。相机不在 Mesh 里，所以第 1 步单独处理它。

5.2 copyMat4Snapshot：验证、复制、冻结

// copyMat4Snapshot.ts:11–41（注释是课程加的）
export function copyMat4Snapshot(source: ArrayLike<number>, fieldName: string): Mat4Tuple {
  // 长度必须正好 16
  if (source === null || typeof source !== 'object' || source.length !== 16)
    throw new InvalidRenderViewError(fieldName, 'must contain exactly 16 components')

  // 每个分量都要是有限数：NaN、Infinity 都拒绝，错误里写出是第几个
  for (let i = 0; i < 16; i++) {
    if (!Number.isFinite(source[i]))
      throw new InvalidRenderViewError(fieldName, 'component ' + i + ' must be finite')
  }

  // 抄进一个普通数组，不是 Float32Array（不泄露可变的类型化数组）
  const result: Mat4Tuple = [
    source[0]!,
    source[1]!,
    // … 一直写到 source[15]!，固定长度让 TypeScript 知道恰好 16 项
    source[15]!
  ]

  return Object.freeze(result)
}

一帧里 Builder 调用它 3 + N 次（N 是可见 Mesh 数）：相机的世界矩阵、V、P，各个 Mesh 的世界矩阵；RenderList 再调用 N 次（5.3 节）。fieldName 只用来写错误信息，比如 mesh.worldMatrix: component 12 must be finite，一看就知道是哪个矩阵的平移出了 NaN。

为什么复制成普通数组而不是 Float32Array？Object.freeze 冻不住类型化数组的元素（对有元素的 Float32Array 调用 freeze 会抛 TypeError），而 Mat4Tuple 约定「只是数值」。代价是数值从 Float32 变成了 Float64 表示的同一个值，不损失精度。

5.3 RenderList：再复制一次

// RenderList.ts:5–33（注释是课程加的）
function snapshotItem(item: RenderItem): RenderItem {
  return Object.freeze({
    geometry: item.geometry, // 同一个对象：借用
    material: item.material, // 同一个对象：借用
    worldMatrix: copyMat4Snapshot(item.worldMatrix, 'item.worldMatrix') // 再验证、复制一次
  })
}

export class RenderList {
  public readonly background: readonly RenderItem[]
  public readonly opaque: readonly RenderItem[]

  constructor(backgroundList: RenderItem[], opaque: RenderItem[]) {
    // map 生成新数组：调用者之后再 push 进原数组，不影响这里
    this.background = Object.freeze(backgroundList.map(snapshotItem))
    this.opaque = Object.freeze(opaque.map(snapshotItem))

    Object.freeze(this) // 连字段也不能换
  }
}

Builder 已经复制、冻结过矩阵，RenderList 为什么还要再复制一次？因为 RenderList 的构造函数是公开的：谁都能 new RenderList(...)，传进来的数组和矩阵可能还在别人手里。RenderList 不知道调用者是不是 Builder，只能自己保证。代价是每个 Mesh 每帧复制两次矩阵（32 个数）；HW2 只有两个 Mesh，可以忽略。

5.4 什么复制，什么借用

东西怎么交出去为什么
世界矩阵、V、P、相机位置复制并冻结只有 16 个（或 3 个）数，复制便宜；它们每帧都可能变（轨道控制拖相机）
两条队列、每个 item 的外壳复制并冻结Pass 之间互不干扰
FrameSnapshotRenderer 复制六个数并冻结（8.1 节）调用者可能每帧改同一个对象
Geometry、Material借用：同一个对象它们大（顶点、纹理），而且对象身份就是 Manager 缓存的 key（第 4 课）。复制一份，Manager 每帧都会当成新资源重新上传
backend借用只有一个设备

所以 RenderItem 的注释专门写了一句：「readonly material 不会使 Material.setParameter 失效」（RenderItem.ts:12）。readonly 只说这个字段不能换成别的 Material，不说 Material 里面不能变。

6.1 RenderPass 接口

// RenderPass.ts:4–17（注释是课程加的）
export interface RenderPass {
  readonly name: string // 只用来诊断

  // 必须同步完成：返回类型是 undefined，不是 void
  execute(context: RenderPassContext): undefined

  // 只释放这个 Pass 自己持有的资源（比如它建的 RenderTarget）；
  // 必须幂等：调两次和调一次一样
  dispose(): void
}

undefined 和 void 差在哪？TypeScript 允许把「返回任何东西的函数」赋给返回 void 的函数类型，所以 async execute()（返回 Promise）能实现一个 void 的接口；返回类型写成 undefined 就不行。我用 strict 的 tsc 实测： 

// 课程写的类型实验（tsc --noEmit，项目的 tsconfig）
class AsyncPass implements RenderPass {
  readonly name = 'AsyncPass'
  async execute(_context: RenderPassContext): Promise<undefined> { return undefined }
  dispose(): void {}
}
// error TS2416: Property 'execute' in type 'AsyncPass' is not assignable
//   to the same property in base type 'RenderPass'.
//   Type 'Promise<undefined>' is not assignable to type 'undefined'.

interface VoidPass { execute(context: RenderPassContext): void }
class AsyncVoidPass implements VoidPass {
  async execute(_context: RenderPassContext): Promise<void> {} // 没有报错
}

为什么不许异步？Pass 会在 scope 里 draw（6.3 节），scope 必须同步地进、同步地出（第 6 课、第 27 课 4.1 节）：如果 execute 在中间 await，别的代码会在 FBO 还绑着的时候插进来，scope 的「退出时恢复」也会提前发生。withRenderSurface 的 callback 是同样的写法（RenderBackend.ts:37）。

6.3 ForwardPass

// ForwardPass.ts:15–49（注释是课程加的）
export class ForwardPass implements RenderPass {
  public readonly name: string = 'ForwardPass'

  execute(context: RenderPassContext): undefined {
    context.backend.withRenderSurface(
      {
        surface: { kind: 'default-framebuffer' }, // 画到屏幕
        clear: {                                  // scope 入口清一次
          color: [0, 0, 0, 1],
          depth: 1
        }
      },
      () => {
        // 先 background 队列
        for (const item of context.renderList.background) {
          context.backend.draw({
            item,
            view: context.view // 所有 draw 共用同一个 ViewState
          })
        }

        // 再 opaque 队列
        for (const item of context.renderList.opaque) {
          context.backend.draw({
            item,
            view: context.view
          })
        }

        return undefined
      }
    )
  }

  // 不持有自己的资源，所以什么都不用释放
  dispose(): void {}
}

它的注释列了四件「不做」的事（ForwardPass.ts:13）：不遍历 Scene、不计算矩阵、不创建资源、不捕获并吞掉 draw 错误。前三件交给了 Builder 和 Backend；第四件的意思是 draw 抛错时，ForwardPass 立刻停下，错误原样往上传（测试 ForwardPass.test.ts:77），scope 的 finally 负责恢复绑定。

7.1 第 1 版：一个数组

旧引擎的 WebGLRenderer 用一个数组存 Pass（WebGLRenderer.ts:45–59、:219–226）。照它的写法、换上新的 RenderPass 接口，课程写的第 1 版：

// 课程写的第 1 版 Pipeline（assets/build/frame-course.ts）
export class PipelineV1 {
  private passes: RenderPass[] = []

    this.passes.push(pass)
  }

7.2 真实代码

// RenderPipeline.ts:19–102（注释是课程加的）
export class RenderPipeline {
  private readonly passes: RenderPass[] = []

  // 收过的 Pass 都记在这里，移除以后也不删：
  // 拒绝重复加入，也拒绝加回已经释放的；WeakSet 不妨碍 GC
  private readonly accepted = new WeakSet<RenderPass>()

  // 生命周期：closing 表示「只能继续清理」
  private state: 'active' | 'closing' | 'disposed' = 'active'

  // 正在 execute 或 dispose：拒绝回调里的同步重入
  private busy: boolean = false

  addPass(pass: RenderPass): void {
    this.assertIdle('addPass')

    if (this.accepted.has(pass))
      throw new RenderExecutionError(
        'RenderPipeline',
        'addPass',
        'pass was already accepted'
      )

    this.accepted.add(pass)
    this.passes.push(pass) // 从此 Pipeline 是它的主人
  }

  removePass(pass: RenderPass): boolean {
    this.assertIdle('removePass')

    const index = this.passes.indexOf(pass)
    if (index === -1) return false

    this.busy = true

    try {
      pass.dispose()               // 先释放
      this.passes.splice(index, 1) // 成功了才移出
      return true
    } catch (error) {
      this.state = 'closing'       // 失败：它可能释放了一半，不能再执行
      throw error
    } finally {
      this.busy = false
    }
  }

  execute(context: RenderPassContext): undefined {
    this.assertIdle('execute')

    this.busy = true

    try {
      for (const pass of this.passes) {
        pass.execute(context) // 抛错就停，后面的 Pass 不执行，错误往上传
      }
    } finally {
      this.busy = false       // 下一帧还能执行
    }
  }
// RenderPipeline.ts:132–180（注释是课程加的）
  dispose(): void {
    if (this.state === 'disposed') return // 全部清理完了：幂等

    this.assertNotBusy('dispose') // closing 允许重试，但不许在清理回调里重入

    this.state = 'closing'
    this.busy = true

    try {
      while (this.passes.length > 0) {
        const pass = this.passes[0]!

        pass.dispose()      // 抛错时下一行不执行，失败的留在队首

        this.passes.shift() // 成功一个移出一个，进度就记在数组里
      }

      this.state = 'disposed' // 全部成功才算完
    } finally {
      this.busy = false
    }
  }

  // 公共入口统一检查：必须 active，而且不忙
  private assertIdle(operation: string): void {
    if (this.state !== 'active') throw new ResourceDisposedError('RenderPipeline')

    this.assertNotBusy(operation)
  }

  private assertNotBusy(operation: string): void {
    if (this.busy)
      throw new RenderExecutionError('RenderPipeline', operation, 'operation in progress')
  }

源码 :104–119 还有一段 TODO，记的是以后 Pass 多了要重新考虑的事：清理顺序该按依赖而不是登记顺序；反复 shift 是 O(n²)，可以换成游标；但不能为了性能直接换成 pop，那会改变清理顺序。现在 HW2 只有一个 ForwardPass，这些都还不是问题。

8.1 render

// Renderer.ts:16–80（节选，注释是课程加的）
export class Renderer {
  private readonly backend: RenderBackend
  private readonly pipeline: RenderPipeline
  private readonly renderListBuilder: RenderListBuilder

  // 和 RenderPipeline 同一套：生命周期 + 忙
  private state: 'active' | 'closing' | 'disposed' = 'active'
  private busy = false

  // …

  render(view: RenderView): void {
    if (this.state !== 'active') {
      throw new ResourceDisposedError('Renderer')
    }

    this.assertNotBusy('render') // 某个 Pass 在 execute 里又调 render：拒绝

    if (!this.backend.ready) return // context 丢了：这一帧什么都不做，连场景都不读

    this.busy = true

    try {
      const source = view.frame

      // 显式抄六个数：调用者之后改原对象，影响不到 Pass
      const frame: FrameSnapshot = Object.freeze({
        frameNumber: source.frameNumber,
        timeSeconds: source.timeSeconds,
        deltaSeconds: source.deltaSeconds,
        drawingBufferWidth: source.drawingBufferWidth,
        drawingBufferHeight: source.drawingBufferHeight,
        pixelRatio: source.pixelRatio
      })

      // 提取，整帧只有这一次
      const { renderList, viewState } = this.renderListBuilder.build(view)

      // 所有 Pass 共用同一个冻结的 context
      const context: RenderPassContext = Object.freeze({
        frame,
        view: viewState,
        renderList,
        backend: this.backend
      })

      this.pipeline.execute(context)
    } finally {
      this.busy = false // 出错也复位：修好以后下一帧照常
    }
  }

顺序有讲究：先问 ready，再提取。context 丢了的时候（第 13 课），提取了也白提取；而且「不读场景」意味着丢失期间场景里坏掉的东西（比如刚释放的 Geometry）不会在这里抛错。Renderer 不保存 Scene、Camera：view 只在这一次调用里用（测试 Renderer.test.ts:59「不保留上次 Scene」）。

复制 frame 防的是什么？Engine 现在每帧新建冻结对象（1.1 节），但 Renderer 不依赖这一点。我实测过：调用者每帧改同一个对象（帧号 600 改成 601），一个 Pass 把两帧的 context.frame 都存下来，读到的是 600 和 601，不会两个都变成 601。

8.2 dispose：先 Pipeline，后 Backend

// Renderer.ts:94–131（注释是课程加的）
dispose(): void {
  if (this.state === 'disposed') return

  this.assertNotBusy('dispose') // 不能在 render 里面拆掉自己

  this.state = 'closing'
  this.busy = true

  try {
    // 先释放 Pass。Pass 拥有的 RenderTarget 被 dispose 时，会通知 Backend 的
    // RenderTargetManager 删 FBO（第 27 课 3.6 节），所以 Backend 这时必须还活着
    this.pipeline.dispose()

    // Pipeline 清理成功才走到这里。不能放进 finally：
    // 否则 Pipeline 失败时也会拆掉它清理要用的 Backend
    this.backend.dispose()
    this.state = 'disposed'
  } finally {
    this.busy = false
  }
}

重试为什么安全？Pipeline 失败时 Renderer 停在 closing，下次 dispose 再从 pipeline.dispose() 开始，Pipeline 自己从失败的 Pass 接着做（7.2 节）。Backend 失败时 Pipeline 已经是 disposed，下次 pipeline.dispose() 直接返回，只重试 backend.dispose()。每一层都把「做到哪了」记在自己身上，上一层只要重新调用就行。

10. 和 Lifecycle 的关系

第 13 课讲过 WebGLContextLifecycle 回答「现在能不能画」。帧编排这一层只通过一个问题和它打交道：backend.ready（WebGL1Backend.ts:114–120：没有 dispose、context 没丢、Lifecycle 处于 ready、当前这一代有效）。

时刻帧编排这一层发生什么
丢失之后、恢复之前ready 是 false，Renderer.render 直接返回（Renderer.ts:51），不读场景、不调 Builder、不开 scope。画布上留着浏览器给的空白
render 正在进行时 context 丢了Backend.draw 的 assertCurrentDraw 抛 WebGLContextLostError（WebGL1Backend.ts:357–363）→ ForwardPass 不接 → Pipeline、Renderer 的 finally 复位 busy → Engine 的 loop 接住：context lost 不停循环（engine.ts:537–540），其他错误停循环
恢复之后ready 变回 true，下一帧照常提取。RenderList 里本来就没有 GPU handle（只有 Geometry、Material 的身份），所以不存在「旧列表里的旧 handle」；Backend 的新一代 Manager 按身份懒上传（第 13、16、17、27 课）
退出 HW2Engine 调 renderer.dispose()（engine.ts:241）：先 Pipeline，后 Backend；Backend 的 dispose 会停掉 Lifecycle 的监听

反过来，Lifecycle 不知道 Renderer、Pipeline 的存在：恢复时它只重建 Backend 里的一代 Manager。帧编排这一层每帧从头提取，所以什么都不用通知它。

问题three.js r177本项目

钩子onBeforeRender：每次 draw 前调用户代码，可以改 uniform、矩阵没有；Builder 的注释写明「本版不提供提取过程的用户钩子」
render 里再 render允许：保存、恢复当前的 render context（common/Renderer.js:1289、:1496），用来做镜面反射、传送门拒绝：busy 检查（8.1 节）。要画两遍就加两个 Pass
多个 Pass旧版没有 Pass，后处理在 examples 的 EffectComposer；新版有 PostProcessing（PostProcessing.js:20），用节点描述RenderPipeline 持有有序的 Pass，并负责释放

共同点是更重要的那一条：两边都在 draw 之前把场景「投影」成一张列表，Backend 只看列表，不看场景。区别在于 three.js 要服务所有人（成千上万个物体、每帧不能分配、用户要钩子），本项目只服务 HW2 到 FFT 这几个场景，所以选了「每帧新建、冻结、不给钩子」这种好推理的写法。哪天物体多到分配成为瓶颈，再学 three.js 复用 item；那时候「item 留不到下一帧」就要写进 RenderPassContext 的契约里。

12. 审查视角

12.1 三处可以改的地方

  1. Renderer 先读 view.frame，再让 Builder 检查 view。Renderer.ts:56 的 view.frame 在 build 之前，所以 renderer.render(null) 得到的是 TypeError: Cannot read properties of null (reading 'frame')，而不是 Builder :43 准备好的 InvalidRenderViewError（实测）；经过 Renderer 调用时，Builder 的这条检查永远走不到。frame 的六个数也没有验证：deltaSeconds: NaN 照样传给所有 Pass（实测）。FrameSnapshot 的注释说「由 Engine 提供合法值」，这是有意的分工，但 Renderer 是公开类，入口先检查 view 是对象、六个数是有限数，代价很小。
  2. closing 状态的报错说「已经释放」。Pipeline 清理失败以后是 closing，这时调用 execute 得到的是 ResourceDisposedError: RenderPipeline has been disposed（:164），可清理其实还没完成。Renderer（:46）同样如此。看错误的人会以为「已经释放干净了」，不会想到要重试 dispose。另外 addPass 的文档注释（:43）抄了 busy 字段的注释，没有说明 addPass 本身做什么。
  3. Builder 第 2 步实测不改变任何结果。相机是 Scene 的后代，第 1 步 copyWorldMatrixTo 已经顺带更新了根节点：Scene 的 worldVersion 在复制相机后从 0 变成 1，执行 :97 以后还是 1（实测）。就算相机不在树里，第 3 步第一个 Mesh 也会更新根节点。这一行不是错，但「更新根节点」容易让人以为它负责更新整棵树；真正保证「每个节点最多重算一次」的是 worldVersion 缓存。
