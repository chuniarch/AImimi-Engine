只做一次与每帧做：GPU 对象按描述对象查表

第 40 课的函数每调用一次，就把 program、阴影图、buffer 全部重建一遍。这一课切第一刀：把「只需要做一次的建造」和「每帧都要做的绘制」分开。先用最直接的办法（一个 setup、一个 drawFrame），再用两个需求把它逼成「用到时才建，按描述对象查表」——拆出来的三个小类，就是 backend/webgl1 里各个 Manager 的形状。

和你的目标的关系 —— HW1 的阴影图、HW2 的 Mary 模型、FFT 的十几张中间纹理，都是「建一次、用很多帧」。可是后端是通用代码，不知道你的场景里会有什么；它只能在第一次见到某样东西时把它建出来，以后再见到时认出它。这一课回答：怎样「认出来」。
默认你已经会的：① 第 40 课的七段代码（①–⑦）；② JavaScript 的 Map：可以拿任何值当 key，set(key, value) 存、get(key) 取，没有就返回 undefined。拿对象当 key 时它怎样比较，第 5 节当场演示。第 4、18、31 课从真实代码讲过这张表；这一课不读真实代码，而是从第 40 课的函数出发，看它为什么会长出来。
这一课讲的：第一版 setup 与 drawFrame；两个需求让第一版接不住；第二版：用到时才建、按描述对象查表；表的 key 为什么是对象本身；什么时候从表里删；顺手得到的名字核对；对照 src/rendering。
在一帧里的位置和寿命：Manager 在 draw 的时候被问「这个东西的 GPU 版本是什么」（上 GPU 的那一层）；它活一个 context 的一代，context 丢失就整套作废。
页面会用到你的显卡：四块 480 × 300 的画布。

1. 灯转的时候，什么不用重做

第 40 课最后一道检查题问过：灯转动时，哪几段不需要重新执行。把三种变化放在一起看：

第 40 课的段灯转了三角形换了形状context 丢失又恢复
① 场景数据（JS 里的数）不用重做三角形的顶点变了不用重做：数据在 JS 里，没丢
② 编译 program不用重做不用重做要重建：旧 program 作废
③ 建阴影图不用重做不用重做要重建
④ 上传顶点不用重做三角形的 buffer 要换要重建
⑤ 矩阵、⑥ 第一遍、⑦ 第二遍每帧都做

②③④ 是建造：把 JS 里的数据变成显卡上的对象。它们什么时候要重做，不由「过了一帧」决定，而由「数据变了没有」和「context 还是不是原来那个」决定。⑤⑥⑦ 是每帧的绘制。这一课只把这两类分开，其余（① 的数据怎样组织、⑥⑦ 的两遍怎样拆）留给后面几课。

2. 第一版：setup 和 drawFrame

最直接的办法：②③④ 搬进 setup，页面加载时调用一次，把建好的 GPU 对象装进一个对象交回来；⑤⑥⑦ 留在 drawFrame，每帧调用，只用 setup 交回来的东西。

setup 和 drawFrame 用到的五个小函数（从第 40 课原样搬出来）

建造代码一行没改，只是从大函数里拿出来，有了名字：makeProgram 是 ②，makeShadowMap 是 ③，makeBuffer 是 ④，frameMatrices 是 ⑤，drawPositions 是 ⑥⑦ 里反复出现的「绑 buffer、设指针、draw」。只多了两行：makeProgram 挂上 shader 后马上 deleteShader（program 删除时 shader 跟着删，不然第 6 节删 program 会留下 shader）；makeShadowMap 最后绑回屏幕。

3. 两个需求，第一版接不住

    
需求一：运行中把三角形换成大的。HW1 的界面上会有「换遮挡物」这类开关；HW2 的 Mary 模型是异步加载完才出现的，第一帧时还没有。第一版里，三角形的 buffer 是 built.triangleBuffer 这个固定的字段，只在 setup 里建过一次。要换，就得另写一个函数：删掉旧 buffer、上传新顶点、塞回 built。以后换别的东西（换阴影图尺寸、换 shader），每一种都要再写一个。还有个问题没人回答：换回小的时候，刚才删掉的要不要重新上传？

    
需求二：context 丢失。点上面画布的「模拟 context 丢失再恢复」。恢复以后 drawFrame 照常调用，画面却只剩深色背景 (20, 23, 31)，getError 报 INVALID_OPERATION。因为 built 里的 program、纹理、buffer 都属于丢失前的那一代 context，恢复以后全部作废（MDN 的 webglcontextrestored 页原话：丢失前建的纹理、buffer 不再有效，要重新创建；第 4、13 课实测过）。

    
第一版也能补：恢复时再调一次 setup。可是 setup 只会建写在它里面的那些东西——如果运行中已经把三角形换成了大的，setup 重建出来的还是小的。「现在场景里有什么」应该由数据说了算，而不是由 setup 说了算。

    
把两个需求合起来看：显卡上的对象只是 JS 数据的一份副本。需要有人做四件事：

    
    
      
  1. 第一次用到某份数据时，建它的 GPU 副本；
    2. 
      
  2. 记住「哪个 GPU 对象是照哪份数据建的」，下次直接拿；
    3. 
      
  3. 某份数据不再用了，删掉它的副本；
    4. 
      
  4. context 丢失时，把所有副本作废；下次用到时，照数据重建。
    5. 
    


    
4. 第二版：用到时才建，按描述对象查表

    
第二版先把「数据」写成几个普通的 JS 对象，叫描述对象：只写「是什么」（源码、顶点、尺寸），不含任何 GPU 对象。页面加载时建一次，之后一直拿着同一批对象。然后给三类 GPU 对象各写一个小类，每个类里一张 Map：key 是描述对象，value 是照它建出来的 GPU 对象。

    
    
三个 Manager 的代码几乎一样：get 先查表，查到就返回；查不到才调用第 2 节那几个建造函数，建完登记，再返回。release 从表里删掉并删除 GPU 对象。

    

    
每帧的绘制改成「用到什么就向 Manager 要什么」。它不再调用任何 create*，也不知道东西是这一帧刚建的还是早就建好的：

5. 表的 key：为什么是对象本身

    
Map 拿对象当 key 时，比的是「是不是同一个对象」，不看里面的内容（MDN · Map · Key equality）。在 Node 里跑：


const table = new Map()
const a = { name: 'triangle' }
const b = { name: 'triangle' }   // 内容和 a 一样，但是另一个对象
table.set(a, 'buffer A')
table.get(a)   // → 'buffer A'
table.get(b)   // → undefined

    
为什么不用别的当 key？下面这块画布可以把第二版的 GeometryManager 换成两种别的写法，其余代码不动：

    

      
      

        
        
        
      

      

        
        
        
        
      

      

    

    

    
上面两段变体是课程写的，项目源码里没有。切换写法时页面会丢掉旧画布、换一块新的，从第 1 帧重新开始。

    
    
      
  • 按名字查表：两个三角形的描述都叫 'triangle'（名字是给人看的，没人保证唯一）。点「三角形：大」，表里已经有 'triangle'，直接返回小三角形的 buffer：新建 0 个，画面和小三角形逐像素相同，不报错。真实代码的注释专门写了这一条：program 的「cache key 是完整 CPU 对象身份，不是 name」（WebGL1ProgramManager.ts:52）；RenderTarget 的 label「不是唯一标识」（RenderTarget.ts:420）。
    • 
      
  • 按内容查表（没放进实验）：每次 get 都把顶点数组整个读一遍算出 key。名字撞车的问题没有了，代价是每帧每个物体都要读一遍全部顶点；Mary 这种几万个顶点的模型，读一遍比查一次 Map 贵得多。
    • 
      
  • 每帧新建描述对象：drawWithManagers 本身没改，只是每帧传进去一个新的三角形描述（内容相同）。点「连续画 60 帧」：切换写法时已经画了 1 帧（表里 2 条），再画 60 帧，表里的几何涨到 62 条，buffer 一共新建 62 个——每画一帧多一条。第 40 课的泄漏又回来了，只是这次藏在表里。
    • 
    

    
所以用对象本身当 key，又快又不会认错，但它对描述对象提出了两个要求：

    
    
      
  1. 一直是同一个对象。描述要建一次、长期拿着，不能在每帧的代码里现做。
    2. 
      
  2. 建过以后内容不再变。如果有人改了 triangleGeometry.positions 里的数，表里那份 buffer 就过时了，而 Manager 只看「是不是同一个对象」，发现不了。
    3. 
    

    
谁来保证这两条？描述对象现在是谁都能改的普通对象，什么也保证不了。第 42 课把它们做成 resources/ 里的类，由 scene/ 拿着。


    
6. 什么时候从表里删

    
表里的 GPU 对象会一直留着，直到有人对它的描述调用 release。第 4 节画布上的「不再用大三角形」按钮就是页面手动调用了 managers.geometries.release(大三角形的描述)：表里少一条，deleteBuffer 一次。

    
该由谁来调用？由知道「这份数据以后不用了」的那一方——数据的主人。Manager 不知道，后端也不知道。第 42 课让描述对象自己在被丢弃时通知：每个 Manager 第一次建它的副本时，顺便登记一个「它被丢弃时叫我」，于是数据的主人只需要丢弃数据，不用知道它在几个 context 里有几份副本。

    
context 丢失是另一回事：不调用 release。旧 context 的对象已经作废，对它们调 delete* 没有意义；正确做法是整张表扔掉，恢复后换一套新的 Manager（第 4 节最后一行）。


    
7. 顺手得到的：名字能核对了

    
第 40 课把 JS 里查位置的 'uLightVP' 拼成 'uLigthVP'，画面变暗，getError 仍是 0，没有任何地方报错。第二版里，ProgramManager 链接以后把这个 program 的全部 active uniform 存成了表，于是 setUniforms 可以反过来核对：shader 里的每个 uniform，这一次都必须有值。

    
下面这块画布运行的是第二版的 drawWithManagers，只改了一处：⑦ 里给值的 uLightVP: lightVP 写成了 uLigthVP: lightVP。和第 40 课一样，课程用 new Function 把函数源码里这一处替换掉再运行。

真实的 Manager 比小引擎多做的事，一句话一条：

    
    
      
  • 建到一半失败，把这次已经建了的删掉，不把半成品登记进表（ProgramManager :184–197、GeometryManager :189–199）。
    • 
      
  • 上传 buffer 以后把原来的绑定恢复原样，不打乱别人的状态（GeometryManager :133–171）。
    • 
      
  • 删 program、buffer 之前先让引用它们的顶点输入（VAO）放手（beforeDelete 钩子，第 18 课）。
    • 
      
  • 正在 release 的时候又被 get，直接报错，不重复删除（releasing 集合）。
    • 
    

    

      这里的检查：各个 Manager 在第一次 get 时检查设备能力（扩展、尺寸上限）、编译链接结果、framebuffer 完整性和 GL 错误；失败就回滚。之后可以放心：表里只有完整可用的 GPU 对象，没有建到一半的。见 校验地图「各个 Manager」一行。
    

    
架构视角：three.js 也是这样一张表。three.js r177 的顶点 buffer 存在一个 WeakMap 里，key 是 BufferAttribute 对象本身（WebGLAttributes.js:3）；几何体按每个对象独有的 id 登记，并在第一次见到它时订阅它的 dispose 事件（WebGLGeometries.js:54–56）。program 是例外：three.js 的 shader 是按材质的设置拼出来的，所以它把设置拼成一个字符串当 key，不同材质只要设置相同就共用一个 program（WebGLPrograms.js:591–600）——这正是第 5 节说的「按内容查表」，代价是每次要算这个字符串。本项目的 shader 源码是手写的 ShaderModule，想共用一个 program，就让几个材质引用同一个 ShaderModule 对象。
