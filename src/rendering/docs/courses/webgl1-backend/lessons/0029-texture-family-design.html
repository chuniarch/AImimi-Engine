纹理一族为什么这样分：resources 与 backend 的设计思路

2. 从需求到六个设计问题

从表里能读出六条需求，每条都有一个具体的起因：

  1. 丢了 context 要能重建。①②③ 能重传，前提是 CPU 上还留着原料；④⑤ 只能重画。
  2. 一份图可能用在两个 context 里。handle 只属于创建它的那个 context（第 4 课实测：跨 context 绑定报 INVALID_OPERATION），而 Backend 将来有 WebGL1、WebGL2 两种。
  3. 来源的「复制」规则不同。8 MiB 的图片对象没法、也不该深拷贝；CPU 数组不复制的话，调用者事后一改，重传的就不是原图了。
  4. ④⑤ 会换尺寸。换尺寸就要重建 GPU 存储，handle 跟着变；正在用它的材质不能拿着旧 handle。
  5. 设备做不到时要早报错。WebGL1 的 NPOT 纹理用了 REPEAT，采样悄悄变黑，没有错误码（第 17 课 2.4 节）。
  6. 采样 GPU 画的图，要防「边写边读」。主 pass 采样阴影贴图没问题；如果某个 pass 采样的正是它自己正在写的那张，WebGL 拒绝这次 draw（8.4 节实测）。

六条需求变成六个设计问题。先把答案列在这里，后面各节一个一个推出来：

问题现在的答案在哪本课

2. 来源不同的纹理怎么分类？二维：两个子类（借用图片 / 复制数组）；cubemap：一个类，source.kind 二选一Texture2D.ts、CubeTexture.ts第 5 节

3. 第 1 版：旧引擎的写法

3.1 旧引擎的 Texture 和阴影贴图

旧引擎的二维纹理是一个类，里面放着 gl 和 handle：

// 旧引擎 src/textures/Texture.ts:6–126（节选；注释是课程加的）
export class Texture {
  // 用字符串当 key 的缓存（相关代码已注释掉，见 :36–49）
  private static cache = new Map<string, Texture>()

  // ① 一个对象绑死一个 context
  private gl: WebGLRenderingContext

  // ② GPU handle 放在 CPU 对象里
  private handle: WebGLTexture | null = null

  constructor(gl: WebGLRenderingContext) {
    this.gl = gl
  }

  // …（省略两个取 handle 的 getter，:17–30）

  createFromImage(image: TextureImageSource): void {
    const gl = this.gl

    this.handle = gl.createTexture()
    if (!this.handle) {
      throw new TextureCreationError('TEXTURE_2D')
    }

    gl.bindTexture(gl.TEXTURE_2D, this.handle)
    gl.pixelStorei(gl.UNPACK_FLIP_Y_WEBGL, true)
    gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, gl.RGBA, gl.UNSIGNED_BYTE, image)

    // ③ 采样参数按尺寸自动决定：2 的幂就 generateMipmap（:76–92），
    //    调用者没法说「这张不要 mipmap」；也没有「颜色空间」这一项
    this.setupFiltering(image.width, image.height)

    gl.pixelStorei(gl.UNPACK_FLIP_Y_WEBGL, false)
    gl.bindTexture(gl.TEXTURE_2D, null)
    // ④ image 没有存下来：context 丢了以后，这个对象拿不出像素重传
  }

  // …（省略 setupFiltering、createFromColor、dispose，:76–125）
}

阴影贴图由 FBO 类自己建、自己拿着纹理；阴影 pass 每帧把纹理 handle 推给材质：

// 旧引擎 src/renderers/passes/shadow/ShadowRenderPass.ts:204–207（每帧都调用）
uniforms['uShadowMap'] = {
  type: UniformType.TEXTURE_2D,
  // 交给材质的是「这一刻」的 WebGLTexture。FBO 一旦重建（换尺寸、context 恢复），
  // 这个 handle 就作废了，所以只能每帧重新取、重新推
  value: this.shadowMapFBO.getShadowMapTexture()
}

对照第 2 节的六条需求，问题出在四处：

  • ① 一个对象只能在一个 context 里用（需求 2）。要在第二个 context 里用同一张图，只能再 new Texture(gl2)，再传一遍图片：两个对象各管各的，谁也不知道它们是「同一张图」。
  • ④ 没留原料（需求 1）。createFromImage 用完 image 就丢了。context 丢了以后，handle 死了，这个对象也拿不出像素重传。
  • ③ 描述不全（需求 5）。采样方式由尺寸自动决定：2048 × 1024 是 2 的幂，就自动 generateMipmap。一张 128 × 128 的查找表（LUT）不想要 mipmap，没有办法说；也没有颜色空间这一项，sRGB 的颜色贴图和线性的法线贴图分不开（旧引擎只在 createFromColor 里用一个 gamma 布尔值区分）。
  • 阴影贴图交的是 handle（需求 4）。FBO 一重建，handle 就换了；旧引擎的对策是每帧重新取、重新推，所以 uShadowMap 只能放在「每帧调用」的函数里。

还有一个小地方：被注释掉的缓存用字符串当 key（Map<string, Texture>）。两张不同的图如果起了同一个名字，会被当成一张。4.2 节会实测现在的做法。

3.2 课程写的第 1 版

为了能在卡片里跑，把旧引擎的形状改写成一个最小的类。它和旧引擎一样：handle 在对象里，像素用完不留：

// 第 1 版：照旧引擎 src/textures/Texture.ts 的形状改写（课程写的，只留和本课有关的部分）
// 一个对象 = 一个 gl + 一个 handle；像素只在上传那一刻经过，用完不留
class TextureV1 {
  // GPU handle 直接放在 CPU 对象里（旧引擎 Texture.ts:11）
  handle: WebGLTexture | null = null

  // 构造时就绑死一个 context（旧引擎 Texture.ts:13–15）
  constructor(private readonly gl: WebGLRenderingContext) {}

  // 旧引擎是 createFromImage(image)；这里换成像素数组，卡片好造数据
  createFromPixels(width: number, height: number, pixels: Uint8Array): void {
    const gl = this.gl
    this.handle = gl.createTexture()
    if (this.handle === null) throw new Error('createTexture failed')

    gl.bindTexture(gl.TEXTURE_2D, this.handle)
    gl.texImage2D(
      gl.TEXTURE_2D, 0, gl.RGBA, width, height, 0, gl.RGBA, gl.UNSIGNED_BYTE, pixels
    )
    gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.NEAREST)
    gl.bindTexture(gl.TEXTURE_2D, null)
    // pixels 没有存下来：函数一返回，这个对象手里只剩 handle
  }
}

4. 第 2 版：描述和 GPU 表示拆开（问题 1）

4.1 拆成两半

第 1 版的毛病都来自一件事：「这张图是什么」和「它在某个 context 里的 GPU 副本」被放进了同一个对象。把它们拆开：CPU 这一半只描述、只留原料，不认识 gl；GPU 这一半每个 context 一个 Manager，手里一张表，key 是 CPU 对象，value 是这个 context 里的 handle。 

// 第 2 版：拆成两半（课程写的）
// CPU 这一半：只描述「是什么」，手里一直留着像素，不认识 gl
class TextureV2 {
  constructor(
    readonly label: string, // 只给人看的名字，不当 key
    readonly width: number,
    readonly height: number,
    readonly pixels: Uint8Array // 例：2 × 1 → [255,0,0,255, 0,0,255,255]
  ) {}
}

// GPU 这一半：一个 context 一个 Manager，按 CPU 对象查「我这里的 handle」
class TextureManagerV2 {
  // key 是 CPU 对象本身；value 是这个 context 里的 handle
  private readonly handles = new Map<TextureV2, WebGLTexture>()

  constructor(private readonly gl: WebGLRenderingContext) {}

  get(texture: TextureV2): WebGLTexture {
    const cached = this.handles.get(texture)
    if (cached !== undefined) return cached // 第二次起：0 条 GL 命令

    const gl = this.gl
    const handle = gl.createTexture()
    if (handle === null) throw new Error('createTexture failed: ' + texture.label)

    gl.bindTexture(gl.TEXTURE_2D, handle)
    gl.texImage2D(
      gl.TEXTURE_2D, 0, gl.RGBA, texture.width, texture.height, 0,
      gl.RGBA, gl.UNSIGNED_BYTE, texture.pixels // 像素从 CPU 对象里拿，随时能再拿一次
    )
    gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.NEAREST)
    gl.bindTexture(gl.TEXTURE_2D, null)

    this.handles.set(texture, handle)
    return handle
  }
}

4.2 真实代码里的对应

  • CPU 这一半不放 handle。Texture 基类的注释（Texture.ts:233–244）写明：它「不保存 WebGLTexture，也不执行 WebGL1 NPOT 验证」，WebGL1 和 WebGL2 的 Manager 可以为同一个 Texture 各建一份 GPU 表示。
  • GPU 这一半是三张表。Map<Texture2D, Entry>（Texture2DManager.ts:89）、Map<CubeTexture, Entry>（CubeTextureManager.ts:66）、Map<RenderTarget, Entry>（RenderTargetManager.ts:57）。Entry 比第 2 版多一个 unsubscribe：Manager 订阅了 CPU 对象的 dispose，CPU 对象释放时 Manager 删自己的 GPU 对象（第 15、16 课的同一套）。

4.3 第 2 版还缺什么

  3. Material 要采样阴影贴图时，参数里写什么？→ 第 7 节。
  4. 它什么都不查：300 × 300 用 REPEAT 也照传，在 WebGL1 上悄悄采样出黑色。→ 第 8 节。
  5. 它直接 bindTexture，会弄乱别人的绑定，也受别人留下的上传设置影响（第 17 课 3.1、3.2 节）。→ 第 9 节，三个 Manager 共用的上传作用域。

5. 像素从哪来，决定类怎么分（问题 2）

先看现在的类层次。每个叶子类最重要的区别，是它手里的像素归不归它：

5.1 图片：借用，不复制

为什么不复制图片？HTMLImageElement 没有通用的深拷贝；ImageBitmap 可以画到 canvas 上再取出来，但 Mary 那张就要再占 8 MiB，而且创建者可能想在合适的时候 close 它。所以 ImageTexture2D 只存引用，dispose 时只断开引用、不调用 close（Texture2D.ts:55–100）。

借用带来两个后果。第一个：构造时只能查「是个对象」，图片加载完没有、真实尺寸多大，要等上传那一刻才查。这件事在 Texture2DManager 的 readSource 里：

// WebGL1Texture2DManager.ts:51–73（注释是课程加的）
function readSource(texture: Texture2D): UploadSource {
  // 数组来源：拿一份副本（DataTexture2D 不把内部数组交出去）
  if (texture instanceof DataTexture2D) {
    return { kind: 'data', ...texture.copySource() }
  }
  // Texture2D 是抽象类，谁都能再派生一个子类；这里只认识两种，
  // 第三种明确拒绝，而不是走进下面的图片分支出怪错误
  if (!(texture instanceof ImageTexture2D)) {
    throw new UnsupportedRenderFeatureError(
      'texture2D ' + texture.label,
      'unknown source class'
    )
  }

  const image = texture.source
  // 图片来源：构造时只检查过「是个对象」，加载状态、尺寸到上传这一刻才查
  if (typeof HTMLImageElement !== 'undefined' && image instanceof HTMLImageElement) {
    if (!image.complete) {
      throw new InvalidTextureSourceError(
        texture.label,
        'image has not finished loading'
      )
    }
    // 用像素尺寸 naturalWidth，不用 CSS 显示尺寸 width
    return {
      kind: 'image',
      image,
      width: image.naturalWidth,
      height: image.naturalHeight
    }
  }
  if (typeof ImageBitmap !== 'undefined' && image instanceof ImageBitmap) {
    return { kind: 'image', image, width: image.width, height: image.height }
  }
  throw new InvalidTextureSourceError(
    texture.label,
    'expected HTMLImageElement or ImageBitmap in this realm'
  )
}

5.2 数组：复制进来，复制出去

CPU 数组为什么要复制？TypeScript 的 readonly data 只禁止给 data 这个属性重新赋值，不禁止改数组里的元素；Object.freeze 也冻不住 TypedArray（Node 实测：Object.freeze(new Uint8Array(4)) 抛 TypeError: Cannot freeze array buffer views with elements）。唯一可靠的办法是拿一份别人碰不到的：

  • 构造时，createTexturePixelSnapshot2D 先查长度，再复制（texturePixelSnapshot.ts:116–132）。长度 = 宽 × 高 × 通道数：2 × 1 的 rgba 要恰好 8 个数。
  • 读取时，copySource 再复制一份交出去（Texture2D.ts:145–149），内部那份永远不外泄。
  • Texture2DManager 上传时调用的就是 copySource（readSource 第一个分支）。

代价是内存。一个纹理占多少字节：

字节数 = 宽 × 高 × 通道数 × 每个数的字节数
// uint8 每个数 1 字节，float32 每个数 4 字节
// 1024 × 1024 的 rgba float32（HDR 环境图常见尺寸）：
//   1024 × 1024 × 4 × 4 = 16,777,216 字节 = 16 MiB

这张图从解码到上传，CPU 上最多同时有三份：调用者自己的那份（如果它还留着）16 MiB、DataTexture2D 的快照 16 MiB、上传时 copySource 的临时副本 16 MiB，峰值 48 MiB。上传结束后临时副本就成了垃圾。这是「内部数组绝不外泄」的价格，12.2 节的想一想会问能不能便宜一点。

5.3 二维用子类，cubemap 用 kind：两种分法

同样是「图片还是数组」两种来源，二维和 cubemap 用了不同的分法：

Texture2DCubeTexture
怎样区分来源两个子类：ImageTexture2D、DataTexture2D一个类，source.kind 是 'images' 或 'data'
两种来源的公开接口不同：Data 有 width、height、copySource；Image 只有 source（尺寸要上传时问图片）相同：sourceKind、copySource（返回带 kind 的联合）
Manager 怎样分支instanceof，第三种子类要在运行时拒绝（readSource 的 'unknown source class'）switch (kind)，漏了分支编译器会报（CubeTexture.ts:330–331 的 assertNever）
加第三种来源（比如视频）新写一个子类就能构造出来；但每个 Manager 都要记得加分支，否则运行时才报错改联合类型；所有没处理新 kind 的 switch 编译不过

这是「开放的类层次」和「封闭的联合类型」的取舍。二维这边接口确实不同（Data 能直接报宽高，Image 不能），用子类让类型更准；代价是 Texture2D 是抽象类、构造函数是 protected，任何人都能再派生一个，Manager 只好在运行时把不认识的拒掉（你的测试「明确拒绝未知 Texture2D 子类」就是测这个）。cubemap 两种来源接口一样，用一个类加 kind 更省事，而且编译器能检查分支是否写全。两种都说得通，但同一个模块里用了两种分法，第 12 节会请你想一想要不要统一。

6. GPU 画的图不是 Texture（问题 3）

6.1 为什么不继承 Texture

最省事的做法是让阴影贴图也当一个 Texture2D：Material 收 Texture2D 就够了。但对照一下两边的性质，几乎每一行都不一样：

Texture 一族RenderTarget
像素从哪来CPU：图片或数组GPU 的生产 pass（例如阴影 pass）
context 丢了以后新 Manager 用 CPU 原料重传新存储是空的，要由拥有它的 pass 重画（RenderTarget.ts:399–409）
会不会变不变：要换图就新建一个 Texture会换尺寸：resize 让 revision 加一
采样设置wrapS、wrapT、min、mag 全套，加 mipmap 策略只有 min、mag；固定 clamp-to-edge、没有 mipmap（RenderTarget.ts:30–46）
GPU 表示一个 WebGLTexture一个 FBO + 每个颜色槽一个纹理 + 可选的深度 renderbuffer
Manager 的缓存对象身份对象身份，再比 revision

如果硬把它当 Texture2D，Texture2DManager 会去找它的像素上传（找不到），丢了 context 会以为能重传（不能），resize 以后缓存也不会失效（静态纹理没有 revision）。每一处都要加「如果是 GPU 画的就……」的特判。所以 RenderTarget 直接继承 Resource：用同一套 dispose 和引用计数，其余自成一类。

6.2 revision：会变的东西怎样缓存

第 12 课讲过 resize 的规则：尺寸真的变了才提交，revision 只增不减。RenderTargetManager 用它判断缓存是否过期。和静态纹理比，get 只多了「比 revision」和「换新」两件事： 

// WebGL1RenderTargetManager.ts:72–124（节选；注释是课程加的；工作区版本）
get(target: RenderTarget): WebGL1RenderTargetResource {
  this.assertReady()
  target.assertUsable()

  // 和静态纹理的唯一区别在这一行：缓存要「同一个对象」而且「同一个 revision」才算命中
  const old = this.entries.get(target)
  const revision = target.revision
  if (old?.resource.revision === revision) return old.resource

  // …（省略：拼诊断用的 label，:80–86）
  let next: WebGL1RenderTargetResource | undefined

  try {
    assertTextureOperation(this.gl, 'begin render target creation', label)

    // 正绑着旧 FBO 时不能重建：画到一半的输出目标不能被删掉
    if (
      old !== undefined &&
      this.gl.getParameter(this.gl.FRAMEBUFFER_BINDING) === old.resource.framebuffer
    ) {
      throw new RenderTargetUnavailableError(
        label,
        'cannot rebuild the currently bound framebuffer; leave its surface scope first'
      )
    }

    // 先建新的（全部成功才有 next），再替换缓存里的条目；订阅只建一次
    this.validate(target.descriptor)
    next = this.create(target.descriptor, revision, label)
    assertTextureOperation(this.gl, 'finish render target creation', label)

    target.assertUsable()

    const unsubscribe = old?.unsubscribe ?? target.onDispose(() => this.release(target))
    this.entries.set(target, { resource: next, unsubscribe })
  } catch (error: unknown) {
    if (this.lost || this.gl.isContextLost()) {
      this.invalidateForContextLoss()
      throw new WebGLContextLostError('create render target')
    }
    // 新的建失败：删掉新的半成品；旧的原封不动，还在缓存里
    if (next !== undefined) this.deleteResource(next)
    throw error
  } finally {
    this.hooks.invalidateState()
  }

  // 新的已经发布，最后才删旧的
  if (old !== undefined) this.deleteResource(old.resource)
  this.hooks.invalidateState()
  return next
}

顺序是「先建新的、发布新的、最后删旧的」。为什么不先删旧的？因为新的可能建失败（显存不够、FBO 不完整）。先删再建，失败时新旧都没了；先建再删，失败时旧的原封不动还在缓存里，调用者拿到一个错误，但没有拿到半成品。FBO 组装的细节留到第 27 课。

7.2 copyTexture2DSamplingSource：Material 这一侧

Material 的 texture2D 参数现在收两种值（materialParameters.ts:50），写入时都经过这个函数：

// Texture2DSamplingSource.ts:16、:40–95（注释是课程加的；工作区版本，还没提交）
export type Texture2DSamplingSource = Texture2D | RenderTargetAttachmentRef

export function copyTexture2DSamplingSource(
  value: unknown, // 可能来自 JavaScript，不信 TypeScript 类型
  fieldName: string // 诊断路径，例：'parameters.uShadowMap'
): Texture2DSamplingSource {
  // 情况 1：CPU 纹理。原样返回同一个对象（身份就是 Manager 的缓存 key）
  if (value instanceof Texture2D) {
    value.assertUsable()
    return value
  }

  // 情况 2：附件地址。先确认是个对象，再逐个字段查
  assertNonArrayObject(
    value,
    () =>
      new InvalidMaterialError(
        fieldName,
        'must reference a Texture2D or a RenderTarget attachment'
      )
  )

  const input = value as Readonly<Record<string, unknown>>
  const target = input.target
  const kind = input.kind
  const index = input.index

  // target 必须是活着的 RenderTarget；WebGLTexture、普通对象都不行
  if (!(target instanceof RenderTarget))
    throw new InvalidMaterialError(
      fieldName + '.target',
      'must reference a RenderTarget'
    )

  target.assertUsable()

  if (kind !== 'color' && kind !== 'depth')
    throw new InvalidMaterialError(fieldName + '.kind', 'must be color or depth', {
      received: kind
    })

  if (typeof index !== 'number' || !Number.isSafeInteger(index) || index < 0)
    throw new InvalidMaterialError(
      fieldName + '.index',
      'must be a non-negative safe integer',
      { received: index }
    )

  // 槽位要真的存在：一个颜色槽的目标，index 只能是 0
  const descriptor = target.descriptor
  if (kind === 'color' && index >= descriptor.colors.length)
    throw new InvalidMaterialError(
      fieldName + '.index',
      'must name an existing color slot',
      {
        received: index,
        colorCount: descriptor.colors.length,
        targetLabel: target.label
      }
    )

  // depth 只有 0 号，而且目标得配了 depth。注意：这里只证明「地址存在」，
  // 能不能采样（WebGL1 的 depth16 是 renderbuffer，不能）由 Backend 判断
  if (kind === 'depth' && (index !== 0 || descriptor.depth === undefined))
    throw new InvalidMaterialError(
      fieldName + '.index',
      'must name an existing depth[0]',
      { received: index, targetLabel: target.label }
    )

  // 新建一个三字段包装并冻结：调用者之后改自己的对象，影响不到 Material。
  // target 还是原来那个 RenderTarget（不复制目标），也不记 revision
  return Object.freeze({
    target,
    kind,
    index
  })
}
10 月 19 日更新：新的参数块 ParameterBlock 也要用这套规则，所以函数多了第三个参数 createError（错误工厂）：上面每处 new InvalidMaterialError(…) 现在写成 createError(…)，不传时默认仍造 InvalidMaterialError（Texture2DSamplingSource.ts:19–28）。规则一条没变；行号变了，类型在 :17，函数在 :53–107。

三个决定，各有理由：

  • Texture2D 原样返回。它的身份就是 Manager 的缓存 key，复制一个就成了另一张图。
  • 地址复制一份再冻结。调用者手里的 { target, kind, index } 是个普通对象，事后改了 index，不能影响已经写进 Material 的那份。
  • target 不复制，revision 不记。地址要跟着目标走：resize 以后同一个地址解析出新 handle。记了 revision 反而会让地址「过期」。

// WebGL1Texture2DManager.ts:104–168（注释是课程加的；你正在写的工作区版本）
get(texture: Texture2D): WebGL1Texture2DResource {
  // ① 两道门：Manager 自己还能用吗（没关、没丢 context）；CPU 纹理还活着吗
  this.assertReady()
  texture.assertUsable()
  // ② 按对象身份查缓存。同 label 的两个对象是两个 key
  const cached = this.entries.get(texture)
  if (cached !== undefined) return cached.resource

  const gl = this.gl
  let handle: WebGLTexture | null = null
  try {
    // ③ 先查完，再动手：清掉前人留下的错误码 → 读来源 → 设备能不能做
    assertTextureOperation(gl, 'begin texture2D upload', texture.label)
    const source = readSource(texture)
    const format = this.validateStorage(texture, source)
    const type = texture.storage.type === 'float32' ? gl.FLOAT : gl.UNSIGNED_BYTE

    // ④ 上传作用域：进来记下别人的绑定和四个上传设置，出去原样还回
    withTextureUploadState(gl, gl.TEXTURE_2D, () => {
      handle = requireNonNull(
        gl.createTexture(),
        () => new WebGLResourceCreationError('texture2D', texture.label)
      )
      gl.bindTexture(gl.TEXTURE_2D, handle)
      // texImage2D 的两种重载：数组要自己给宽高；图片由浏览器给
      if (source.kind === 'data') {
        gl.texImage2D(
          gl.TEXTURE_2D,
          0,
          format,
          source.width,
          source.height,
          0,
          format,
          type,
          source.data
        )
      } else {
        gl.texImage2D(gl.TEXTURE_2D, 0, format, format, type, source.image)
      }
      assertTextureOperation(gl, 'upload texture2D pixels', texture.label)
      this.applySampler(texture)
      if (texture.mipmapPolicy === 'generate') gl.generateMipmap(gl.TEXTURE_2D)
      assertTextureOperation(gl, 'configure texture2D', texture.label)
    })

    // ⑤ 全部成功才发布：再确认一次 CPU 纹理没在上传期间被释放，
    //    然后订阅它的 dispose、写进缓存。这是唯一的发布点
    assertTextureOperation(gl, 'restore texture2D upload state', texture.label)
    texture.assertUsable()
    const resource = Object.freeze({
      handle: requireNonNull<WebGLTexture>(
        handle,
        () => new WebGLResourceCreationError('texture2D', texture.label)
      ),
      target: gl.TEXTURE_2D
    })
    const unsubscribe = texture.onDispose(() => this.release(texture))
    this.entries.set(texture, { resource, unsubscribe })
    return resource
  } catch (error: unknown) {
    // ⑥ 失败：context 丢了就整代作废、不发命令；否则删掉这次建的半成品
    if (this.lost || gl.isContextLost()) {
      this.invalidateForContextLoss()
      throw new WebGLContextLostError('create texture2D')
    }
    if (handle !== null) gl.deleteTexture(handle)
    throw error
  } finally {
    // 上传 helper 恢复真实 GL 状态后，上层缓存也必须失效。
    this.hooks.invalidateState()
  }
}

注意这段里检查和动手的先后：③ 的三件事全部在 withTextureUploadState 之前，所以 8.3 节表里时刻 ② 的检查失败时，还没有任何 GPU 对象、任何状态被改过；⑤ 是唯一写缓存的地方，⑥ 只需要删掉这一次建的 handle。

为什么不写一个 abstract class TextureManagerBase，让三个 Manager 继承？因为三个 get 的骨架不一样：

Texture2DManagerCubeTextureManagerRenderTargetManager
缓存命中条件同一个对象同一个对象同一个对象且同一个 revision
上传前要查的尺寸宽、高各一个六面同尺寸，取一个边长descriptor 的宽高，加上 MRT 数量
GPU 上建什么1 个纹理，1 次 texImage2D1 个纹理，6 次 texImage2D1 个 FBO + n 个纹理（像素传 null）+ 可选 renderbuffer，再查 completeness
命中失败时还有旧的吗没有没有可能有：先建新、再删旧

基类的做法通常是「模板方法」：基类写好 get 的骨架，子类填几个钩子。可 RenderTargetManager 的骨架（比 revision、正绑着不能重建、换新删旧）另外两个都没有，硬塞进一个骨架里，要么基类长出一堆只有它用的分支，要么它自己覆盖掉整个 get，基类就白写了。共同的部分其实只是几个「小动作」（查错、查上限、上传作用域），抽成函数，各自按自己的骨架组合，最简单。

Texture2DManager 和 CubeTextureManager 的 validateStorage 几乎一样。逐段对比（Texture2DManager.ts:178–234 对 CubeTextureManager.ts:203–262）：

10. 和 Lifecycle 的关系

第 13 课第 2 节说，context 丢了以后，Backend 要把旧的一代作废、再建新的一代。纹理一族在这两件事里做的事：

  • 一代一份。ResourceManager 新建 CubeTextureManager、RenderTargetManager（WebGL1ResourceManager.ts:108–109）；Texture2DManager 接进来以后也应该在这里。缓存跟着 Manager 走，也是一代一份。
  • lost 事件到达：丢记录、退订，不 delete。三个 Manager 的 invalidateForContextLoss 都一样：记下 lost，退订所有 CPU 对象，清空表，通知 State（Texture2DManager.ts:280–285、CubeTextureManager.ts:281–286、RenderTargetManager.ts:380–385）。GPU 对象已经随 context 失效，对死掉的 context 发 delete 没有意义。
  • 恢复以后：静态纹理重传，GPU 画的图重画。新一代的 Manager 表是空的。DataTexture2D 从自己的快照重传；ImageTexture2D、CubeTexture 从借用的图片重传，前提是创建者还没把图片关掉（5.1 节第三行）。RenderTarget 得到的是一块新的空存储：Manager 只能重建存储，不知道里面该画什么，要由拥有它的 pass 重画（RenderTargetManager.ts:152：「新建存储不意味着旧内容已恢复，生产者需要重新绘制」）。

11. 架构视角：对照 three.js r177

  • 同样的拆分。three.js 的 Texture 是 CPU 描述加来源（source），不放 GPU 对象；新渲染器把每个纹理的 GPU 数据放在一张以纹理对象为 key 的 WeakMap 里（DataMap.js:20，Textures 继承 DataMap，Textures.js:15）。和本项目的 Map<Texture2D, Entry> 是一回事；它用 WeakMap，本项目用 Map 加 onDispose 退订（第 4 课讲过两者的区别）。
  • 附件的「地址」：three.js 用一个 Texture 对象。three.js 的 RenderTarget 构造时为每个颜色附件建一个 Texture，打上 isRenderTargetTexture = true，再记住它属于哪个目标（core/RenderTarget.js:137–145）。材质直接写 material.map = renderTarget.texture。setSize 改掉这些纹理的尺寸并 dispose（:284–301），下次用到时重建 GPU 存储；纹理对象本身没换，所以材质里那个引用一直有效。效果和本项目的地址一样：材质拿着一个「不会过期的东西」。区别在代价放在哪：three.js 让附件「看起来是一个 Texture」，于是所有处理 Texture 的代码都要认得这个标记，比如更新纹理时要跳过上传（Textures.js:203–206）；本项目让两种东西保持两种类型，在 Material 的参数类型里用联合写明，由 Backend 分别解析。
  • 更新：版本号 vs 不可变。three.js 的纹理改了内容设 needsUpdate = true，version 加一（Texture.js:742–747），Textures 比版本决定是否重传（Textures.js:201）。本项目的静态纹理不可变，要换图就新建一个 Texture；只有 RenderTarget 有 revision，而且只管尺寸。好处是 Manager 简单（缓存命中只看身份），代价是做视频纹理、动态贴图时要另设计一个 version/update 契约（Texture2D.ts:14–21 的注释已经写明）。

12.1 dispose 中途失败以后，能不能接着清理

ResourceManager.dispose 的注释说：某一步抛错就停在那一步，下次 dispose 从那一步重试；「当前步骤内部的部分清理和重试安全仍由该 Manager 保证」（WebGL1ResourceManager.ts:189–191）。三个 Manager 对这句话的落实不一样：Texture2DManager 用 closing 表示「不再接新工作」，删除成功一个才从表里去掉一个，所以第二次 dispose 能接着删剩下的（Texture2DManager.ts:262–304，你的测试 :395 测的就是这个）；CubeTextureManager 和 RenderTargetManager 用 disposed，第二次 dispose 直接返回，而且第一次就先把表清空了（CubeTextureManager.ts:289–304）。同一个故障注入在两个 Manager 上：

deleteTexture 在正常 WebGL 里几乎不会抛错（传错类型才会），所以这更像契约一致性的问题，不是线上会频繁碰到的故障。要不要让三个 Manager 统一成 Texture2DManager 的写法，由你决定。
