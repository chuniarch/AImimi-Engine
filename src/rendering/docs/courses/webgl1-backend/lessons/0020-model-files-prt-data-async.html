0. 热身：前几课还记得吗

1. 一个模型由什么组成

屏幕上的 3D 模型，是由很多三角形拼出来的表面。mary 就是 10174 个小三角形。每个三角形有 3 个角 (corner)，画一个角，GPU 需要知道三样东西：

数据英文几个数例子用来做什么
位置position3：x y z(−27.9, 0, 27.9)这个角在空间里的哪里
纹理坐标texture coordinate，常叫 UV2：u v(0, 0)贴图上取哪个点的颜色。u 是横向、v 是纵向，各从 0 到 1，覆盖整张贴图
法线normal3：x y z(0, 1, 0)表面在这里朝哪边，算光照时要用（比如 n·l）

一个角上的这三样合起来，就是 vertex shader 每次执行拿到的那一份 attribute：位置进 aVertexPosition，UV 进纹理坐标那个 attribute，法线进法线那个 attribute。

相邻的三角形共用角。一块正方形地板是 2 个三角形、6 个角，可不同的点只有 4 个，对角线上的两个点被两个三角形同时用到。所以模型文件不会把每个角的坐标都写一遍，而是先列出所有的点、给它们编号，三角形只写「我用几号点」。这就是热身第 1 题的索引，模型文件也用同一个办法。

2. 读一份完整的 OBJ：16 行的地板

OBJ（Wavefront OBJ）是最常见的模型文件格式之一。它是纯文本，用记事本就能打开。建模软件（这里是 Blender）把模型导出成一行一行的文字：每行开头一个关键字 (keyword)，说明这一行是什么，后面跟着用空格隔开的数。

仓库里正好有一份完整的小 OBJ：HW1 的地板 floor.obj，一共 16 行。下面是全文，行尾的说明是我加的： 

 1  # Blender v2.91.0 OBJ File: ''            ← # 开头：注释，程序跳过
 2  # www.blender.org                         ← 注释
 3  mtllib floor.mtl                          ← 材质写在 floor.mtl 这个文件里（第 3 节）
 4  o Plane                                   ← 开始一个物体，名叫 Plane（第 3 节）
 5  v -27.924055 0.000000 27.924055           ← 1 号位置
 6  v 27.924055 0.000000 27.924055            ← 2 号位置
 7  v -27.924055 0.000000 -27.924055          ← 3 号位置
 8  v 27.924055 0.000000 -27.924055           ← 4 号位置
 9  vt 0.000000 0.000000                      ← 1 号纹理坐标
10  vt 1.000000 0.000000                      ← 2 号纹理坐标
11  vt 1.000000 1.000000                      ← 3 号纹理坐标
12  vt 0.000000 1.000000                      ← 4 号纹理坐标
13  vn 0.0000 1.0000 0.0000                   ← 1 号法线：朝上
14  usemtl None                               ← 下面的面用名叫 None 的材质（第 3 节）
15  s off                                     ← 不做平滑（第 3 节）
16  f 1/1/1 2/2/1 4/3/1 3/4/1                 ← 一个面，4 个角

读法只有四条规则：

  1. 每行第一个词是关键字，决定这一行的意思。v 是位置 (vertex)，vt 是纹理坐标 (vertex texture)，vn 是法线 (vertex normal)，f 是面 (face)。
  2. v、vt、vn 各是一张清单，各自按出现的先后从 1 开始编号（不是从 0）。第 5 行是 1 号位置，第 9 行是 1 号纹理坐标，第 13 行是 1 号法线。三张清单互不相干：1 号位置和 1 号纹理坐标之间没有任何关系。
  3. f 行不写坐标，只写编号。空格隔开的每一段是一个角，写成「位置号/纹理坐标号/法线号」。
  4. 一个面可以有 3 个以上的角。第 16 行有 4 个角，是一个四边形。GPU 只画三角形，所以读的程序要把它切成两个三角形（第 8 节看 OBJLoader 怎么切）。

把第 16 行拆开：

角写法位置纹理坐标法线
A1/1/11 号 (−27.9, 0, 27.9)1 号 (0, 0)1 号 (0, 1, 0)
B2/2/12 号 (27.9, 0, 27.9)2 号 (1, 0)1 号
C4/3/14 号 (27.9, 0, −27.9)3 号 (1, 1)1 号
D3/4/13 号 (−27.9, 0, −27.9)4 号 (0, 1)1 号

注意 C 角写的是 4/3/1：位置用 4 号，纹理坐标用 3 号，法线用 1 号，三个编号可以各不相同。四个角都用 1 号法线，因为地板是平的，处处朝上，一个法线就够了。这也是为什么 vn 的行数可以比 v 少。

角的先后顺序也有意义。这份文件里，从法线所指的那一侧（上方）看，A、B、C、D 是逆时针排的（我用叉积算过：(B−A)×(C−A) 指向 +y，和法线同向）。渲染器靠这个顺序分辨正面和背面，第 11 课的剔除 (cull) 用的就是它。

角还有另外几种写法，读 OBJ 的程序都要认识：

写法意思
f 1 2 3只有位置，没有纹理坐标和法线
f 1/1 2/2 3/3位置/纹理坐标，没有法线
f 1//1 2//1 3//1位置//法线，中间空着表示没有纹理坐标（第 5 节的立方体就这样写）
f -3 -2 -1负数编号：从目前为止最后一个往回数，−1 是最近定义的那一个（第 8 节的 parseVertexIndex 处理它）

3. MTL、o、s：建模软件留下的信息

floor.obj 里还剩几种行没讲：mtllib、usemtl、o、s。它们是建模软件里的概念，导出时顺便写进了文件。PRT 一个都用不上，但读文件的程序得知道怎么对待它们。

3.1 材质：mtllib 与 usemtl

材质 (material) 是表面的外观参数：底色是什么、高光多强、用哪张贴图。OBJ 自己不写这些参数，只写材质的名字；参数放在另一个 .mtl 文件里。

  • mtllib floor.mtl：材质库 (material library) 是 floor.mtl 这个文件。
  • usemtl None：从这一行开始，后面的面都用名叫 None 的材质，直到遇到下一个 usemtl。

HW1 的 Marry.mtl 定义了 mary 用到的两个材质，节选如下： 

newmtl MC003_Kozakura_Mari            ← 定义一个材质，名字是 MC003_Kozakura_Mari
Kd 0.800000 0.800000 0.800000         ← 漫反射颜色 (diffuse color)：RGB
Ks 0.000000 0.000000 0.000000         ← 高光颜色 (specular color)
Ns 900.000000                         ← 高光指数 (shininess)
d 1.000000                            ← 不透明度 (dissolve)，1 是完全不透明
map_Kd MC003_Kozakura_Mari.png        ← 漫反射贴图：底色从这张图里取

newmtl 材质                           ← 第二个材质，名字就叫「材质」
Kd 0.270588 0.552941 0.874510         ← 偏蓝的底色，没有贴图

HW2 的 mary.obj 第 3 行写着 mtllib Marry.mtl，可 hw2/mary/ 文件夹里只有 mary.obj，这个 .mtl 在 hw1/mary/ 下面。这不影响 HW2：PRT 的亮度全靠预计算的系数，反照率当成 1，根本不需要材质，所以 HW2 的加载器不去读 .mtl。

3.2 物体与组：o 和 g

在 Blender 里，一个场景由多个物体 (object) 组成，比如身体、头发、裙子可以各是一个物体。导出 OBJ 时，每个物体前面写一行 o 名字。g 名字 是分组 (group)，作用类似，把面分成有名字的几组。

floor.obj 只有一个 o Plane，mary.obj 也只有一个 o。这件事在第 8 节很重要：three.js 的 OBJLoader 给每个 o 或 g 建一个独立的 Mesh。文件里要是有多个物体，位置就会分散到多个 Mesh 里。

3.3 平滑组：s

s 1 表示后面的面属于 1 号平滑组 (smoothing group)，s off 表示不属于任何平滑组。它是写给「需要自己算法线的程序」看的：同一组里相邻的面在共用的角上可以共用法线，看起来光滑；不在组里的面各用各的法线，棱角分明。文件已经写了 vn 时，法线以 vn 为准。three.js 只拿 s 决定材质要不要用平面着色 (flatShading)：第 8 节实测，floor 的 s off 让材质的 flatShading 变成 true。PRT 不用 s。

5. GPU 的一个顶点 = 一种组合

OBJ 让一个角对三张清单分别编号：位置号、纹理坐标号、法线号可以各不相同，比如地板的 C 角写成 4/3/1。GPU 不行。WebGL 的 drawElements 只有一份索引，一个索引号同时从 position、uv、normal 三个 buffer 里取同一个位置的元素（第 10 课）。

所以把 OBJ 交给 GPU 时，「位置号/纹理坐标号/法线号」这三个数的每一种新组合，都要在 GPU 上占一个顶点。最典型的例子是立方体：

我写了一个只有位置和法线的立方体 OBJ，和地板、mary 一起数了一遍（Node 实测）：

模型位置 v纹理坐标 vt法线 vn三角形的角不同的组合
floor44164
立方体8063624
mary741974196260305227905

于是把模型交给 GPU 有两种办法：

办法怎么做mary 要多少适合
索引画法每种组合建一个顶点，再给一份索引说明每个三角形用哪三个7905 个顶点 + 30522 个索引省显存；顶点数据和角一一对应时要先建映射
按面展开 (face-expanded)不去重，按 f 行的顺序每个角一个顶点，不要索引30522 个顶点最简单：第 k 个顶点就是第 k 个角

拿 PRT 每个顶点要的数据算显存：位置 3 个 float 加传输系数 9 个 float，一共 12 个，每个 4 字节。索引画法是 7905 × 12 × 4 + 30522 × 2（Uint16 索引）≈ 430 KiB；按面展开是 30522 × 12 × 4 ≈ 1.40 MiB，大约 3.3 倍。HW2 选的是按面展开，原因在第 7 节：transport 文件本来就是按角写的，展开以后「第 k 个顶点配 transport 第 k 行」，不用再算谁和谁是同一种组合。多出的 1 MiB 左右，在 mary 这个规模上可以接受。

表里 mary 的 7905 是「不同组合的个数」，第 21 课里那个神秘的 transport 文件头 7905 就是它，下一节会看到原因。

6. 预计算工具 prt/：它是谁、做了什么

6.1 它是谁

仓库里的 prt/ 目录是一个 C++ 程序，基于 EPFL 的教学用光线追踪器 Nori（prt/README.md）。GAMES202 作业 2 在 Nori 里加了一个名叫 prt 的积分器 (integrator)，代码在 prt/src/prt.cpp。编译好的程序是 prt/build/nori，在这台 Mac 上是 arm64 的可执行文件。

prt.cpp 里有一些 // Edit Start 和 // Edit End 包起来的代码：环境光的投影、传输项的计算、除以 π。这些是作业 2 里要你自己补的部分。PRT 的数学这门课不展开：后面两节只关心文件里的数怎样排、怎样一一对上。

6.2 怎么运行

在终端里运行 nori 场景文件.xml（不带参数时，程序会打印用法 Syntax: nori <scene.xml>，main.cpp:164）。场景文件 prt/scenes/prt.xml 写着这一次要算什么： 

<integrator type="prt">                                   ← 用作业 2 的 prt 积分器
    <string name="type" value="interreflection" />        ← 传输类型：unshadowed / shadowed / interreflection 三选一
    <integer name="bounce" value="1" />                   ← interreflection 算几次反弹
    <integer name="PRTSampleCount" value="100" />         ← 每个顶点采样 100 个方向
    <string name="cubemap" value="cubemap/CornellBox" />  ← 用哪个环境的 6 张图
</integrator>
<mesh type="obj">
    <string name="filename" value="mary.obj"/>            ← 用哪个模型（和 public 下的 mary.obj 逐字节相同）
    <bsdf type="diffuse"/>                                ← 漫反射表面
</mesh>                                                     （节选，prt.xml:8–21）

想要另一个环境、另一种类型的数据，就改这两行，再运行一次。4 个环境 × 3 种类型，就是 HW2 用到的 12 个 transport 文件。

6.3 它做了什么

主要工作都在 PRTIntegrator 的 preprocess 里（prt.cpp:221–343），按顺序是：

步做什么代码
1读环境的 6 张 jpg。stbi_loadf 把像素读成浮点，顺便按 gamma 2.2 解码成线性值（上一次答疑讲的 pow(2.2) 就在这里做了）prt.cpp:16–41
2环境光投影：6 张图上的每个像素代表一个方向，把「颜色 × 这个方向上的基函数值 × 这个像素占的立体角」累加到 9 个系数上，写进 light.txtprt.cpp:81–131、:253–257
3读 mary.obj。Nori 自己的 OBJ 读取器把「位置号/纹理坐标号/法线号」相同的角合并成一个顶点，得到 7905 个顶点、10174 个三角形，每个三角形记 3 个顶点编号obj.cpp:92–103
4对 7905 个顶点逐个算传输系数：从顶点出发朝 100 个方向采样，每个方向算 max(0, n·ω)；shadowed 还要沿这个方向发一条射线，被模型自己挡住就记 0。把这个函数投影到 9 个系数，再除以 π。interreflection 再加上反弹回来的光prt.cpp:263–296、:302–322
5写 transport 文件：先写顶点数 7905，再逐个三角形，按它的 3 个顶点编号各写一行 9 个系数，一共 30522 行prt.cpp:262、:325–340
6之后照常渲染一张预览图（prt.png）。WebGL 用不到这一步Nori 的渲染流程

第 3 步就是第 5 节说的「每种组合一个顶点」。传输系数和法线有关，同一个位置上法线不同的两个角，系数就不同，所以 Nori 按组合算，一共算 7905 次。第 5 步再按角写出来，方便 WebGL 那边按面展开、直接对齐。

输出写在 cubemap 文件夹里，和那 6 张图放在一起（prt/scenes/cubemap/Indoor/ 等）。仓库 public/assets/data/prt/hw2/ 下 4 个环境的 light.txt 和 transport 文件，和这里的同名文件逐字节相同（我用 cmp 核对过），是从这里拷过去的。浏览器只读这些现成的 txt，从来不运行 nori。

7.1 light.txt：9 行，每行 3 个数

Indoor 的 light.txt 全文：

这是环境光投影到 9 个球谐基函数上得到的系数，也就是 PRT 里描述「环境光」的那一半。每行一个系数，三列是 R、G、B 三个颜色通道。行的顺序按 GetIndex(l, m) = l(l+1) + m 排（spherical_harmonics.h:65）：第 0 行是 l = 0，第 1–3 行是 l = 1，第 4–8 行是 l = 2。第 0 行三个数都接近 0.5，是环境光的平均亮度，偏一点点灰白；后面 8 行描述不同方向上的明暗变化，有正有负。

shader 要的排法和文件相反：每个颜色一组、每组 9 个数（uLightSH_R、uLightSH_G、uLightSH_B）。所以读进来以后要转置：R 组是 [0.518558, −0.0139227, −0.0229861, …]，G、B 同理。

几个容易误会的地方：

  • 文件头 7905 不是行数。它是第 6 节第 3 步 Nori 去重后的顶点数，也就是第 5 节表里的「不同的组合」。真正的行数是 30522。
  • 三种类型是三个文件。transport_mary_unshadowed、_shadowed、_interreflection 的排法完全一样，只是数值不同。
  • 每个环境文件夹里的 transport 数值有一点不同。传输系数只和模型、类型有关，和环境无关；可 4 个文件夹里的同名文件是分别运行 nori 得到的，而投影用随机采样（spherical_harmonics.cc:631–633），每个顶点只有 100 个样本，所以每次的结果带着不同的噪声。比如第 1 行第一个数，Indoor 是 0.229094，CornellBox 是 0.236425。

8. three.js 的 OBJLoader 怎样解析

OBJLoader 是 three.js 自带的 OBJ 读取器（OBJLoader.js，r177，955 行）。它有两个入口：load(url) 自己下载再解析，parse(text) 只解析一段已经拿到手的文字。HW2 只用 parse，原因在第 21 课 2.3 节：load 内部的下载取消不了。

8.1 parse 的三个阶段

阶段做什么代码
预处理把 Windows 的换行 \r\n 换成 \n；行尾的反斜杠 \ 表示续行，和下一行拼起来；然后按 \n 切成行:541–555
逐行处理看每行开头是什么，分别处理（下表）。v、vt、vn 只记进清单；遇到 f 才生成三角形:558–764

逐行处理时，各种行的去向：

8.2 按面展开发生在 addFace 里

parseVertexIndex: function ( value, len ) {                   // :213–218：编号 → 数组下标
  const index = parseInt( value, 10 );
  return ( index >= 0 ? index - 1 : index + len / 3 ) * 3;      // 1 号 → 下标 0；负数编号从末尾往回数
},
addVertex: function ( a, b, c ) {                             // :234–242
  const src = this.vertices;                                  // 总清单
  const dst = this.object.geometry.vertices;                  // 当前物体的数组
  dst.push( src[ a + 0 ], src[ a + 1 ], src[ a + 2 ] );       // 把三个角的坐标依次抄到末尾
  dst.push( src[ b + 0 ], src[ b + 1 ], src[ b + 2 ] );
  dst.push( src[ c + 0 ], src[ c + 1 ], src[ c + 2 ] );
},

addFace（:336）先用 parseVertexIndex 把 OBJ 的编号换成清单里的下标，再调用 addVertex 把坐标抄过去，纹理坐标和法线也这样抄（没有 vn 时，它会自己算一个面法线）。它只管抄，不管这个点是不是已经抄过，所以 OBJLoader 的输出永远是按面展开的。

9. fetch、Promise 与 await

9.1 读文件要发网络请求

浏览器里的程序不能像 C++ 那样直接打开硬盘上的文件，mary.obj、light.txt 都要通过网络请求从服务器取回来。发请求的函数是 fetch(url)。网络要花时间，从几毫秒到几秒不等，可 JavaScript 不会停下来干等，fetch 会马上返回一个 Promise：一个「结果以后才有」的占位对象。

Promise 的状态意思
等待中 (pending)结果还没出来
成功 (fulfilled)有了一个值，比如 fetch 拿到的 Response
失败 (rejected)有了一个失败原因，通常是一个 Error

一个 Promise 只会从「等待中」变一次，变成成功或失败以后就不再变。

9.2 await：在这里等结果

async function loadText(url: string): Promise<string> {
  const response = await fetch(url)        // ① 暂停，等到服务器的响应头 (headers) 到了，拿到 Response
  if (!response.ok) {                      // ② 404、500 这类 HTTP 错误不会让 fetch 失败，要自己查
    throw new Error('HTTP ' + response.status)
  }
  return await response.text()             // ③ 再暂停，等正文 (body) 全部到达，拿到字符串
}

在 async 函数里写 await 某个 Promise：函数在这一行暂停，Promise 成功就拿到值、接着往下走；失败就像 throw 一样把原因抛出来，可以用 try/catch 接住。

暂停期间，浏览器会去做别的事：处理用户的点击、运行别的回调。所以 await 前后，外面的世界可能已经变了，比如用户在等待时换了场景。第 21 课「每个 await 之后都要再查一次取消」，根源就在这里。

9.3 实测：fetch 什么时候成功、什么时候失败

我在 Node 里起了一个本地服务器，用真实的 fetch 试了三种情况：

情况结果
文件存在fetch 成功，ok = true，status = 200，text() 拿到文件内容
文件不存在（404）fetch 照样成功，只是 ok = false，status = 404。不检查 ok，就会把一个错误页面当成数据
服务器根本连不上fetch 失败，抛出 TypeError

项目里的 fetchTextWithTimeout 就是 9.2 那三步的加强版：404 时抛 HttpError，连不上时抛 NetworkError，超时抛 NetworkTimeoutError（http.ts）。第 21 课 2.7 节的错误分类表，讲的就是这几种错误分别从哪里来。

10. Promise.all 与 AbortController

10.1 Promise.all：同时等好几个

const [lightText, transportText] = await Promise.all([   // 两个请求同时发出去
  fetchTextWithTimeout(lightPath),
  fetchTextWithTimeout(transportPath)
])                                                        // 全部成功：结果按输入顺序排成数组

Promise.all 接收一组 Promise：全部成功，它才成功，结果按输入的顺序排好，不是按谁先完成；任何一个失败，它立刻失败，原因就是那个失败的原因。但是，它不会让其余的请求停下来。Promise 本身没有「取消」这回事，Promise.all 只是不再等其余的结果。

10.2 AbortController：取消的遥控器

要真正停下一个请求，得用 AbortController：

const controller = new AbortController()     // 遥控器
const signal = controller.signal             // 信号 (AbortSignal)：交给要能被取消的操作
fetch(url, { signal })                       // fetch 会一直盯着这个信号
controller.abort(new Error('换场景了'))      // 按下取消：signal.aborted 变成 true，
                                             //   signal.reason 就是这个 Error，fetch 立刻以它失败
signal.throwIfAborted()                      // 已经取消就抛出 signal.reason，没取消什么都不做

我在 Node 里把它的几条规矩都试了一遍：

操作结果
abort 之前signal.aborted = false，signal.reason = undefined
controller.abort()，不给原因aborted = true；reason 是一个名叫 AbortError 的 DOMException；之前挂上的 abort 监听触发了 1 次
abort 之后才 addEventListener('abort', …)永远不会被调用：abort 事件已经发生过了
再 abort 一次，换一个原因没有效果，reason 还是第一次的那个：一个信号只取消一次
controller.abort(自己的 Error)reason 就是你传的那个对象
请求进行到一半时 abort(原因)fetch 立刻失败，抛出的正是你传的原因

这几条在第 21 课里分别对应：

  • 「abort 之后才挂监听，永远收不到」：所以要先 throwIfAborted 再开始干活。项目的 fetchWithTimeout 只挂监听、不先检查，已经取消的 signal 交给它，请求照样发出去（旧版 http.ts:20–22，第 21 课 2.6 节）。10 月 7 日你按第 23 课重写了 fetchWithTimeout（提交 d2e6cdf），现在它进门先 callerSignal?.throwIfAborted()（http.ts:111）。
  • 超时也是用遥控器做的：fetchWithTimeout 自己建一个 controller，setTimeout 到 6 秒就按一下（http.ts:115–120）。
  • 一个信号只取消一次：所以每次加载都要新建 controller，不能复用旧的。

10.3 子 controller：自己失败时取消兄弟请求

把 10.1 和 10.2 合起来，就是 HW2 工厂的写法：调用者给一个 signal；工厂自己再建一个「子 controller」，把它的 signal 交给所有请求。 

const controller = new AbortController()                         // 子 controller
const forwardAbort = () => controller.abort(signal.reason)       // 调用者取消 → 转给子 controller
signal.addEventListener('abort', forwardAbort, { once: true })
try {
  await Promise.all([ …每个请求都拿 controller.signal… ])
} catch (error) {
  controller.abort(error)                                        // 自己有一个请求失败 → 取消兄弟请求
  throw error
} finally {
  signal.removeEventListener('abort', forwardAbort)              // 用完解除转发
}                                                                // （简化自 createHW2Scene.ts:251–253、:388、:394）

这样分两层，是因为「我的一个请求失败了」和「调用者不要这次结果了」是两件事：前者只该取消这一次构建的兄弟请求，不该把调用者的 signal 改成已取消。所以取消只往下传（调用者 → 子 controller），不往上传。loadHW2CubeImages 对自己的六张图也是这么做的。
