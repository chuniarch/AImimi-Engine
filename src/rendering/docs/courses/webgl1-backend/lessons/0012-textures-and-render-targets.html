1. 设计问题：纹理和目标要回答什么

一张纹理、一个离屏目标，都要把下面几件事说清楚。和前两课一样，第一层只负责「描述」，凡是和具体设备有关的判断都留给后端：

问题由谁描述（第一层）设备相关的部分由谁查（第三层）
怎样采样Texture 的 sampler（环绕、过滤）和 mipmapPolicyCubeTextureManager：NPOT 限制、浮点纹理能不能线性过滤
像素怎样存Texture 的 storage（通道、标量类型）和 colorSpaceCubeTextureManager：浮点扩展、EXT_sRGB
像素从哪来ImageTexture2D 借图片，DataTexture2D 复制数组，CubeTexture 两种都行上传时：图片加载完没有、真实尺寸是多少
画到哪里RenderTarget 的 descriptor：尺寸和附件RenderTargetManager：尺寸上限、多目标扩展、FBO 完整性
尺寸变了怎么通知RenderTarget 的 revisionManager 比较 revision，不同就重建
怎样指称画出来的结果附件引用 (attachment ref)RenderTargetManager.resolveAttachment

这一课有三样前两课没有的东西：

  • 借用外部对象。浏览器的图片不能像 TypedArray 那样深拷贝，只能保存引用，而且不负责关闭它（第 4.1 节）。
  • 跨字段的约束。minFilter 要用 mipmap，mipmapPolicy 就必须是 generate，两个字段要一起查（第 3.3 节）。
  • 版本号。纹理是完全静态的，RenderTarget 却能改尺寸。它用 revision 告诉后端「GPU 上那份过期了」（第 6.4 节）。第 4 课「缓存怎样发现输入变了」的三种办法里，这是第二种。

3.2 为什么要这五项：一块地板的三张贴图

像素数组只回答「每个格子里存了什么数」。上面五项回答的是另外几件事：数字本身答不出来，后端调 GL 时却每一件都要有答案。设想一块平铺的地板要用三张图：颜色贴图、法线贴图，再加一张 GGX 的 E(μ) 查找表 (lookup table)，也就是仓库根目录 lut-gen/Emu_MC.cpp:122 写出的 GGX_E_MC_LUT.png。三张都是 RGB、每通道 8 位的 PNG，字节格式一模一样，用法却完全不同：

描述颜色贴图法线贴图E(μ) 查找表
这些数是什么颜色方向：xyz 从 [−1, 1] 映射到 0–255能量比例；横向是 μ = cosθ，纵向是粗糙度（Emu_MC.cpp:110–118）
colorSpace先不填，留给第 8 节的想一想data：不是颜色data：不是颜色
sampler 的 wraprepeat：地板要平铺repeat：跟颜色贴图一起平铺clamp-to-edge：坐标超过 1 没有意义
sampler 的 filterlinear-mipmap-linearlinear-mipmap-linearlinear：表是平滑函数，相邻格子可以插值
mipmapPolicygenerate：远处的地板会缩得很小generatenone：表不会被「缩小着看」
storagergb / uint8rgb / uint8rgb / uint8
label（课程起的名字）'floor-albedo''floor-normal''ggx-e-lut'

storage 三列一样，其余几项各不相同。差别不在字节里，在用途里，而用途只有加载这张图的人知道，所以这些信息必须跟着 Texture 一起交给后端。地板贴图是 2D 纹理，后端目前还没实现（第 7 节），这里只用它来讲描述本身。

五项里最隐蔽的是 colorSpace。法线贴图里一个「正朝上」的纹素 (texel) 是 (128, 128, 255)：

其余几项填错会怎样

  • wrap：查找表要是用了 repeat，在 μ 接近 1 的地方采样时，线性过滤会把最后一列和第一列（μ 接近 0，即掠射角）平均起来，正对着看时的能量补偿就混进了掠射角的数据。反过来，地板贴图要是用了 clamp-to-edge，超出 [0, 1] 的部分会被最边上一圈像素拉成长条，铺不满。
  • filter：能不能插值，取决于数的含义。一张存「材质编号」的图（3 号、5 号……），线性过滤会在交界处插出一个根本不存在的 4 号，这种图要用 nearest。
  • mipmapPolicy：远处的地板，一个屏幕像素会覆盖几十个纹素。没有 mip 链，就只能在原图上取相邻的 4 个，画面会闪烁、出摩尔纹。只写了 mipmap 过滤器却不生成 mip 链，纹理就不完整，采样结果是黑色 (0, 0, 0, 1)，同样不报错，所以快照函数直接拒绝这种组合（第 3.3 节）。
  • storage：同样是 16 个字节、宽高 2×2，按 rgba 解释正好一张图，按 rgb 就多出 4 个字节。DataTexture2D 靠它核对数组的类型和长度（texturePixelSnapshot.ts:102–124）。它还决定后端需要哪些扩展：float32 要 OES_texture_float，用线性过滤还要 OES_texture_float_linear（第 7 节）。
  • label：场景里有几十张纹理，其中一张上传失败时，错误信息得说出是哪一张。它只给人看：缓存按对象身份区分，「相同 label 的两个 CPU 对象不会合并」（WebGL1CubeTextureManager.ts:79）。

为什么有的有默认值，有的必须写。sampler 和 mipmapPolicy 的默认值 clamp-to-edge、linear、none，是 WebGL1 上对任何尺寸都合法的组合：宽高不是 2 的幂的纹理必须 clamp-to-edge、不带 mipmap（第 7 节）。用默认值最多是不够好看，不会出错。storage、colorSpace、label 没有安全的猜法，colorSpace 猜错就是图 3 那种静默的错，所以必须写，不写快照函数就会抛错（Texture.ts:200–201）。

3.3 createTextureDescriptorSnapshot：先填默认值，再逐项、跨项验证

export function createTextureDescriptorSnapshot(options, createError) {             // Texture.ts:140–231（节选）
  if (typeof options.label !== 'string' || options.label.trim().length === 0) throw createError('label must be a non-empty string')
  if (options.sampler !== undefined && (options.sampler === null || typeof options.sampler !== 'object'))
    throw createError('sampler must be an object when provided')                    // sampler 整个传 null：拒绝
  if (options.storage === null || typeof options.storage !== 'object') throw createError('storage must be an object')

  const samplerInput = options.sampler ?? {}
  const wrapS = samplerInput.wrapS ?? 'clamp-to-edge'                               // ?? 把 null 和 undefined 一样对待
  const wrapT = samplerInput.wrapT ?? 'clamp-to-edge'
  const minFilter = samplerInput.minFilter ?? 'linear'
  const magFilter = samplerInput.magFilter ?? 'linear'
  const format = options.storage.format, type = options.storage.type
  const colorSpace = options.colorSpace                                             // 必填：没有默认值
  const mipmapPolicy = options.mipmapPolicy ?? 'none'

  if (!WRAP_MODES.has(wrapS)) throw createError(`unsupported wrapS ${String(wrapS)}`)   // :176–206 每一项查允许集合
  …（wrapT、minFilter、magFilter、format、type、colorSpace、mipmapPolicy 同理）
  if (mipmapPolicy === 'none' && MIPMAP_MIN_FILTERS.has(minFilter))                 // :208–210 跨字段约束
    throw createError(`minFilter ${minFilter} requires mipmapPolicy "generate"`)

  const sampler = Object.freeze({ wrapS, wrapT, minFilter, magFilter })              // 新对象，冻结
  const storage = Object.freeze({ format, type })
  return Object.freeze({ label: options.label, sampler, storage, colorSpace, mipmapPolicy })
}
作用把调用者的描述验证一遍，复制成几个冻结的新对象。Texture 的构造函数拿到结果后，把五项存成 public readonly 字段（Texture.ts:260–270）。
顺序先查三个外层结构（label、sampler、storage），再填默认值，然后逐项查允许集合，最后查跨字段约束。允许集合是运行时的 Set（:107–133），挡的是 JavaScript 和错误的类型断言。
跨字段约束mipmapPolicy 是 none 时不许用 mipmap 过滤（卡片 B）。这不是风格偏好：ES 2.0 规范 3.8.2 节规定，缩小过滤要 mipmap、纹理又没有完整的 mip 链时，采样结果是 (0, 0, 0, 1)，也就是黑色，而且不报任何错。这个错不需要设备就能发现，所以构造时就拒绝。
null 的含义sampler 里的字段用 ?? 补默认值，?? 对 null 和 undefined 一视同仁：{ wrapS: null } 被当成没填（卡片 C）。第 11 课的 Material 正好相反，null 会被拒（审查视角 1）。colorSpace 没有默认值，传 null 会在允许集合那一步被拒。
为什么冻结两层sampler 和 storage 是嵌套对象，只冻结外层的话，texture.sampler.wrapS = 'repeat' 仍然能改。这里三个对象都是新建的，各自冻结（测试 Texture2D.test.ts:88）。
没有检查的WebGL1 的限制：NPOT 纹理只能 clamp-to-edge、不能要 mipmap，浮点纹理要扩展。这些由后端上传时查（:239–240），同一个 Texture 交给 WebGL2 的后端，限制就不一样了。

4.1 ImageTexture2D：借用浏览器图片

export type TextureImageSource = HTMLImageElement | ImageBitmap                     // Texture2D.ts:20

}

为什么只存引用「HTMLImageElement/ImageBitmap 不能像 TypedArray 一样通用地深拷贝」（Texture2D.ts:61–63）。要复制，得先画到 canvas 再读回来，那就变成另一种来源了。
借用意味着什么图片的寿命归创建它的人：dispose 只断开引用，不调 ImageBitmap.close()。同一张 ImageBitmap 可能还被别的纹理用着。
为什么只查是不是对象图片加载完没有、能不能交给 texImage2D，都要等上传时由后端查（:65–66，卡片 I）。资源层不依赖 DOM 类型，单元测试可以在 Node 里跑；后端在浏览器里运行，才用 instanceof HTMLImageElement 去认它。
状态构造后不再变；读取都先 assertUsable（测试 Texture2D.test.ts:238）。

4.2 DataTexture2D 与 texturePixelSnapshot：复制进来，复制出去

export function createTexturePixelSnapshot2D(source, storage, createError) {        // texturePixelSnapshot.ts:82–133
  if (source === null || typeof source !== 'object') throw createError('pixel source must be an object')

    throw createError(`width and height must be positive integers; …`)

    throw createError('data must be a Uint8Array or Float32Array')
  if (storage.type === 'uint8' && !(source.data instanceof Uint8Array)) throw …      // 数组类型要和 storage.type 对上
  if (storage.type === 'float32' && !(source.data instanceof Float32Array)) throw …
  const expectedLength = source.width * source.height * getChannelCount(storage.format)   // 宽 × 高 × 通道数
  if (!Number.isSafeInteger(expectedLength)) throw …                                 // 乘法不能超出安全整数
  if (source.data.length !== expectedLength) throw createError(`data length … does not match expected length …`)
  return Object.freeze({ data: copyTexturePixelArray(source.data), width: source.width, height: source.height })   // 复制数组，冻结外壳
}

copySource(): TexturePixelSource2D {                                                 // Texture2D.ts:145–149

作用验证一份二维像素，存一份调用者碰不到的快照。DataTexture2D 用它（Texture2D.ts:119–123），CubeTexture 的 data 模式对六面各用一次。
校验宽高是正整数；数组是 Uint8Array 或 Float32Array，而且和 storage.type 一致；长度正好等于宽 × 高 × 通道数（rgba 是 4，:38–47）。canvas 的 getImageData().data 是 Uint8ClampedArray，它不是 Uint8Array，会被拒（卡片 A）。
为什么进出都复制注释说得很准：「readonly 只能阻止重新赋值 data 属性，不能阻止修改 TypedArray 的元素」（:19–21）。有元素的 TypedArray 又冻结不了（热身第 1 题），所以只能进来复制一份、出去再复制一份。
「复制」要复制到哪一层new Uint8Array(existing) 逐个复制元素，得到新的底层内存；new Uint8Array(existing.buffer) 只是同一块内存的另一个视图（模块说明 :21）。卡片 A 里调用者交进来的就是视图，纹理仍不受影响，因为纹理自己又复制了一次。
copy 为什么不再验证它只接收内部已经验证过的快照；「重新验证既不能增加边界安全性」，还会把读取和构造混在一起（:141–143）。
没有检查的数组里的值是否合理（float32 里的 NaN、Infinity 照收）；尺寸是否超过设备上限，由后端上传时查。

function createCubeSourceSnapshot(label, source, storage) {                         // :225–248

「正方形、六面同尺寸」不依赖任何后端（:42–48），所以写成一个独立函数，错误类型由调用方的工厂决定。数据面的尺寸构造时就知道，立刻查；图片的真实尺寸要等它加载完，只能在上传时查。规则只写了一份，检查时机按「什么时候知道」来定。这和第 10 课「能早查的尽量早查」是同一个原则。

注意 NPOT 不在这里：一个 3×3 的 data cubemap 配 repeat 能构造成功（测试 CubeTexture.test.ts:221）。ES 2.0 规范 3.8.2 节规定，NPOT 的 cubemap 只要不是 clamp-to-edge、或者要 mipmap，采样就得到黑色；这条限制属于 WebGL1，由 Manager 在上传前拒绝（第 7 节）。

6. RenderTarget：描述写到哪里，不描述画什么

6.1 为什么不继承 Texture

RenderTarget 继承 Resource，而不是 Texture：「没有可重新上传的 CPU 图片或像素源」，context 恢复之后，GPU 里画出来的内容要由它的所有者重新执行生产它的 Pass（RenderTarget.ts:405–408）。Texture 的五项描述也大多不适用：它的颜色附件固定是 rgba8，采样方式由 Manager 定死（第 7 节）。它的所有者一般是某个 Pass 或功能模块，而不是 Scene（第 5 课第 2 节）。

6.2 为什么是这四项：一帧里的三块画布

拿 Texture 对比着看：Texture 描述一份已经存在的数据，讲它怎么存、怎么取、代表什么；RenderTarget 描述一块要交给 GPU 去写的空画布，讲它多大、有几层颜色、每层什么格式、要不要一层深度。所以它只有 width、height、colors、depth 四项，而且都是后端建 FBO 之前必须知道的。FBO 建好就定型了，尺寸一变只能整套重建，所以才需要第 6.4 节的 resize 和 revision。画什么、清成什么、之后谁怎么读，都不归它管。

阴影贴图后处理目标GBuffer（HW3 的延迟渲染）

阴影贴图这一列，就是旧引擎 ShadowMapFBO 在设备没有 WEBGL_depth_texture 时用的布局（ShadowMapFBO.ts:41–52）。三块画布用的是同一个 RenderTarget 类型，后端建出来的 FBO 却各不相同：

每一项不写或写错会怎样

  • width、height：分配存储要用：每个颜色纹理的 texImage2D 和深度的 renderbufferStorage 都要宽高（WebGL1RenderTargetManager.ts:272–282、:316）；进入 scope 时，viewport 也设成目标的宽高（WebGL1State.ts:207–216）。宽高属于整块画布，不属于单个附件：ES 2.0.25 第 4.4.5 节要求「All attached images have the same width and height」，做不到 FBO 就不完整（FRAMEBUFFER_INCOMPLETE_DIMENSIONS），所以描述里只有一组宽高。
  • colors 的个数：决定片元着色器能同时写几个输出。每个槽对应一张纹理，挂在 COLOR_ATTACHMENT0 + i 上（:299–301），shader 往 gl_FragData[i] 写。多于 1 个就需要 WEBGL_draw_buffers，而且不能超过 MAX_COLOR_ATTACHMENTS_WEBGL 和 MAX_DRAW_BUFFERS_WEBGL（:206–227）。这些检查、要建几张纹理、drawBuffersWEBGL 的槽位列表，都得在建 FBO 之前知道个数。
  • colors 的格式：决定每个像素能存什么值。rgba8 每通道 8 位，写进去的值会被夹到 [0, 1]。GBuffer 的世界坐标和深度远远超出这个范围，所以旧引擎全用 FLOAT。新的描述目前只允许 rgba8，GBuffer 因此还描述不了；浮点格式写在 TODO 里（RenderTarget.ts:56–58），注释特意说明不把尚未支持的 HDR 字段当作「无效占位参数」。
  • depth：需要却没给时，ES 2.0.25 第 4.1.5 节规定「If there is no depth buffer, it is as if the depth buffer test always passes」。Material 开着深度测试也没用：后画的三角形直接盖住先画的，阴影贴图里存下的是最后画的表面而不是最近的，阴影全错，而且不报错。不需要就别要：后处理可以省掉一张「宽 × 高 × 2 字节」的 renderbuffer。depth16 在后端是 renderbuffer，只能做深度测试、不能采样（第 6.5 节），所以阴影贴图得把深度另外 pack 进颜色附件，这正是旧引擎的做法。

为什么格式只有 rgba8 和 depth16。WebGL 1.0 规范「Framebuffer Object Attachments」一节只保证这几种组合在任何设备上一定完整：COLOR_ATTACHMENT0 = RGBA/UNSIGNED_BYTE 纹理；它加上 DEPTH_ATTACHMENT = DEPTH_COMPONENT16 renderbuffer；它加上 DEPTH_STENCIL_ATTACHMENT = DEPTH_STENCIL renderbuffer。同一节还规定，挂在 DEPTH_ATTACHMENT 上的 renderbuffer 必须是 DEPTH_COMPONENT16。「rgba8 加可选的 depth16」正好落在前两种里（RenderTarget.ts:13–16）；描述要求至少有一个颜色附件（:52），也和这几种组合一致。多个附件、浮点格式、可采样的深度都要靠扩展，所以交给后端按设备能力判断。

作用验证尺寸和附件布局，建一份每一层都冻结的新描述。所有检查通过之前，什么都不发布（:321）。
UnvalidatedFields 是干什么的一个小技巧：它把每个字段都变成可选的 unknown。这样写 input.width 时编辑器还能提示字段名、拼错会报错，但类型系统不会假装值已经可信，逼着每个值都过一遍验证函数（:104–117）。
拒绝未知字段和第 11 课的 RenderState 一样：多写一个 stencil: true 会被拒，不会被悄悄忽略（卡片 H）。每个附件对象也各查一遍自己的字段名。
格式列表颜色只有 rgba8，深度只有 depth16，类型从列表推出来（:13–22），和第 11 课 builtInUniforms 的名单是同一个做法。rgba8「只规定存储格式，不自动执行 sRGB/线性颜色转换」（:53）。
为什么冻结每一层colors 数组和每个附件对象都冻结，调用者拿到描述后没法改数组、换格式，只能通过 resize 这一个受控入口改尺寸（:382–393）。调用者传进来的对象不被冻结，这里冻结的都是自己新建的（测试 RenderTarget.test.ts:107–139）。
允许的NPOT 尺寸、多个颜色附件、不要深度（RenderTarget.test.ts:142）。多个附件要不要扩展、尺寸超不超上限，都由后端判断（:54）。
留着没做的浮点格式、写 cubemap 某一面或某一层 mip 的视图，都在 TODO 里（:56–58），而且明确「不把尚未支持的 face、mip、HDR 字段作为无效占位参数」。

6.4 resize 与 revision

resize(width: number, height: number): void {                                       // RenderTarget.ts:475–493
  this.assertUsable()
  const nextWidth = requireDimension(width, 'width')                                 // 两个尺寸都先验证
  const nextHeight = requireDimension(height, 'height')
  const current = this.descriptorValue!
  if (current.width === nextWidth && current.height === nextHeight) return          // 没变：什么都不做，revision 不加
  const next = Object.freeze({ ...current, width, height })                          // 浅展开：colors、depth 沿用已冻结的对象
  this.descriptorValue = next                                                        // 提交
  this.revisionValue++                                                               // 版本加一
}
作用只改尺寸，附件的数量和格式不变。
原子性两个尺寸都验证通过才提交；resize(512, 1.5) 里宽度虽然合法，也不会单独生效（卡片 F，测试 RenderTarget.test.ts:228）。
revision 记的是什么「描述版本，不是 GPU 已完成创建的证明，也不是撤销历史」（:426）。尺寸没变不加；A → B → A 是两次修改，加两次，不会退回去（:469，卡片 E）。Manager 只需要比较「我建的时候是第几版」和「现在是第几版」。
为什么不直接比尺寸比尺寸也能发现「变了」。但 revision 把「变了没有」收成一个整数，Manager 缓存一个数就够；将来如果还能改别的（比如附件格式），比较方式也不用改。这正是第 4 课说的第二种办法：输入自带版本号，缓存记下「我基于哪一版」。
旧快照先前拿到的 descriptor 不会跟着变：resize 换的是一个新对象（:449）。浅展开让新旧两份共用同一个已冻结的 colors 数组，这是安全的，因为它本来就不能改（模块说明 :51）。

6.5 附件引用：一个逻辑地址

export interface RenderTargetAttachmentRef {                                         // RenderTarget.ts:131–135

getColorAttachment(index: number): RenderTargetAttachmentRef {                      // :501–513
  this.assertUsable()
  if (!Number.isSafeInteger(index) || index < 0 || index >= colors.length) throw …('must name an existing slot')
  return Object.freeze({ target: this, kind: 'color', index })                       // 每次一个新的冻结包装
}
getDepthAttachment(): RenderTargetAttachmentRef | null {                             // :519–524

  if (this.descriptorValue!.depth === undefined) return null                         // null 只表示「没有深度附件」

它是什么「附件的逻辑地址，不是像素副本或 GPU handle」（:120–129）。{ target, kind: 'color', index: 0 } 的意思是「这个目标的第 0 个颜色槽」，不是「这一代的某个 WebGLTexture」。index 是槽号，不是像素下标、纹理单元号或 cubemap 的面号（模块说明 :47）。
为什么不存 revisionresize 之后，GPU 上的纹理换了一张，槽位却还是那个槽位。引用只记地址，由 Manager 解析成当前版本的纹理（图 2）。消费者不用握着一个会过期的句柄。
不 retain拿着引用不会给目标加引用数，也挡不住它的所有者释放它（:128）；目标释放之后，旧引用也不能让它复活（测试 RenderTarget.test.ts:287）。
每次新包装两次 getColorAttachment(1) 得到两个不同的对象，字段相同（卡片 G）。所以比较引用要比三个字段，不能比对象身份（审查视角 3）。
深度的特殊之处depth16 在后端是 renderbuffer，不是纹理，「在本阶段不能作为纹理采样」（:127）。null 的意思被刻意限定：「绝不表示默认 framebuffer」（:517），默认 framebuffer 由 RenderSurface 的 kind: 'default-framebuffer' 表示（第 6 课）。
谁在用写这课时只有 RenderTargetManager.resolveAttachment（第 7 节），Material 的纹理参数还不能接它。10 月 12 日起，Material 的 texture2D 参数也能放颜色附件的地址（提交 b54b581；第 11 课 4.3 节、第 29 课第 7 节），深度附件仍被拒绝。当时 Material.ts 里的 TODO 列了三件后端的事：解析当前 revision 的附件、拒绝「采样正在写的目标」、context 恢复后重新生产。10 月 19 日这段注释随参数类型搬进了 materialParameters.ts:35–39：前两件 Backend 已经做了，注释里直接写明；TODO 剩下可采样的深度附件、face/mip/layer 子资源视图，以及恢复后由生产者重画附件内容（第 27 课 4.2 节）。
TypeScript 接口不是凭证「Backend 消费时仍须验证 target/kind/index」（:129）：任何人都能手写一个长得一样的对象。

  source: { kind: 'images', faces: [faces[0], faces[1], faces[2], faces[3], faces[4], faces[5]] },   // 借用六张图
  storage: { format: 'rgb', type: 'uint8' },                                          // JPG 没有 alpha
  colorSpace: ???                                                                     // 见下面的「想一想」
}))                                                                                    // sampler、mipmapPolicy 用默认：clamp-to-edge、linear、none

想一想：colorSpace 填什么？先把三条事实摆出来：

  1. 选 'srgb'：后端要求 EXT_sRGB，没有就抛错，「no implicit color-space fallback」（WebGL1CubeTextureManager.ts:247–259）；有的话，采样时会把 sRGB 编码的值解码成线性（:198）。
  2. 写回屏幕时没人替你编码。ES 2.0 规范 3.8.2 节说片元输出只被夹到 [0, 1] 再转成定点数。WebGL 规范对 drawingBufferColorSpace 的定义是「the color space used to interpret the drawing buffer's content values」，只规定怎样解释缓冲里的值，不做转换。旧引擎 engine.ts（提交 4b500f9 的 :170）的注释说设成 'srgb' 能让输出「走 sRGB 编码」，这个说法不准确；何况 'srgb' 本来就是默认值。10 月工作区里的 engine.ts 已经删掉了这句注释，只剩赋值（engine.ts:99）。
  3. 旧引擎为什么看起来是对的：它采样时没解码，输出时也没编码，两边都是 sRGB 编码的值，原样显示正好就是图片本来的样子。

问题：选 'srgb' 而不改 shader，背景会变亮还是变暗？选 'linear' 或 'data' 呢？哪一个在语义上才是对的？想两全其美，管线里还缺哪一步？（CubeTextureManager 的注释也说了，输出到屏幕的颜色编码「属于后续 shader/pipeline」，:199。）

12. 架构视角

12.1 对照 three.js 的 Texture 与 RenderTarget

three.js本项目
像素texture 直接引用你给的来源（Texture.js:92）；DataTexture 的 image 是 { data, width, height }，data 不复制（DataTexture.js:50）DataTexture2D 和 cube data 进出都复制；只有图片是借用
改了之后改完设 needsUpdate = true，version 加一，渲染器下次重新上传（Texture.js:742–747）纹理完全静态；只有 RenderTarget 能改尺寸，靠 revision
默认采样minFilter 是 LinearMipmapLinear，generateMipmaps 为 true（Texture.js:47、:256）linear，mipmapPolicy 是 none；要 mipmap 必须两个字段都写
颜色空间colorSpace 属性，默认 NoColorSpace（:47、:298）colorSpace 必填：srgb、linear、data 三选一
谁定 colorSpace加载器按贴图用途设：GLTFLoader 给 baseColor、emissive 设 SRGBColorSpace（GLTFLoader.js:3658、:3750），法线、metalness/roughness、AO 不设（:3715、:3667–3668、:3731）创建 Texture 的人必须写（第 3.2 节的三张贴图）
RenderTarget 改尺寸setSize 改完尺寸直接 this.dispose()，下次用到时重新分配（core/RenderTarget.js:284–301）revision 加一；Manager 先建好新的、发布、再删旧的；CPU 对象一直活着
深度可以挂一个 depthTexture 用来采样（:183）depth16 是 renderbuffer，暂时不能采样
RenderTarget 的默认附件depthBuffer 默认 true，多个颜色附件用 count（core/RenderTarget.js:57、:63）depth 省略就是不要；colors 写几个就是几个（第 6.2 节的三块画布）

和前两课一样，three.js 选的是灵活：共享你的数组，改完打个标记，渲染器自己去重传。本项目初版选的是「数据不变，GPU 副本就不会过期」，唯一会变的 RenderTarget 用一个只增不减的版本号收口。setSize 的写法差别也值得注意：three.js 让「释放」兼任「失效」，本项目把两件事分开了，resize 只让版本过期，对象本身和它的引用都还有效。

12.2 审查视角：三处值得讨论，一道找茬题

  1. null 的含义不一致。Texture 的 sampler 字段用 ??，null 当作没填（Texture.ts:161–174）；第 11 课的 Material 用 defaultIfUndefined，null 被拒（Material.ts:85–95）。想一想：哪一种更好？如果要统一，应该改哪边、放在哪一层（比如 core 里一个共用的函数）？
  2. 图片来源的检查全部推迟到上传。CubeTexture 的 images 模式和 ImageTexture2D 只查「是不是对象」（CubeTexture.ts:85–87）。好处是资源层不依赖 DOM；代价是尺寸不对、图片没加载完，要到第一次 draw 才报错，离出错的地方很远。想一想：哪些检查可以提前、应该放在哪里（资源类、loader，还是工厂）？
  3. 附件引用没有稳定的身份。每次 getColorAttachment 都返回新包装（RenderTarget.ts:496）。写这课时只有 resolveAttachment 用它，没问题；10 月 12 日 Material 的纹理参数也接上了它（第 11 课 4.3 节），如果有人拿引用当 Map 或 WeakMap 的键，同一个槽位就会变成好几个键。（Material 存的也是复制出来的新包装，copyTexture2DSamplingSource 每次都新建一个。）想一想：是该缓存每个槽位的引用对象，还是在文档里写明「只能按字段比较」？
  4. 找茬题：Texture.ts 的构造函数附近，有一处一模一样的东西出现了两次。找到了告诉我。
