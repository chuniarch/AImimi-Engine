生命周期的边角情况：回调出错、回调里关掉自己、旧一轮的错误

第 13 课第 2 节讲了 context 丢失、恢复的主线：两个事件，Backend 交来的五个回调，五个状态回答「现在能不能画」。那一节默认每个回调都正常返回。这一课回答剩下的问题：回调执行到一半抛错了怎么办？回调里有人回头调用这个对象（把它关掉，或者又派发一次丢失），外面那一轮还能不能把状态写成 ready？已经作废的那一轮抛出的错误该记在哪里？WebGLContextLifecycle 300 行，一大半是为这些问题写的。这一课先用真实浏览器看一次「恢复途中又丢了」，再用「架构师七步」把要应付的情况一格一格列出来，然后一版一版写出代码，最后读真实代码，看它和 Backend、各个 Manager 怎样配合。

和你的目标的关系 —— 做 HW1、HW2 时，GPU 驱动重置、标签页切走太久、同时开太多 WebGL 页面，都可能让 context 丢失。这一课决定了那时候画面会怎样：是等浏览器恢复后自动接着画，还是停在「恢复失败」并留下原因，或者因为一个旧回调把状态写错，在已经失效的 context 上继续 draw。以后想在恢复失败时提示用户、或者自动退出 HW2，回调里就会出现这一课讲的重入。
默认你已经会的：① 第 13 课第 2 节：两个事件、五个回调、五个状态，以及 Backend.ready 怎样挡住渲染循环；② 第 14–18 课各自的「和 Lifecycle 的关系」：丢失时 State 只忘不发，各个 Manager 丢掉记录、不调 delete；恢复时建一套全新的一代；③ 第 18 课：ResourceManager 的 invalidateForContextLoss 先标记、再逐个通知六个 Manager；④ 第 31 课：一代 GPU 对象和 CPU 原件的关系。如果其中哪一条其实没懂，告诉我，我先补那一块。
这一课从零讲的：回调的三种结局（正常、抛错、回头调用自己）各从哪里来；七步法；状态 × 事件 × 回调结局表；第 1、2 版和两种「核对」办法；号码牌（transitionVersion）；作废那一轮的错误（onSuppressedError）；通知自己失败（notificationError）；Backend 自己的第二层检查（epoch）；对照 three.js。

1. 原始输入：回调里到底在做什么，会怎样结束

1.1 五个回调

生命周期类自己不碰任何 GPU 对象，具体的事都由 Backend 在构造时交给它（WebGL1Backend.ts:78–110）：

// WebGL1Backend.ts:78–110（注释是课程加的）
this.lifecycle = new WebGLContextLifecycle(canvas, {
  // lost：这一代整体作废。State 忘掉缓存，ResourceManager 通知六个 Manager
  // 丢掉记录、退订，不调 delete（:344–349，第 14–18 课）
  onLost: () => {
    this.invalidateGeneration()
  },

  // restored：建新的一代（重新探测能力，新建 State、ResourceManager……）
  restore: () => {
    const epoch = this.epoch
    const candidate = this.createGeneration() // :259–305，探测可能抛错

    // 第二层检查，第 4 节讲
    if (this.disposedValue || epoch !== this.epoch || this.gl.isContextLost()) {
      candidate.resources.invalidateForContextLoss()
      candidate.resources.dispose()

      throw new WebGLContextLostError('publish restored backend')
    }

    this.generation = candidate // 发布新的一代
  },

  // 收尾：再问一次有没有又丢
  onReady: () => {
    if (this.gl.isContextLost()) {
      throw new WebGLContextLostError('finish restoration')
    }
  },

  // 恢复失败的通知：现在是空的，失败只记在 lastFailure 里
  onRestoreFailed: () => {
    // 原始错误由 lifecycle.lastFailure 保存，不在 DOM listener 中继续抛出。
  },

  // 旧一轮的错误：存起来供诊断（3.5 节）
  onSuppressedError: (error) => {
    this.suppressedValue = error
  }
})

1.2 每个回调可能怎样结束

一个回调交出控制权以后，只有三种结局。每一种都能在项目里找到具体来源：

  • 正常返回。第 13 课讲的都是这种。
  • 抛错。
    • restore：createGeneration 第一步就是 detectWebGL1Capabilities，它在查询前后各问一次 isContextLost，发现又丢了就抛 WebGLContextLostError（WebGL1Capabilities.ts:49、:63；行号按 10 月 14 日深夜你刚加了 colorBufferFloat 的版本）。1.3 节在真实浏览器里制造了这种情况。
    • onReady：Backend 收尾时又发现丢了，主动抛错。
    • onLost：ResourceManager 先标记、再逐个通知六个 Manager（WebGL1ResourceManager.ts:171–179）。其中一个抛错，onLost 就抛错，这是第 18 课审查视角的第 2 条。
  • 回头调用自己（重入，reentrancy）：回调还没返回，就调用了 lifecycle 的 dispose，或者让 canvas 又派发了一次事件。
    • 现在的五个回调都不会这样做，onRestoreFailed 还是空的。
    • 以后很可能会有。第 13 课审查视角问过：恢复失败时，怎样让上层知道、提示用户或者退出 HW2？如果在 onRestoreFailed 里通知 Engine 退出 HW2，就会接上这条全程同步的链：Engine.clearScene → this.session?.renderer.dispose()（engine.ts:241）→ this.backend.dispose()（Renderer.ts:126）→ this.lifecycle.dispose()（WebGL1Backend.ts:249）。也就是说，lifecycle 还在 handleRestored 里面，自己就已经被关掉了。
    • 「回调里又来一次 lost」在真实浏览器里不会同步发生：loseContext() 返回时事件还在排队（第 13 课 2.5 节）。它出现在测试里，或者手动调用 canvas.dispatchEvent 的时候。

2. 七步：先把要应付的情况列全

你读第 13 课时问过：「作为架构师应该怎样思考」。下面用这个类走一遍我当时给的七步。重点在第 4 步：表要按「当前状态 + 事件 + 回调结局」三样来填。我第一次给你的表只填了「回调全部正常」，漏了「lost 状态收到 restored，restore 抛错 → restore-failed」这一格，被你指了出来。

2.1 一句话职责

把浏览器的两个事件，变成上层随时能问的「现在能不能画」；按固定顺序调用 Backend 的回调；回调出了什么事，都不能让状态说谎，也不能让异常逃出 DOM 监听器。

2.2 输入清单

  • 外部事件：webglcontextlost、webglcontextrestored。重复、乱序都可能出现，比如没有 lost 就来了 restored。
  • 调用者：Backend 调 dispose()；渲染循环问 isReady、state、lastFailure。
  • 每个回调的结局：正常、抛错、回头调用自己（dispose，或者又派发一次事件），也可以是「先回头调用、再抛错」。

2.3 从上层要问的问题倒推状态

第 13 课 2.4 节已经推过：ready、lost、restoring、restore-failed、disposed。五个状态里有四个都「不能画」，但再收到 restored 时该怎么办、上层看到它时该怎么做，各不相同。这一课新增的是第 4 列：每个状态下，失败记录 lastFailure 该是什么。

2.5 每个转移里面的步骤

格子定了，再定每个转移里面先做什么、后做什么。顺序都是从「回调执行时别人会看到什么」倒推出来的：

  • lost：① 已关闭就不理；② preventDefault，告诉浏览器「我想恢复」；③ 已经是 lost 就返回；④ 先改状态、清旧记录，再调 onLost。这样 onLost 执行时，谁来问都会得到「不能画」。
  • restored：① 只在 lost、restore-failed 时接受；② 改成 restoring、清旧记录；③ 调 restore；④ 调 onReady；⑤ 最后才写 ready。每一步失败都改成 restore-failed，记下是哪一步，再通知。
  • 每个回调返回以后：先确认「这一轮还算数」，才能接着往下走、才能写状态。这一条是这一课的核心，第 3 节一步步推出来。

2.6 不变量

不管事件和回调怎样组合，这五条都要成立。第 3 节每一版代码，都用它们来检验：

  1. 不说谎：isReady 为 true，当且仅当最近一次转换是一次完整成功的恢复（或者从构造起就没丢过），并且之后没有发生过更新的转换。
  2. 关了就不再变：disposed 以后状态不再改变，也不再调用任何回调。
  3. 记录属于当前这一轮：lastFailure 只描述当前这一轮。作废那一轮的错误不能写进来，也不能悄悄丢掉。
  4. 异常不出监听器：任何回调抛出的异常，都不能从 DOM 事件监听器里逃出去。
  5. 不重复：同一轮丢失只调用一次 onLost，同一轮恢复只调用一次 restore。

3. 一版一版写出来

下面的卡片把生命周期类放在一个假的 canvas 上（就是一个 EventTarget：浏览器派发的两种事件本来就是普通 DOM 事件，类只用到 addEventListener 和 removeEventListener），按剧本一步一步派发事件。真实浏览器里事件是排队以后异步派发的；这里为了看清顺序，每一步都同步派发。每个回调被调用时，记录里会写出那一刻的状态。

3.1 第 1 版：一个布尔值，两个监听

// 课程写的第 1 版（lifecycle-course.ts）
class LifecycleV1 {
  ready = true // true：可以 draw

  constructor(canvas: EventTarget, private readonly callbacks: Callbacks) {
    canvas.addEventListener('webglcontextlost', (event) => {
      event.preventDefault() // 我想恢复：不调用的话，以后不会有 restored
      this.callbacks.onLost() // 通知后端：这一代的缓存全部作废
      this.ready = false // 标记：不能再 draw
    })
    canvas.addEventListener('webglcontextrestored', () => {
      this.callbacks.restore() // 重新探测能力，建新的 State 和 Manager
      this.callbacks.onReady() // 收尾
      this.ready = true // 可以 draw 了
    })
  }
}

3.2 第 2 版：状态机、先改状态再通知、异常留在监听器里

第 1 版违反了不变量 1（onLost 执行时还说可以画）和不变量 4（异常逃出监听器）。第 2 版改了四处，每处都用「← 」标出来（lifecycle-course.ts:37–101）：

// 课程写的第 2 版（节选）
class LifecycleV2 {
  // ← 改动：一个布尔值分不清丢了、正在恢复、恢复失败、已关闭，换成五个状态
  state: State = 'ready'
  // ← 新增：失败要留下记录，供上层查看（哪一步失败、原始错误是什么）
  lastFailure: { phase: string; error: unknown } | null = null

  // …构造函数注册两个监听；isReady 是 state === 'ready'
  // ← 新增：dispose 时摘掉两个监听；以后的事件一概不处理

  private readonly handleLost = (event: Event): void => {
    if (this.state === 'disposed') return
    event.preventDefault()
    // ← 新增：重复的 lost 事件不再执行一次 onLost
    if (this.state === 'lost') return
    // ← 改动：先改状态，再调用回调。回调执行时看到的 isReady 已经是 false
    this.state = 'lost'
    this.lastFailure = null
    try {
      this.callbacks.onLost()
    } catch (error) {
      // ← 新增：把错误记下来，不让它逃出 DOM 监听器
      this.lastFailure = { phase: 'on-lost', error }
    }
  }

  private readonly handleRestored = (): void => {
    // ← 新增：只有 lost、restore-failed 才接受恢复；其余一律忽略
    if (this.state !== 'lost' && this.state !== 'restore-failed') return
    this.state = 'restoring' // 恢复期间 isReady 是 false
    this.lastFailure = null
    let phase = 'restore'
    try {
      this.callbacks.restore()
      phase = 'on-ready'
      this.callbacks.onReady()
      this.state = 'ready' // 全部成功，最后才改成 ready
    } catch (error) {
      this.state = 'restore-failed' // 和 lost 分开：上层能看出恢复过、但失败了
      this.lastFailure = { phase, error }
      try {
        this.callbacks.onRestoreFailed(error)
      } catch {
        // 通知自己也可能抛错；这一版先吞掉
      }
    }
  }
}

第 2 版对「回调正常」和「回调抛错」两种结局都没问题。第三种结局，回调回头调用了自己，它没有考虑：

3.3 回调返回以后，核对什么

第 2 版的两个错误是同一个原因：外层的 handleRestored 调用回调时，回调里又发生了一次更新的转换（dispose，或者新的 lost）。回调一返回，外层不知道「自己这一轮已经过时了」，照样往下走，最后写下了 ready。这里没有多线程，也没有 async，只是一个函数在执行中途，调用了另一个会改状态的函数。

所以每个回调返回以后，都要先核对「这一轮还算不算数」。拿什么核对？最直接的办法是看状态：我写下的是 restoring，回来以后还是 restoring，就当作没人动过。课程按这个想法写了一版 LifecycleStateCheck（lifecycle-course.ts:109–169），只在第 2 版上加了四行：

// 课程写的「核对状态」版（节选，只列和第 2 版不同的四行）
// handleLost 的 catch：
if (this.state === 'lost') this.lastFailure = { phase: 'on-lost', error }
// handleRestored：restore 返回后、onReady 返回后、catch 里各一次
if (this.state !== 'restoring') return

把 3.2 节那两个剧本换成它来跑：restore 里 dispose，最后是 disposed；restore 里又 lost，最后是 lost。两个都对了（可以在 3.6 节自己选来跑）。那还缺什么？状态只有五个值，中途发生了好几次转换、最后又回到同一个状态时，它就分不出来了。下面这个剧本：onLost 执行到一半，先同步来了一次 restored（restore 抛错，进入 restore-failed），又来了一次 lost（回到 lost，调了第二次 onLost），然后最外层的 onLost 才抛出它自己的错误。

3.4 第 3 版：给每一轮发一个号码牌

状态会重复，可「第几次转换」不会。每次转换开始时把计数器加 1，并把新值抄进局部变量，这就是这一轮的号码牌。回调返回以后，核对号码牌是否还等于计数器：不等，就说明中途发生过更新的转换，不管现在的状态碰巧是什么。第 3 版（lifecycle-course.ts:173–243）：

// 课程写的第 3 版（节选）
class LifecycleV3 {
  // ← 新增：每次转换（lost、开始恢复、dispose）加 1：现在是第几轮
  private transitionVersion = 0

  dispose(): void {
    if (this.state === 'disposed') return
    this.state = 'disposed'
    this.transitionVersion++ // ← 新增：dispose 也算一次转换，正在进行的旧一轮作废
    // …摘掉两个监听
  }

  private readonly handleLost = (event: Event): void => {
    if (this.state === 'disposed') return
    event.preventDefault()
    if (this.state === 'lost') return
    // ← 新增：先把成员加 1，再把新值抄进局部变量。局部变量是号码牌，之后不变
    const version = ++this.transitionVersion
    this.state = 'lost'
    this.lastFailure = null
    try {
      this.callbacks.onLost()
    } catch (error) {
      // ← 改动：号码牌还对得上，这一轮才有资格记录失败
      if (version === this.transitionVersion) this.lastFailure = { phase: 'on-lost', error }
    }
  }

  private readonly handleRestored = (): void => {
    if (this.state !== 'lost' && this.state !== 'restore-failed') return
    const version = ++this.transitionVersion // ← 新增：这一轮恢复的号码牌
    this.state = 'restoring'
    this.lastFailure = null
    let phase = 'restore'
    try {
      this.callbacks.restore()
      // ← 新增：号码牌对不上，这一轮已经作废：立刻退出，更不能写 ready
      if (version !== this.transitionVersion) return
      phase = 'on-ready'
      this.callbacks.onReady()
      if (version !== this.transitionVersion) return // ← 新增：同上
      this.state = 'ready'
    } catch (error) {
      // ← 新增：作废那一轮的错误，不能写进现在的状态
      if (version !== this.transitionVersion) return
      this.state = 'restore-failed'
      this.lastFailure = { phase, error }
      try {
        this.callbacks.onRestoreFailed(error)
      } catch {
        // 这一版先吞掉
      }
    }
  }
}

3.5 真实代码：在第 3 版之上多做了什么

第 3 版把作废那一轮的错误直接 return 掉了，违反了不变量 3 的后半句（不能悄悄丢掉）。真实代码多了一个诊断出口 onSuppressedError：作废那一轮的错误被打包成一份冻结的快照交出去，标明 stale: true，以及「这一轮的号码」和「现在的号码」。它只用来记日志、做监控，不能改状态，也不能重试。另外两处补强：onRestoreFailed 通知自己也抛错时，两个错误都留着；诊断出口本身抛错时，也不让异常逃出监听器（WebGLContextLifecycle.ts:169–189、:227–264、:281–299）：

// WebGLContextLifecycle.ts（节选；注释是课程加的，原文件里的注释更长）
private readonly handleLost = (event: Event): void => {                // :169
  if (this.stateValue === 'disposed') return
  // 放在「重复 lost」判断之前：重复的 lost 事件也照样表示允许恢复
  event.preventDefault()
  if (this.stateValue === 'lost') return
  const version = ++this.transitionVersion
  this.stateValue = 'lost'
  this.failureValue = null
  try {
    this.callbacks.onLost()
  } catch (error: unknown) {
    if (version === this.transitionVersion) {
      // 本轮仍有效：记成当前失败
      this.failureValue = Object.freeze({ phase: 'on-lost', error })
    } else {
      // 本轮已作废：交给诊断出口，不碰现在的状态
      this.reportSuppressedError(error, 'on-lost', version)
    }
  }
}

private readonly handleRestored = (): void => {                        // :227
  if (this.stateValue !== 'lost' && this.stateValue !== 'restore-failed') return
  const version = ++this.transitionVersion
  this.stateValue = 'restoring'
  this.failureValue = null
  let phase: 'restore' | 'on-ready' = 'restore'
  try {
    this.callbacks.restore()
    if (version !== this.transitionVersion) return
    phase = 'on-ready'
    this.callbacks.onReady()
    if (version !== this.transitionVersion) return
    this.stateValue = 'ready'
  } catch (error: unknown) {
    if (version !== this.transitionVersion) {
      // 第 3 版在这里直接 return，错误就没了
      this.reportSuppressedError(error, phase, version)
      return
    }
    this.stateValue = 'restore-failed'
    const failure: WebGLContextFailure = Object.freeze({ phase, error })
    this.failureValue = failure
    try {
      this.callbacks.onRestoreFailed(error)
    } catch (notificationError: unknown) {
      if (version === this.transitionVersion) {
        // 通知自己也失败了：两个错误都留着，不拿后一个覆盖最初的恢复错误
        this.failureValue = Object.freeze({ ...failure, notificationError })
      } else {
        this.reportSuppressedError(notificationError, 'on-restore-failed', version)
      }
    }
  }
}

// 作废那一轮的错误：包成冻结的诊断快照，交给 Backend 提供的观察者   // :281
private reportSuppressedError(
  error: unknown,
  phase: WebGLContextSuppressedError['phase'],
  capturedVersion: number
): void {
  try {
    this.callbacks.onSuppressedError(
      Object.freeze({
        error,
        phase,
        stale: true,
        capturedVersion,
        currentVersion: this.transitionVersion
      })
    )
  } catch {
    // 诊断出口自己也不许抛错：抛出去就又逃出了 DOM 监听器
  }
}

还有一处在类型上：回调写成 onLost(): undefined，不是 (): void（WebGLContextLifecycle.ts:33–50），目的是让 async 函数过不了类型检查。async 函数返回 Promise，号码牌在 Promise 完成之前就核对完了，所有保护都会失效。所以这些回调必须同步执行完。第 30 课 RenderPass.execute 返回 undefined 也是同一个道理。

3.6 自由组合

任选一版、任选一个剧本运行，自己核对 2.6 节的五条不变量：

4. 和 Backend 怎样接：第二层号码牌

回到 1.1 节 Backend 的 restore 回调。它在发布新的一代之前，又自己检查了一遍（WebGL1Backend.ts:83–95）：

// WebGL1Backend.ts:83–95（注释是课程加的）
restore: () => {
  const epoch = this.epoch                  // Backend 自己的号码牌：一个空对象
  const candidate = this.createGeneration() // 先建好，先不发布

  // 三种情况都不能发布：已经关了、中途换过一代、context 又丢了
  if (this.disposedValue || epoch !== this.epoch || this.gl.isContextLost()) {
    candidate.resources.invalidateForContextLoss() // 候选的一代先作废
    candidate.resources.dispose()                  // 再关掉（里面还没有 GPU 对象）

    throw new WebGLContextLostError('publish restored backend')
  }

  this.generation = candidate // 通过了才写字段
},

Lifecycle 已经有号码牌了，为什么 Backend 还要一个 epoch？因为两个号码牌保护的是不同的字段：

  • transitionVersion 只保护 Lifecycle 自己的 stateValue、failureValue。它能阻止旧的一轮写 ready，管不到 Backend 里的 this.generation。
  • restore 回调里写 this.generation = candidate 的是 Backend 自己。要是这时 Backend 已经被关闭，或者 context 又丢了，这一代就不能发布。epoch 在 invalidateGeneration（:344–349）和 dispose（:248）里都会换成新对象。

这是同一个规则用了两次：谁写字段，谁就在写之前核对自己的号码牌。Backend 用对象身份 {} 当号码牌，不用计数器（:52–53），比较的是「是不是同一个对象」，效果一样。

1.3 节卡片里还有一处值得再看。loseContext() 刚返回、事件还没派发时，Lifecycle 的 state 还是 ready，Backend.ready 却已经是 false，调用 Backend 也会抛 WebGLContextLostError。这是因为 ready 和 requireGeneration 都会先问一次 gl.isContextLost()，发现丢了就自己作废这一代（:114–120、:351–368）。Lifecycle 记录的是「已经观察到的事件」（WebGLContextLifecycle.ts:1 的注释），Backend 还要再看一眼「物理上现在怎样」。restore-failed 期间，如果 context 本身没丢，requireGeneration 抛的是带状态名的 WebGLOperationError（:359–361），上层能从错误里看出「恢复失败过」。

5. 和各个 Manager 的关系

把第 14–18 课各节「和 Lifecycle 的关系」放到边角情况里看，每种出错各留下了什么：

  • restore 中途抛错，要不要回滚 GPU 对象？不用。createGeneration 只建 CPU 侧的管理对象：State、ResourceManager 和六个 Manager、Uniforms、SurfaceScope 的构造函数都不创建 GPU 对象，第一次 get 时才创建（第 18 课卡片「建好时 0 个」）。detectWebGL1Capabilities 第一步就抛错时，连这些对象也还没建。如果是 4 节那道检查没通过，候选的一代先 invalidate、再 dispose，里面也没有 GPU 对象要删。懒创建让「恢复到一半失败」没有东西需要回滚。
  • restore-failed 期间，Backend 手里是哪一代？还是丢失前的旧一代，它的 valid 已经是 false（invalidateGeneration 设的），所以 ready 一直是 false。下一次 restored 会从头再建一代，不会复用失败那次的半成品。
  • onLost 抛错，会留下什么？ResourceManager 先置 lost = true、再逐个通知（第 18 课审查第 2 条）。假设第 3 个 Manager 的 invalidateForContextLoss 抛错，后三个就收不到通知；Lifecycle 记下 lastFailure = on-lost，状态保持 lost。之后的恢复照样建全新的一代，旧的一代不会再被用来 draw。可是那三个没收到通知的 Manager，还订阅着 CPU 资源的 onDispose（第 4 课）。后果留作 7.2 节的想一想。
  • 恢复成功以后：新的一代每张表都是空的，第一帧从 CPU 原件重新编译、上传（第 31 课 5.4 节的卡片）。

6. 架构视角：对照 three.js r177

  • 只有一个布尔值，而且恢复时的顺序相反。丢失时先 preventDefault，再把 _isContextLost 设为 true（WebGLRenderer.js:1013–1021）。恢复时先把 _isContextLost 改回 false，再调用 initGLContext 重建（:1023–1035）。如果重建抛错，异常会逃出事件监听器，而 renderer 已经认为自己恢复好了，下一帧就在半成品上画。这正是 3.1 节第 1 版的两个问题，只是顺序反了过来。它也没有 restore-failed 状态，没有重入保护。
  • 丢失时不调用任何清理。onContextLost 只改一个布尔值，资源的作废推迟到 initGLContext 整体重建时，WebGLProperties、WebGLAttributes 这些表都会换成新的（WebGLRenderer.js:403–425）。所以在 three.js 里，丢失到恢复之间没有「onLost 抛错」这一格。
  • 取舍。three.js 的做法简单，对绝大多数应用够用：context 丢失本来就少见，回调里重入就更少见了。本项目为此单独写了一个类，换来的是：恢复失败看得见、关闭以后不会被复活、旧回调改不了新状态，而且每种情况都有测试。代价是 300 行代码（一大半是注释）和 12 组单元测试（其中两组各跑两种情况），以及第 7 节要讨论的问题：这些保护里，有一部分现在还用不上。

7. 审查视角

7.1 对照表格找出来的

  1. 表里有几格没有测试。按 2.4 节的表逐格对照单元测试，下面几格找不到对应的用例（我在测试文件里搜过 restore-failed、Once 等写法）：restore-failed 状态再收到 restored、这次恢复成功；restore-failed 状态收到 lost；dispose 以后保留最后一次 lastFailure（源码注释承诺了这一点，:114）；3.3 节那个「回到同一个状态」的剧本。第一格最重要：第 13 课说过「restore-failed 时再来一次 restored 可以再试」，这是唯一能从失败里走出来的路，却没有测试守着。1.3 节的卡片在真实浏览器里走的是另一条路：restore-failed 之后先来了 lost，又回到了 lost。
  2. 大部分重入保护，现在的 Backend 还用不上。五个回调都不会回头调用 Lifecycle，onRestoreFailed 是空的，真实浏览器又是排队派发事件。真正会发生的，只有「restore 或 onReady 抛错」这一格（1.3 节）。号码牌和 onSuppressedError 防的是以后接上 Engine 通知（1.2 节那条链）、以及测试里手动派发事件的情况。它们不是错误，但读代码时要知道哪些路径现在是活的。
  3. 上层只能轮询失败。Engine 用 getter 把 Backend 的 lastFailure 暴露出去（engine.ts:167–170），没有人在失败时被主动通知。第 13 课审查视角问的「上层怎样知道该提示用户」，现在的答案是：每帧或定时去读 lastBackendFailure。
