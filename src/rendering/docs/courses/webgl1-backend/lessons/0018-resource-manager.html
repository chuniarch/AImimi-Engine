backend ⑥：一代 GPU 资源的组合根——WebGL1ResourceManager

第 15、16、17、29、27 课各讲了一个 Manager：program、buffer、顶点输入、二维纹理、cubemap、离屏目标。每个 Manager 都管得很好，可它们要一起工作：顶点输入的 VAO 记着 GeometryManager 的 buffer、按 ProgramManager 的 program 配置；context 丢了，六个都得知道；Backend 关闭时，六个要按一个安全的顺序删。WebGL1ResourceManager 只有 228 行，不画图、不上传、不缓存任何资源，专门回答「谁来建、谁来接线、谁来借出、谁来通知、按什么顺序关」。这一课先看一代里到底有哪些 GPU 对象，再写一个让 Backend 自己拿着六个 Manager 的第 1 版，看它在哪几处出事，最后读真实代码。

和你的目标的关系 —— HW1 的阴影会多出一个 RenderTarget 和一张 Mary 的颜色贴图，HW3 会多出 GBuffer；它们的 GPU 对象全都住在这一课讲的「一代」里。切换场景、退出 HW2、context 丢失再恢复时，这些对象是怎样被一次性忘掉或删掉的，答案都在 ResourceManager。
默认你已经会的：① 第 4 课：CPU 资源和每个 context 的 GPU 表示是一对多，Manager 用 Map<CPU 对象, entry> 按对象身份缓存；② 第 13 课第 2 节：「一代」——context 丢失后旧 handle 全部作废，恢复后建一套新的 Manager；③ 第 15 课 2.6 节：beforeDelete 钩子——ProgramManager 删 program 之前，先调一个从外面递进来的函数，让顶点输入放掉相关的 VAO；④ 第 16 课 4.4 节：OES 顶点输入按「Geometry、program」两层缓存 VAO；⑤ 第 17、29、27 课：二维纹理、cubemap、离屏目标三个 Manager 各自的 get、release、invalidateForContextLoss、dispose；⑥ 第 30 课 8.2 节：Renderer.dispose 先 Pipeline、后 Backend。如果其中哪一条其实没懂，告诉我，我先补那一块。第 19 课不是前置。
这一课从零讲的：一代里有哪些 GPU 对象、谁拥有谁借用；「组合根」是什么，为什么 Manager 之间互不 import；六个 getter 和 assertAvailable；一次丢失怎样通知到全部六个；关闭顺序怎么定、为什么已经有 beforeDelete 还要排顺序；失败后停在原地、重试从失败那一步接着做；关闭途中 context 丢了怎么办；它和 Backend、Lifecycle 怎样接；对照 three.js。

1. 原始输入：一代里有什么

1.1 Backend 在哪里用到它

Backend 每建「一代」（第 13 课），就新建一个 ResourceManager；之后 draw、丢失、关闭都经过它（WebGL1Backend.ts:259–305）：

// WebGL1Backend.ts（节选，注释是课程加的；工作区版本）
// :259–305 建一代：能力快照、State、ResourceManager……
private createGeneration(): Generation {
  const capabilities = detectWebGL1Capabilities(this.gl) // 这一代的能力
  const state = new WebGL1State(this.gl)

  // 六个 Manager 由它一次建好；三样东西都属于这一代
  const resources = new WebGL1ResourceManager(this.gl, capabilities, {
    invalidateState: () => {
      state.invalidate() // 任何 Manager 直接动了 GL，都让这一代的 State 忘掉缓存
    }
  })
  // …
  const uniforms = new WebGL1Uniforms(
    this.gl,
    capabilities.maxTextureUnits,
    (texture) => resources.cubeTextures.get(texture),       // 每次都经过 getter
    (source, uniformName) => {
      if (source instanceof Texture2D) return resources.textures2D.get(source).handle
      // …
      return resources.renderTargets.resolveSampledColor(source)
    }
  )
  // …
}

// :208–217 每次 draw：从它借出 Manager
const program = generation.resources.programs.get(material.shaderModule)
const buffers = generation.resources.geometries.get(geometry)
// …
generation.resources.vertexInputs.bind(geometry, buffers, program)

// :331–336 context 丢了：整代作废
private invalidateGeneration(): void {
  this.epoch = {}
  this.generation.valid = false
  this.generation.state.invalidate()
  this.generation.resources.invalidateForContextLoss()
}

// :242–256 Backend 关闭
dispose(): void {
  // …
  this.generation.resources.dispose()
  this.cleanupComplete = true
}

四个用法对应 ResourceManager 的四件事：构造（建六个 Manager 并接线）、借出（六个 getter）、通知丢失（invalidateForContextLoss）、关闭（dispose）。

1.2 一代里到底有哪些 GPU 对象

先看实物。下面这张卡片在你的浏览器里建一代，给 gl 套一层记账的代理，数一数「刚建好时」和「用过一次以后」各有哪些 GPU 对象；用过一次是指：取一个 program、一个三角形的 buffer、配一次顶点输入、一张 1 × 1 的颜色贴图、一个 4 × 4 的离屏目标。最后关闭，看删除的顺序。

我在 Chrome 里跑的结果是：

刚建好：create 0 次
用过一次：create shader#1、shader#2、program#1，
          delete shader#1、shader#2（第 15 课：链接后只留 program），
          create buffer#1、vao#1、texture#1（颜色贴图），
          create framebuffer#1、texture#2（离屏目标的颜色附件）
关闭：delete vao#1 → framebuffer#1 → texture#2 → texture#1 → buffer#1 → program#1

把这些对象按「谁拥有、谁借用」排一排：

Manager拥有（负责删）借用别人的讲过的课
ProgramManagerprogram#1—第 15 课
GeometryManagerbuffer#1（顶点、索引）—第 16 课
Texture2DManagertexture#1—第 29 课
CubeTextureManagercubemap 纹理（这张卡片没用到）—第 17 课
RenderTargetManagerframebuffer#1、texture#2（以及深度 renderbuffer）—第 27 课
VertexInputManager（OES 策略）vao#1vao#1 里记着 buffer#1；它的配置按 program#1 的 location 来第 16 课

六个 Manager 里，只有顶点输入借用别人的东西。整个 ResourceManager 的设计，有一半是围绕这一条借用关系展开的。

2. 需求

#需求具体场景
①六个 Manager 一起建：同一个 gl、同一份能力快照、同一个 invalidateState；建的时候不碰 GPUBackend 每代建一次；恢复时要很快建出新的一代（第 13 课）
②接线：删 buffer、program 之前，先删掉借用它们的 VAO；但 GeometryManager、ProgramManager 不应该认识顶点输入调试时换 shader，旧 program 被删（第 15 课 2.6 节）
③借出：Backend 每次 draw 都要拿 Manager；关闭以后、丢失以后不能再拿到退出 HW2 后，残留的回调又去要 program
④丢失：六个 Manager 都要「只忘不删」，一个都不能漏第 27 课的卡片：没收到通知的 RenderTargetManager 恢复后交出一个已经失效的 FBO
⑤关闭：按「先借用方、后所有者」的顺序删；某一步失败就停下、报错，之后可以重试，重试不重复已经做完的步骤Engine 退出 HW2（第 30 课 8.2 节：Renderer 先关 Pipeline，再关 Backend）
⑥关闭途中 context 丢了：剩下的步骤改成只忘不删关页面、显卡驱动重置恰好发生在清理中途

3. 第 1 版：Backend 自己拿着六个 Manager

最直接的写法：六个 Manager 是公开字段，各建各的；关闭时挨个 dispose。这段是课程写的，项目里没有，下面的卡片跑的就是它：

// 课程写的第 1 版（assets/build/resource-course.ts）
export class ManagersV1 {
  readonly programs: WebGL1ProgramManager
  readonly geometries: WebGL1GeometryManager
  readonly textures2D: WebGL1Texture2DManager
  readonly cubeTextures: WebGL1CubeTextureManager
  readonly renderTargets: WebGL1RenderTargetManager
  readonly vertexInputs: WebGL1VertexInputManager

  constructor(
    gl: WebGLRenderingContext,
    capabilities: WebGL1Capabilities,
    hooks: ManagersV1Hooks
  ) {
    // 没有 beforeDelete：删 program、删 buffer 之前，没人通知顶点输入
    this.programs = new WebGL1ProgramManager(gl, { invalidateState: hooks.invalidateState })
    this.geometries = new WebGL1GeometryManager(gl, capabilities, {
      invalidateState: hooks.invalidateState
    })
    this.textures2D = new WebGL1Texture2DManager(gl, capabilities, hooks)
    this.cubeTextures = new WebGL1CubeTextureManager(gl, capabilities, hooks)
    this.renderTargets = new WebGL1RenderTargetManager(gl, capabilities, hooks)
    this.vertexInputs = createWebGL1VertexInputManager(gl, capabilities, hooks)
  }

  /** context 丢了：逐个通知。前提是调用者记得调用它。 */
  invalidateForContextLoss(): void {
    for (const manager of this.all()) manager.invalidateForContextLoss()
  }

  /** 尽力而为：一个失败了，接着清理下一个，最后把第一个错误抛出去。 */
  dispose(): void {
    let firstError: unknown = null
    for (const manager of this.all()) {
      try {
        manager.dispose()
      } catch (error) {
        firstError ??= error
      }
    }
    if (firstError !== null) throw firstError
  }

  /** 声明顺序：借用 buffer 和 program 的顶点输入排在最后。 */
  private all() {
    return [
      this.programs,
      this.geometries,
      this.textures2D,
      this.cubeTextures,
      this.renderTargets,
      this.vertexInputs
    ]
  }
}

看起来没毛病，而且每个子 Manager 自己都很严谨。先看第一处：

第 1 版一共有四处问题，后面几节逐个对上真实代码：

第 1 版后果真实代码在哪里补
Manager 之间没接线删 program 时 VAO 没人删，一直占着（卡片）构造时接 beforeDelete（第 4 节）
字段公开，谁都能一直拿着用关闭后、丢失后照样能拿到 Manager；物理丢失只有被访问的那一个 Manager 自己发现六个 getter + assertAvailable（第 5 节）

关闭「尽力而为」，借用方排在最后顶点输入清理失败时，buffer 和 program 已经被删了，VAO 还拿着它们先借用方的固定顺序、失败停在原地、游标重试（第 7 节）

4. 真实代码 ①：构造——组合根

4.1 代码

// WebGL1ResourceManager.ts:74–120（注释是课程加的）
constructor(
  gl: WebGLRenderingContext,
  capabilities: WebGL1Capabilities, // 这一代的能力快照，六个 Manager 共用
  hooks: WebGL1ResourceManagerHooks // { invalidateState }，接到这一代的 State
) {
  // 已经丢失的 context 上不组装：建出来也只能立刻作废
  if (gl.isContextLost()) throw new WebGLContextLostError('create resource manager')

  this.gl = gl

  // 顶点输入：按能力二选一（有 OES 扩展用 VAO，没有就手动接线，第 16 课）
  this.vertexInputsValue = createWebGL1VertexInputManager(gl, capabilities, hooks)

  // 接线：GeometryManager 删 buffer 之前，先请顶点输入放掉这个 Geometry 的 VAO
  this.geometriesValue = new WebGL1GeometryManager(gl, capabilities, {
    invalidateState: hooks.invalidateState,
    beforeDelete: (geometry) => {
      this.vertexInputsValue.releaseGeometry(geometry)
    }
  })

  // 接线：ProgramManager 删 program 之前，先请顶点输入放掉按它配置的 VAO
  this.programsValue = new WebGL1ProgramManager(gl, {
    invalidateState: hooks.invalidateState,
    beforeDelete: (program) => {
      this.vertexInputsValue.releaseProgram(program)
    }
  })

  // 三个纹理类 Manager 不借用任何人，只拿 invalidateState
  this.textures2DValue = new WebGL1Texture2DManager(gl, capabilities, hooks)
  this.cubeTexturesValue = new WebGL1CubeTextureManager(gl, capabilities, hooks)
  this.renderTargetsValue = new WebGL1RenderTargetManager(gl, capabilities, hooks)

  // 先结束借用方，再结束被借用的 GPU 资源所有者（第 7 节）
  this.disposalOrder = Object.freeze([
    this.vertexInputsValue,
    this.renderTargetsValue,
    this.textures2DValue,
    this.cubeTexturesValue,
    this.geometriesValue,
    this.programsValue
  ])
}
  • 构造时不碰 GPU。六个 Manager 的构造函数都不创建 GPU 对象，program、buffer、纹理、FBO、VAO 都是第一次 get 时才建（1.2 节的卡片：建好时 create 0 次）。所以恢复时建一代很快，也不会在构造中途失败、留下一半 GPU 对象。
  • 为什么先建顶点输入？两个钩子是闭包，里面写的是 this.vertexInputsValue，要到真正删除时才读这个字段。严格说先建谁都行，只要构造过程中不发生删除；先建它，读代码的人一眼看出「后面两个 Manager 依赖它」。
  • disposalOrder 用 Object.freeze 冻结。顺序是这个类最重要的约定之一，冻结以后谁也不能在运行时往里插、改顺序。

4.2 谁 import 谁：为什么需要「组合根」

我逐个看了 webgl1 目录下这几个文件顶部的 import（只看它们之间的）：

文件import 了哪些 Manager
WebGL1GeometryManager.ts无
WebGL1ProgramManager.ts无
WebGL1Texture2DManager.ts、CubeTextureManager.ts、RenderTargetManager.ts无（只用共享的 TextureUploadSupport）
WebGL1OESVertexInputManager.ts、ManualVertexInputManager.ts只 import type 了 Geometry、Program 两个 Manager 交出来的结果类型，不引用它们的类
WebGL1ResourceManager.ts全部六个
WebGL1Backend.ts只有 ResourceManager（外加 State、Uniforms、SurfaceScope、Lifecycle）

这种「只有一个地方认识所有零件，并负责把它们装起来、接好线」的写法叫组合根 (composition root)。零件只声明自己需要什么（GeometryManager 说「删除之前，我会调用 beforeDelete，如果有人给了的话」），不去 import 别的零件。好处是：

  • GeometryManager 可以单独测试、单独使用（它的单元测试就不带顶点输入，beforeDelete 是可选的 ?，GeometryManager.ts:50）。
  • 换掉顶点输入的实现（OES 或手动，甚至以后的 WebGL2 VAO），只改组合根一处。
  • 依赖关系全写在一个构造函数里：想知道「删 buffer 前会发生什么」，看 ResourceManager 的第 93–98 行就够了，不用在六个文件之间来回找。

4.3 两种钩子，两种规矩

invalidateStatebeforeDelete
给谁六个 Manager 都给，同一个函数只给 GeometryManager、ProgramManager
做什么让这一代的 State 忘掉缓存（第 14 课），因为 Manager 直接动了 GL 绑定真正的清理：请顶点输入删掉相关 VAO
能不能抛错不能（ResourceManager.ts:14–22 的注释：只改 CPU 缓存标记，不发 GL 命令、不抛错）。它常在 finally 里调用，抛错会盖住原来的异常可以。抛错就是「屏障」：调用方停下，不删 buffer / program，保留记录供重试（第 15 课 2.6 节）
为什么写成闭包类型要求返回 undefined（块体 { … } 不返回值）；直接传 this.vertexInputsValue.releaseGeometry 会丢掉 this

5. 真实代码 ②：借出——六个 getter

// WebGL1ResourceManager.ts:122–159、:217–227（节选，注释是课程加的）
get programs(): WebGL1ProgramManager {
  this.assertAvailable() // 每次借出之前都检查
  return this.programsValue
}
// … geometries、textures2D、cubeTextures、renderTargets、vertexInputs 写法相同

private assertAvailable(): void {
  // 关闭已经开始（哪怕清理失败了）：不许开始新工作
  if (this.closing) {
    throw new WebGLBackendDisposedError('access resource manager')
  }

  // 这一代已经作废，或者 context 物理上已经丢了（可能比 DOM 事件早）
  if (this.lost || this.gl.isContextLost()) {
    this.invalidateForContextLoss() // 一个入口发现，六个全部作废
    throw new WebGLContextLostError('access resource manager')
  }
}
  • 为什么不直接公开字段？公开字段谁都能一直拿着用；getter 让「借出」变成一个动作，每次都能检查这一代还能不能用。Backend 的解析闭包也是每次 draw 都写 resources.cubeTextures.get(…)，不把子 Manager 存在自己的变量里（1.1 节），所以每次 draw 都经过这道检查。
  • 物理丢失：一个入口发现，六个全部作废。context 可能已经丢了，但 webglcontextlost 事件还没派发（第 13 课）。这时 Backend 无论访问哪个 getter，都会先把六个 Manager 一起作废。第 1 版只能靠每个 Manager 在自己的 get 里各自发现，没被访问的那几个就不知道（第 9 节的卡片对比了这两种情况）。
  • 它收不回已经借出去的引用。注释写得很清楚（:40–42）：「Getter 不是 JavaScript 引用撤销机制」。如果有人提前把 resources.geometries 存进变量，之后 getter 再拒绝也管不到它；好在每个子 Manager 自己也会检查 disposed 和 lost，这是第二道防线。

6. 真实代码 ③：丢失——一次通知六个

// WebGL1ResourceManager.ts:171–179（注释是课程加的）
invalidateForContextLoss(): void {
  if (this.lost) return // 只做一次；后面再调用直接返回

  this.lost = true // 永久：恢复事件不会把它改回 false

  // 按关闭的顺序逐个通知；每个子 Manager 只丢记录、退订，不发 GL 命令
  for (const manager of this.disposalOrder) {
    manager.invalidateForContextLoss()
  }
}
  • 只忘不删。旧 context 上的 handle 已经全部作废，对它们调用 delete 没有意义；子 Manager 只清空自己的表、取消对 CPU 资源的订阅（不然 Geometry 释放时还会回调一个已经作废的 Manager）。
  • 永久。恢复以后 gl.isContextLost() 又是 false，但这一代不复活，Backend 会新建一代（第 9 节）。这和每个子 Manager 的 lost 标记是同一个规矩。
  • 谁调用它。两个入口：Lifecycle 收到 lost 事件后经 Backend.invalidateGeneration 调用；或者 assertAvailable、dispose 自己发现物理丢失时调用。

7. 真实代码 ④：关闭

// WebGL1ResourceManager.ts:197–215（注释是课程加的）
dispose(): void {
  // 正在关闭（同步重入）或者已经全部做完：直接返回
  if (this.disposing || this.disposalIndex === this.disposalOrder.length) return

  this.closing = true   // 第一次调用就置上：从此不再借出 Manager，失败了也不恢复
  this.disposing = true

  try {
    while (this.disposalIndex < this.disposalOrder.length) {
      // 每一步之前都看一眼：context 中途丢了，剩下的改成只忘不删
      if (this.gl.isContextLost()) this.invalidateForContextLoss()

      const manager = this.disposalOrder[this.disposalIndex]!
      manager.dispose()        // 抛错：下一行不执行，游标停在这一步，错误原样往外传
      this.disposalIndex += 1  // 只有这一步成功了才前进
    }
  } finally {
    this.disposing = false     // 出错也复位，调用者处理完异常可以再调一次
  }
}

7.1 顺序怎么定

顺序是 vertexInputs → renderTargets → textures2D → cubeTextures → geometries → programs。先列出六个 Manager 之间真正的借用关系：

谁引用了谁的 GPU 对象对顺序的要求
vertexInputs 的 VAOgeometries 的 buffer、programs 的 program（配置按它的 location）必须在 geometries、programs 之前
renderTargets 的 FBO只引用自己建的附件纹理、renderbuffer自己内部先删 FBO 再删附件；对别人没有要求
textures2D、cubeTextures谁都不引用没有要求

所以硬性的只有一条：顶点输入在 buffer 和 program 之前。三个纹理类排在中间，彼此的先后只是约定。

已经有 beforeDelete 了，为什么还要排顺序？确实，就算把顺序反过来，GeometryManager 删每个 buffer 之前也会通过 beforeDelete 先删掉相关 VAO。固定「借用方在前」仍然有三个好处：

  1. 一次删完，钩子变成空操作。vertexInputs.dispose 一次删掉全部 VAO；之后 geometries、programs 的 beforeDelete 再调用 releaseGeometry / releaseProgram 时，顶点输入已经关闭，直接返回（OESVertexInputManager.ts:163–164）。
  2. 不依赖一个可选的钩子。beforeDelete 是可选的；关闭的正确性不该建立在「别人记得传了这个函数」上。
  3. 失败时有屏障。借用方的清理失败了，就停下来，不去删它还引用着的东西。这一条最重要，下一节用卡片看。

同一条规则「先放手，再删除」在三个粒度上都出现：ResourceManager 的 disposalOrder（Manager 之间）、beforeDelete（单个 Geometry 或 program）、RenderTargetManager 内部先删 FBO 再删附件（单个目标）。

7.2 屏障与重试

先说明一点：真实的 gl.deleteBuffer 这类调用不会抛错。会让某一步清理失败的，是钩子、退订 CPU 资源时的监听器、Manager 自己的代码缺陷，或者手动顶点输入策略在 unbind 里读到别人留下的 GL 错误码。下面的卡片用注入错误来模拟「顶点输入这一步失败了」。

第 1 版这里的问题不是「最后清理不干净」：重试一次，它也能把 VAO 删掉。问题在失败和重试之间：GeometryManager 以为 buffer 已经删了，isBuffer 也说 false，可 VAO 还拿着它，显存没有释放，用这个 VAO 照样画得出图（卡片里画出了紫色）。如果调用者没有重试，这块显存就一直被一个「已经删除」的 buffer 占着，任何记账都看不到它。真实代码停在第一步，所有对象都还活着、记录都还对得上，重试时从顶点输入接着做，每个对象只删一次。

游标 disposalIndex 只在某一步正常返回后才加一，所以重试不会重复已经成功的步骤。第 30 课的 RenderPipeline.dispose 用的是同一个思路（成功一个 shift 一个）；Renderer、Backend、ResourceManager、各个子 Manager 一层套一层，每一层都把「做到哪了」记在自己身上，上一层只要再调一次 dispose。

7.3 关闭途中 context 丢了

每一步之前都检查一次 gl.isContextLost()：丢了就先 invalidateForContextLoss（六个全部只忘不删），再继续走完剩下的 dispose。子 Manager 的 dispose 看到自己已经 lost，就不发 delete 命令（比如 RenderTargetManager.ts:388–402）。

9. 和 Lifecycle 的关系

第 13 课讲过 WebGLContextLifecycle 的两件事：丢失时作废一代，恢复时建新一代。落到 ResourceManager 上：

丢失：canvas 的 webglcontextlost
      → Lifecycle.onLost → Backend.invalidateGeneration()
      → resources.invalidateForContextLoss()          （第 6 节）
      → 六个子 Manager 各自 invalidateForContextLoss：清表、退订，不 delete

恢复：canvas 的 webglcontextrestored
      → Lifecycle 调用 restore → Backend.createGeneration()
      → 重新探测能力 → new WebGL1ResourceManager(…)   （新的一代，表全是空的）
      → 下一次 draw：按 CPU 对象身份懒创建，从仍然活着的 Geometry、Texture 等重新上传
         离屏目标只能新建空存储，内容要由生产者重画（第 27 课）

three.js 先删 buffer、后删 VAO 也能工作：它在每帧结束时把绑定记录重置，删 VAO 紧跟在删 buffer 后面，中间不会有 draw，buffer 成为「僵尸」的时间极短（课程备忘里实测过僵尸 buffer 的现象）。本项目选「先放手、再删除」，是为了让每一步失败时都有一个干净的停顿点，而不是依赖「两步之间没人用它」这个时间上的巧合。

11. 审查视角

11.1 重试只和每一步一样可靠

ResourceManager 的注释把「当前步骤内部的部分清理和重试安全」交给各个 Manager（:189–191）。可六个子 Manager 的 dispose 写法并不一样：GeometryManager、ProgramManager、Texture2DManager 的 dispose 没有「调过一次就直接返回」的开关，某个条目清理失败就留在表里，下次 dispose 接着处理；CubeTextureManager 和 RenderTargetManager 一进来就置 disposed、先把表清空再逐个删，删到一半抛错，剩下的对象就没人记得了（找茬题 19，第 29 课 12.1 节、第 27 课第 7 节讨论过）。放到 ResourceManager 里看，后果更隐蔽：

重试时 RenderTargetManager.dispose 看到 disposed 已经是 true，直接返回；ResourceManager 以为这一步成功了，游标前进，最后报告「全部完成」，FBO 和它的颜色附件却永远留在 GPU 上。修法是让这两个 Manager 也改成 Texture2DManager 那样：用 closing 标记拒绝新工作，dispose 不早退，删成功的才移出表。

11.2 通知丢失时，前提是没有一个会抛错

invalidateForContextLoss 先置 lost = true，再逐个通知。如果第 2 个子 Manager 的 invalidateForContextLoss 抛了错，后面四个就收不到通知；而第二次调用会因为 lost 已经是 true 直接返回，再也补不上。现在六个子 Manager 的这个方法都不发 GL 命令、只调用不许抛错的 invalidateState，所以契约上成立；但这个前提只写在注释里（:168），没有代码兜底。
