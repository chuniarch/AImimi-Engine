scene ①：Transform 与 SceneNode——一个矩阵什么时候该重算

每个物体画出来之前，都要先知道它的世界矩阵：把它从自己的坐标系搬到世界坐标系的那个 4×4 矩阵。这一课逐个函数读 Transform（保存局部的平移、旋转、缩放）和 SceneNode（把祖先的变换逐层组合起来），看它们怎样做到「不每帧全部重算，却永远不读到过期的矩阵」，以及树结构怎样保证「要么全改，要么不改」。

和你的目标的关系 —— 将来的 RenderListBuilder（Task 16）会对每个 Mesh 调用 copyWorldMatrixTo，拿到的就是 DrawSubmission 里的 worldMatrix，也就是第 19 课 WebGL1Uniforms 上传的 uModel。这一课讲清这个矩阵从哪来、什么时候重算、为什么一定是最新的。

0. 热身：前几课还记得吗

1. 设计问题：世界矩阵依赖三样东西

一个节点的世界矩阵 = 父节点的世界矩阵 × 自己的局部矩阵。所以它依赖三样东西：自己的平移、旋转、缩放（TRS）、父节点的世界矩阵、自己挂在谁下面。任何一样变了，缓存的世界矩阵就过期了。

最省事的做法是每帧把所有节点全部重算一遍——three.js 默认就是这样（第 8.1 节）。本项目选了另一条路：谁被读，就只检查谁；三样东西都没变，就直接用缓存。要做到这一点，每样东西都得有一个「变了没有」的记录：

2. Transform：保存局部 TRS，懒计算局部矩阵

2.1 字段一览

字段是什么谁会改它
positionValue、rotationValue、scaleValue（:106–112）三个 gl-matrix 的 vec3，Float32 存储；旋转单位是弧度只有三个 setter
localMatrixValue（:115）按当前 TRS 算出来的局部矩阵缓存只有 updateLocalMatrixIfNeeded
localMatrixDirty（:126）缓存是不是落后于 TRSsetter 设成 true；重算后变回 false

2.2 三个 setter：先量化，再比较，真变了才记账

setPosition(position: Vec3Tuple): void {                             // Transform.ts:186–192
  if (!setFloat32ComponentsIfChanged(this.positionValue, position)) {
    return                                         // 存储值没变：不动 dirty，也不加 version
  }
  this.invalidateLocalMatrix()                     // 真变了：记一次账
}

function setFloat32ComponentsIfChanged(current: vec3, next: Vec3Tuple): boolean {   // :36–50
  const nextX = Math.fround(next[0])               // ① 先按 Float32 量化：0.1 → 0.10000000149011612
  const nextY = Math.fround(next[1])
  const nextZ = Math.fround(next[2])
  const unchanged =                                // ② 再和已经存着的 Float32 值精确比较
    Object.is(current[0], nextX) && Object.is(current[1], nextY) && Object.is(current[2], nextZ)
  if (unchanged) return false
  vec3.set(current, nextX, nextY, nextZ)           // ③ 写入的正是刚才比较用的那组量化值
  return true
}

private invalidateLocalMatrix(): void {            // :241–244
  this.localMatrixDirty = true                     // 缓存过期
  this.versionValue += 1                           // 发生了一次真实变化
}
作用修改局部 TRS；只有存储值真正变化时，才让局部矩阵失效、让 version 加一。
所在层第一层 scene（纯 CPU，不知道 GL）。调用者是应用代码或将来的动画系统。
为什么这样设计version 是给 SceneNode 用的「变了没有」的信号。如果「设了一个一模一样的值」也加一，子孙节点就会白白重算。量化必须在比较之前：内部存的是 Float32，拿 JavaScript 的 0.1（binary64）直接和存着的 0.10000000149011612 比，永远不相等，每次都会误报变化（注释在 :15–35）。
校验没有运行时校验。只靠 TypeScript 类型保证是三个数；NaN、Infinity、长度不对的数组都会被存进去（第 8.2 节的审查发现）。
状态变化真变化时：对应的 vec3、localMatrixDirty = true、version + 1。没变化时：什么都不改。
生命周期无。Transform 是 SceneNode 独占的组成部分（第 5 课答疑：真正的组合），随节点一起被回收。
顺序能不能换「量化 → 比较 → 写入」不能换：先写入再比较，就永远是「没变化」；比较用原值、写入用量化值，比较语义和存储语义就分家了（:30–31 的注释）。

Object.is 而不是 ===：它把两个 NaN 看成相同，又区分 +0 和 -0，这样「重复设 NaN」不会反复加 version，「0 改成 -0」也算一次真实变化（:33–34）。

2.3 三个 getter：返回新的数组，不交出内部的 vec3

position 每次都 new 一个 [x, y, z]（:148–150）。调用者拿到的只是一份拷贝，改它不会绕过 setter、不会漏掉 version。读回来的值是 Float32 量化之后的：设 0.1，读到 0.10000000149011612（类注释 :65–67）。

2.4 copyLocalMatrixTo：懒计算，只在需要时重算

copyLocalMatrixTo(out: mat4): void {               // Transform.ts:229–232
  this.updateLocalMatrixIfNeeded()                 // 过期了才算
  mat4.copy(out, this.localMatrixValue)            // 交出去的是拷贝
}

private updateLocalMatrixIfNeeded(): void {        // :253–274
  if (!this.localMatrixDirty) return               // 没过期：一次矩阵运算都不做
  const rotationQuaternion = quat.create()
  quat.fromEuler(rotationQuaternion,               // gl-matrix 要角度，这里存的是弧度
    this.rotationValue[0] * RADIANS_TO_DEGREES, …)
  mat4.fromRotationTranslationScale(this.localMatrixValue, rotationQuaternion,
    this.positionValue, this.scaleValue)           // local = T · R · S
  this.localMatrixDirty = false                    // 只清 dirty，不动 version
}

记号：T、R、S 分别是平移、旋转、缩放矩阵，作用在列向量上，所以 local = T · R · S 的意思是先缩放、再旋转、最后平移。R 本身由三个欧拉角组成。Rx(θ) 表示绕 x 轴转 θ 弧度（右手系），Ry、Rz 同理。gl-matrix 3.4 的 fromEuler 没有「顺序」参数，按它的公式展开是 

R = Rz(z) · Ry(y) · Rx(x)        先绕 x 轴，再绕 y 轴，最后绕 z 轴（都是固定的坐标轴）

例：rotation = [90°, 90°, 0]。原来的 x 轴 (1, 0, 0)：Rx 不动它，Ry(90°) 把它转到 (0, 0, −1)，Rz = 单位矩阵。所以矩阵的第 0 列是 (0, 0, −1)（卡片 F）。three.js 默认的 'XYZ' 顺序是 R = Rx · Ry · Rz，同样三个数会得到 (0, 1, 0)——第 8.1 节再说这对搬场景数据意味着什么。

2.5 dirty 与 version：为什么是两个字段，而不是一个

操作localMatrixDirtyversion这一步算不算矩阵
新建 Transformtrue0不算
第一次 copyLocalMatrixTotrue → false0算一次（单位矩阵）
setPosition、setRotation、setScale 各一次true1 → 2 → 3一次都不算
再 copyLocalMatrixTotrue → false3三次修改合并成一次重算
再 copyLocalMatrixTofalse3不算，直接复制

这张表来自 Transform 的类注释（:78–95）。关键在最后一句：dirty 会被任何一个读矩阵的人清掉，version 不会（:97–98）。假设有两个子系统都关心这个 Transform：A 读了矩阵，dirty 变回 false；B 再来看 dirty，就会以为什么都没变。所以 SceneNode 不能看 dirty，只能记下「上次看到的 version」，下次比较——version 只增不减，谁读都不影响它。dirty 是 Transform 自己的缓存开关，version 是给外面看的变化通知。

3. SceneNode 的世界矩阵：拉取式更新

3.1 四个缓存字段

字段记的是什么用来发现
worldMatrixValue（:86）上次算好的世界矩阵——
observedTransformVersion（:95）上次算的时候，自己 Transform 的 version；初始 −1自己的 TRS 变了
observedParentWorldVersion（:104）上次算的时候，父节点的 worldVersion；没有父节点记 −1父节点的矩阵变了
worldMatrixDirty（:63）结构有没有变过；初始 true换了父节点、被摘下
worldVersionValue（:119）自己真正重算的次数给子节点当「父节点变了没有」的信号

初始值是故意选的：Transform 的 version 从 0 开始，observed 从 −1 开始，第一次比较必然不相等，所以第一次读一定会算。

3.2 updateWorldMatrix：先更新父节点，再比较三个记录

updateWorldMatrix(): void {                                        // SceneNode.ts:353–381
  let parentWorldVersion = -1
  if (this.parentValue !== null) {
    this.parentValue.updateWorldMatrix()          // ① 先让父节点（递归到根）变成最新
    parentWorldVersion = this.parentValue.worldVersionValue   // ② 再读它的版本
  }
  const transformVersion = this.transform.version
  const cacheIsCurrent =                          // ③ 三个记录都没变？
    !this.worldMatrixDirty &&
    this.observedTransformVersion === transformVersion &&
    this.observedParentWorldVersion === parentWorldVersion
  if (cacheIsCurrent) return                      //    是：直接用缓存，worldVersion 不变

  this.transform.copyLocalMatrixTo(this.worldMatrixValue)          // ④ out = local
  if (this.parentValue !== null) {
    mat4.multiply(this.worldMatrixValue, this.parentValue.worldMatrixValue, this.worldMatrixValue)
  }                                               // ⑤ out = parent world × out（原地）
  this.observedTransformVersion = transformVersion                 // ⑥ 记下这次看到的
  this.observedParentWorldVersion = parentWorldVersion
  this.worldMatrixDirty = false
  this.worldVersionValue += 1                     // ⑦ 对子节点宣布：我变了
}
作用保证 worldMatrixValue 反映最新的祖先链和局部 TRS；没变化时什么都不做。
所在层第一层 scene。调用者：copyWorldMatrixTo（本节点或子孙节点读矩阵时），以及递归中的子节点。
为什么这样设计谁被读就只更新谁的祖先链，不读的子树不花任何代价；三个记录都没变就立即返回，读多少次都只算一次。
校验不做数值校验（输入早就由 Transform 存好）。它只判断「缓存还有没有效」。
状态变化重算时：worldMatrixValue、三个 observed 记录、worldMatrixDirty = false、worldVersion + 1；递归中祖先也可能各自重算。没变化时：什么都不改。
和谁有关读 Transform 的 version 和 local 矩阵（Transform 被 SceneNode 独占）；读父节点的 worldVersion 和 worldMatrixValue（父子之间只通过这两个值联系）。

顺序约束——每一条都能换吗？

约束如果调换
① 先更新父节点，再读父节点的 worldVersion读到的是父节点更新前的版本：父节点这一刻才重算、版本刚加一，而子节点比较的还是旧值，结论是「没变」，于是用了过期的矩阵。
④ 先复制 local，再乘父矩阵乘法要的就是 parent × local，out 里必须先放好 local。gl-matrix 的 multiply 允许输出和右操作数是同一个数组（覆盖前先缓存一整列），所以不用给每个节点多留一个 mat4（注释 :339–351）。
⑤ 乘法顺序 parent × local列向量约定下，先施加 local 再施加父节点的变换。换成 local × parent，只要父节点有旋转或缩放，结果就错了（:350–351）。
⑥⑦ 先记下观察值，最后 worldVersion + 1这两步之间没有别的代码会读它们，可以对调。但它们必须都放在矩阵算完之后：记录是「矩阵已经反映了这些版本」的声明，先写记录、后算矩阵，一旦将来中间加了可能抛错的步骤，就会留下「记录说是最新、矩阵却没算完」的状态——先做事、再记账。

3.3 已经有两个版本号，为什么还要 worldMatrixDirty

版本号只能说明「同一个对象变没变」。换了父节点，比较的就是另一个对象的版本号，数字可能恰好一样（注释 :336–337）：

3.4 copyWorldMatrixTo：唯一的读取入口

copyWorldMatrixTo 只有两行：先 updateWorldMatrix，再复制给调用者。没有「直接拿到内部矩阵」的 getter，所以不存在「绕过更新、读到旧矩阵」的路径，调用者也改不了内部缓存。这和 Transform 的 getter 返回拷贝是同一条规矩。

4. SceneNode 的树结构：要么全改，要么不改

4.1 add：先全部验证，再全部提交

add(...nodes: SceneNode[]): this {                                 // SceneNode.ts:208–228
  const seen = new Set<SceneNode>()
  for (const node of nodes) {                      // —— 验证阶段：一个都不改 ——
    if (seen.has(node)) throw new DuplicateSceneNodeError(node.debugLabel)   // 同一次调用里重复
    seen.add(node)
    this.assertCanAdopt(node)                      // 会不会成环
  }
  for (const node of nodes) {                      // —— 提交阶段：全部验证通过才进来 ——
    node.removeFromParent()                        // ① 先从旧父节点摘下
    node.parentValue = this                        // ② 再认新父节点
    this.childrenValue.push(node)                  // ③ 加进自己的子节点列表
    node.markWorldMatrixDirtyRecursively()         // ④ 世界矩阵失效（等下次读时再算）
  }
  return this
}
作用把一个或多个节点接到当前节点下面，保持参数顺序。
为什么这样设计批量操作最怕做到一半失败：前面几个已经接上、后面的没接上，调用者既不知道哪些成功了，也没法撤销。两阶段让它变成「要么全成，要么全不变」——和 Scene.retain「先让资源同意再记账」、Material「先验证再写 Map」是同一条规矩。
校验① 同一次调用里的重复节点；② 成环（包括 add 自己）。不校验节点是不是已经是 this 的子节点：再 add 一次，它会被挪到最后（先摘下、再追加）。
状态变化旧父节点的 children 少一个；node.parent；this.children 多一个；node 的整棵子树 worldMatrixDirty = true。不重算任何矩阵，也不改 worldVersion。
生命周期不涉及。树结构不决定任何资源的寿命（第 5 课「挂在树上 ≠ 拥有」），add 不会 retain 任何东西。

提交阶段的顺序能不能换？① 和 ② 不能换。如果先写 node.parentValue = this 再调 removeFromParent()，removeFromParent 会去「新父节点」this 的列表里找它——找不到，什么也不做（remove 是幂等的）。结果旧父节点的 children 里还留着它，它同时出现在两个父节点的列表里：遍历时被访问两次，双向关系就破了。③ 和 ① 对调其实也能得到正确结果：先 push 再摘，remove 用 indexOf 删掉的是第一次出现的位置，也就是旧位置，新追加的那一份留了下来。但这要靠 remove 恰好删第一个——哪天有人把它改成 lastIndexOf，这里就坏了。保持「先摘下、再挂上」，每一步都不依赖这种细节。

4.2 assertCanAdopt：只查祖先链

private assertCanAdopt(node: SceneNode): void {                   // SceneNode.ts:406–410
  for (let current = this as SceneNode | null; current !== null; current = current.parentValue) {
    if (current === node) throw new SceneGraphCycleError(this.debugLabel, node.debugLabel)
  }
}

新加的边是 this → node。什么时候会成环？只有 node 已经在 this 的祖先链上（包括 this 自己）。所以从 this 沿 parent 往上走一遍就够了：时间和树高成正比，不需要额外空间，也不用遍历 node 的整棵子树（注释 :402–404）。

4.3 remove、removeFromParent、removeAllChildren

方法做什么不是子节点时状态变化
remove(node)从自己的列表里删掉 node，断开它的 parent什么都不做，不抛错（幂等）children、node.parent、node 子树 dirty
removeFromParent()让父节点 remove 自己没有父节点就什么都不做同上
removeAllChildren()断开全部直接子节点——每个子节点的 parent、子树 dirty；列表清空

三个方法都是「两边一起改」：父节点的列表和子节点的 parent 永远一致。children getter 返回拷贝（:176–178），外面没法绕过这几个方法去改列表。

4.4 traverse 与 traverseVisible

两个都是先父后子的深度优先遍历（:287–313）。traverseVisible 遇到 visible === false 立即返回：不访问这个节点，也不访问它的任何后代——隐藏一个 Group 就隐藏了整棵子树。注意：它直接遍历内部的 childrenValue，不是拷贝。visitor 里如果改了树，就会出问题（卡片 E，第 8.2 节）。

8.1 对照 three.js 的 Object3D

方面本项目three.js r177
世界矩阵怎样更新拉取式：读谁就沿祖先链更新到谁；三个记录都没变就直接返回推送式：每帧从根调用 updateMatrixWorld，一路 force = true 传给所有子节点（Object3D.js:1126–1150）

遍历中改树会跳过兄弟节点（卡片 E）同样的问题；文档写着「不建议在回调里修改场景图」（:1040），而且遍历前缓存了长度，删掉节点后可能访问到 undefined 而报错
欧拉角R = Rz · Ry · Rx（gl-matrix 3.4 的 fromEuler）默认 'XYZ'：R = Rx · Ry · Rz（Matrix4.js:327 开始的分支）

取舍：three.js 每帧全部重算，代码简单，每帧的代价与节点数成正比，不用担心缓存失效；本项目只算被读的，代价与「被读的节点数 × 树高」成正比，而且多了三个记录要维护。欧拉角那一行对搬场景数据很重要：从 three.js 拿来的旋转角，直接填进这里的 Transform，两个以上的轴非零时方向就不对了。好在旧引擎的 Mesh 也用同一个 quat.fromEuler（src/objects/Mesh.ts:480），HW2 从旧引擎迁过来的预设数据不受影响。

  3. 递归标脏是不是必要的？add、remove 会把被移动节点的整棵子树都标成 dirty（:419–425），代价与子树大小成正比。想一想：如果只标记被移动的那个节点，它的子孙还能算对吗？（提示：子孙比较的是哪个版本号？它是谁的？）

    能算对。孙节点比较的是自己父节点（被移动节点的子节点）的 worldVersion，而那个子节点比较的是被移动节点的 worldVersion。被移动节点因为 dirty 会重算，worldVersion 加一；这个变化沿版本链一层层传下去，每一层都会重算。我把 markWorldMatrixDirtyRecursively 临时改成只标记自己，做了实验：把一个三层的子树从 A 挪到 B 下面，孙节点的世界坐标照样正确。所以递归标脏对正确性不是必需的，它是一份保险——也是一份和子树大小成正比的开销。要不要去掉，取决于你更看重「少一种依赖版本链的推理」还是「reparent 更便宜」。
