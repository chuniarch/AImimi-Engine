src/rendering 全景：为什么要这样分层

这一课回答三个问题：旧引擎哪里疼、新架构用什么判据来切分、切完以后每一层放了什么。读完你应该能在一张纸上画出 src/rendering 的四层、两条继承体系和一次 draw 的路径，并说出每一处切分换来了什么、付出了什么。

课程改版：从这一课起改为精读，不需要手敲代码。每课的结构是：设计问题 → 逐行注释的源码 → 为什么这样写 → 检查题 → 架构视角（对照 three.js）。第 1、2 课保留为选修的动手课，不看也不影响后面的内容。
和你的目标的关系 —— 你要学的是这套代码的架构设计思想、详细设计思想和代码细节。这一课是地图：后面每一课精读一个模块时，你都应该能在这张图上指出它的位置、它依赖谁、谁依赖它。

1. 先看旧引擎哪里疼

阅读指南给每个设计定下的第一个问题是：「没有它时，哪段具体代码会重复、混乱或出错？」所以先看旧代码。下面三处都在你的仓库里，链接会在 VS Code 里打开对应的行。

旧代码它同时做了什么具体的疼
objects/Mesh.ts 持有 gl（:23）、VBO 和 IBO（:33–34）、按 program 分的 VAO（:42）、location 缓存（:45），还有 transform（:30） CPU 数据、GPU 资源、场景变换三件事搅在一个类里。它自己的注释写着：location 缓存「隐含假设一个 Mesh 只被一个 program 绘制」，而 ShadowPass 和 FFT 计算 pass 都违反了这个假设（:36–38）。按 program 分的 VAO 表，就是为了这个问题打的补丁。
materials/Material.ts 持有 WebGLFramebuffer（:12）和 WebGLUniformLocation 缓存（:14）；applyUniforms(gl, shader, textureUnitStart) 直接发 GL 调用，还自己分配纹理单元（:45） uniform location 只对查询它的那个 program 有效，材质一旦配上第二个 program，缓存就是错的。材质本该只描述「长什么样」，却被迫知道当前在画哪个 framebuffer、纹理单元从几号开始。
renderers/BaseRenderer.ts 构造时就 mesh.createVBOs(gl)、缓存 location（:73–75）；每次 draw 直接 uniformMatrix4fv（:196） 「资源什么时候上传到 GPU」和「对象什么时候被创建」绑死了。context 丢失以后，没有一个地方知道有哪些 GPU 对象需要重建。

用数字看（重构方案 PLAN.md §1.2 实测）：删掉死代码以后，活代码里还有 456 个 gl.* 调用点，散落在 Shader、Mesh、Material、BaseRenderer、textures、framebuffers、passes 等十几个文件里。没有一个地方独占 GL。由此带来三个后果：

  1. 换 WebGL2 要改遍整个仓库。任何一个文件都可能直接依赖 WebGL1 的扩展写法（例如旧 Mesh 专门有一个取 OES VAO 扩展的 getter）。
  2. context 丢失无法统一处理。GPU 句柄 (handle) 散在各个对象里，丢失时没法「整批作废、整批重建」。
  3. 共享一加入，就得给对象加维度。同一个 Mesh 被第二个 program 画，就得把缓存从「按名字」改成「按 program × 名字」。每一种新的共享方式，都要回头改数据对象。

2. 切分的判据：只有一句话

重构方案给出的核心判据（PLAN.md §5.1）：

一个类型属于哪一层，看它知不知道 gl 的存在。

阅读指南换了个说法：CPU 对象描述「是什么」；Backend 决定「在这个 context 上怎样实现」。于是 texParameteri 从一条散落在各处的命令，变成了 Texture 上的一个数据字段（sampler 描述），由 Backend 在创建 GPU 对象时统一读取。整个架构都是从这一句推出来的。

3. 四层，以及两种「方向」

来源：HW2 架构设计 §4（架构设计文档）。标注的「已实现 / 未实现」是 2026-09-23 的源码状态。

10 月 12 日更新：下面标「未实现」「还没写」的几样，现在都写好了。第二层的 frame/ 多了 RenderList、RenderListBuilder、RenderView、FrameSnapshot、copyMat4Snapshot；passes/ 下有 RenderPass、RenderPassContext、RenderPipeline、ForwardPass；最上面是 Renderer。frame/、passes/ 和 Renderer.ts 现在一共约 670 行。第三层的 WebGL1Backend（Task 15）也已完成。这张图和第 5 节的记录保留 9 月 23 日的样子，方便对照设计文档。这几个类由第 30 课专门讲（10 月 13 日发，排在第 18 课之前）。
第一层 · 场景与逻辑资源（CPU）· 已实现
scene/：SceneNode、Transform、Group、Scene、Mesh、Camera、PerspectiveCamera
resources/：VertexAttribute、Geometry、ShaderModule、Material、Texture 家族、RenderTarget
横切的基础：core/ 里的 Resource（生命周期）、errors（错误类型）、requireNonNull
↓ 数据：第二层读取第一层，复制成一帧的「值」
第二层 · 帧提取与编排 · 只有两个类型
frame/：RenderItem、ViewState。RenderList、RenderListBuilder、Pass、Pipeline、Renderer 都还没写（Task 16–18）
↓ 调用：只通过 RenderBackend 接口
第三层 · 设备后端 · 零件已实现，编排类未实现
backend/：RenderBackend（接口）、RenderSurface；webgl1/ 下 13 个文件；WebGL1Backend（Task 15）
↓ 调用：唯一持有 gl 的一层
第四层 · 平台
HTMLCanvasElement · WebGLRenderingContext · 驱动 · GPU
更正（2026-09-24）：这一节原来的标题是「四层，依赖只能向下」。这句话不能照字面读：图上第一层在最上面，而第三层的后端明明 import 了第一层的 Geometry、Material——照图看是「向上」依赖，却完全合法；「Material 不知道 Backend」禁止的反倒是「向下」依赖。问题出在图里其实混着两种不同的方向。

图中各层的顺序，是一帧数据流动的顺序：场景数据被提取成一帧的值，交给后端，后端驱动设备。「依赖」则要分成两种方向来看：

  1. 调用方向（谁调用谁、谁持有谁）：只能沿着 Engine → Renderer → Pipeline → Pass → Backend → GL 往下走。设计文档里「依赖只能向下」这句话下面列出的，全是这条调用链上的边（§4）。这个方向上的「反向」，是被调用的一方反过来知道调用它的一方：Pass 不保存 Renderer，Backend 不知道 ForwardPass。
  2. 知识方向（谁 import 谁的类型）：处理数据的机器可以读数据——第一层的 Geometry、Material，第二层的 RenderItem、ViewState——但数据本身不知道任何读它的机器。这个方向上的「反向」，是数据知道了消费它的机器：Material 不知道 Frame、Backend；Resource 不知道具体的 Manager；Mesh 不知道 GL；Scene 不调度 Pass。

两条合起来是同一条原则：被依赖的一方要更稳定、更通用，不能反过来知道依赖它的、更具体、更易变的一方。设计文档还有一条「Material 不知道 Camera」：它们同在第一层，这条管的不是层次，而是职责——同一个 Material 被许多 Mesh 共用，同一帧还可能从不同视角去画，相机数据如果存进 Material，这些视角就会互相覆盖。所以相机数据每次随 ViewState 传进后端（Task 15 改动前的 RenderBackend.ts 注释写着「item 的模型矩阵和 view 的相机快照不会塞入共享 Material」；现在由 WebGL1Uniforms 在每次 draw 时从 DrawSubmission 读取内建值来保证，见 WebGL1Uniforms.ts:272）。

当前源码实际的 import 方向：core 被所有包依赖；resources → core；scene → core、resources（Mesh 借用 Geometry、Material）；frame → resources、scene；backend → core、resources、frame（只用 RenderItem、ViewState 这些值类型）。另外还有一条不该有的 resources → scene，见 7.2 节。

这不只是文档上的约定——我用 grep 核对过当前源码：scene/、resources/、core/、frame/ 下没有一个文件 import backend/；整个 src/rendering 也没有 import 任何旧引擎模块（只借用了 @/errors 里的两个通用工具）。你可以自己跑一下（输出为空就说明没有违规）： 

grep -rln "rendering/backend" src/rendering/scene src/rendering/resources src/rendering/core src/rendering/frame

4. 两条继承体系，外加「借用」

阅读指南特意强调：「架构关系不是一条继承链」（design-reading-guide.zh-CN.md:32）。实际上有两条互不相干的继承体系，它们之间靠借用连起来：

Resource（core/Resource.ts：一次性释放、Scene 引用计数、onDispose 通知）
├── Geometry            由若干 VertexAttribute 组成（VertexAttribute 本身不是 Resource）
├── ShaderModule
├── Material ───────────── 借用 → ShaderModule、Texture2D / CubeTexture
├── Texture（抽象）
│   ├── Texture2D（抽象）
│   │   ├── ImageTexture2D
│   │   └── DataTexture2D
│   └── CubeTexture
└── RenderTarget

SceneNode（scene/SceneNode.ts：UUID、父子关系、遍历、world matrix 缓存；内含一个 Transform）
├── Group
│   └── Scene ───────────── retain → 任意 Resource（同一个 Scene 对同一资源只记一次）
├── Mesh ───────────────── 借用 → Geometry、Material
└── Camera（抽象）
    └── PerspectiveCamera

不在任何一条链上：backend/ 里的 Manager、State、Lifecycle。
其中四个 Manager 通过 onDispose 注册监听器（订阅资源的释放事件），
各自维护「CPU 对象 → 这一代 GPU 表示」的表。State、Lifecycle 不订阅资源。

两条体系回答的是两个不同的问题：

ResourceSceneNode
代表什么可以被多处共享、需要显式释放、会被 Manager 映射成 GPU 对象的数据在树里有位置、有变换的东西
生命周期一次性：disposed 之后不能复活；最后一个 Scene 引用释放时自动清理没有 dispose；从树上摘下来还能再挂回去
和 GPU 的关系每个 context 的 Manager 以它的对象身份为 key 建 GPU 表示没有直接关系；Mesh 的 world matrix 在提取时被复制进 RenderItem

所以 Mesh 继承的是 SceneNode 而不是 Resource：它只是把「在这里、用这个材质、画这个几何体」组合起来，借用 Geometry 和 Material，自己没有要交给 GPU 的数据，也没有 dispose()（Mesh.ts:10–14）。这是 has-a（对象组合 object composition，即「组合优于继承」里的组合，不是 UML 里那个管寿命的「组合」关系）与 is-a（继承）的分工：Mesh 是一个节点，有一个几何体。

5. 一次 draw 穿过各层（目标路径）

两个 Mesh 共用同一个 Geometry 和 Material，分别放在 x = 0 和 x = 10。它们的一次绘制要这样穿过四层：

第一层  Scene ─ Mesh（借用 geometry、material；自己的 transform）          已实现
          │ RenderListBuilder 遍历可见节点，复制出这一帧的值              未实现（Task 16）
第二层  RenderItem { geometry, material, worldMatrix ← 复制 }             类型已定义
        ViewState  { viewMatrix, projectionMatrix, cameraWorldPosition ← 复制 }
          │ ForwardPass 调用 backend.draw({ item, view })                 未实现（Task 17–18）
第三层  RenderBackend 接口 → WebGL1Backend.draw                          接口已定义；实现是 Task 15
          │ programs.get → geometries.get → state.useProgram → 上传矩阵
          │ → vertexInputs.bind → drawElements                           这些零件都已实现
第四层  WebGLRenderingContext → 驱动 → GPU

注意第二层做的事：它把可变的场景复制成值。RenderItem 带的是 worldMatrix 的副本，ViewState 带的是相机矩阵的副本。于是 Backend 永远看不到 Mesh、SceneNode、Camera，同一批 draw 里看到的也都是冻结下来的值。这种「值快照当边界」的做法，是层与层解耦的关键。

6. 这些切分换来了什么，付出了什么

换来付出
  • GL 只存在于一层：可以换后端，也可以让 WebGL1、WebGL2 两个后端并存，逐像素对比（PLAN.md §3.1 选这条路的决定性理由）
  • context 丢失时整代丢弃、重建，CPU 数据原封不动
  • 第一层可以脱离 GL 测试：tests/unit/rendering/scene 和 resources 下的测试全都不需要 GL
  • 共享是天然的：多个 Mesh、多个 Scene 共用一个 Geometry，只上传一次
  • 多了间接层：每次 draw 都要查几次 Map（按对象身份找 GPU 表示）
  • 生命周期必须显式管理：retain/release、onDispose 订阅、Manager 的 unsubscribe、固定的释放顺序——概念和代码都变多了
  • 边界上有复制成本：值快照、copyData()、冻结的 descriptor
  • 编排层没写完之前，整条链路没法端到端验证（这是现状）

7. 架构视角

7.1 对照 three.js

  • 数据对象不碰 GL，这一点和 three.js 一致。three.js 的 Object3D、BufferGeometry、Material 本来就不持有 GL 句柄，GPU 数据放在渲染器内部、按对象保存的 WeakMap 里（旧渲染器是 WebGLProperties）。反倒是本仓库的旧引擎是例外：Mesh 和 Material 自己拿着 gl。
  • 后端抽象更接近 three.js 的新渲染器。旧的 WebGLRenderer 把编排和 GL 细节写在一个 3505 行的闭包里，再配约 30 个 WebGL* 模块；新渲染器（src/renderers/common/）让 Renderer 只跟抽象的 Backend 说话，下面有 WebGPUBackend 和 WebGLBackend 两个实现。本项目的 RenderBackend 加 WebGL1Backend（将来加 WebGL2Backend）是同一个形状。
  • 本项目多了一样 three.js 没有的东西：第一层的显式生命周期。three.js 靠用户手动 geometry.dispose()；本项目有 Scene 级的引用计数，最后一个引用释放时自动清理。这是第 5 课的主题。

7.2 一个小小的审查发现

核对依赖时我发现：resources/Material.ts 和 frame/ViewState.ts 当时都为了一个 Vec3Tuple 类型，去 import scene/Transform.ts（2026-09-25 已修复，见本节末尾）。两处都只是 import type，运行时没有依赖；但它们在不同的层，问题也不一样（2026-09-24 更正：原文把两处当成了同一种问题）：

  • Material.ts → scene（第一层内部，两个兄弟包）：Mesh.ts:2–3 本来就让 scene 依赖 resources（Mesh 借用 Geometry、Material），再加上这一条，就成了 scene ⇄ resources 的包循环依赖。两个包从此只能一起理解、一起测试、一起复用，违反无环依赖原则 (Acyclic Dependencies Principle)。
  • ViewState.ts → scene（第二层读第一层）：方向本身允许，将来的 RenderListBuilder 本来就要读场景。问题在于 ViewState 是交给后端的值类型，RenderBackend.ts:2 import 了它，于是后端的类型依赖顺着它一路连到了 scene/Transform，「Backend 不知道 Scene」在类型层面被打破了。

修法：把 Vec3Tuple，连同 frame/ViewState.ts 里同类的 Mat4Tuple，搬进一个不依赖任何包的纯类型模块，例如 core/math/（这是你在答疑里提出的位置，我认为合适：core 本来就被所有包依赖，搬进去不会新增任何依赖方向）。这是一个很好的练习方向：审查架构时，不只看层与层之间，也看同一层内部有没有包循环，以及值类型会把哪些依赖「带」过边界。

2026-09-25 已修复：按上面的修法，两个类型搬进了 core/math/tuples.ts（只放纯类型，不引入 gl-matrix）。materialParameters.ts:2（10 月 19 日以前在 Material.ts，参数类型搬家时跟着走了）、ViewState.ts:1、RenderItem.ts:1、Transform.ts:3 都改从这里导入。现在 resources 不再 import scene，RenderBackend 的类型依赖里也不再有 scene 的文件。
