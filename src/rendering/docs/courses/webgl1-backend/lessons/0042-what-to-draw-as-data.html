画什么写成数据：resources/ 与 scene/

第 41 课的描述对象是谁都能改的普通对象，「有哪些物体」也还写死在每帧的函数里。这一课把它们做成类：resources/ 里的 Geometry、ShaderModule、Material、RenderTarget 回答「是什么」，并向 Manager 保证自己不会悄悄变；scene/ 里的 Mesh、Scene 和灯回答「有哪些、在哪」。每帧的函数变成遍历场景，后端只读这些数据。

和你的目标的关系 —— HW1 要地面、遮挡物、一盏灯和它的阴影设置；HW2 要 Mary、背景盒和相机。写成数据以后，换一个作业只是换一份数据，画的代码一行不改。10 月 16 日定下的「阴影设置挂在灯上」，这一课第一次出现在代码里。
默认你已经会的：① 第 41 课：Manager 按描述对象查表、release、第 5 节末尾的两条要求（一直是同一个对象、建过以后内容不再变）；② JavaScript 的 class 和 extends。这一课用到两个可能没见过的写法：#positions 这种带 # 的是私有字段，只有类自己的方法能读写，类外面连读都读不到（相当于 TypeScript 的 private，但运行时也真的拿不到）；Object.freeze(obj) 冻结对象，之后给它的属性赋值，在严格模式下抛 TypeError。
这一课讲的：第 41 课还剩的四处疼；Mesh 和 Scene；数据的三种变法和后端怎样知道；资源被丢弃时自己通知；构造时就检查；阴影设置挂在灯上；对照 src/rendering。
在一帧里的位置和寿命：这些对象由应用建、应用拿着，活得比任何一帧都长，也比 context 的一代长（context 丢失不影响它们）。每帧只被读，不被后端改。

1. 第 41 课还剩四处疼

  1. 「有哪些物体」还写死着。drawWithManagers 里第一遍画地面、画三角形，第二遍又画地面、画三角形。再加一个三角形，要加一个描述、一行 geometries.get，再在两遍里各加一段 draw，一共四处。
  2. 描述对象谁都能改，改了表里的副本也不知道。下面这块画布跑的是第 41 课的第二版，原样没动。点「直接改描述里的数组」：把三角形三个顶点的高度从 1.2 改成 2.0。画面不变——表里那个 buffer 是照改之前的数上传的，Manager 只认「是不是同一个对象」，发现不了。再点「模拟 context 丢失再恢复」：表重建了，照的是改过的数，三角形这才跳到 2.0 的高度。同一份数据，画成什么样，取决于副本是哪一刻建的。（第 31 课第 2 节用两个 context 演示过同一件事。）
  3. release 要页面自己调用。第 41 课第 6 节：只有数据的主人知道它不用了，可是主人不知道它在几个 context 里有几份副本。
  4. 坏数据不报错。第 5 节的第一张检查卡片：给第 41 课的引擎一个 4 个顶点的三角形描述，它不抛错，getError 是 0，第 4 个顶点被悄悄丢掉。

这块画布用的是第 41 课的 drawWithManagers（assets/shadow-41.js），只是三角形的描述换成了自己的一份数组副本，免得改动影响页面上别的画布。读数里的像素 (240, 162) 是三角形在 1.2 高度时的中间。

3. 数据变了，表里的副本怎么办

再治第 2 处。数据不是不能变，而是每一种数据都要说清楚怎么变，好让后端知道副本什么时候过时。小引擎里有三种：

数据怎么变后端怎样知道为什么这样选
Geometry、ShaderModule不能变。构造时复制，之后没有任何改的入口。要新形状，就建一个新的 Geometry不需要知道：同一个对象，内容永远不变；新对象在表里查不到，自然会建顶点多、上传贵，又很少变
RenderTargetresize(size)：尺寸变了，revision 加 1Manager 每次 get 比一比 revision，不一样就照新尺寸建一份、删掉旧的阴影图会随设置改尺寸，但对象身份要留着（材质、灯都引用它）
材质参数、物体位置、灯的方向随时改：setParameter、mesh.position、light.toLight不需要知道：后端根本不缓存它们，每次 draw 时现读、现设 uniform只有几个数，每帧设一遍几乎不花时间

在上面的画布上试三种：

  • 三角形变绿：页面调用 material.setParameter('uColor', [0.2, 0.8, 0.3])。下一帧就是绿的，新建 0 个、删除 0 个。
  • 阴影图 512 ↔ 1024：页面调用 light.shadow.target.resize(1024)。下一帧 RenderTargetManager 发现 revision 从 0 变成 1：新建纹理、深度缓冲、framebuffer 各 1 个，再删掉旧的 3 个；表里还是 1 条。再下一帧什么都不建。影子边缘的锯齿变细了（备课时在只有两个物体的场景里实测，1666 个像素有变化）。
  • 三角形换形状：Geometry 改不了，所以页面建一个新的 Geometry 和一个新的 Mesh 换上去，再把旧的 Geometry 丢弃（第 4 节）。新建 buffer 1 个，删除 buffer 1 个。

资源类是怎样做到「不能变」的，看代码里的「复制」「冻结」「私有字段」三个按钮：

架构视角：three.js 走的是另一条路——顶点数组可以原地改，改完要自己写 attribute.needsUpdate = true，它让 version 加 1（BufferAttribute.js:152），渲染器比较 version 决定要不要重新上传（WebGLAttributes.js:206）。好处是改几个顶点不用建新对象；代价是忘了写 needsUpdate 就是上面那块画布的样子。本项目的 Geometry 选了「不能变」，只有 RenderTarget 用和 three.js 一样的版本号。第 31 课第 9 节比较过两种做法。

4. 谁来调用 release：资源自己通知

治第 3 处。所有资源继承同一个基类 Resource：它记着一组「我被丢弃时叫你」的回调。Manager 第一次为某个资源建 GPU 副本时，顺手登记一个回调：「它被丢弃时，叫我 release 它」。于是：

  • 数据的主人只管调用 geometry.dispose()，不用知道有几个 context、几张表里有它的副本；
  • 每张表在 dispose 那一刻同步删掉自己那份 GPU 副本；
  • Manager 自己先关掉（或者 context 丢失）时，用登记时拿到的 unsubscribe 取消回调，免得资源以后叫一个已经不存在的 Manager。

如果不看就丢呢？第 5 节最后一张检查卡片：Geometry 已经丢弃、场景里的 Mesh 还拿着它，下一帧 geometries.get 开头的 assertUsable 直接抛「Geometry 已经释放」——一个看得见的错误，而不是去画一个已经删掉的 buffer。真实代码把「还有谁在用」做成了计数：场景用 scene.retain(resource) 登记（Scene.ts:77），还有场景持有时 dispose() 抛 ResourceHasSceneReferencesError（Resource.ts:182–190），最后一个场景释放时自动丢弃（Resource.ts:139–146）。

6. 灯也是数据：阴影设置挂在灯上

    
第 40 课 ① 里的 toLight、shadowBias、阴影图尺寸、正交范围 4.5，都变成了灯上的数据。照 10 月 16 日的决定（和 three.js 一样）：灯有 castShadow 和 shadow 两个字段；shadow 是一份阴影设置，拥有自己的阴影图（一个 RenderTarget）和 bias。

    

    
所以「阴影图 512 ↔ 1024」按钮改的是 light.shadow.target：阴影图属于这盏灯，不属于哪个 Pass，也不属于 drawScene。拖滑块改的是 light.toLight，和材质颜色一样每次 draw 现读。

    
src/rendering 里现在还没有灯。这里的两个类对应 HW1 阴影设计文档里的提案（设计 §3.4 灯、§3.5 DirectionalLightShadow）；提案里 DirectionalLightShadow 还是一个 Resource，并且拥有一个参数块——那是第 45 课的事。

    
留一个问题给第 43 课：drawScene 在第一遍和第二遍里各读了一次 light.toLight、mesh.position。如果两遍之间有人改了它们，阴影图和画面就是照两个不同的场景画的。
