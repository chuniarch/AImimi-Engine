0. 热身：前几课还记得吗

1. 设计问题：四个子类各加了什么

场景树上的东西有三类：用来分组的（Group、Scene），要画出来的（Mesh），用来看的（Camera）。它们都需要位置、父子关系、可见性和世界矩阵，所以都继承 (inheritance) SceneNode——它们「是一种」节点。各自多出来的东西却很少：

类加了什么为什么要加（或者为什么只加这么点）
Group只有一个稳定的诊断类型在代码里表达「这是一个分组」；SceneNode 本身就能 new，Group 不是技术上必需的（第 3.1 节）
Scene资源账本 retainedResources、单向的 disposed场景树的根，同时替这个场景登记它要用的资源（第 5 课、第 6 节）
Mesh借来的 Geometry、Material，两个检查存活的 getter「在哪里」由节点给，「画什么」由借来的资源给；Mesh 自己不拥有它们（第 3.3 节）
Camera投影矩阵、projectionVersion，抽象的 copyProjectionMatrixTo相机的位置和朝向由节点给（世界矩阵），镜头由投影给；两者独立变化
PerspectiveCamerafovY、aspect、near、far，验证与原子更新具体的投影规则；参数一次整组提交，要么全改、要么不改（第 5 节）

继承和组合 (composition) 在这里各管一半。Mesh 继承 SceneNode（它「是」一个节点），同时组合了 Geometry 和 Material（它「有」两个资源），但只是借用 (borrow)，不拥有。设计文档写的是两个公开只读字段（设计 §14.1），实现改成了私有字段加检查存活的 getter：借用方在使用时检查（第 5 课第 5 节）。

3.1 Group：什么都不加的类

export class Group extends SceneNode {                                     // Group.ts:17–31
  protected override get debugType(): string {
    return 'Group'                                                         // 唯一加的东西：稳定的诊断类型
  }
}
作用表示「这些节点在场景结构里属于同一组」。父子关系、Transform、遍历、世界矩阵全部继承 SceneNode（Group.ts:9–15）。
所在层第一层 scene。
为什么需要它一是语义：new Group() 比 new SceneNode() 更清楚地说出意图；二是诊断标签 (debug label)：不覆写的话，一个没起名的分组在日志里显示成 SceneNode#xxxxxxxx。
为什么写死字符串生产构建会压缩 (minify) 类名，constructor.name 不可靠（:24–26）。第 7 课实测过：RenderingError.ts 里没写 name 的 19 个错误类，压缩后 name 是空字符串。scene 的类都用 debugType 写死了类型，没有这个问题。
状态、生命周期没有新增状态。不是 Resource，没有 dispose，不拥有任何资源（:12–13）。

3.2 Scene：第 5 课读过的账本，这里只补三点

export class Scene extends Group {                                         // Scene.ts:22–144（节选）
  private disposedValue = false                                            // 单向：false → true
  private readonly retainedResources = new Set<Resource>()                  // 本 Scene 的账本：每个资源最多记一次
  retain<T extends Resource>(resource: T): T { … return resource }           // 返回原对象，可以写成一个表达式
  release(resource: Resource): boolean { … }                               // 没登记过、或者已经在释放：返回 false，不抛错
  dispose(): void { … }                                                    // 第 6 节
}

retain、release、dispose 各自的顺序，第 5 课第 4 节已经逐行读过了（先让资源同意再记账、先销账再交还、先标记再释放）。第 5 课没讲的三点：

  1. Scene 也是节点。它继承 Group，所以有 Transform，也能被 add 到别的节点下面——包括另一个 Scene。add 只检查重复和环（第 8 课），不拒绝 Scene。卡片 G 和审查视角 1 讨论这件事。
  2. 三个返回值各有用意。retain 返回传进来的那个对象，并保留具体类型（泛型 T）：const geometry = scene.retain(new Geometry(…)) 一行里创建并登记（:72–75）。release 返回 boolean：「没登记过」是正常情况，不值得抛错。dispose 幂等：调几次都一样。
  3. 真实流程里怎样用它。HW2 场景工厂加载失败时，已经 retain 的资源由 scene.dispose() 一起交还；还没登记的，由创建它的代码自己 dispose（设计 §26）。所以工厂最稳妥的写法，是资源一创建就 retain。

3.3 Mesh：借来的资源，换不掉

constructor(geometry: Geometry, material: Material) {                     // Mesh.ts:35–45
  super()                                                                  // JS 规定：用 this 之前先调父类构造
  if (!(geometry instanceof Geometry)) throw new InvalidMeshError('geometry')   // 运行时类型：TS 的类型编译后就没了
  if (!(material instanceof Material)) throw new InvalidMeshError('material')
  geometry.assertUsable()                                                  // 已经释放的资源不能借：抛 ResourceDisposedError
  material.assertUsable()
  this.geometryValue = geometry                                           // private readonly：构造之后再也换不了
  this.materialValue = material                                            // 不 retain、不订阅：只借用
}

get geometry(): Geometry {                                                 // Mesh.ts:56–59
  this.geometryValue.assertUsable()                                        // 每次读都查：构造之后资源仍可能被释放
  return this.geometryValue                                                // 读字段，不读 this.geometry（那会无限递归）
}
10 月 10 日更新：这三处以前写的是 if (geometry.disposed) throw new ResourceDisposedError('Geometry')，资源名要手写；现在调用资源自己的 assertUsable()（它从 protected 改成了 public，见第 7 课的更新），错误里的名字由资源的 resourceType 给出。行为没变。
作用把「在哪里」（继承来的节点和世界矩阵）和「画什么」（借来的 Geometry、Material）组合起来。
所在层第一层 scene。第二层的 Builder 每帧读它（第 4 节）。
校验构造时两层：类型不对抛 InvalidMeshError（调用者传错了东西），已释放抛 ResourceDisposedError。之后每次读 geometry、material 都再查一次存活（:56–69）。
状态变化构造之后，Mesh 自己的状态只有继承来的那些（Transform、父子关系、可见性）。两个 getter 什么都不改。
生命周期Mesh 没有 dispose（:14）。它的对象寿命交给垃圾回收：没人引用了就回收。它「能不能用」是另一回事，取决于借来的资源是否还活着（第 7 节的表）。
为什么不能替换构造时验证一次就够了；如果允许 mesh.geometry = other，替换时就得重新验证类型和存活，还得决定谁去 retain 新资源——Mesh 并不知道自己在哪个 Scene 里。另外，将来任何按 Mesh 缓存的数据都要多一种失效（第 8 课答疑讲的「重绑」）。卡片 A 看看赋值会怎样。
模型矩阵在哪就是继承来的世界矩阵，不另存一份，也不写进 Material（:16–19）。两个 Mesh 共用一个 Material 时，各自的模型矩阵仍然独立（测试 Mesh.test.ts:103）。
如果挪位置构造函数里先赋值、后验证也不会留下「半个 Mesh」：构造函数一抛错，对象根本不会交到调用者手里。构造函数天然是原子的；真正要讲究顺序的是能被反复调用的 setter（第 5 节）。

3.4 PerspectiveCamera 的构造：先有节点，再有镜头

constructor(options: PerspectiveCameraOptions) {                          // PerspectiveCamera.ts:165–176
  super()                                                                  // Camera → SceneNode：先有节点
  const next = copyValidatedOptions(options)                               // ① 每个字段读一次、验证，得到自己的快照
  const projection = createProjection(next)                                // ② 用快照算候选矩阵，并检查 Float32 结果
  this.fovYValue = next.fovY                                               // ③ 全部通过才写
  this.aspectValue = next.aspect
  this.nearValue = next.near
  this.farValue = next.far
  mat4.copy(this.projectionMatrixValue, projection)                        //    版本保持 0：新相机还没有「变化」
}
作用构造一个有效的透视相机：构造一结束，投影矩阵就可以用，projectionVersion 为 0。
所在层第一层 scene 的 cameras/。父类 Camera 是抽象类，构造器是 protected（:26–28）：只有单位矩阵占位的「相机」不算一个完整对象，外面不能直接 new。
为什么这样分工相机的位置和朝向是节点的事：世界矩阵，由 SceneNode 管，所以相机可以挂在移动的物体上。镜头是投影的事：由 fovY、aspect、near、far 决定。两者各有自己的版本号（worldVersion、projectionVersion），互不影响（测试 PerspectiveCamera.test.ts:204）。
Camera 不做的事不缓存视图矩阵 (view matrix)：它就是世界矩阵的逆，由每帧提取时去求，不可逆的情况也在那里处理（Camera.ts:11–12）。不是 Resource，没有引用计数，也没有 GPU 生命周期（:15）。
生命周期和 Mesh 一样交给垃圾回收。一个场景里可以有多个相机，它不是全局单例（设计 §14.2）。

构造用到的两个函数，也是第 5 节 setPerspective 的前两步，下面逐个读。

3.5 copyValidatedOptions：读一次，得到自己的快照

function copyValidatedOptions(options: PerspectiveCameraOptions): PerspectiveCameraOptions {   // :38–86
  assertNonArrayObject(                                                    // null、数组、数字都不是 options
    options,
    () => new InvalidPerspectiveCameraError('options', 'must be a non-array object')
  )
  const fovYInput = options.fovY                                           // 每个字段只读这一次
  const fovY = requireFiniteNumber(                                        // 必须是 number 而且有限
    fovYInput,
    () =>
      new InvalidPerspectiveCameraError('fovY', 'must be a finite number', { received: fovYInput })
  )
  // aspect、near、far 照样：先存进 aspectInput 这样的局部变量，再查（:51–70）
  if (fovY<= 0 || fovY >= Math.PI) throw …('fovY', 'must satisfy 0 < fovY < PI')   // 弧度：写成 90 度会被挡住
  if (aspect <= 0) throw …('aspect', 'must be positive')
  if (near <= 0) throw …('near', 'must be positive')
  if (far <= near) throw …('far', 'must be greater than near')           // 字段之间的关系
  return { fovY, aspect, near, far }                                       // 新对象：之后只用它，不再碰调用者的 options
}
作用把调用者传来的配置读一遍、验证，复制成一个新的快照 (snapshot)。
为什么要快照两个原因。一是验证过的值就是后面使用的值：如果提交时再去读 options.near，调用者的对象（比如一个 getter）完全可以返回另一个值（卡片 B）。二是不留别名：相机不保存调用者的对象，构造之后调用者再改它，相机不受影响（测试 PerspectiveCamera.test.ts:51）。
校验形状：是对象、不是数组、不是 null；类型：四个字段都是有限的 number（字符串 '2' 不行）；范围：0 < fovY < π，aspect > 0，near > 0；关系：far > near，不接受 Infinity。测试把 19 种坏输入逐个试过（:165–195）。
没有检查的多余的字段。它只读这四个字段，别的字段悄悄忽略；第 19 课的 SurfaceScope 却会拒绝未知字段（审查视角 2）。
状态变化无：这是一个纯函数，只读调用者的对象、返回新对象，不碰相机（:20）。
10 月 10 日更新：这个函数换了写法，行为没变。以前它用本文件里自己写的 requireFiniteNumber(value, fieldName)，对象检查也是手写的 if；现在两样都换成 core/validation.ts 的共用函数（第 7 课 6.1 节），错误对象由这里传进去的工厂造。每个字段先存进 fovYInput 这样的局部变量：工厂捕获的就是这一次读到的值，报错时 details 里的 received 不会再去读一遍 options。

3.6 createProjection：候选矩阵，先检查 Float32 结果

function createProjection(options: PerspectiveCameraOptions): Float32Array {   // :110–133
  const matrix = new Float32Array(16)                                      // 候选：独立的缓冲，还没交给相机
  const { fovY, aspect, near, far } = options
  mat4.perspective(matrix, fovY, aspect, near, far)                        // 用 Number 计算，写入时舍入成 Float32
  for (const value of matrix) {
    if (!Number.isFinite(value)) throw …('projectionMatrix', 'must contain only finite Float32 values')
  }
  if (matrix[0] === 0 || matrix[5] === 0 || matrix[14] === 0) {           // x、y 的缩放和深度项：归零就塌了
    throw …('projectionMatrix', 'must not collapse a projection axis or depth term to zero')
  }
  return matrix
}

先把矩阵写出来。记号：fovY 是垂直视场角（弧度）；aspect 是视口宽 ÷ 高；near、far 是近、远裁剪面到相机的正距离，单位和场景一致（比如米）；f = 1 / tan(fovY / 2)。按列主序存放，下标 i 对应「列 × 4 + 行」：

m[0]  = f / aspect                          x 方向缩放
m[5]  = f                                   y 方向缩放
m[10] = (far + near) / (near − far)         深度的线性项
m[11] = −1                                  把 −z 放进 w：透视除法的来源
m[14] = 2 · far · near / (near − far)       深度的常数项
其余各项都是 0

例（测试用的那组）：fovY = π/2、aspect = 2、near = 1、far = 11
→ f = 1，m[0] = 0.5，m[5] = 1，m[10] = −1.2，m[14] = −2.2（PerspectiveCamera.test.ts:69–73）
作用在一块独立的 Float32 缓冲里算出候选 (candidate) 投影矩阵，确认它能用，再交回去；自己不提交任何东西。
为什么要检查结果「输入有限」不等于「Float32 结果可用」（mesh-and-camera.zh-CN.md:35）。计算用 Number（Float64），写进 Float32Array 时才舍入：fovY = 1e-39 通过了输入验证，但 f ≈ 2×10³⁹ 超出了 Float32 的上限（约 3.4×10³⁸），存进去就是 Infinity（卡片 C）。
为什么只查这三项是不是 0x_clip = m[0]·x：m[0] 归零，所有点的 x 都塌成 0；m[5] 同理管 y。深度：z_ndc = (m[10]·z + m[14]) / (−z) = −m[10] − m[14]/z，只有 m[14] 让深度随 z 变化；它归零，所有点的深度都一样，深度测试就失效了。m[10] 不用查：near、far 都是正数，|far + near| > |near − far|，所以 |m[10]| 总大于 1。m[11] 恒为 −1。
它不拦什么只拦「明确不可用」的结果：Infinity、NaN、归零（:100–102）。aspect = 1e39 时，m[0] = 1e-39 在 Float32 里是一个次正规数 (subnormal)，不是 0，所以会被放行；aspect = 1e46 时 m[0] 舍入成 0，才会被拒绝（我用 Node 实测过）。这不是数值条件数评估。
如果挪位置先把矩阵算进相机自己的缓冲、再检查，检查失败时旧矩阵已经被覆盖了。所以它必须用独立缓冲，检查通过才让调用者复制进去（第 5 节的 ④）。

4. 每帧读取：Task 16 的 Builder 会调用什么

（10 月 13 日补：Builder 已经实现，和这段示意的差别见第 30 课 5.1 节。）Builder 还没实现。下面是按设计 §16 的顺序写的示意，是课程写的，项目里还没有这段代码；看它调用了这一课的哪些方法：

// 示意（课程写的）：RenderListBuilder.build 会按这个顺序读场景
build({ scene, camera }) {
  const world = new Float32Array(16)
  camera.copyWorldMatrixTo(world)                // ① 相机的世界矩阵（会先更新它的祖先）
  const view = invert(world)                     //    视图矩阵是它的逆；不可逆（比如缩放为 0）要在这里拒绝
  const projection = new Float32Array(16)
  camera.copyProjectionMatrixTo(projection)      //    投影：复制一份，拿不到内部数组
  const viewState = freeze({ viewMatrix: tuple(view), projectionMatrix: tuple(projection),
                             cameraWorldPosition: [world[12], world[13], world[14]] })
  scene.traverse((node) => node.updateWorldMatrix())   // ② 设计里的「更新场景 world matrix」：每个节点最多重算一次
  scene.traverseVisible((node) => {                // ③ 只走可见的子树
    if (!(node instanceof Mesh)) return
    const matrix = new Float32Array(16)
    node.copyWorldMatrixTo(matrix)               // ④ 模型矩阵就是世界矩阵：复制
    items.push(freeze({ geometry: node.geometry, //    getter：先查存活，再借出同一个对象
                        material: node.material,
                        worldMatrix: tuple(matrix) }))
  })
  … 按 material.queue 分到 background / opaque，再冻结
}
被调用的方法它保证什么为什么这样设计
camera.copyWorldMatrixTo(out)（SceneNode.ts:391）先沿父链按需更新，再把世界矩阵复制进 out相机是节点，所以挂在移动的父节点上也能拿到正确位置。视图矩阵不缓存，由 Builder 求逆（Camera.ts:11–12）
camera.copyProjectionMatrixTo(out)（:238–240）只复制：不重算、不加版本、不交出内部缓冲如果交出内部数组，调用者改了它，就绕过了 setPerspective 的验证和版本号（测试 :99）
scene.traverseVisible(visitor)（SceneNode.ts:303）跳过不可见节点的整棵子树visible 管的是「画哪些 Mesh」。相机不靠遍历取得：RenderView 直接给出它，所以相机挂在不可见的分组下照样能用（卡片 F）
mesh.geometry、mesh.material（Mesh.ts:56–69）资源已释放就抛 ResourceDisposedError场景里漏 retain 的资源，会在提取这一步就报出来，而不是等到 draw（第 5 课卡片 E）
mesh.copyWorldMatrixTo(out)同第一行模型矩阵就是世界矩阵；每个 Mesh 一份，和共用的 Material 无关
material.queue（Material.ts:293）background 或 opaque决定进哪个列表；第 11 课读 Material 时细讲

这一步之后，本帧的 Pass 和 Backend 再也不读相机和 Mesh：ViewState 的注释说「Backend 不接收 Camera，因此不能在同一批 draw 中重新读取可变相机状态」（ViewState.ts:11）。第 6 课讲的「值快照当边界」，就发生在这里。

5. 改镜头：setPerspective

setPerspective(options: PerspectiveCameraOptions): void {                 // PerspectiveCamera.ts:209–228
  const next = copyValidatedOptions(options)                               // ① 验证（可能抛错）
  if (next.fovY === this.fovYValue && next.aspect === this.aspectValue &&
      next.near === this.nearValue && next.far === this.farValue) {
    return                                                                 // ② 四个 Number 全等：什么都不做
  }
  const projection = createProjection(next)                                // ③ 候选矩阵（可能抛错）
  this.fovYValue = next.fovY                                               // ④ 提交：从这里开始不会再失败
  this.aspectValue = next.aspect
  this.nearValue = next.near
  this.farValue = next.far
  mat4.copy(this.projectionMatrixValue, projection)
  this.projectionVersionValue++                                            // ⑤ 真的变了才加一
}
作用原子地 (atomically) 提交一整组新的透视参数：要么参数、矩阵、版本一起变，要么都不变（:141–142）。
所在层第一层 scene。调用者是应用层：窗口缩放时改 aspect，调焦时改 fovY。
为什么要整组传不接受部分更新（:205），调用者要显式保留其余字段：camera.setPerspective({ fovY: camera.fovY, aspect: w / h, near: camera.near, far: camera.far })。多写几个字，换来的是：每一次修改都是一组完整、验证过的配置，不存在「改了一半」的中间状态。
校验第 3.5、3.6 节的全部检查，外加 ② 的全等比较。
状态变化成功：四个参数、投影矩阵、projectionVersion + 1。相同或失败：什么都不变。和 worldVersion、Transform 都无关（卡片 F 的相机位置不受它影响）。
版本的含义参数按 Number 保存、按 Number 比较，只有矩阵是 Float32（:144–148）。所以重复设 near = 0.1 不加版本（测试 :117）；而两个只差 2ε 的 aspect 算出完全相同的 Float32 矩阵，版本仍然加一（卡片 E）。版本记的是「配置变了」，不是「矩阵变了」。它是给消费者发现旧快照过期用的，不是历史记录（mesh-and-camera.zh-CN.md:52）。
调换硬 / 软换了会怎样
④ 挪到 ③ 之前（先写参数，再算矩阵）硬③ 抛错时，参数已经是新的，矩阵还是旧的：相机自相矛盾，也回不到调用前。
③ 算进相机自己的缓冲硬检查失败时旧矩阵已被覆盖。所以候选矩阵必须用独立缓冲（第 3.6 节）。
② 挪到 ③ 之后（先算，再比较）软结果一样，只是相同的配置也白算一次矩阵。
⑤ 挪到 ④ 之前软④ 不会抛错，结果相同；但读代码的人要多想一步：「版本加了、状态没写」可能发生吗？
① 挪到后面不可能后面每一步用的都是 ① 返回的快照。

两种避开「Float64 输入比 Float32 存储」的办法。第 8 课的 Transform 和这里的相机都要回答「这次设置算不算变化」，做法不同：

Transform（第 8 课）PerspectiveCamera
保存成什么Float32（vec3）参数存 Number，只有矩阵是 Float32
比较什么先 Math.fround，再比 Float32直接比 Number
重复设 0.1version 不变projectionVersion 不变
只差一点点的两个值量化后相同 → 不变Number 不同 → 加一，即使矩阵完全相同
版本记的是存储的值变了配置变了

6. 换场景：Scene.dispose 做什么、不做什么

dispose(): void {                                                          // Scene.ts:131–143
  if (this.disposedValue) return                                           // 幂等
  this.disposedValue = true                                                // 先标记：之后 retain 抛错、release 返回 false
  this.removeAllChildren()                                                 // 只摘下直接子节点（它们的世界矩阵被标脏）
  for (const resource of this.retainedResources) {
    resource.releaseSceneReference()                                       // 交还自己那一份引用，不是 resource.dispose()
  }
  this.retainedResources.clear()
}
做的事不做的事
标记 disposed，从此拒绝 retain不释放任何节点：节点不是 Resource。摘下来的 Mesh、相机还能挂到别的场景（测试 Mesh.test.ts:125）
摘下全部直接子节点不把自己从父节点上摘下：Scene 如果被挂在别的节点下，dispose 之后还挂在那里（我用 Node 实测过）
对账本里每个资源交还一份引用；归零的资源随之真正释放不级联到子 Scene：被挂在下面的另一个 Scene 只是被摘下，它自己的账本原封不动（卡片 G）
清空账本不直接调用 resource.dispose()：别的 Scene 还持有的资源只少一份引用（第 5 课）

在真实流程里：Engine.setScene 先完成新场景、新相机的替换，再 dispose 旧场景；传入的相机不在新场景的树里就拒绝（设计 §26）。先换新、后释放，新旧场景共用的资源才不会在交接的一瞬间被释放（第 5 课的检查题）。「相机必须在场景树里」这条检查，在这一课的类里还没有，是 Engine（Task 21）要做的。

10.2 审查视角：三处值得讨论的地方

  1. 「Scene 是根」只是约定。Scene 的注释说它是「场景图根节点」（Scene.ts:6），但代码允许把它挂到任何节点下面，包括另一个 Scene；dispose 既不把自己摘下，也不级联到子 Scene（卡片 G）。挂在别的节点下时，场景里所有物体的世界矩阵还会带上那个父节点的变换。想一想：要不要在 add 里拒绝 Scene 当子节点？这样做会不会挡住什么合理的用法？
  2. 两种输入校验风格。第 19 课的 SurfaceScope 拒绝未知字段（WebGL1SurfaceScope.ts:55–57），PerspectiveCamera 只读四个字段，其余静默忽略。想一想：从 three.js 迁移时，写出 { ...options, zoom: 2 } 是很自然的事，这时会发生什么？这个边界上哪种风格更合适？
  3. 单位检查只挡住了一半。fovY 用弧度，写成 90（度）会被 0 < fovY < π 挡住（测试 :171）；但本意是 3 度、写成 3 的，会被当成 3 弧度（约 172°）接受。three.js 的 fov 是度数。想一想：迁移 HW2 的相机代码时，怎样防止单位写错？
