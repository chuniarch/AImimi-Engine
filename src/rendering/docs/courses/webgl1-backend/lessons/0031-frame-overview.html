0. 先给结论

  1. scene 和 resources 里的东西不会被「转换过去」。Backend 每次 draw 都拿 CPU 对象去查表：programs.get(material.shaderModule)、geometries.get(geometry)。表里没有才编译、上传，有就直接用。CPU 对象始终是原件，GPU 对象只是某个 context 里的副本：可以有好几份，丢了还能从原件重建。证明见第 3、5 节。
  2. 每个类的职责由三个问题决定：这个信息谁知道？多久变一次？活多久、归谁管？五个目录正好对应五种不同的回答（第 1、6、9 节）。
  3. 复制和冻结只有两条规则。一是数据从「能改它的人」手里交到「需要它不变的人」手里时，复制一份。二是一份数据同时交给好几个读者时，冻结它。对象身份本身就是查表的 key，所以 Geometry、Material 这类对象不复制，只借用（第 7 节）。

1. 原始输入：画两个三角形，gl 要哪些参数

先忘掉项目代码。下面是课程写的最直接的版本（overview-course.ts:82）：每一帧编译 program、上传顶点，然后画。每行右边的注释回答同一个问题：这个参数是从哪里来的。

// 课程写的第 1 版（节选，省略了类型标注；注释是课程加的）
function drawFrameV1(gl, meshes) {
  gl.clearColor(0, 0, 0, 1)            // 清成黑色：这一遍画画的设定
  gl.clear(gl.COLOR_BUFFER_BIT)
  // shaderSource(VERTEX_SOURCE)：shader 文件里的源码
  const program = createProgramV1(gl)
  for (const mesh of meshes) {
    // bufferData(mesh.positions / mesh.indices)：模型文件
    const buffers = uploadV1(gl, mesh)
    drawOneV1(gl, program, buffers, mesh)
  }
}

function drawOneV1(gl, program, buffers, mesh) {
  gl.useProgram(program)               // 哪个 program：这个 context 建出来的
  // 物体摆在哪：场景
  gl.uniform1f(gl.getUniformLocation(program, 'uOffsetX'), mesh.offsetX)
  // 什么颜色：材质
  gl.uniform3fv(gl.getUniformLocation(program, 'uColor'), mesh.color)
  // 哪个 buffer：同样是这个 context 建出来的
  gl.bindBuffer(gl.ARRAY_BUFFER, buffers.positionBuffer)
  gl.enableVertexAttribArray(0)
  // 每个顶点 2 个 float：顶点数据的格式
  gl.vertexAttribPointer(0, 2, gl.FLOAT, false, 0, 0)
  gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, buffers.indexBuffer)
  // 画几个索引：模型
  gl.drawElements(gl.TRIANGLES, buffers.count, gl.UNSIGNED_SHORT, 0)
}

课程版把物体的位置简化成一个 uOffsetX。真实代码里它是 4 × 4 的模型矩阵 uModel，相机还会多出 uView、uProjection 两个矩阵。把这些参数逐个拿出来，问三个问题：谁知道它？多久变一次？坏了归谁管？答案只有五种，正好是 src/rendering 下的五个目录：

图 1 里最容易忽略的是最下面一行。createBuffer 返回的 handle 只在这个 context 里有效，context 丢了就全部作废。所以它不能放进 Geometry：Geometry 被两个 canvas 共用时该存哪一个？context 丢失后谁来把它换掉？这类东西只能放在 backend/，每个 context 一份。第 3 课说的分层判据「看它知不知道 gl 的存在」，就是从这一行推出来的。

2. 需求

把第 1 版交给一个真实的作业项目，会被下面六条卡住。后面每一版代码都用这六条验收：

  1. R1 GPU 对象只建一次。两个三角形画 3 帧，program 只编译 1 次，顶点和索引一共只上传 4 次，而不是 3 帧 × 4 = 12 次。
  2. R2 一份 CPU 数据可以给几个 context 用。例如 HW1 调试时把阴影图画到第二个 canvas 上。每个 context 必须用自己建的 buffer：第 5.4 节的卡片实测，把 A 的 buffer 绑到 B 上，B 报 1282（INVALID_OPERATION）。
  3. R3 GPU 对象丢了能重建。context 丢失后旧 handle 全部作废，要从同一份 CPU 数据再传一次。
  4. R4 一帧里所有 Pass 看到同一份数据。HW1 的阴影 Pass 和 ForwardPass 必须用同一个模型矩阵；阴影 Pass 为了自己方便重新排序物体时，不能改掉 ForwardPass 看到的顺序。
  5. R5 通过了的校验，不能被事后的修改悄悄作废。Geometry 构造时检查过每个索引都小于顶点数，用户之后改数组，也不能让某个索引变成 7。
  6. R6 错误要在离原因最近、能说出字段名的地方抛出。不能拖到 GPU 那里，变成「少画了半个方块」却没有任何报错。

3.2 第 2 版：用物体本身当 key 缓存

要让 R1 成立，第一次建好的 GPU 对象就得存起来，下一帧再找回来。用什么去找？最自然的 key 是物体对象本身：同一个对象，就是同一份顶点（overview-course.ts:98–122）：

// 课程写的第 2 版（节选）
class DrawerV2 {                       // 一个 context 一个
  private program: WebGLProgram | null = null
  // key：物体对象本身
  private readonly buffers = new Map<MeshDataV1, ReturnType<typeof uploadV1>>()

  drawFrame(meshes: readonly MeshDataV1[]): void {
    // …清屏
    this.program ??= createProgramV1(gl) // 只在第一帧编译
    for (const mesh of meshes) {
      let buffers = this.buffers.get(mesh)
      if (buffers === undefined) {
        buffers = uploadV1(gl, mesh)     // 这个 context 第一次见到这个物体
        this.buffers.set(mesh, buffers)
      }
      drawOneV1(gl, this.program, buffers, mesh)
    }
  }
}

R1 解决了。因为 handle 只属于一个 context，每个 context 各有一个 DrawerV2，R2 也满足了。第 2 版看起来已经很像真实代码：Map<CPU 对象, GPU 对象> 就是第 4 课讲的 Manager。

3.4 推出来的结论

3.3 节暴露的问题是：缓存里存的是「当时那份数据」的 GPU 副本，可 key 背后的数据还能被人改。A 缓存的是旧数据，B 上传的是新数据，同一个 key 在两个 context 里对应了两份不同的数据。context 丢失后重新上传，也会是改过以后的那份。改法只有两个方向：

  • 让 key 背后的内容永远不变：构造时复制一份、检查这一份、不给任何修改方法。缓存就永远不会过期，构造时的检查也永远有效（R5）。项目的 VertexAttribute、Geometry、ShaderModule 都这样做（第 4 节）。
  • 允许修改，但要让缓存知道：每改一次，版本号加 1，Manager 发现版本变了就重新上传。three.js 的 BufferAttribute 是这样做的（第 10 节）；项目的 RenderTarget 用 revision 也是这个思路（第 4 课 5.2 节）。

这就回答了「scene 和 resources 只是描述，那它们怎样到 backend 去」：它们不去 backend，backend 拿它们当 key 来查。它们「只是描述」也不是因为不重要：GPU 对象会丢，可以有好几份，CPU 对象是唯一不会丢的那一份原件，所以它必须完整、合法、不会悄悄变。

5.2 Manager 的表：命中就返回，没命中才上传

以 GeometryManager 为例（WebGL1GeometryManager.ts:104–188）：

// WebGL1GeometryManager.ts:104–188（节选；注释是课程加的；长行已折行）
get(geometry: Geometry): WebGL1GeometryResource {
  this.assertAvailable('get geometry')
  if (geometry.disposed) throw new ResourceDisposedError('Geometry')
  // …正在释放时拒绝（:109–111）
  // entries: Map<Geometry, GeometryEntry>；热路径：第 2 帧起都走这里
  const cached = this.entries.get(geometry)
  if (cached !== undefined) return cached.resource

  // 冷路径：这个 context 第一次见到这个 Geometry
  // …
  for (const name of geometry.getAttributeNames()) {
    const attribute = geometry.getAttribute(name)!
    const data = attribute.copyData()          // 从原件取一份副本来上传
    const type = this.attributeType(data)
    const buffer = this.upload(
      gl.ARRAY_BUFFER, data, `Geometry.attribute:${name}`, owned
    )
    // …
  }
  // …索引、恢复绑定、检查错误
  const resource: WebGL1GeometryResource = Object.freeze({
    attributes,
    indexBuffer,
    indexType,
    drawCount: geometry.drawCount,
    primitiveMode: mode
  })

  // 原件释放时，删掉自己这份副本
  const unsubscribe = geometry.onDispose(() => this.release(geometry))
  this.entries.set(geometry, { resource, unsubscribe })
  return resource
}

三个细节都和第 3 节对得上：key 是 Geometry 对象本身；上传用的是 copyData() 的副本，所以原件永远不变；Geometry 被 dispose 时，Resource 基类会通知每个订阅了它的 Manager，各自删掉自己那份 GPU 副本（第 4 课第 3 节）。

6. 真实代码 ③：一帧的照片——scene 和 frame 为什么分开

第 5 节的 draw 收到的不是 Mesh，而是 DrawSubmission = { item, view }。为什么要多这一层？先看 Mesh 身上有什么：父节点、子节点、Transform、visible、uuid、世界矩阵缓存，外加借来的 Geometry 和 Material。这些都是可变的：轨道控制每次 pointermove 都会改相机，动画每帧都会改 Transform。把 Mesh 直接交给 Pass 和 Backend，会有两个问题：

  • Backend 能看到 parent、children，就能去遍历场景、改场景。它的职责是「怎样调 gl」，不该知道场景树。
  • 两个 Pass 各读一次 Mesh，中间只要有人改了 Transform，两次读到的值就不同。这违反了 R4，而且没有任何报错。

所以每帧开始时，RenderListBuilder 遍历一次场景，给它「拍一张照」，之后的 Pass 和 Backend 只看照片。照片里放什么？只放下游真正用到的字段。数据结构是从消费者的需要倒推出来的（RenderItem.ts:15–20、ViewState.ts:13–20、RenderBackend.ts:6–9）：

// RenderItem.ts:15–20、ViewState.ts:13–20、RenderBackend.ts:6–9
// （节选；注释是课程加的）
export interface RenderItem {
  readonly geometry: Geometry   // → programs/geometries 查表的 key（借用身份）
  readonly material: Material   // → shader、参数、RenderState、队列（借用身份）
  readonly worldMatrix: Mat4Tuple // → uModel（复制的值，16 个数）
}

export interface ViewState {
  readonly viewMatrix: Mat4Tuple        // → uView
  readonly projectionMatrix: Mat4Tuple  // → uProjection
  readonly cameraWorldPosition: Vec3Tuple // → cameraPosition（shader 用到时）
}

export interface DrawSubmission {
  readonly item: RenderItem
  readonly view: ViewState
}

7. copy 和 freeze：两条规则

7.1 规则

  • 规则一：所有权换手的地方复制。数据从「能改它的人」手里，交到「需要它不变的人」手里。用户 → Geometry（第 4 节）、Mesh 的世界矩阵 → 一帧的照片（7.2 节）、Engine 的 frame 对象 → Renderer（7.4 节），都属于这种情况。反过来交出去的时候也一样：Geometry 把内部数组交给调用者，给的是副本。
  • 规则二：一份数据同时交给几个读者时冻结。RenderList 给每个 Pass 读，ViewState 给每次 draw 读，RenderState 给每个用这个 Material 的 draw 读。只要有一个读者能改它，其他读者就会看到被改过的数据（7.3 节）。
  • 例外：身份就是 key 的对象不复制。Geometry、Material、纹理是第 5 节那些表的 key，复制一份就成了一个新 key（7.5 节）。

下面每一条都用一个「去掉这一处复制或冻结」的变体来跑。

7.2 提取时复制：不复制会怎样

RenderListBuilder 遍历场景时，用一块 scratch 缓冲接每个 Mesh 的世界矩阵，再用 copyMat4Snapshot 复制成冻结的普通数组（RenderListBuilder.ts:99–119）：

// RenderListBuilder.ts:99–119（注释是课程加的）
const background: RenderItem[] = []
const opaque: RenderItem[] = []
const scratch = new Float32Array(16) // 一块缓冲，整次遍历共用

scene.traverseVisible((node) => {
  if (!(node instanceof Mesh)) return

  // SceneNode 不交出内部矩阵，只肯复制到你给的缓冲里
  node.copyWorldMatrixTo(scratch)

  const renderItem: RenderItem = {
    geometry: node.geometry,           // 借用身份
    material: node.material,           // 借用身份
    // 检查有限数、复制、冻结
    worldMatrix: copyMat4Snapshot(scratch, 'mesh.worldMatrix')
  }

  if (renderItem.material.queue === 'background') {
    background.push(renderItem)
  } else {
    opaque.push(renderItem)
  }
})

7.3 共享就冻结：一个排序 Pass 引出的问题

HW1 的阴影 Pass 可能想先按离灯的远近给物体排序。最顺手的写法是直接在 context.renderList.opaque 上 sort（overview-course.ts:184–199）。但这个数组也是排在它后面的 ForwardPass 要读的：

// 课程写的 SortByLightPassV1（节选）
execute(context: RenderPassContext): undefined {
  const distance = (item: RenderItem) => Math.abs(item.worldMatrix[12] - this.lightX)
  ;(context.renderList.opaque as RenderItem[]).sort((a, b) => distance(a) - distance(b))
  return undefined
}

代码里的 as RenderItem[] 是故意加的。去掉它，TypeScript 先拦一次：error TS2339: Property 'sort' does not exist on type 'readonly RenderItem[]'（我用项目的 tsconfig 实测过）。可 readonly 只在编译时有效：as、any、普通 JavaScript 调用者都能绕过去。运行时的那道关是 Object.freeze，在 RenderList 的构造函数里（RenderList.ts:5–32）：

// RenderList.ts:5–11、:27–32
function snapshotItem(item: RenderItem): RenderItem {
  return Object.freeze({
    geometry: item.geometry,
    material: item.material,
    worldMatrix: copyMat4Snapshot(item.worldMatrix, 'item.worldMatrix')
  })
}
// …
constructor(backgroundList: RenderItem[], opaque: RenderItem[]) {
  this.background = Object.freeze(backgroundList.map(snapshotItem))
  this.opaque = Object.freeze(opaque.map(snapshotItem))

  Object.freeze(this)
}

7.4 复制和冻结一起用：FrameSnapshot

Renderer.render 收到 Engine 给的 view.frame（帧号、时间、画布尺寸六个数），先抄一份再冻结，然后交给所有 Pass（Renderer.ts:56–76）：

// Renderer.ts:56–76（注释是课程加的）

const frame: FrameSnapshot = Object.freeze({ // 复制六个数，再冻结这份副本

7.6 一帧路径上的全部复制与冻结

逐处列出来，每处都写明它挡住的是哪个卡片里的错误：

  • ① 入口复制：VertexAttribute.ts:100、Geometry.ts:196、:225、copyParameter（materialParameters.ts:141，Material 和 ParameterBlock 共用）。挡住 3.3 节的「A、B 画得不一样」和「索引 7」，以及 4 节卡片里的「共享数组」「NaN」。
  • 出口复制：copyData（:123）、copyIndices（Geometry.ts:284）、getParameter（Material.ts:312）、ParameterBlock 的 get（ParameterBlock.ts:84）、copyWorldMatrixTo（SceneNode.ts:391）。拿到副本的人改它，不影响原件。
  • ② 提取复制：相机（RenderListBuilder.ts:68、:82、:92–93）、每个 Mesh（:111）、RenderList 再复制一次（RenderList.ts:9）、FrameSnapshot（Renderer.ts:58–65）。挡住 7.2 节的「三个 item 都是 x = 2」和 7.4 节的「Pass 改了 Engine 的对象」。
  • ③ 冻结：每个矩阵（copyMat4Snapshot.ts:40）、两条队列和 RenderList 本身（RenderList.ts:28–31）、ViewState（RenderListBuilder.ts:91）、RenderPassContext（Renderer.ts:69）、RenderState（Material.ts:116）、GPU 表项（WebGL1GeometryManager.ts:177）。挡住 7.3 节的「排序改了别人的顺序」。
  • ④ 上传时的副本：WebGL1GeometryManager.ts:145。原件不交出内部数组，只在第一次上传时给一份副本；第 2 帧起走缓存，不再复制。
  • 不复制：RenderItem 里的 geometry、material（RenderList.ts:7–8），Material 里的纹理（materialParameters.ts:204–214），以及 Material 借用的参数块。它们是 Manager 的 key，7.5 节的卡片说明了为什么不能复制。

8. 校验为什么分在三层

你还问到「数据校验」。整个代码里的校验分布在三层，原则只有一句：放在最早知道答案的那一层。早了，信息还不够；晚了，错误就离原因太远（R6）。

  • 构造时（resources）：只看描述本身就能判断的，比如索引是否越界、itemSize 是否整除、参数是不是有限数、枚举值是否合法。
  • 提取时（frame）：要等到这一帧才知道的。Transform 的 setPosition 不做检查（Transform.ts:186–192），因为轨道控制每次 pointermove 都会调它。世界矩阵要经过父子相乘才算得出来，相机矩阵可不可逆也一样。所以 copyMat4Snapshot 每帧检查一次有限数，Builder 检查相机矩阵能不能求逆（RenderListBuilder.ts:84–85）。
  • draw 时（backend）：要有设备、有编译好的 program 才知道的。比如 uColor 在 shader 里到底是 vec3 还是 vec4，只有链接后的反射才知道。Material 不解析 GLSL（materialParameters.ts:222），所以这类错误要等到 Uniforms.prepare（WebGL1Uniforms.ts:160–162）。Uint32 索引要不要扩展、sampler 数量有没有超过纹理单元上限，也属于这一层。

还有一类看起来重复的检查：Backend.draw 一开头又检查一遍 instanceof Geometry（WebGL1Backend.ts:197–204），可是 RenderList 明明来自 Builder。原因是 RenderBackend 是公开接口，测试、自己写的 Pass 都能直接调 draw，Backend 不能假设调用者是 Builder。公开入口不信任调用者，私有函数信任已经检查过的输入。卡片里把五种错误各触发一次：

9. 每个类的职责表

把前面的结论收成一张表，方便回查。「不知道」那一列是故意的：每一格都对应一个「知道了就会出事」的理由，理由写在括号里。

以后读到一个新类，先问三个问题：它知道什么？它活多久？它故意不知道什么？三个都答得出来，这个类的职责就清楚了。答不出来，往往说明它在两个寿命不同的东西中间，值得多看两眼。

10. 架构视角：对照 three.js r177

three.js 面对同样的六条需求，做了几乎相反的取舍：少复制，靠约定。

  • 顶点数据：版本号加用户自觉。BufferAttribute 直接拿着用户的数组。改完要写 attribute.needsUpdate = true，这个 setter 只做一件事：this.version++（BufferAttribute.js:152–156）。WebGLAttributes 发现缓存的版本比对象的旧，就重新上传（WebGLAttributes.js:206–216）。忘了写 needsUpdate，就是 3.3 节 context A 的情况：GPU 上留着旧数据，没有任何报错。项目的初版 Geometry 是静态的，干脆不允许改（第 10 课）。
  • 矩阵：draw 时现读。renderObject 先调用户的 object.onBeforeRender，再现读 object.matrixWorld（WebGLRenderer.js:2001–2005）。用户回调可以在两次 draw 之间改物体，后面的 draw 就会看到改过的值。项目里的 Pass 根本拿不到 Scene。
  • 渲染列表：跨帧复用对象，存的是活对象的引用。getNextRenderItem 复用上一帧的 renderItem，只把 renderItem.object = object 等字段换掉（WebGLRenderLists.js:69–101）。每帧零分配，可一帧内的一致性只能靠约定。
  • 表：WeakMap。WebGLAttributes 的表是 WeakMap（WebGLAttributes.js:3），CPU 对象被回收时表项跟着消失，但 GPU buffer 不会自动删，还是要调 dispose。项目用 Map，表项要等 dispose 才删（7.5 节卡片的 20 个 buffer）。

两种取舍各有适用的场合。three.js 要服务上万个物体、各种用户代码，零分配很重要；代价是忘了 needsUpdate、在回调里改物体这类错误，只会表现成画面不对。项目选「多复制，靠机制」：1000 个 Mesh 每帧多花约 0.4 ms（7.7 节），换来的是错误在离原因最近的地方、带着字段名抛出来。对 GAMES202 这种几个到几十个物体的作业，这笔账是划算的。

11. 审查视角

11.1 跑卡片时测出来的两件事

  1. 每次绑定顶点输入，都会清空整个 State 缓存。5.3 节卡片的第 2 帧里，两次 draw 用的是同一个 program、同样的深度和剔除设置，第二次 draw 却照样发出 useProgram、enable、depthMask、depthFunc、cullFace。原因在 OES 顶点输入的 bind：热路径在 try 里 return，finally 照样执行 this.hooks.invalidateState()（WebGL1OESVertexInputManager.ts:68–73、:136–139）；而 invalidate 会把 program、深度、剔除的缓存一起清掉（WebGL1State.ts:272–280）。注释说的理由是「VAO 切换改变 EBO」，真正需要作废的只有 ELEMENT_ARRAY_BUFFER 这一项。结果没错，只是每次 draw 多发 6 条调用，State 缓存在连续的 draw 之间一次也命中不了。
  2. Transform 接受 NaN，报错时却说不出是哪个 Mesh。setPosition([NaN, 0, 0]) 不报错，直到下一帧提取才抛 mesh.worldMatrix: component 12 must be finite（7.2 节卡片）。场景里有 1000 个 Mesh 时，这条信息不够你找到是哪一个。SceneNode 有现成的 debugLabel，可以放进错误信息。

另外两件看起来像问题、实测不是问题的事：第 2 帧的 138 条 gl 调用里有 72 条是 isContextLost，每条约 6 ns，一帧加起来不到 1 µs；getError 每条约 40 µs，但只出现在第 1 帧的冷路径（14 条），第 2 帧一条都没有。Builder 复制一次、RenderList 又复制一次，矩阵确实抄了两遍，但 7.7 节的数字说明代价很小；RenderList 是公开类，它不能假设调用者已经复制过。
