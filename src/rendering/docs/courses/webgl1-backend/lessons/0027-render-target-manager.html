backend ⑤ 续：给 GPU 一块离屏画布——RenderTargetManager 与 FBO

HW1 的阴影要画两遍：第一遍从光源看场景，把「离光源多远」画进一张看不见的图（阴影贴图）；第二遍正常画，每个像素去那张图里查自己是不是被挡住了。第一遍画到的那块「看不见的画布」，在 CPU 上是一个 RenderTarget，在 GPU 上是一个 framebuffer 对象（FBO）加上挂在它上面的纹理和 renderbuffer。这一课先把阴影贴图里存的数和 FBO 的 GL 调用看明白，再从旧引擎的 FBO 类出发一版一版写，最后读真实的 RenderTargetManager，以及使用它的 SurfaceScope。

和你的目标的关系 —— HW1 阴影、HW3 的 GBuffer、将来的后处理和环境烘焙，都要「先画进一块离屏画布，再拿它当纹理用」。你 10 月 12 日刚接上的 sampler2D 采样附件（Backend 里的 scope.assertCanSample → resolveSampledColor），读的就是这一课讲的 Manager 建出来的东西。

这一课从零讲的：阴影贴图里一个像素存的是什么（打包公式和具体数）；FBO 是什么、颜色附件和深度附件各管什么；完整性检查和它的状态码；MRT 的 drawBuffers 记在哪里；旧引擎 FBO 的两个问题；validate、create、release；SurfaceScope 怎样用 Manager 建出来的 FBO；采样附件时的反馈环检查；和 Lifecycle 的关系。

1. 原始输入与需求

1.1 阴影贴图里存的是什么

阴影 pass 画每个片元时，并不输出颜色，而是输出「这个点离光源多远」：深度 d，0 是近平面，1 是远平面。可颜色附件每个通道只有 8 位，存 0～255 的整数，一个通道只能把 d 分成 256 档，太粗。HW1 的做法是把 d 拆成四个 8 位数，分别放进 R、G、B、A，像写一个四位的 256 进制小数： 

d ≈ r + g / 256 + b / 256² + a / 256³     // r、g、b、a 各在 [0, 1)，存成 0～255 的整数
// 类比十进制：0.3141 = 0.3 + 0.01 + 0.004 + 0.0001，每一位只管自己那一档

这一步写在阴影 pass 的片元 shader 里：

// 旧引擎 src/shaders/lighting/shadow/directional/rgbaPack.frag
// :5–12、:21–24（注释是课程加的）
// 阴影 pass 的片元 shader：把这个片元离光源多远（深度 d，0～1）写成一个 RGBA 颜色
vec4 pack(float depth) {
  // 把 d 拆成 4 位「256 进制小数」：d ≈ r + g/256 + b/256² + a/256³
  const vec4 bitShift = vec4(1.0, 256.0, 256.0 * 256.0, 256.0 * 256.0 * 256.0);
  const vec4 bitMask = vec4(1.0 / 256.0, 1.0 / 256.0, 1.0 / 256.0, 0.0);
  // fract(d × 256^k)：第 k 位以及它后面的所有位
  vec4 rgbaDepth = fract(depth * bitShift);
  // 每一位减掉「下一位已经表示了的那部分」，只留自己这一位
  rgbaDepth -= rgbaDepth.gbaa * bitMask;
  return rgbaDepth;
}

void main() {
  // gl_FragCoord.z：深度测试用的那个深度值，0 = 近平面，1 = 远平面
  gl_FragColor = pack(gl_FragCoord.z);
}

把 d = 0.3 和 d = 0.7 代进去（Node 按 shader 的公式逐步算，存储按 8 位通道取整到 k / 255，解码用接收阴影的 shader 里的 unpack，directLight/fragment.frag:55–58）：

dpack 输出 (r, g, b, a)存进纹理的 4 个字节读回再解码
0.3(0.296875, 0.796875, 0.796875, 0.8)76, 203, 203, 2040.30116
0.7(0.699219, 0.199219, 0.199219, 0.2)178, 51, 51, 510.69882
顺带一个数值细节：解码只差 0.001 左右，不是正好 0.3。原因是 pack 按 256 进位，而 8 位通道存的是 k / 255，两者对不上。同一个文件里被注释掉的 EncodeFloatRGBA（rgbaPack.frag:14–19）按 255 进位，Node 实算 0.3、0.5、0.7 都能精确还原（它的第四个常数写成了 160581375，255³ 应该是 16,581,375）。这是旧引擎 shader 的事，不在 src/rendering 里；将来新架构写阴影 shader 时值得记得。

为什么阴影贴图要用 nearest 过滤？解码是一个加权求和（线性的），所以线性过滤两个纹素，解出来正好是两个深度的加权平均（Node 实算：0.3、0.7 两组字节各取一半，解出 0.49999）。问题在于这个平均值是编出来的。看一个阴影边缘：左边纹素是挡光物体，存 0.3；右边是地板，存 0.7。地板上一个点 P 离光源 0.70，采样位置在两个纹素之间、偏右 75%：

  • nearest：取右边那个纹素，0.7。P 的 0.70 不比它远，判为被照亮（对）。
  • linear：0.25 × 0.3 + 0.75 × 0.7 = 0.6。P 的 0.70 比 0.6 远，判为在阴影里（错）。没有任何表面离光源 0.6，这个深度是插值编出来的。

所以 RenderTarget 允许为颜色附件选过滤方式，而且注释里专门写了「RGBA 打包深度用于硬阴影时应显式选择 nearest」（RenderTarget.ts:30–39）；默认是 linear，因为普通的离屏颜色（后处理、缩放）要平滑。

阴影 pass 还需要第二样东西：一个深度缓冲。光源看过去，同一个像素上可能有好几个物体，要留下最近的那个。这个深度缓冲只在阴影 pass 里做深度测试，主 pass 不读它。两样东西的大小（HW1 默认 2048 × 2048，DirectionalLight-refactor.ts:143）： 

颜色（存打包后的深度）：2048 × 2048 × 4 字节 = 16,777,216 字节 = 16 MiB
深度缓冲（depth16）  ：2048 × 2048 × 2 字节 =  8,388,608 字节 =  8 MiB
// 两样都在显存里；CPU 上一个字节都没有，内容全靠阴影 pass 每帧画

1.2 CPU 上的描述

新架构里，这块画布先在 CPU 上写成一个 RenderTarget（第 29 课第 6 节）。项目里还没有代码建它，下面是课程按 HW1 写的：

// 课程写的：HW1 的阴影贴图，用新架构的 RenderTarget 描述（项目里还没有代码建它）
const shadow = new RenderTarget(
  {
    width: 2048, // 像素，不是 CSS 尺寸；DirectionalLight 默认的阴影分辨率
    height: 2048,
    colors: [
      {
        format: 'rgba8', // 存 pack 后的深度：每像素 4 字节，2048² × 4 = 16 MiB
        // 1.1 节：线性过滤会在边缘编出不存在的深度，所以用 nearest
        sampler: { minFilter: 'nearest', magFilter: 'nearest' }
      }
    ],
    depth: { format: 'depth16' } // 阴影 pass 自己做深度测试用：2048² × 2 = 8 MiB
  },
  { label: 'shadow/main' } // 只用于报错时认出是哪块画布
)
// 这一行之后：CPU 上只有一份冻结的描述，revision 是 0；GPU 上什么都还没有

描述里的每一项，在 GPU 上变成什么：

描述GPU 上本课
width、height颜色纹理和 renderbuffer 的尺寸；画进去时的 viewport3.4、4.1 节
colors[i].format: 'rgba8'一张 RGBA、UNSIGNED_BYTE 的空纹理，挂到第 i 个颜色槽2.1、3.4 节
colors[i].sampler这张纹理的 MIN_FILTER、MAG_FILTER；wrap 固定 clamp-to-edge，没有 mipmap3.4 节
colors.length > 1MRT：要 WEBGL_draw_buffers，还要设 drawBuffers2.4、3.3 节
depth: { format: 'depth16' }一个 DEPTH_COMPONENT16 的 renderbuffer，挂到深度槽；不能被 shader 采样2.2 节
label不上 GPU，只出现在报错里—
revision（resize 时加一）不上 GPU；Manager 用它判断旧 FBO 是否过期3.5 节

1.3 谁来要：一条写的路，一条读的路

1.4 需求

  1. 按需建，一代一份。描述在 CPU 上，GPU 对象第一次用到才建，context 丢了整代重建（和纹理一样）。
  2. 设备做不到就早报错。尺寸超过上限、多颜色附件没有扩展，要在建任何东西之前拒绝。
  3. 建出来的必须能用。「完整性」检查不过，宁可报错，也不交出一个 draw 不进去的 FBO。
  4. 不弄乱别人。建 FBO 时要临时绑这绑那；建完，进来时绑着的 framebuffer、renderbuffer、纹理都要原样还回。
  5. 失败不留半成品。建到一半失败，这次建的全删。
  6. 会换尺寸。revision 变了要换新的，而且失败时旧的还能用（第 29 课 6.2 节）。
  7. 不能边写边读。正往里画的那块画布，这次 draw 不能采样它。

2. 先把 GL 调用看明白

2.1 FBO：一块插座板

bindFramebuffer(gl.FRAMEBUFFER, null) 的 null 不是「没有」，而是「canvas 自带的那套缓冲」，WebGL 叫它默认 framebuffer。颜色纹理用 texImage2D(…, null) 分配：只要显存，不传像素，WebGL 规定这块新存储全是 0。下面的卡片画一次看看：

2.2 深度附件：没有它，深度测试等于没开

深度测试比较的是「深度缓冲里已有的值」。一个 FBO 如果没有挂深度附件，就没有深度缓冲可比：开了 DEPTH_TEST 也不起作用，后画的永远盖住先画的。阴影 pass 要留下离光源最近的物体，所以必须挂深度附件。

为什么用 renderbuffer 而不是纹理？renderbuffer 是「只给 GPU 自己画的时候用」的存储，shader 不能采样它；深度纹理要 WEBGL_depth_texture 扩展（旧引擎有这条路，ShadowMapFBO.ts:30–51）。本项目现在只描述 depth16，就是 renderbuffer，所以第 29 课里采样 depth 地址会被拒绝。

2.3 完整性：checkFramebufferStatus

插座板插得不对，FBO 就「不完整」，往里 draw 或 clear 都会失败。checkFramebufferStatus 返回一个状态码告诉你哪里不对。本机实测（SwiftShader）：

插法状态码名字
RGBA 纹理 4 × 4 + depth16 4 × 436053FRAMEBUFFER_COMPLETE
什么都没插36055INCOMPLETE_MISSING_ATTACHMENT
RGBA 纹理 4 × 4 + depth16 8 × 836057INCOMPLETE_DIMENSIONS（WebGL1 要求所有附件同尺寸）
LUMINANCE 纹理36054INCOMPLETE_ATTACHMENT（这种格式不能当画布）
只插 depth1636053COMPLETE（只做深度也可以）

往不完整的 FBO 上 clear，getError 得到 1286（INVALID_FRAMEBUFFER_OPERATION），什么都没写。WebGL 不会因为 FBO 不完整而抛异常，只留一个错误码，所以建完必须自己问一次状态。

2.4 MRT：drawBuffers 记在 FBO 里

GBuffer 一次 draw 要同时写几张图：shader 写 gl_FragData[0]、gl_FragData[1]……，FBO 挂 COLOR_ATTACHMENT0、1……。中间还要一张对照表：「第 i 个输出写进哪个槽」，这就是 WEBGL_draw_buffers 的 drawBuffersWEBGL([...])。关键是这张表存在哪：

实测说明，这张表是每个 FBO 自己的：在 A 上设了 [C0, C1]，B 的第 1 项仍是 NONE；默认 framebuffer 的第 0 项是 BACK。所以只要在建 FBO 时（它正绑着的时候）设一次就够了，以后每次 bind 都自动生效，也不会影响别的 FBO。旧引擎每次 bind() 都重设一遍（FBO.ts:257–271），是多余的。

2.5 设备上限

能建多大、能挂几个颜色槽，每台设备不同。本机 SwiftShader 的值和这张卡片在你浏览器里打印的值，多半不一样：

上限管什么本机 SwiftShader
MAX_TEXTURE_SIZE颜色纹理的边长8192
MAX_RENDERBUFFER_SIZE深度 renderbuffer 的边长8192
MAX_COLOR_ATTACHMENTS_WEBGL能挂几个颜色槽（要扩展）8
MAX_DRAW_BUFFERS_WEBGL一次 draw 能同时写几个（要扩展）8

3. 一版一版写

3.1 第 1 版：旧引擎的 FBO

旧引擎的 FBO 类在构造函数里就建好全部 GPU 对象，最后调用 initFrameBuffer 收尾：

// 旧引擎 src/framebuffers/FBO.ts:77–126（节选；注释是课程加的）
// 构造函数 new FBO(gl, options) 最后调用它：一 new 就在这个 gl 上建好全部 GPU 对象
private initFrameBuffer(colorAttachmentCount: number) {
  const gl = this.gl

  this.framebuffer = gl.createFramebuffer()
  if (!this.framebuffer) {
    console.error('无法创建帧缓冲区对象')
    throw new FramebufferCreationError(this.width, this.height)
  }
  gl.bindFramebuffer(gl.FRAMEBUFFER, this.framebuffer)

  // …（省略：建颜色纹理并挂上去，MRT 时设 drawBuffersWEBGL，:88–107）

  if (this.depthMode === 'texture') {
    this.createDepthTexture()
  } else {
    this.createDepthRenderbuffer()
  }

  const status = gl.checkFramebufferStatus(gl.FRAMEBUFFER)
  if (status !== gl.FRAMEBUFFER_COMPLETE) {
    // ② 抛错，但上面已经建好的 framebuffer、纹理、renderbuffer 一个都没删
    throw new FramebufferIncompleteError(
      status,
      this.width,
      this.height,
      colorAttachmentCount
    )
  }

  // ① 一律清成 null：不管调用者进来时绑的是哪个 FBO、哪张纹理、哪个 renderbuffer
  this.gl.bindFramebuffer(gl.FRAMEBUFFER, null)
  this.gl.bindTexture(gl.TEXTURE_2D, null)
  this.gl.bindRenderbuffer(gl.RENDERBUFFER, null)
}

阴影贴图包了一层 ShadowMapFBO，画之前 bind、画完 unbind：

// 旧引擎 src/framebuffers/ShadowMapFBO.ts:56–71（节选；注释是课程加的）
bind(): void {
  const gl = this.gl
  this.fbo.bind()
  gl.viewport(0, 0, this.resolution, this.resolution)
}

// ⑤ 「画完」= 回到屏幕：unbind 一律绑 null，viewport 要调用者传 canvas 尺寸进来。
//    如果进来之前绑的是另一个 FBO（比如 GBuffer），它不知道，也还不回去
unbind(fullWidth: number, fullHeight: number): void {
  this.fbo.unbind()
  this.gl.viewport(0, 0, fullWidth, fullHeight)
}

对照 1.4 节的需求，问题有五处：

  • ① 收尾一律绑 null（需求 4）。如果调用者正在画 GBuffer，中途第一次用到阴影贴图、触发创建，创建完 GBuffer 的 FBO 就被换成了 canvas，之后的 draw 全画到屏幕上；纹理单元里原来的纹理、原来的 renderbuffer 也被清掉。
  • ② 完整性失败不收拾（需求 5）。抛错前建的 framebuffer、纹理、renderbuffer 没人删，也没人记得它们。
  • ③ new 的时候就建、绑死 gl（需求 1、6）。没有 resize，换分辨率只能 new 一个新的；context 丢了以后对象里的 handle 全死，也没人知道该重建。
  • ④ 悄悄降级（需求 2）。过滤方式不被支持时，checkTexureConfig 打一行 warn 就改成别的（FBO.ts:403–457），调用者拿到的和描述的不一样。
  • ⑤ 退出只会回屏幕（需求 4）。unbind 绑 null，viewport 要调用者传 canvas 尺寸；嵌套在别的离屏画布里时还不回去。

把 ① ② 改写成一个可以在卡片里跑的最小函数：

// 建好的三样 GPU 对象（第 1、2 版共用这个返回类型）
interface TargetHandles {
  readonly framebuffer: WebGLFramebuffer
  readonly color: WebGLTexture
  readonly depth: WebGLRenderbuffer
}

// 第 1 版：照旧引擎 FBO.ts 的 initFrameBuffer 改写（课程写的；一个颜色槽 + 深度）
// 旧引擎每个 create 之后都查 null 并抛错，这里用 ! 省略
function createTargetV1(gl: WebGLRenderingContext, size: number): TargetHandles {
  const framebuffer = gl.createFramebuffer()!
  gl.bindFramebuffer(gl.FRAMEBUFFER, framebuffer)

  // 颜色槽：一张 size × size 的空纹理（像素传 null），挂到 COLOR_ATTACHMENT0
  const color = gl.createTexture()!
  gl.bindTexture(gl.TEXTURE_2D, color)
  gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, size, size, 0, gl.RGBA, gl.UNSIGNED_BYTE, null)
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.NEAREST)
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.NEAREST)
  gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT0, gl.TEXTURE_2D, color, 0)

  // 深度槽：一个同样大的 renderbuffer，挂到 DEPTH_ATTACHMENT
  const depth = gl.createRenderbuffer()!
  gl.bindRenderbuffer(gl.RENDERBUFFER, depth)
  gl.renderbufferStorage(gl.RENDERBUFFER, gl.DEPTH_COMPONENT16, size, size)
  gl.framebufferRenderbuffer(gl.FRAMEBUFFER, gl.DEPTH_ATTACHMENT, gl.RENDERBUFFER, depth)

  const status = gl.checkFramebufferStatus(gl.FRAMEBUFFER)
  if (status !== gl.FRAMEBUFFER_COMPLETE) {
    // 和旧引擎一样：抛错，上面建的三样都没删
    throw new Error('framebuffer incomplete: ' + status)
  }

  // 和旧引擎 FBO.ts:123–125 一样：一律清成 null
  gl.bindFramebuffer(gl.FRAMEBUFFER, null)
  gl.bindTexture(gl.TEXTURE_2D, null)
  gl.bindRenderbuffer(gl.RENDERBUFFER, null)
  return { framebuffer, color, depth }
}

3.2 第 2 版：记下、还回；登记、失败删

第 16 课 GeometryManager 上传 buffer 时用过的两个办法，搬到 FBO 上：

// 第 2 版（课程写的）：进来先记下三个绑定；建一样登记一样；
// 失败时删掉登记过的；无论成败，最后把绑定原样还回去
function createTargetV2(gl: WebGLRenderingContext, size: number): TargetHandles {
  // ① 记下别人的（例：外层正在画 GBuffer，绑着它的 FBO；纹理单元里有它的纹理）
  const previousFramebuffer: WebGLFramebuffer | null =
    gl.getParameter(gl.FRAMEBUFFER_BINDING)
  const previousRenderbuffer: WebGLRenderbuffer | null =
    gl.getParameter(gl.RENDERBUFFER_BINDING)
  const previousTexture: WebGLTexture | null = gl.getParameter(gl.TEXTURE_BINDING_2D)

  // ② 账本：null = 还没建
  let framebuffer: WebGLFramebuffer | null = null
  let color: WebGLTexture | null = null
  let depth: WebGLRenderbuffer | null = null

  try {
    framebuffer = gl.createFramebuffer()!
    gl.bindFramebuffer(gl.FRAMEBUFFER, framebuffer)

    color = gl.createTexture()!
    gl.bindTexture(gl.TEXTURE_2D, color)
    gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, size, size, 0, gl.RGBA, gl.UNSIGNED_BYTE, null)
    gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.NEAREST)
    gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.NEAREST)
    gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT0, gl.TEXTURE_2D, color, 0)

    depth = gl.createRenderbuffer()!
    gl.bindRenderbuffer(gl.RENDERBUFFER, depth)
    gl.renderbufferStorage(gl.RENDERBUFFER, gl.DEPTH_COMPONENT16, size, size)
    gl.framebufferRenderbuffer(gl.FRAMEBUFFER, gl.DEPTH_ATTACHMENT, gl.RENDERBUFFER, depth)

    const status = gl.checkFramebufferStatus(gl.FRAMEBUFFER)
    if (status !== gl.FRAMEBUFFER_COMPLETE) {
      throw new Error('framebuffer incomplete: ' + status)
    }
    return { framebuffer, color, depth }
  } catch (error) {
    // ③ 只在失败时做：账本里有什么删什么，不留半成品
    if (framebuffer !== null) gl.deleteFramebuffer(framebuffer)
    if (color !== null) gl.deleteTexture(color)
    if (depth !== null) gl.deleteRenderbuffer(depth)
    throw error
  } finally {
    // ④ 无论成败都做：还回进来时的三个绑定，而不是一律 null
    gl.bindFramebuffer(gl.FRAMEBUFFER, previousFramebuffer)
    gl.bindRenderbuffer(gl.RENDERBUFFER, previousRenderbuffer)
    gl.bindTexture(gl.TEXTURE_2D, previousTexture)
  }
}

3.3 真实代码：validate，动手之前先查

// WebGL1RenderTargetManager.ts:191–230（注释是课程加的；工作区版本）
// 只查询、不创建：任何一条不满足，都在第一次 createFramebuffer 之前抛错
private validate(descriptor: RenderTargetDescriptorSnapshot): void {
  const gl = this.gl
  // 颜色附件是纹理，受 MAX_TEXTURE_SIZE 限制（本机 SwiftShader：8192）
  const maximum = requireTextureLimit(gl, gl.MAX_TEXTURE_SIZE, 'MAX_TEXTURE_SIZE')
  // 有深度附件时，它是 renderbuffer，还受 MAX_RENDERBUFFER_SIZE 限制；没有就不问
  const maximumDepth =
    descriptor.depth === undefined
      ? maximum
      : requireTextureLimit(gl, gl.MAX_RENDERBUFFER_SIZE, 'MAX_RENDERBUFFER_SIZE')

  // 所有附件同尺寸（2.3 节：不同尺寸是 36057），所以宽高要同时满足两个上限
  if (
    descriptor.width > Math.min(maximum, maximumDepth) ||
    descriptor.height > Math.min(maximum, maximumDepth)
  ) {
    throw new UnsupportedRenderFeatureError('render target size', 'exceeds device limits')
  }

  // 一个颜色槽不需要扩展；两个以上（GBuffer）要 WEBGL_draw_buffers
  if (descriptor.colors.length > 1) {
    const extension = this.capabilities.drawBuffers
    if (extension === null) {
      throw new UnsupportedRenderFeatureError('MRT', 'WEBGL_draw_buffers is required')
    }

    // 两个上限都要满足：能挂几个槽、一次 draw 能同时写几个槽（本机都是 8）
    const colors = requireTextureLimit(
      gl,
      extension.MAX_COLOR_ATTACHMENTS_WEBGL,
      'MAX_COLOR_ATTACHMENTS_WEBGL'
    )
    const draws = requireTextureLimit(
      gl,
      extension.MAX_DRAW_BUFFERS_WEBGL,
      'MAX_DRAW_BUFFERS_WEBGL'
    )

    if (descriptor.colors.length > Math.min(colors, draws)) {
      throw new UnsupportedRenderFeatureError(
        'MRT',
        'color attachment count exceeds device limits'
      )
    }
  }
}

private create(
  descriptor: RenderTargetDescriptorSnapshot,
  revision: number,
  label: string // 例：'shadow/main (RenderTarget revision 0)'
): WebGL1RenderTargetResource {
  const gl = this.gl
  // ① 记下别人的 framebuffer、renderbuffer 绑定（纹理那一格交给下面的上传作用域）
  const previousFramebuffer = gl.getParameter(
    gl.FRAMEBUFFER_BINDING
  ) as WebGLFramebuffer | null
  const previousRenderbuffer = gl.getParameter(
    gl.RENDERBUFFER_BINDING
  ) as WebGLRenderbuffer | null

  // ② 账本：null / 空数组 = 还没建
  let framebuffer: WebGLFramebuffer | null = null
  let depth: WebGLRenderbuffer | null = null
  const colors: WebGLTexture[] = []
  const { width, height } = descriptor

  try {
    // 第 17 课的上传作用域：记下并还回当前单元的 TEXTURE_2D 格子和四个上传设置
    return withTextureUploadState(gl, gl.TEXTURE_2D, () => {
      framebuffer = requireNonNull(
        gl.createFramebuffer(),
        () => new WebGLResourceCreationError('framebuffer', label)
      )
      gl.bindFramebuffer(gl.FRAMEBUFFER, framebuffer)

      for (let index = 0; index < descriptor.colors.length; index++) {
        const texture = requireNonNull(
          gl.createTexture(),
          () => new WebGLResourceCreationError('color-texture', label + ' color ' + index)
        )
        colors.push(texture) // 先登记，再做可能失败的事
        gl.bindTexture(gl.TEXTURE_2D, texture)

        // 只分配存储、不传像素（null）；WebGL 保证新存储全是 0
        gl.texImage2D(
          gl.TEXTURE_2D,
          0,
          gl.RGBA,
          width,
          height,
          0,
          gl.RGBA,
          gl.UNSIGNED_BYTE,
          null
        )

        // CPU Snapshot 已补齐 sampler；硬阴影的打包深度可显式选择 nearest。
        const sampler = descriptor.colors[index]!.sampler
        gl.texParameteri(
          gl.TEXTURE_2D,
          gl.TEXTURE_MIN_FILTER,
          sampler.minFilter === 'nearest' ? gl.NEAREST : gl.LINEAR
        )
        gl.texParameteri(
          gl.TEXTURE_2D,
          gl.TEXTURE_MAG_FILTER,
          sampler.magFilter === 'nearest' ? gl.NEAREST : gl.LINEAR
        )
        // 固定 clamp、没有 mipmap：任何尺寸（包括 NPOT）都能用，也不用每帧重建 mipmap
        gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_S, gl.CLAMP_TO_EDGE)
        gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_T, gl.CLAMP_TO_EDGE)

        // 第 index 个颜色槽 ← 这张纹理（GBuffer：0、1、2……）
        gl.framebufferTexture2D(
          gl.FRAMEBUFFER,
          gl.COLOR_ATTACHMENT0 + index,
          gl.TEXTURE_2D,
          texture,
          0
        )

        // 显存不够时 texImage2D 只留一个错误码；每个槽建完问一次
        assertTextureOperation(gl, 'allocate color attachment ' + index, label)
      }

      if (descriptor.depth !== undefined) {

      for (const texture of colors) gl.deleteTexture(texture)
      if (depth !== null) gl.deleteRenderbuffer(depth)
    }
    throw error
  } finally {
    // ④ 无论成败：还回 framebuffer、renderbuffer；viewport 从头到尾没动过
    if (!gl.isContextLost()) {
      gl.bindFramebuffer(gl.FRAMEBUFFER, previousFramebuffer)
      gl.bindRenderbuffer(gl.RENDERBUFFER, previousRenderbuffer)
    }
  }

// Backend 结束时：先退订，再删自己建的 GPU 对象；不 dispose CPU 的 RenderTarget
dispose(): void {
  if (this.disposed) return
  this.disposed = true

  this.entries.clear()
  for (const entry of entries) entry.unsubscribe()

  if (this.lost || this.gl.isContextLost()) {
    this.invalidateForContextLoss()
    return
  }

  for (const entry of entries) this.deleteResource(entry.resource)
  this.hooks.invalidateState()
}

4. 谁在用它：SurfaceScope

4.1 run：进去、画、原样出来

旧引擎的 bind / unbind 有 ⑤ 的问题：退出只会回屏幕。新架构把「画到哪」写成一个作用域：backend.withRenderSurface({ surface, clear }, () => { …draw… })，Backend 转给 SurfaceScope.run（WebGL1Backend.ts:180–182）。作用域可以嵌套，每一层退出都还原到进入前的样子： 

// WebGL1SurfaceScope.ts:191–244（注释是课程加的；工作区版本）
run(descriptor: RenderSurfaceScopeDescriptor, callback: () => undefined): void {
  this.assertAvailable()
  this.assertUnchanged()

  // 先验证、复制调用者的输入（surface、clear），这时还没发任何 GL 命令
  const next = snapshot(descriptor)

  if (typeof callback !== 'function')
    invalid('callback', 'must return undefined synchronously')

  const target = next.surface.kind === 'render-target' ? next.surface.target : null

  // 这一层的「身份证」：画到哪个目标、进来时它的 revision、canvas 多大。
  // assertUnchanged 之后拿它比对，发现中途被 resize、dispose 就报错
  const frame: ActiveScope = {
    target,
    revision: target === null ? 0 : target.revision,
    drawingWidth: this.gl.drawingBufferWidth,
    drawingHeight: this.gl.drawingBufferHeight
  }

  // ① 先记下进来时的真实绑定和 viewport（例：外层 GBuffer 的 FBO，0,0,1920,1080）
  const previous = this.state.captureSurfaceState()
  let failed = false
  let failure: unknown

  this.stack.push(frame)

  try {
    // ② 第一次用到这个目标时，这一行让 RenderTargetManager 建 FBO（懒创建）
    const resource = target === null ? null : this.hooks.resolveTarget(target)

    this.assertDrawable()
    // ③ 绑上这个目标的 FBO，viewport 设成它的宽高（默认输出则是 null 和 canvas 尺寸）
    this.state.bindSurface(resource)
    // ④ 入口清除：每次进入只清一次
    this.clearAttachments(next.clear)
    this.assertDrawable()

    // ⑤ 调用者在这里 draw（必须同步，不能 await）
    const result: unknown = callback()

    if (result !== undefined) invalid('callback', 'must return undefined synchronously')

    this.assertDrawable()
  } catch (error: unknown) {
    failed = true
    failure = error
  } finally {
    // ⑥ 无论成败：出栈，还回 ① 记下的绑定和 viewport
    this.stack.pop()

    try {
      this.restoreEntry(previous)
    } catch (restoreError: unknown) {
      // 操作失败、还原也失败：两个错误都留下，装进一个 AggregateError
      failure = failed
        ? new AggregateError(
            [failure, restoreError],
            'Surface operation and restoration failed'
          )
        : restoreError
      failed = true
    }
  }

  if (failed) throw failure
}

② 那一行就是 Manager 被调用的地方。注意 ① 在 ② 之前：先记下真实绑定，再去可能建 FBO 的 resolveTarget。Manager 的 create 自己会还原绑定，但 scope 不依赖这一点（第 7 节想一想）。③ 的 bindSurface 只做两件事：绑 FBO、把 viewport 设成目标的宽高（WebGL1State.ts:207–217）。

// assertDrawable 里调用的检查：逐层比对 run 进来时记下的「身份证」
private assertUnchanged(): void {
  for (const frame of this.stack) {
    // canvas 尺寸变了（drawing buffer 被 resize）
    if (
      this.gl.drawingBufferWidth !== frame.drawingWidth ||
      this.gl.drawingBufferHeight !== frame.drawingHeight
    ) {
      throw new RenderTargetUnavailableError(
        'drawing buffer',
        'resized inside an active scope'
      )
    }

    // 某一层的目标被 dispose 或 resize 了：它的 FBO 已经或即将被换掉
    if (
      frame.target !== null &&
      (frame.target.disposed || frame.target.revision !== frame.revision)
    ) {
      throw new RenderTargetUnavailableError(
        'active scope',
        'target was disposed or resized'
      )
    }
  }
}

为什么只比栈顶？GL 只往当前绑着的那一个 FBO 里写。在 gbuffer 里嵌套画 shadow 时，gbuffer 暂停了，这时读 gbuffer 没有冲突；回到 gbuffer 以后，读 gbuffer 才是边写边读。为什么能用 RenderTarget 的身份比，而不比 WebGLFramebuffer？因为本阶段每个 RenderTarget 独占自己的存储，「同一个目标」就等于「同一组纹理」（:269 的注释）。

4.3 scope 里不能改目标

run 进来时给每一层记了一张「身份证」：目标、它的 revision、canvas 尺寸。assertUnchanged 逐层比对。为什么要逐层、而不只是栈顶？设想外层在画 gbuffer，内层在画 shadow，这时有人把 gbuffer resize 了：下一次 draw 采样 gbuffer，resolveSampledColor 会让 Manager 按新 revision 重建 gbuffer、删掉旧 FBO，而外层 scope 记下的「退出时还回去」的正是那个旧 FBO。Manager 自己的检查（「正绑着的 FBO 不能重建」）只看当前绑定，看不到暂停中的外层（RenderTargetManager.ts:48–50 的注释就写了这个限制），所以要 scope 来补。

结果是「宁可整串报错，也不画到错的地方」：内层 run 的操作失败、还原也失败（assertUnchanged 在 restoreEntry 里又查了一次），两个错误装进一个 AggregateError；外层 run 把它原样抛出，但外层自己的还原成功了，所以最后绑定和 viewport 回到了 canvas。scope 只能发现违规，不能阻止调用者去 resize（:251–252 的注释）。

5. 和 Lifecycle 的关系

第 13 课第 2 节说，context 丢了以后，Backend 要把旧的一代作废、再建新的一代。RenderTargetManager 在这两件事里做的事：

  • 一代一个。ResourceManager 新建它（WebGL1ResourceManager.ts:109），SurfaceScope 的 resolveTarget 和 Uniforms 的附件解析用的都是这一代的（Backend.ts:279、:292–302）。释放顺序里它排在两个纹理 Manager 前面（:112–119）：它是借用方之后最先结束的所有者。
  • lost 事件到达：丢记录、退订，不 delete。invalidateForContextLoss（:380–385）和纹理 Manager 一样；create 的 catch、finally 遇到 lost 也不删、不还原绑定（3.4 节）。SurfaceScope 的还原遇到 lost 只让 State 忘掉缓存（SurfaceScope.ts:294–298）。注意 lost 标记只有两个来源：有人调用 invalidateForContextLoss，或者丢失期间有人调用 get、自己看到 isContextLost。下面的卡片里，一个没人通知、丢失期间也没被调用的 Manager，恢复后会把旧 FBO 当缓存交出去：这就是 lost 事件必须通知到每个 Manager 的原因。
  • 恢复以后：新的 FBO，空的内容。RenderTarget 的描述和 revision 都还在 CPU 上，新一代的 Manager 第一次 get 就能建出一样大小的 FBO。但里面的像素是 GPU 画的，CPU 上从来没有，所以新存储是全 0：要由拥有它的 pass 重画（RenderTarget.ts:407；Backend.ts 的 attachment-content-rebuild 注释）。这和纹理不同：纹理从 CPU 原料重传，画布只能重画。

6. 架构视角：对照 three.js r177

  • 同样懒创建。three.js 的 setRenderTarget(rt) 发现这个目标还没有 FBO，就当场建（WebGLRenderer.js:2683、:2704–2706），和本项目「第一次 get 才建」一样。
  • 不查完整性。r177 的源码里一次都没有调用 checkFramebufferStatus（全目录搜索为 0）：它相信自己的格式表配出来的组合一定完整。本项目在 WebGL1 上要处理扩展有无、设备差异，所以每次建完都问，并把状态码变成 IncompleteFramebufferError。
  • 建完绑回 null，切换靠调用者手动保存。three.js 挂附件后直接 bindFramebuffer(null)（WebGLTextures.js:1552–1564），和旧引擎一样。它能这样做，是因为它独占 context，每次 setRenderTarget 都重新绑定。嵌套使用时，由调用者自己记住旧目标再设回去，比如 PMREMGenerator 先 getRenderTarget() 存下（PMREMGenerator.js:127），用完 setRenderTarget(旧的)（:253）。本项目把这件事做进了 SurfaceScope 的栈，调用者忘不了。
  • 深度。three.js 的 RenderTarget 默认带深度缓冲，WebGL2 下也可以用深度纹理直接采样；本项目 WebGL1 只描述 depth16 renderbuffer，阴影走 RGBA 打包（1.1 节）。

7. 审查视角

  • 想一想：capture 为什么要在 resolveTarget 之前？run 的注释说「首次创建 FBO 可能改变实际绑定」，可 3.4 节的 create 明明会还原 framebuffer 和 renderbuffer。既然 Manager 已经还原了，scope 先 capture 还有什么用？如果把 ① 挪到 ② 之后，在什么情况下会出错？（提示：resolveTarget 是一个 hook，scope 不知道它背后是谁；再想想 create 中途 context 丢失时 finally 做了什么。）
  • 想一想：要采样深度该怎么改？Capabilities 里已经探测了 WEBGL_depth_texture（WebGL1Capabilities.ts:46）。如果要让阴影贴图直接用深度纹理（省掉 1.1 节的打包），RenderTarget 的描述、validate、create、resolveSampledColor、SurfaceScope 的 depth clear 检查，各要改什么？哪些检查放在 CPU 资源里，哪些放在 Manager 里（第 29 课 8.1 节的三个问题）？
  • 想一想：半分辨率的附件怎么描述？2.3 节实测，WebGL1 要求一个 FBO 的附件同尺寸（36057）。如果 GBuffer 想要一张一半分辨率的环境光遮蔽图，在现在的 RenderTarget 描述里该怎么表达？要不要给颜色槽加一个「各自的尺寸」字段？
  • 和第 29 课 12.1 节同一个问题。RenderTargetManager 的 release 先从表里删掉条目、再删 GPU 对象；dispose 用 disposed 早退、先清空表（3.6 节节选）。某一次 delete 抛错的话，剩下的对象再没人删。Texture2DManager 的写法（closing + 删成功才移出表）可以重试。
