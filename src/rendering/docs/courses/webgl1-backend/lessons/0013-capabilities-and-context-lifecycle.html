backend ①：这台设备能做什么，context 丢了又回来怎么办

后端开工之前要回答两个问题。第一，这台设备、这个 context 支持哪些扩展，上限是多少：这由 Capabilities 回答。第二，GPU 随时可能被浏览器收回，收回又还回来时，怎样不在坏掉的 context 上画、怎样把要用的东西重新建起来：这由 ContextLifecycle 安排。Capabilities 按「先写需求，再一版一版写出来」的方式讲；ContextLifecycle 只讲主线，边角情况放到第 28 课。

和你的目标的关系 —— WebGL1Backend 每建一代 Manager，都先调用一次 detectWebGL1Capabilities（WebGL1Backend.ts:259–260）；context 丢失和恢复的全部顺序，都由 WebGLContextLifecycle 安排（:78–111）。第 19 课讲的是 Backend 怎样用它们，这一课讲它们自己为什么这样写。
默认你已经会的：getExtension、getParameter、isContextLost 这些调用，以及「丢失期间每个入口都要问一次浏览器」（第 2 课）；每个 context 一份 GPU 表示，丢失时整批作废（第 4 课）；第 6 课那张五个状态的图；Backend 的 generation 和 epoch（第 19 课）。
这一课从零讲的：Capabilities 每一行防的是什么；context 什么时候会丢，丢了以后必须做哪两件事，Backend 怎样通过回调完成它们，五个状态怎样回答「现在能画吗」。回调抛错、回调里关掉 Backend、transitionVersion，留到第 28 课。
页面会用到你的显卡：第 1、2 节的卡片都会在你的浏览器里创建 WebGL context，并用 WEBGL_lose_context 让它丢失、再恢复。卡片跑完会把 context 释放掉。

1. Capabilities：这台设备、这个 context 能做什么

1.1 需求：谁要用这些信息

WebGL1 的很多功能是扩展，不同设备不一样。后端的几个 Manager 开工前，都要先知道一件具体的事：

  • 顶点输入用哪种策略：有 OES_vertex_array_object 就用 VAO，没有就每次手动接线（WebGL1VertexInputManager.ts:67–73）。
  • 能不能用 Uint32 索引：没有 OES_element_index_uint 时，Uint32 索引只有在每个值都不超过 65535 时，才转成 Uint16 继续用；否则抛 UnsupportedIndexTypeError（WebGL1GeometryManager.ts:290–304）。
  • 能不能一次写多个颜色附件：要 WEBGL_draw_buffers（WebGL1RenderTargetManager.ts:207）。
  • 能不能用浮点纹理、浮点纹理能不能线性过滤：OES_texture_float、OES_texture_float_linear（WebGL1CubeTextureManager.ts:234–239）。
  • 最多几个顶点属性、几个纹理单元：MAX_VERTEX_ATTRIBS 给顶点输入用，MAX_TEXTURE_IMAGE_UNITS 给 sampler 计数用（WebGL1Uniforms.ts:138）。

所以 Capabilities 要做的事很简单：问浏览器一遍，把答案装进一个对象，交给这些 Manager。难点在「问的时候 context 可能正在丢」。

1.2 先看原始输入：浏览器交回什么

gl.getExtension(名字) 支持就交回一个扩展对象，不支持就交回 null；gl.getParameter(常量) 交回一个数字。下面这张卡片在你的浏览器里真的跑一遍项目的 detectWebGL1Capabilities。我备课时用无界面 Chrome 的软件渲染（SwiftShader）跑出来的结果是：六个扩展都有，MAX_VERTEX_ATTRIBS 是 16，MAX_TEXTURE_IMAGE_UNITS 是 32。你的显卡可能不同。

1.3 第 1 版：直接查

// 第 1 版：直接查，存成一个对象
function detectNaive(gl: WebGLRenderingContext) {
  return {
    // 支持就是扩展对象，不支持就是 null
    vertexArrayObject: gl.getExtension('OES_vertex_array_object'),
    elementIndexUint: gl.getExtension('OES_element_index_uint'),
    drawBuffers: gl.getExtension('WEBGL_draw_buffers'),
    depthTexture: gl.getExtension('WEBGL_depth_texture'),
    textureFloat: gl.getExtension('OES_texture_float'),
    textureFloatLinear: gl.getExtension('OES_texture_float_linear'),
    maxVertexAttributes: gl.getParameter(gl.MAX_VERTEX_ATTRIBS) as number, // 以为一定是数字
    maxTextureUnits: gl.getParameter(gl.MAX_TEXTURE_IMAGE_UNITS) as number
  }
}

1.4 真实代码：查询前后各问一次，上限必须是正整数

// 项目里的真实代码（WebGL1Capabilities.ts:26–65，注释是课程加的）

// 上限必须是正的安全整数。丢失期间 getParameter 返回 null，
// 不能当成「上限是 0」或「上限未知」混过去
function reqiurePositiveLimit(value: unknown, name: string): number {
  if (typeof value !== 'number' || !Number.isSafeInteger(value) || value <= 0)
    throw new UnsupportedRenderFeatureError(name, 'must report a positive safe integer')
  return value
}

export function detectWebGL1Capabilities(gl: WebGLRenderingContext): WebGL1Capabilities {
  // 第一道：已经丢了就别查。否则后面全是 null，看起来像「这台设备什么都不支持」
  if (gl.isContextLost()) throw new WebGLContextLostError('detect capabilities')

  const vertexArrayObject = gl.getExtension('OES_vertex_array_object')
  const elementIndexUint = gl.getExtension('OES_element_index_uint')
  const drawBuffers = gl.getExtension('WEBGL_draw_buffers')
  const depthTexture = gl.getExtension('WEBGL_depth_texture')
  const textureFloat = gl.getExtension('OES_texture_float')
  const textureFloatLinear = gl.getExtension('OES_texture_float_linear')

  // 先收成 unknown：getParameter 的返回值是 any，丢失期间是 null，不能直接当数字用
  const maxVertexAttributes: unknown = gl.getParameter(gl.MAX_VERTEX_ATTRIBS)
  const maxTextureUnits: unknown = gl.getParameter(gl.MAX_TEXTURE_IMAGE_UNITS)

  // 第二道：查询途中丢了，上面那些 null 可能是「丢了」造成的，不是「不支持」。整份结果作废
  if (gl.isContextLost()) throw new WebGLContextLostError('detect capabilities')

  // 冻结外层：快照发出去以后谁也改不了。扩展对象是浏览器给的，不去冻结它
  // 每次调用都返回一个新快照，不缓存：恢复以后必须重新探测（见 1.5）
  return Object.freeze({
    vertexArrayObject,
    elementIndexUint,
    drawBuffers,
    depthTexture,
    textureFloat,
    textureFloatLinear,
    maxVertexAttributes: reqiurePositiveLimit(maxVertexAttributes, 'MAX_VERTEX_ATTRIBS'),
    maxTextureUnits: reqiurePositiveLimit(maxTextureUnits, 'MAX_TEXTURE_IMAGE_UNITS')
  })
}

1.5 为什么不缓存，恢复以后为什么要重新探测

detectWebGL1Capabilities 每次调用都返回新的快照，Backend 每建一代 Manager 都重新探测一次，包括恢复的时候（第 2.3 节）。为什么不在第一次探测后存起来复用？看看恢复以后，继续用旧快照里的扩展对象会怎样：

MDN 对恢复的说法是：丢失之前创建的纹理、buffer 等资源都失效了，要重新初始化、重新创建（MDN · webglcontextrestored）。扩展对象也一样，要重新 getExtension。我在规范里没找到「旧扩展对象调用时会怎样」的明确条文，Chrome 的表现是上面这样：不报错，结果却是坏的。所以不能指望旧对象，整份快照重新探测。

2. ContextLifecycle：context 丢了又回来

这一节只讲主线：什么时候会丢、丢了以后必须做哪两件事、这两件事由谁来做、渲染循环怎样知道「现在不能画」。回调里抛错、回调里把 Backend 关掉这些边角情况，放到第 28 课：要先认识 State 和各个 Manager，才知道丢掉、重建的到底是什么。

2.1 真实场景：页面的 GPU 被收走

GPU 是整台电脑共用的，浏览器可以收走某个页面的 WebGL context。常见的原因有：

  • 显卡驱动崩溃或被系统重置；
  • 浏览器的 GPU 进程崩溃；
  • 页面开的 WebGL context 太多：Chrome 超过上限时，会丢掉最早的一个。

调试时还可以用 WEBGL_lose_context 扩展手动制造一次：loseContext() 让它丢失，restoreContext() 请浏览器恢复。下面的卡片就用它，在你的浏览器里建一个 buffer，然后丢一次、恢复一次：

浏览器在这件事里只做两件事：

  1. 丢失时，在 canvas 上派发 webglcontextlost 事件。
  2. 能恢复时，再派发 webglcontextrestored 事件。恢复后的 gl 还是原来那个对象，但里面是空的：之前建过的 buffer、program、纹理、framebuffer 全都失效了。

2.2 不写类，最少要做什么

先不管项目的类，只用最少的代码应付这两个事件：

let canDraw = true // 渲染循环每帧先看它：false 就这一帧什么都不画

canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault() // 告诉浏览器「我想要恢复」：不调用的话，浏览器不会再派发 restored
  canDraw = false        // 旧的 GPU 对象全失效了，不能再拿它们去画
  // 第一件事：把记着旧 buffer、旧 program 的那些表作废
})

canvas.addEventListener('webglcontextrestored', () => {
  // 第二件事：gl 又能用了，但它是空的。重新探测设备（第 1.5 节），重新建好要用的东西
  canDraw = true // 都准备好了，才允许继续画
})

WebGLContextLifecycle 做的，本质上就是这十几行：监听两个事件，维护「现在能不能画」，在合适的时候做那两件事。

2.3 两件事交给 Backend：回调

生命周期类只管「什么时候做、按什么顺序做」。它不知道项目里有哪些 buffer、哪些 program，所以「具体做什么」由 Backend 在构造时以回调的形式交给它（WebGL1Backend.ts:78–111）：

回调对应上面哪一处Backend 实际做的事
onLost第一件事：把旧的作废invalidateGeneration：把这一代整体标成失效，清空 State 的缓存，让每个 Manager 丢掉自己的记录，但不对失效的 handle 调用 delete（:331–336）
restore第二件事：重新建createGeneration：重新探测 Capabilities，新建 State、ResourceManager（里面是全新的 ProgramManager、GeometryManager……）、Uniforms 和 scope（:259–305）
onReady恢复的最后一步再问一次 isContextLost，确认没有又丢
onRestoreFailed恢复失败时通知上层现在是空的（第 4 节审查视角第 2 条）
onSuppressedError诊断用第 28 课再讲

拿 HW2 的 PRT shader 走一遍（ProgramManager 是第 15 课的内容，这里只需要知道它有一个缓存）：

第 1 帧      programs.get(PRT shader)：编译、链接得到 program P1，存进第 1 代 ProgramManager 的缓存
……浏览器收走 GPU……
lost         P1、Mary 的 buffer、背景 cubemap 全部失效
             onLost → 第 1 代整体作废（连同它的 ProgramManager 和缓存）
……浏览器说可以恢复了……
restored     restore → 建第 2 代：一个全新的 ProgramManager，缓存是空的
下一帧       programs.get(PRT shader)：缓存里没有，重新编译，得到 P2；buffer、cubemap 也重新上传

Scene、Mesh、Material、ShaderModule 这些 CPU 对象从头到尾没有变，只有 GPU 那一份被扔掉、重建。这正是第 4 课「一份 CPU 资源，每个 context 一份 GPU 表示」换来的好处：重建时，CPU 那一份就是原料。从第 14 课起，每讲一个 Manager，都有一节「和 Lifecycle 的关系」，说明它在这两件事里各做什么。

2.4 状态：回答「现在能画吗」

2.2 节用一个布尔值就够表达意思了。项目把它细分成 5 个状态，因为上层除了「能不能画」，还要知道别的。先看一条时间线：

时间     发生了什么                    状态            渲染循环
t=0      Backend 建好                  ready           每帧照常画
t=5 s    浏览器收走 GPU（lost）        lost            每帧跳过
t=5.1 s  restored 到了，正在建第 2 代  restoring       跳过（只要几毫秒）
t=5.1 s  第 2 代建完                   ready           又开始画，先重新编译、上传
另一种结局：重建时出错（比如又丢了）   restore-failed  跳过；再来一次 restored 时可以再试
用户离开 HW2，Engine 关掉 Backend      disposed        以后什么事件都不理

lost、restoring、restore-failed、disposed 四个状态都「不能画」，但对后面的事回答不同，所以不能合成一个布尔值：

状态再收到 restored 怎么办上层能看出什么
lost开始恢复正在等浏览器
restoring忽略：不能同时建两代正在重建
restore-failed再试一次恢复失败过，要报告给用户
disposed忽略：已经关了已经关闭

渲染循环就是这样用它的：Backend.ready 等于 lifecycle.isReady 并且这一代有效；如果浏览器已经丢了、事件还在排队，它先发现、先作废这一代（WebGL1Backend.ts:114–120）。Renderer.render 第一行就是 if (!this.backend.ready) return（Renderer.ts:51）。所以丢失、重建期间每一帧都直接返回，不会拿已经失效的 P1 去 draw。

2.5 备课时的实测记录

同样的过程，备课时在无界面 Chrome 里记下的时间：

  0 ms  构造完成（state=ready，isReady=true）
  5 ms  调用 loseContext()，它返回时 state 还是 ready      ← lost 事件还在排队，没派发
  5 ms  onLost 被调用（state=lost，isReady=false）          ← 事件派发：先改状态，再调回调
 56 ms  调用 restoreContext()，它返回时 state 还是 lost     ← restored 事件同样要排队
179 ms  restore 被调用（state=restoring，isReady=false）    ← 重新探测：8 个字段
179 ms  onReady 被调用（state=restoring，isReady=false）    ← 收尾时仍然不能 draw
180 ms  之后（state=ready，isReady=true）                   ← 全部完成，最后才变成 ready

另一次实测里，restored 事件过了 2.2 秒才到。恢复要多久，由浏览器决定。还有一点：lost 事件里如果不调用 preventDefault()，这个 context 就不会被标记为可恢复，restoreContext() 会失败（WEBGL_lose_context 规范）。实测：不调用的话，restored 事件始终没有来。

2.6 留到第 28 课的：边角情况

上面讲的是「回调都正常结束」的主线。真实代码里还有一大半在处理边角情况：onLost 或 restore 抛错了怎么办；回调执行到一半，有人把 Backend 关了，或者 context 又丢了，外面那一轮还能不能把状态写成 ready；作废那一轮的错误要不要记。lastFailure、onSuppressedError 和 transitionVersion 都是为这些情况准备的。它们排在第 28 课（第 18 课之后）：到那时你已经知道每个 Manager 在丢失、重建时做什么，再看「这几步中途出错」才有具体的东西可想。

3. 架构视角：对照 three.js r177

  • 扩展：一样要重新查。three.js 的 WebGLExtensions 第一次 get 某个扩展时调用 getExtension，之后从对象里取缓存（WebGLExtensions.js:7–40）。恢复时 initGLContext 会新建 WebGLExtensions 和 WebGLCapabilities（WebGLRenderer.js:401–408），所以缓存也跟着换掉了。两边的结论相同：快照只属于一代。不同的是 three.js 的上限（WebGLCapabilities.js:97、102）直接拿 getParameter 的返回值，不检查是不是数字。
  • 生命周期：three.js 只用一个布尔值 _isContextLost。丢失时调用 preventDefault 并把它设为 true，恢复时设回 false、再整体重建（WebGLRenderer.js:1013–1035）。主线和本项目一样：丢了就不画，恢复了就重建。两边在「重建途中出错」时的差别，放到第 28 课和项目的处理一起比。
