2. 显示器的节拍

最底下是硬件。显示器每秒刷新固定的次数：60 Hz 就是每 1000 / 60 ≈ 16.67 ms 刷一次，120 Hz 是 8.33 ms。每次刷新从上到下逐行扫出一整张图。两次刷新之间有一小段空档，叫垂直消隐期 (vertical blanking interval)，换下一张图就在这时候换；如果扫到一半就换，上半屏是旧图、下半屏是新图，这叫撕裂 (tearing)。「现在可以换图了」这个信号叫垂直同步 (vertical sync，简称 vsync)。

浏览器跟着这个节拍走。HTML 规范把「这一刻能把页面内容交给用户看」叫作一次渲染机会 (rendering opportunity)；它举的例子是：浏览器想做到 60 Hz，渲染机会就最多每 1/60 秒一次，约 16.7 ms（HTML 规范 8.1.7.3）。Chrome 的架构文档说，主线程上的渲染「按和设备显示器相同的节奏安排」（RenderingNG architecture）。每到一次渲染机会，浏览器就往主线程的队列里放一个「更新渲染」(update the rendering) 任务，rAF (requestAnimationFrame) 回调就在这个任务里运行。所以：

  • 一帧在这一课里指一次「更新渲染」：浏览器跑一遍 rAF 回调，再把结果交给屏幕。
  • rAF 回调多久跑一次，由显示器决定。MDN 的说法是回调频率「通常和显示器刷新率一致」（MDN · requestAnimationFrame）。
  • 所以代码里不能写死 16 ms：120 Hz 的屏上每帧只有 8.33 ms。

3. 主线程一次只做一件事

页面上的 JS 都在一条线程上跑，叫主线程 (main thread)。主线程上有一个事件循环 (event loop)，HTML 规范把它写成三步（8.1.7.3 的第 2.1–2.8 步）：

  1. 挑一个任务队列（挑哪个由浏览器决定，Chrome 会优先处理输入），取出里面最早的一个可以运行的任务 (task)；
  2. 运行它，一直到它的调用栈空了为止；
  3. 做一次微任务检查点 (microtask checkpoint)，见第 4 节；然后回到第 1 步。

任务就是浏览器交给主线程的一段「从头跑到底」的工作：一次事件派发（点击、按键、input），一个到点的定时器回调，一次网络请求完成后的回调，还有第 2 节的「更新渲染」。第 2 步没有「跑到一半先停一下」：一个任务开始以后，中途不会被别的任务打断，这就是第 43 课说的 run-to-completion（MDN · Run-to-completion）。

那用户在这一帧的第 8 ms 点了鼠标，谁收下这个点击？不是主线程。操作系统把输入交给浏览器，浏览器在另一条线程上收下它，给主线程排一个任务（Chrome 的合成器线程「处理输入事件」，见 RenderingNG 文档）。主线程正在跑 Engine.loop，就排着。图 1 里那条红色的排队，就是这段等待。

实测（无界面 Chrome，用 DevTools 协议 (Chrome DevTools Protocol) 模拟真人点击）：一帧的 rAF 回调里两遍各忙 150 ms，在第 72 ms 点按钮。

4. 一帧里的顺序

「更新渲染」这个任务里有 23 小步（HTML 规范 update the rendering）。和这一课有关的是这几步：

小步做什么项目里是谁
第 8 步 resize窗口尺寸变了，派发 resize 事件Engine.handleResize
第 14 步 rAF 回调依次调用这一帧之前登记的 rAF 回调，每个回调都拿到同一个时间戳Engine.loop：两遍都在这里
第 16 步 样式、布局重算样式和布局，其中跑 ResizeObserver 回调项目没用 ResizeObserver（engine.ts:800 的注释）
第 22 步 更新画面把这一帧的结果交给合成器 (compositor)，由它在 vsync 时显示WebGL 画布在这里交出去

四条规则，都能在规范里找到原文：

  • rAF 回调里再登记的 rAF，排到下一帧。第 14 步开头先取出「现在已有的回调编号」，再一个个调用（run the animation frame callbacks 第 1–3 步）。所以 Engine 每帧在 finally 里登记下一帧，不会在这一帧里转圈。
  • 微任务 (microtask) 在调用栈空了的时候跑。微任务是 Promise.then 的回调、await 后面的那部分代码。规范的规则是：一段脚本跑完，如果 JS 的调用栈已经空了，就做一次微任务检查点，把微任务队列全部跑完（clean up after running script 第 3 步）。Engine.loop 到 Pass 2 是同一个调用栈，所以 Pass 1 里排下的 then，要等整个 loop 返回才跑。
  • 事件回调的派发也是同步的。浏览器自己派发的事件要排队；可你在代码里调 dispatchEvent，监听器就在这一行里立刻跑完再返回（第 8 节卡片 D）。
  • resize 回调在 rAF 回调之前。窗口在一帧中间变了，resize 事件等到下一次更新渲染的第 8 步才派发，那时这一帧的 Engine.loop 早已返回，下一帧的还没开始。
  • 拖动产生的 pointermove 也对齐到帧。Chrome 60 起，pointermove 这类连续事件会被推迟、几次合并成一次，放在 rAF 回调之前派发；pointerdown、keydown 这类离散事件来了就排队（Chrome · Aligned input events；备课实测也是这样，拖动时 pointermove 回调紧挨着下一个 rAF 回调）。所以第 26 课拖动画布转相机，写 Transform 的那一刻就在 Engine.loop 开始前一点点，下一帧马上画出来，也同样插不进两遍之间。

实测顺序（无界面 Chrome。Pass 1 里依次排了一个 then、一个 setTimeout(…, 0)、一条 MessageChannel 消息、一个 rAF，又同步 dispatchEvent 了一个 pointerdown；另一次实验在帧中间改视口尺寸）：

离这一帧开始发生了什么
20.5 msdispatchEvent 的监听器（Pass 1 里面，同步）
40.5 msPass 2 结束，rAF 回调返回
40.5 msPass 1 排的 then 回调：回调一返回，栈空了，马上跑
40.5 ms同一帧登记的第二个 rAF 回调
40.7 msPass 1 排的 setTimeout 0，然后是 MessageChannel 消息：它们是任务，排在这次更新渲染之后
40.7 msPass 1 里登记的 rAF：已经是下一帧（这一帧做了 40 ms，下一个 vsync 早过了，所以下一帧马上开始）

改视口那一次（两遍各 150 ms，第 60 ms 改成 900 宽）：rAF 回调在 300.0 ms 返回；302.0 ms 下一次更新渲染开始，先是 resize 回调（innerWidth = 900），然后是 rAF 回调，最后 302.1 ms 是 ResizeObserver 回调。顺序和规范的第 8、14、16 步一致。

WebGL 画布什么时候交出去。WebGL 规范说，画布在「合成之前」交给合成器；默认（preserveDrawingBuffer: false）合成之后画布内容清成默认值（WebGL 1.0 规范 2.2 节）。合成在第 22 步之后发生，所以「画完再读」只有在同一次更新渲染里才读得到。第 22 课课程代码里 snapshot 的注释「要在画完的同一个任务里调用」，原因就在这里。

5. 一帧超过 16.7 ms 会怎样

Engine.loop 跑得比一个 vsync 间隔还久，这一次渲染机会就错过了。错过以后浏览器怎样安排下一帧，实测比 9 月那次对话说的要好：那次说「60 Hz 下帧率只能是 60、30、20、15」，可在 Chrome（无界面）里量出来不是这样。下面是每帧在 rAF 回调里多忙一会儿，连续 60 帧：

每帧多忙rAF 时间戳的差回调真正开始的平均间隔帧率
5 ms、12 ms全是 16.7 ms16.7 ms60
20 ms16.7 和 33.4 混着来（60 个里 12 个是 33.4）20.0 ms约 50
40 ms33.3 和 50.0 混着来40.0 ms约 25

两件事：

  • 帧率约等于「刷新率」和「1000 / 每帧工作毫秒」两者中较小的一个。工作 20 ms 时，上一帧一做完，下一帧就开始（错过的 vsync 已经过了，浏览器不再等），所以平均 20 ms 一帧。
  • rAF 拿到的时间戳总是落在 vsync 上，所以时间戳之差是 16.7 的整数倍，单看一个差值会以为掉到了 30。同一帧里所有 rAF 回调拿到同一个时间戳（MDN）。

6. JS 之外还在变的东西

run-to-completion 只保证一件事：别的 JS 回调插不进来。别的线程、别的进程照样在跑，它们改的东西，你的代码下一次去读就能读到：

  • GPU 进程。context 可能在任何时刻丢失。WebGL 规范的丢失步骤是：先立起「已丢失」标志（第 3 步），再「排一个任务」去派发 webglcontextlost（第 6 步）。所以 Pass 1 末尾丢了，Pass 2 里 isContextLost() 马上是 true，lost 回调却要等这一帧跑完。这就是 Backend 每次 draw 都自己查 isContextLost()、不等事件的原因（第 46、47 课；稳定的一帧里查 159 次）。见下面的卡片 E。
  • 合成器线程。页面滚动、只改 transform 和 opacity 的 CSS 动画，可以不经过主线程（RenderingNG 文档：滚动和动画「可以并行运行」）。和画布内容无关，这里不展开。
  • Worker（以后）。如果 FLIP 的仿真放进 Worker，主线程和 Worker 共用一块 SharedArrayBuffer 存粒子位置，那么 Worker 可以在你的两遍之间改它——run-to-completion 管不到另一条线程。到时候要么每帧开头抄一份（第 43 课的快照思路），要么两块缓冲区轮流用。

7. 哪种写法让保证失效：await

保证的单位是一个调用栈。async 函数遇到 await，会先把调用栈还回去：await 后面的代码要么变成微任务，要么要等某个任务完成以后才接着跑。把两遍之间写成三种样子，每种都在 Pass 1 进行到 70–80 ms 时点一下按钮（无界面 Chrome，两遍各 150 ms）：

两遍之间点击回调什么时候跑插进两遍之间了吗
什么都不做72.2 ms 点击，回调返回之后（300.5 ms）才跑，输入延迟 228.1 ms没有
await null81.6 ms 点击，回调返回之后（300.3 ms）才跑，输入延迟 218.7 ms。await 一个已经完成的值，后面的代码是微任务，只有微任务插得进来，点击是任务没有
await 一个定时器81.1 ms 点击，150.3 ms 就跑了（输入延迟 69.1 ms）：Pass 1 在 150.0 结束，点击回调先跑，Pass 2 在 150.5 才开始。同一帧登记的第二个 rAF 回调也在 150.0 抢先跑了插进来了

插进来以后可能出三种事：① 回调改了场景，两遍看到的不一样（第 9 节的实验台可以亲眼看）；② 别的 rAF 回调在两遍之间跑；③ 让出去的时间够长，浏览器会在两遍之间更新一次画面，把只画了一半的画布交出去。

项目从三处防这件事：

  • 接口的返回类型。RenderPass.execute 的返回类型写的是 undefined，注释写明「必须同步完成；不得返回 Promise」（RenderPass.ts:7–8）。async 函数一定返回 Promise，所以写成 async execute() 编译不过。备课时用 TypeScript 5.8.3 和项目的 tsconfig 试过：报 TS2416（Property 'execute' … is not assignable to the same property in base type 'RenderPass'）。如果返回类型写成 void，同样的 async 写法就能编译通过——TypeScript 允许把返回 Promise 的函数赋给返回 void 的函数类型。所以这里用 undefined 是有意的。withRenderSurface 的回调同样是 () => undefined。
  • 作用域检查。WebGL1SurfaceScope 的注释把「跨 await」和「目标销毁、改尺寸」并列为不合法的作用域行为，出作用域时检查画布和目标有没有被改过（WebGL1SurfaceScope.ts:318–333）。
  • 异步只放在帧外。Engine.enterRenderMode 返回 Promise，可现在的 WebGL1 在调用里同步建好；注释里的 TODO 写着：接入异步后端（WebGPU 申请 adapter、device）时，await 期间要有「打开中」状态（engine.ts:251–253）。因为那段 await 期间，rAF 照样一帧帧来，用户事件也照样来。

所以两道防线各管一半：run-to-completion 挡住帧外的代码（事件、定时器），快照挡住帧内的代码（排在中间的 Pass、await 之后插进来的回调）。两道都在，一帧才稳。


    
10. 对照 three.js

    
    
      
  • 动画循环。WebGLRenderer.setAnimationLoop（WebGLRenderer.js:1496–1503）交给 WebGLAnimation：rAF 回调里先跑你的循环函数，再登记下一帧（WebGLAnimation.js:8–14），和 Engine 的 loop + scheduleFrame 是一个形状。进入 WebXR 时换成 XR 会话自己的 rAF（:1499 的 xr.setAnimationLoop），因为头显的刷新率和显示器不同。
    • 
      
  • render 是同步的。帧内能插进两遍之间的，是 onBeforeRender、onBeforeShadow 这类回调（第 43 课第 2 节）：它们是帧内代码，run-to-completion 挡不住，只能靠约定。
    • 
      
  • WebGPU 那一套（renderers/common/）也只在帧外 await。初始化要申请 GPU 设备，是异步的：renderAsync 先 await this.init()，再同步画（common/Renderer.js:974–978）；没初始化就调 render，会警告并转去 renderAsync（:1188–1193）；setAnimationLoop 也先等初始化（:1603–1608）。画一帧本身不 await——和本项目 execute(): undefined 是同一个思路。
    • 
      
  • 回读要跨帧。readRenderTargetPixelsAsync（WebGLRenderer.js:2929）用 WebGL2 的 fenceSync 等 GPU 做完再读，结果要过几帧才到。以后 FLIP 的 GPU 版要把结果读回 CPU（第 22 课 R3 ④），就得自己记住「这份数据属于哪一帧」。
    • 
    


    
11. 小结：把第 1 节的表补完

    

      

        
谁什么时候运行插得进两遍之间吗

        
滑块的 input 回调、拖动画布的 pointermove 回调浏览器排的任务：等这一帧的更新渲染跑完不能（除非帧里 await 一个任务，第 7 节）

        
窗口的 resize 回调下一次更新渲染的第 8 步，rAF 回调之前不能

        
排在两遍之间的另一个 Pass同一个调用栈里，按顺序能：靠快照（第 43 课）

        
Pass 1 里排的 Promise.thenrAF 回调返回、栈空了的那一刻不能：它在两遍之后、下一个 rAF 回调之前

        
帧里 dispatchEvent 触发的监听器就在那一行，同步能：它是帧内代码

        
GPU 丢失 context标志随时变，事件排成任务状态能变（isContextLost() 立刻是 true），回调不能
