1. 要解释的那句话

迁移计划（claude-workspace/fft-ocean-migration/2026-10-02-fft-ocean-migration-plan.zh-CN.md）决定 4 的原文：

FFT 每次 draw 都换目标，所以每个 draw 要单独开一个 scope。默认配置下（4 层，N = 512，log₂N = 9）：每层每帧 74 次 draw：频谱 1 次、IFFT 4 × 2 × 9 = 72 次、assembly 1 次；4 层共 296 个 scope，每帧约 592 次状态查询；旧 v3 只在 pass 入口查 7 次。

这句话里藏着四个问题：

  1. 「查询」是什么，和别的 GL 调用有什么不同？（第 2 节）
  2. 为什么「开一个 scope」就要查询？一次查几项？（第 3 节）
  3. 为什么 FFT「每次 draw 都换目标」，于是每次 draw 都要开一个 scope？（第 4 节）
  4. 74、296、592 怎么来的？旧代码为什么只要 7 次？（第 5、6 节）

先说两个用词。scope 就是一次 backend.withRenderSurface(…)：从进入到退出这一段，画出来的东西都落在同一个目的地上。这一课把「进入 scope」叫进门，「退出 scope」叫出门。目标 (target) 就是目的地：屏幕，或者一块 RenderTarget。

2. 命令和查询

JavaScript 调用的 WebGL 方法分两种：

命令 (command)查询 (query)
做什么让 GL 去做一件事问 GL 一件事
返回值没有有：一个答案
例子bindFramebuffer、viewport、uniform1f、drawArraysgetParameter、isEnabled、isFramebuffer、getError
JavaScript 要不要等不用：交出去就往下走要：拿到答案才能往下走

为什么「等不等」要紧？Chrome 等浏览器把 WebGL 放在一个单独的 GPU 进程 (GPU process) 里执行，你的 JavaScript 在另一个进程里。命令可以先排在队里，攒一批再送过去，JavaScript 不用停。查询不一样：代码要用答案，浏览器如果自己答不上来，就只能把问题送到 GPU 进程，停下来等它回话（往返一次，round trip）。MDN 的 WebGL 最佳实践因此建议生产环境少用这类同步调用（见延伸阅读）。

还有一个方法叫 isContextLost，项目几乎每一步都要调用它（下面的卡片里每进一次门、画一次，约 46 次）。它也有返回值，但按 WebGL 规范，它只返回 context 对象上的一个标志（context lost flag），不需要问 GPU 那边。所以这一课不把它算作查询，卡片里单独列出。

下面这张卡片画一帧 HW2 那样的画面：ForwardPass，一个绿色三角形。课程写了一个计数器 countGL，给 context 上的每个方法套一层，先记账再调用原来的方法；查询按「方法（问的是哪一项）」分类，命令只数总数。

第 1 帧多出来的 30 次查询，是第一次用到 shader、几何体时的「建」：编译完问编译结果（getShaderParameter）、问 program 里有哪些 attribute 和 uniform、建 VAO 前后用 getError 检查。这些只在第一次发生，以后从缓存里取。每一帧都会发生的，只有 7 次。下一节看这 7 次是谁问的。

3. 在哪里问：进门的时候

3.1 进门问两件事，出门绑回去

withRenderSurface 交给 WebGL1SurfaceScope.run 去做。去掉检查和异常处理，剩下五步：

// WebGL1SurfaceScope.ts:191–243（节选，注释是课程加的）
run(descriptor: RenderSurfaceScopeDescriptor, callback: () => undefined): void {
  // …（省略：检查 context、复制描述、记下目标的尺寸版本）
  // ① 进门：问 GL 现在绑着哪块画布、viewport 是多少，记下来
  const previous = this.state.captureSurfaceState()
  // …
  try {
    // 第一次用到这块 RenderTarget 时，这里才真正建 FBO
    const resource = target === null ? null : this.hooks.resolveTarget(target)
    // …
    this.state.bindSurface(resource)  // ② 绑上目的地、设 viewport：两条命令
    this.clearAttachments(next.clear) // ③ 要清屏的话：清（清屏前还要再问几项）
    // …
    const result: unknown = callback() // ④ 你的 draw 都在这里面
    // …
  } catch (error: unknown) {
    // …
  } finally {
    // …
      this.restoreEntry(previous)     // ⑤ 出门：绑回 ① 记下的画布和 viewport
    // …
  }
  // …
}

第 ① 步就是 WebGL1State.captureSurfaceState：

// WebGL1State.ts:180–197（节选，注释是课程加的）
captureSurfaceState(): SurfaceStateSnapshot {
  this.assertContextAvailable('capture surface')
  // 查询 1：现在绑着哪个 framebuffer（null 表示屏幕）
  const framebuffer = this.gl.getParameter(
    this.gl.FRAMEBUFFER_BINDING
  ) as WebGLFramebuffer | null
  // 查询 2：现在的 viewport [x, y, 宽, 高]
  const viewport = this.gl.getParameter(this.gl.VIEWPORT) as Int32Array
  this.assertContextAvailable('capture surface')
  // …（省略：把 viewport 抄成冻结的四元组 copiedViewport）
  return Object.freeze({ framebuffer, viewport: copiedViewport })
}

第 ⑤ 步 restoreEntry 一般只发两条命令（bindFramebuffer、viewport）。只有一种情况它也要问：进门时绑着的是一块离屏画布（也就是这个 scope 套在另一个 scope 里），它先用 isFramebuffer 确认那块画布还在（:302），再绑回去。这一课的 FFT 不套 scope，所以用不到这一次。

3.2 为什么不自己记

「进门前绑的是什么」，为什么不让 State 自己记住，非要问 GL？因为进门前的那个状态，不一定是 State 自己设的：

  • 进门前不一定是屏幕。阴影 Pass 可能套在别的 scope 里，进门前绑着的是外层那块画布。出门一律绑回屏幕，外层剩下的 draw 就画错了地方（第 27 课的嵌套卡片）。
  • 有人不经过 State 改了绑定。RenderTargetManager 第一次建 FBO 时，自己调用 bindFramebuffer 把新的 FBO 绑上去挂附件，挂完再绑回原来那个（WebGL1RenderTargetManager.ts:288、:392）。迁移期同一个 context 上还跑着旧引擎的代码，它们直接调用 gl，State 一概不知道。

所以设计选了最稳的办法：每次进门都问真实值。State 的注释写明了这是有意的，和每次 draw 设深度状态时「信自己的缓存」不是同一种频率和职责（WebGL1State.ts:112–114）。代价是：每进一次门，问 2 次。

3.3 清屏再问五项

ForwardPass 进门时要清屏：颜色清成黑、深度清成 1。WebGL 的 clear 会受写掩码 (write mask) 和裁剪 (scissor) 影响：如果之前有人关掉了颜色写入，clear 就清不掉颜色。所以 clearAttachments 先问出这几项，临时打开写入、关掉 scissor 和 dithering，清完再按问到的值恢复：

  • getParameter(DEPTH_BITS)：这块画布到底有没有深度附件，没有就不能清深度；
  • getParameter(COLOR_WRITEMASK)、getParameter(DEPTH_WRITEMASK)：清完要恢复的写掩码；
  • isEnabled(SCISSOR_TEST)、isEnabled(DITHER)：清完要不要重新打开。

2 + 5 = 7，就是卡片 A 里第 2 帧的那 7 次。FFT 的每一轮都把整块画布重写一遍，不需要清屏，所以 FFT 的每次进门只有 2 次。

3.4 规律：查询跟着进门的次数走

把上面合起来，一帧的查询次数是：

每帧查询 = 把每次进门的「2 + 清屏要问的 + 出门要问的」加起来
HW2：     进门 1 次 × (2 + 5 + 0) = 7

公式里没有 draw 的次数。下面这张卡片验证这一点：同一个 ForwardPass，场景里放 2 个物体和 200 个物体。

这就是「HW2 每帧只问 7 次」的原因：它不管画多少东西，都在同一个 scope 里画，只进一次门。一帧要问多少次，问题变成了：一帧要进几次门？

4. FFT 为什么每次 draw 都要进一次门

4.1 GPU 怎样「算」一张图

FFT 海面每一帧要算出每一层海浪在这个时刻的样子：一张 512 × 512 的图，每个像素存这一点的高度和水平位移。它从一张「频谱 (spectrum)」算出来，算法叫逆快速傅里叶变换 (inverse FFT，IFFT)。这一课不需要它的数学，只需要知道 GPU 怎样算一张图：

  1. 把一块 RenderTarget 当作输出，在上面画一个盖满整块画布的矩形。
  2. fragment shader 对这块画布的每一个像素各运行一次，算出这个像素的结果，写进去。
  3. 需要的输入（比如上一步的结果）放在纹理里，shader 用 texture2D 去读。

所以「一次 draw」= 把整张图的每一格各算一遍，而且是同时算的：GPU 不保证哪个像素先算，一个像素也读不到同一次 draw 里别的像素刚算出来的值。它只能读 draw 开始之前就已经写好的纹理。

4.2 为什么分很多轮

IFFT 不能一次 draw 算完。以一行 N = 8 个数为例，它分 log₂8 = 3 轮；每一轮里，第 i 格的结果由上一轮的两格算出来（旧 shader 的公式，FFTStockham2D.frag:103–108）：

第 s 轮（s = 1, 2, 3），sub = 2^s：
  even = ⌊i / sub⌋ × (sub/2) + (i mod (sub/2))
  odd  = even + N/2
  这一轮的[i] = 上一轮的[even] + W × 上一轮的[odd]      （W 是一个按 i 算的复数系数）

代进去算一格：第 3 轮（sub = 8）第 5 格，even = ⌊5/8⌋ × 4 + (5 mod 4) = 1，odd = 1 + 4 = 5，所以它读第 2 轮的第 1、5 格。图 2 把每一格读哪两格都画出来，蓝色是从第 3 轮第 5 格往回追的路线：

能不能一次 draw 算完？能，但要让每个像素直接读输入的全部 N 格（直接按定义算 DFT）。比一比每个像素要读多少次纹理（2D 图要先对每一行做、再对每一列做，所以乘 2）：

              一行 N = 8          一行 N = 512
一次算完：    每格读 8 次          每格读 512 次 × 2 个方向 = 1024 次
分轮算：      3 轮 × 2 次 = 6 次   9 轮 × 2 次 × 2 个方向 = 36 次

N = 512 时，分轮算每个像素少读约 28 倍。分很多轮，是用「多几次 draw」换「少很多读取」，这正是快速傅里叶变换「快」的地方。

4.3 为什么来回换画布

每一轮要读上一轮的结果、写这一轮的结果。能不能读写同一块画布？不能：同一次 draw 里边读边写同一块纹理，叫反馈环 (feedback loop)，WebGL 规范规定这时 draw 报 INVALID_OPERATION；项目在 draw 之前就检查并抛错（第 27 课的 assertCanSample）。

所以要准备两块画布 ping 和 pong，轮流写：第 1 轮读输入写 ping，第 2 轮读 ping 写 pong，第 3 轮读 pong 写 ping……这叫 ping-pong。结果是：每一次 draw 写的画布，都和上一次 draw 不同。

而一个 scope 只对应一个目的地：withRenderSurface 进门时就定好了画到哪（RenderSurface.ts:38），里面不能换。要换画布，只能出门、再进另一扇门。合起来就是迁移计划那句话的前半句：FFT 每次 draw 都换目标，所以每个 draw 都要单独开一个 scope。

下面用项目真实的 Renderer、Pipeline、Backend 跑一个课程写的 Pass，看 ping-pong 在新架构里怎么写。IFFT 的系数 W 是复数，结果不好核对，所以这里换成一个结构完全相同、结果一眼能核对的算法：前缀和 (prefix sum)。输入 1, 2, …, 8，第 s 轮每格加上「往左隔 2^(s−1) 格」那一格（左边没有就加 0），三轮之后第 i 格就是前 i + 1 个数的和。它同样是每格读上一轮的两格，同样要 log₂8 = 3 轮。

// query-course.ts：课程写的 ScanPass（节选）
execute(context: RenderPassContext): undefined {
  const { backend, view } = context
  this.log.length = 0

  // 第 0 轮：写入 1..8
  drawInto(backend, view, into(this.ping), this.item(this.seed))
  this.log.push('第 0 轮　写 ping')

  let read = this.ping
  let write = this.mode === 'ping-pong' ? this.pong : this.ping

  for (let s = 0; s < 3; s++) {
    const input = read.getColorAttachment(0) // 上一轮写好的那块画布
    this.step.setParameter('uInput', { type: 'texture2D', value: input })
    this.step.setParameter('uOffset', { type: 'float', value: 2 ** s })
    const note = '读 ' + label(read) + '，写 ' + label(write) + '（d = ' + 2 ** s + '）'
    this.log.push('第 ' + (s + 1) + ' 轮　' + note)
    drawInto(backend, view, into(write), this.item(this.step))

    if (this.mode === 'ping-pong') [read, write] = [write, read]
  }

  const result = read.getColorAttachment(0)
  this.copy.setParameter('uInput', { type: 'texture2D', value: result })
  drawInto(backend, view, SCREEN, this.item(this.copy))
  this.log.push('最后　读 ' + label(read) + '，写屏幕')
  return undefined
}

逐行说明：

  • drawInto(backend, view, 目的地, item) 是课程写的三行小函数：backend.withRenderSurface(目的地, () => { backend.draw({ item, view }); return undefined })。每调用一次，就进一次门。
  • into(this.ping) 生成 { surface: { kind: 'render-target', target: this.ping } }，就是「画到 ping 这块画布上」；SCREEN 是 { surface: { kind: 'default-framebuffer' } }。
  • this.step 是一个 Material，它的 shader 读 uInput 这张纹理里的第 i 格和第 i − d 格，相加后写出去。每一轮用 setParameter 换掉它要读的纹理（input：上一轮写好的那块画布的颜色附件）和往左隔几格 d。
  • [read, write] = [write, read]：交换两个变量，这一轮写的，下一轮读。
  • 最后一次画到屏幕上，只是为了让课程能用 readPixels 把 8 个数读出来：项目的 Backend 还没有读回接口（迁移计划决定 5）。

5. 数到 592

FFT 海面每层每帧要做的 draw（旧代码的做法，claude-workspace/fft-ocean-migration/2026-10-02-legacy-v3-fft-pass-reference.zh-CN.md 第 5、6 节）：

  • 频谱 1 次：按时间 t 把初始频谱推到这一刻。
  • IFFT 4 × 2 × 9 = 72 次：
    • 4 路信号：海面要 8 张实数图（高度、两个水平位移和它们的导数）。一次复数 IFFT 能同时算两张实数图（一张放实部、一张放虚部），所以 8 张两两打包成 4 路，做 4 次 IFFT。
    • 2 个方向：二维的 IFFT 先对每一行做一遍，再对每一列做一遍。
    • 9 轮：N = 512 = 2⁹，每个方向 log₂512 = 9 轮（图 2 是 N = 8 的 3 轮）。
  • 组装 1 次：把 4 路结果拆开，算出海面 shader 要采样的位移、梯度、导数三张图。
每层每帧 draw：1 + 4 × 2 × 9 + 1 = 74
4 层（每层覆盖 256、64、16、4 米的海面）：4 × 74 = 296 次 draw
每次 draw 写的画布都和上一次不同（ping-pong）→ 296 次进门
每次进门问 2 次（不清屏，不套 scope）→ 296 × 2 = 592 次查询

下面的实验台用真实的 Renderer、Pipeline、Backend 跑课程写的 FFTShapedPass：它照旧代码的顺序进门、draw，每层依次写 spectrum → ping → pong → … → packed → … → final，shader 只是把上一步的结果搬过来（我们只关心进门几次，不关心算出什么）。画布实际是 4 × 4 像素：查询次数和画布大小无关，小一点跑得快。你可以改层数、N 和「一次 IFFT 处理几路信号」，看公式和实际次数是否一致。

6. 旧代码为什么只问 7 次

旧的 FFT 计算 Pass 是一整块代码，自己拿着 gl（FFTOceanComputePass-multi-layers-v3.ts:391）：

// FFTOceanComputePass-multi-layers-v3.ts:391–427、:474–504
// （节选，注释是课程加的）
execute(context: FrameContext, _camera: PerspectiveCamera): void {
  const gl = this.gl
  // 保存 GL 状态
  const saved = captureGLState(gl) // 入口问 7 项：整个 Pass 只问这一次
  gl.disable(gl.DEPTH_TEST)
  for (let i = 0; i < this.layerStates.length; i++) {
    // …（每层：频谱、4 次 IFFT（每次 18 轮）、组装，一共 74 次 draw）
  }
  restoreGLState(gl, saved)        // 出口只写回，不再问
  // …
}

private renderStockhamStage(/* …输入纹理、输出 FBO、sub、N… */): void {
  const gl = this.gl
  gl.bindFramebuffer(gl.FRAMEBUFFER, outputFBO.getFrameBuffer()) // 直接绑这一轮的画布
  gl.viewport(0, 0, transformSize, transformSize)
  // …（设 uniform）
  gl.drawElements(
    gl.TRIANGLES,
    this.fullscreenQuad.count,
    this.fullscreenQuad.indexData!.type,
    0
  )
  // 画完不还原：下一轮自己会绑它要的画布
}

captureGLState 问的 7 项是：framebuffer、viewport、CULL_FACE、SCISSOR_TEST、BLEND、DEPTH_TEST、COLOR_WRITEMASK。

旧代码能只问一次，靠的是三个前提：

  1. 它自己拿着 gl，可以直接调用 bindFramebuffer 换画布，不用经过任何「门」。
  2. 它知道自己的顺序：下一次 draw 一定是自己的，而且一定会自己绑画布、设 viewport，所以两次 draw 之间不用还原。
  3. 中间没有别人：74 × 4 次 draw 一口气做完，只有整个 Pass 的进出才需要保存和还原。

新架构把这三条都拿掉了。第 30 课讲过，Pass 拿到的只有 context.backend，没有 gl；换画布的唯一办法是 withRenderSurface。而 withRenderSurface 是一个通用的零件：它不知道自己是 296 次中的第几次，不知道下一个 scope 会不会自己绑画布，也不信任自己的记忆（3.2 节），所以每次都问、每次都还原。图 3 下面那一行的每个「还原」，紧接着就被下一个 scope 的「绑」覆盖掉，这是白发的命令；每个「问 2」问到的，其实都是屏幕，这是白问的查询。

下面这张卡片在真实的 WebGL context 上，对同一串 296 块画布，分别按旧代码的写法和新架构的写法走一遍（省掉了 draw 本身）。新架构的写法用课程写的简化版 LiteScope：它只做「进门问、绑、出门绑回」三件事，和项目的 scope 问的是同样两项。

旧代码其实问得也不少。上面说的只是「状态查询」。旧的 Shader.getUniformLocation 没有缓存，每设一次 uniform 就调用一次 gl.getUniformLocation；参考文档估算 FFT 每帧约 2084 次。新架构在第一次 draw 时就把 uniform 位置缓存起来了（WebGL1Uniforms.ts:214），卡片 A 里第 2 帧一次 getUniformLocation 都没有。所以「新代码问得多」只对 framebuffer 和 viewport 这两项成立。

7. 问得多就慢吗

到这里，迁移计划那句话的每个数都有了来历。但「每帧 592 次查询」只是一个次数。它要多久，取决于浏览器怎样回答这两项查询（图 1）。备课时在无界面 Chrome（软件渲染 SwiftShader）里量到的：

每帧做 296 次进门、出门（不 draw）：
  每次都问（项目现在的做法）     约 0.20–0.37 ms
  自己记住、不问                 约 0.05–0.10 ms
  只算那 592 次 getParameter     约 0.14 ms   （第 14 课量到的也是 0.14 ms）
一帧的预算（60 帧每秒）：         16.7 ms

差别约 0.1–0.3 ms，不到一帧预算的 2%（三次运行的范围）。作为对照，getError 每次要等 GPU 进程回话，37–62 μs 一次，592 次就是约 23 ms，超过一整帧（第 14 课 3.4 节）。所以在 Chrome 上，这 592 次查询是「频繁」，但不「贵」。Edge 用的是 Chrome 同一套内核，结果应该接近；Firefox、Safari 我没有测。

用你的浏览器量一量：下面每次运行做 6 轮，每轮 60 帧，两种做法交替。前一两轮常常偏高（浏览器还在「热身」），看后几轮。

8. 如果要省：三种办法

迁移计划列了三种办法，再加上决定 8 的「少换几次画布」。用 LiteScope 和 FFTShapedPass 实测（4 层，N = 512）：

办法每帧查询代价和前提
A. 保持现状：每次进门都问592最稳；在 Chrome 上约 0.3 ms
C. 从栈推导：套在外层 scope 里时，入口就是外层刚绑的那块，只有最外层问不套：592
每层套一个外层 scope：8		要改 FFT Pass 的写法（每层套一层），性能规则带进了 Pass；项目现在的代码套了反而更多，第 14 课实测 896（出门多一次 isFramebuffer）
B. State 自己记住上一次绑了什么第 1 帧 2，之后 0Backend 必须独占 context，所有绕过 State 的绑定都要让缓存失效；记错了会画到别处，而且不报错（卡片 I）
决定 8：一次 IFFT 同时处理 4 路信号（多附件 MRT）160每层 74 → 20 次 draw，查询跟着少；要改 shader 和画布的附件数

B 的前提有一半已经有了：Engine 的新旧路径互斥已经在工作区实现（engine.ts:266 的 assertLegacyMode），新路径运行时旧代码不能碰 context。剩下的一半是第 14 课 2.5 节说的：每次绑定顶点输入都会让 State 的缓存整份失效，要先拆细，否则 B 记住的东西每次 draw 都被清空。

迁移计划的原则是「先测量再优化」。按第 7 节的数字，在 Chrome 上 A 是可以接受的；如果你的浏览器量出来明显更慢，再按 C、B 的顺序考虑。
