1. 设计问题：一次 draw 还要回答什么

第 10 课的 Geometry 回答了「画什么形状」。剩下的问题，这一课的两个类负责写成数据：

要回答的问题由谁描述（第一层，不知道 gl）由谁执行（第三层）
编译哪份源码、用哪种 GLSLShaderModule：一种语言、两份源码ProgramManager：编译、链接，按 ShaderModule 的对象身份缓存（第 19 课 3.4 节）
每个 uniform 填什么Material 的参数表（共享的外观）；模型矩阵等内建值不在这里，来自这一次 draw；10 月 19 日起还可以借用参数块（第 4.6 节）Uniforms.prepare 与 upload（第 19 课 3.6 节）
深度、剔除怎样设Material 的 RenderStateapplyDrawState 加 State 缓存（第 19 课 3.9 节）
先画谁Material 的 queueRenderList 与 ForwardPass（Task 16、17，还没实现；10 月 13 日补：已实现，见第 30 课）

两个类都继承 Resource，都不编译、不上传、不保存任何句柄（ShaderModule.ts:175–177）。读的时候盯住四件事：

  • 描述和执行分开。ShaderModule 只说清楚「编译什么」，这个后端能不能用，由后端判断（第 3.1 节、卡片 I）。
  • 运行时也按类型检查。第 10 课你问过「构造函数上不是有类型检查吗」。这两个类的做法正好回答了这个问题：TypeScript 的类型在运行时不存在，所以能查的都在运行时再查一遍（第 3.3、4.2 节）。
  • 共享的外观和每次 draw 的数据分开。一个 Material 可以被很多 Mesh 共用，每次 draw 都不同的值（模型矩阵）不能存进去（图 2、第 4.6 节）。
  • 写入要么完整、要么不变。先验证并复制，全部通过才写（第 4.8 节）。

3.1 一个实例，一种语言

export type WebGLShaderLanguage = 'glsl-es-100' | 'glsl-es-300'                     // ShaderModule.ts:11
interface ShaderModuleBaseOptions { name; vertexSource; fragmentSource; builtInUniforms? }   // :14–32（节选）
export interface GLSLES100ShaderModuleOptions extends ShaderModuleBaseOptions {
  readonly language: 'glsl-es-100'                                                 // 标签：一个实例只能是其中一种
}
export interface GLSLES300ShaderModuleOptions extends ShaderModuleBaseOptions {
  readonly language: 'glsl-es-300'
}
export type ShaderModuleOptions = GLSLES100ShaderModuleOptions | GLSLES300ShaderModuleOptions   // :55 互斥联合
作用用 language 这个标签 (discriminant) 区分两种输入。构造输入是两种接口的联合 (discriminated union)，language 决定是哪一种。
和设计的差别设计 §11 里一个 ShaderModule 同时装 webgl1 和可选的 webgl2 两份源码（设计 §11）。实现改成互斥联合，理由在 :48–53：一个实例在任何时刻只有一个身份；写 WebGL2 shader 的人直接用 glsl-es-300，不用伪造一份 WebGL1 源码或传 null；将来某个内建材质真要两种版本，由更高层的 ShaderFamily 或工厂组合两个 ShaderModule。
谁判断能不能用后端。WebGL1ProgramManager 在编译之前先看 language，不是 glsl-es-100 就抛 UnsupportedShaderLanguageError（WebGL1ProgramManager.ts:92–94，卡片 I）。同一个 ShaderModule，将来交给 WebGL2 的后端就能用。ShaderModule 自己「不替用户转换 GLSL」（模块说明 :7）。
残留的说法（已改）这个错误原来叫 UnsupportedShaderVariantError，信息是「does not provide a webgl1 variant」，还是双变体设计的说法。现在一个 ShaderModule 只有一种语言，准确地说是「这种语言这个后端不支持」。2026-09-30 按这个说法改了（RenderingError.ts:255–274）：类名改成 UnsupportedShaderLanguageError，错误码改成 UNSUPPORTED_SHADER_LANGUAGE；构造时多传一个 language，也写进 details；信息变成「uses glsl-es-300, which the webgl1 backend does not support」。10-01 又显式写了 this.name，生产构建压缩类名后 name 不再是空字符串（第 7 课 9.2 节）。
状态name 和 language 是 public readonly，构造后不再变。

3.2 构造：五步验证

constructor(options: ShaderModuleOptions) {                                        // ShaderModule.ts:204–235
  super()                                                                           // Resource：没有构造副作用
  const shaderName = getShaderDiagnosticLabel(options.name)                         // ① 先备一个报错用的名字（name 不合法时是 '<unnamed>'）
  this.name = requireNonBlankText(shaderName, 'name', options.name)                 // ② name：非空白字符串
  const language: unknown = (options as { readonly language?: unknown }).language   // ③ 故意当成 unknown：不信静态类型
  if (language !== 'glsl-es-100' && language !== 'glsl-es-300') {
    throw new InvalidShaderModuleError(shaderName, `unsupported shader language ${String(language)}`, { language })
  }
  this.language = language                                                          // 比较之后，TypeScript 把它收窄成两种之一
  this.vertexSourceValue = requireNonBlankText(shaderName, 'vertexSource', options.vertexSource)       // ④ 两份源码
  this.fragmentSourceValue = requireNonBlankText(shaderName, 'fragmentSource', options.fragmentSource)
  this.builtInUniformsValue = createBuiltInUniformSnapshot(shaderName, options.builtInUniforms)     // ⑤ 内建映射（3.3）
}

function requireNonBlankText(shaderName: string, fieldName: string, value: unknown): string {   // :109–117
  if (typeof value !== 'string' || value.trim().length === 0) {                     // trim 只用来判断是不是空的
    throw new InvalidShaderModuleError(shaderName, `${fieldName} must be a non-empty string`, { fieldName })
  }
  return value                                                                      // 返回原文，不是 trim 之后的
}
作用把 name、language、两份源码和内建映射验证之后存下来。
所在层第一层 resources。调用者是场景工厂（Task 19）或自定义 shader 的使用者。
校验name 和两份源码是非空白字符串；language 是两种之一；映射见 3.3。任何一步失败都抛 InvalidShaderModuleError，信息里带诊断名。诊断名先由 getShaderDiagnosticLabel（:94–100）备好：name 本身不合法时用 <unnamed>，所以连「name 错了」这条报错也有名字可写（Node 实测：name 为 42 时，信息是「Shader module <unnamed> is invalid: name must be a non-empty string」）。
为什么把 language 当 unknown类型上它已经是两种之一；直接比较，TypeScript 会认为抛错那一支永远走不到。先转成 unknown，等于声明「这里不信静态类型」，运行时检查才名正言顺。测试的注释说得很直白：「TypeScript 联合类型是编译期防线；运行时仍可能收到 JavaScript 或反序列化数据」（ShaderModule.test.ts:137）。
为什么源码只拿 trim 来判断保存 trim 之后的结果，会「擅自修改行号、缩进」（:106–107）。驱动报编译错误时说的是第几行，源码开头少一个换行，行号就全差一行（卡片 B）。
原子性构造函数一抛错，对象就不会交到调用者手里。Resource 的构造没有副作用（不登记、不订阅），失败不留痕迹（第 9 课第 3.3 节）。
没有检查的GLSL 本身对不对：语法、有没有声明映射里的 uniform，ShaderModule 一概不看，要等 ProgramManager 编译链接才知道（模块说明 :9）。两个语义映射到同一个名字，也不查（审查视角 1）。
错误类的小差别InvalidShaderModuleError 没写 this.name，生产构建压缩后它的 name 是空字符串（第 7 课 9.2 节）；InvalidMaterialError 写了（InvalidMaterialError.ts:23）。

3.3 builtInUniforms：语义到 GLSL 名字的一张表

const BUILT_IN_UNIFORM_SEMANTICS = ['modelMatrix', 'viewMatrix', 'projectionMatrix', 'normalMatrix', 'cameraPosition'] as const   // :57–63 唯一的名单
export type BuiltInUniformSemantic = (typeof BUILT_IN_UNIFORM_SEMANTICS)[number]      // :65 类型从名单推出
const BUILT_IN_UNIFORM_SEMANTIC_SET: ReadonlySet<string> = new Set(BUILT_IN_UNIFORM_SEMANTICS)   // :74 运行时也用这份名单
export type BuiltInUniformBindings = Readonly<Partial<Record<BuiltInUniformSemantic, string>>>   // :91 语义 → GLSL 名

function createBuiltInUniformSnapshot(shaderName, bindings) {                     // :122–160（节选）
  if (bindings === undefined) return Object.freeze({})                              // 没给：一张冻结的空表
  if (bindings === null || typeof bindings !== 'object') throw …('builtInUniforms must be an object when provided')
  for (const semantic of Object.keys(bindings)) {                                   // 第一遍：对方给了哪些键，逐个核对
    if (!BUILT_IN_UNIFORM_SEMANTIC_SET.has(semantic)) throw …(`unsupported built-in uniform semantic ${semantic}`)
  }
  const snapshot = {}
  for (const semantic of BUILT_IN_UNIFORM_SEMANTICS) {                              // 第二遍：按名单复制
    const uniformName = bindings[semantic]
    if (uniformName === undefined) continue                                         // 只映射一部分也可以
    snapshot[semantic] = requireNonBlankText(shaderName, `builtInUniforms.${semantic}`, uniformName)
  }
  return Object.freeze(snapshot)                                                    // 复制并冻结
}
作用告诉后端：shader 里哪个 uniform 是模型矩阵、视图矩阵、投影矩阵、法线矩阵、相机位置。这些值每次 draw 从 submission 取，不来自 Material（图 2）。
为什么要映射GAMES202 的 shader 用自己的名字：uModelMatrix、uViewMatrix、uProjectionMatrix（PRT 顶点 shader :14–16）。three.js 的 ShaderMaterial 把名字规定死（第 10.1 节）；这里不规定，名字由 shader 说了算，映射告诉后端去哪找。
一份名单，两种用途类型从名单推出来（:65），运行时的 Set 也由它建（:74）。加一个语义只改一处，静态类型和运行时检查不会各说各的（模块说明 :11）。Set 的注释说明了它存在的理由：「TypeScript 联合类型在编译后会消失」（:71–72）。
为什么要走两遍只按名单复制的话，拼错的键根本不会被读到，会被悄悄丢掉（卡片 A）。所以先用 Object.keys 核对对方给的每个键，再按名单复制。
为什么不存 locationuniform location 属于某个 program、某个 context（:80–81）；同一个 ShaderModule 在两个 context 里是两个 program。
状态复制加冻结：调用者之后改自己的对象不影响它（测试 ShaderModule.test.ts:56）。没给映射时是一张冻结的空表，读的一方不用判断 undefined。
和设计的差别设计 §11 只有四个语义，字段名叫 builtIns（设计 :737–742）；实现多了 normalMatrix（视图空间的法线矩阵，第 19 课 3.6 节），字段名改成 builtInUniforms。
没有检查的值是不是合法的 GLSL 标识符（只查非空白）；两个语义映射到同一个名字：{ modelMatrix: 'uM', viewMatrix: 'uM' } 能构造成功（Node 实测），要到第一次 draw 才被后端拒绝（审查视角 1）。

3.4 读取与释放

get vertexSource(): string { this.assertUsable(); return this.vertexSourceValue! }       // :238–242（fragmentSource、builtInUniforms 同理）

protected disposeCPUData(): void {                                                 // :264–268
  this.vertexSourceValue = null                                                     // 三个字段都不是 readonly，

作用三个 getter 都先 assertUsable()，释放之后一律抛 ResourceDisposedError（测试 ShaderModule.test.ts:197）。builtInUniforms 直接给出冻结的那一份，不再复制。

它不管的借用它的 Material。Material 在使用时自己查 shader 还活没活着（第 4.7 节）。

4.1 参数为什么带类型标签

export type MaterialParameter =                                                    // materialParameters.ts:41–51
  | { readonly type: 'float'; readonly value: number }
  | { readonly type: 'int'; readonly value: number }                                // 同样是 number，标签不同
  | { readonly type: 'bool'; readonly value: boolean }
  | { readonly type: 'vec2'; readonly value: Vec2ParameterValue }
  | { readonly type: 'vec3'; readonly value: Vec3Tuple }
  | { readonly type: 'vec4'; readonly value: Vec4ParameterValue }
  | { readonly type: 'mat3'; readonly value: readonly number[] }                    // 9 个，列主序
  | { readonly type: 'mat4'; readonly value: readonly number[] }                    // 16 个
  | { readonly type: 'texture2D'; readonly value: Texture2DSamplingSource }         // Texture2D，或 RenderTarget 颜色附件的地址；都不是 WebGLTexture
  | { readonly type: 'cubeTexture'; readonly value: CubeTexture }
作用每个参数自带「在 shader 里是什么类型」。它也是一个带标签的联合：type 定了，value 的类型就定了。
为什么值本身不够模块说明 :25：同一个数字 1，可能要 uniform1f，也可能要 uniform1i；长度同为 9 的数组，可能是 mat3，也可能是别的。标签在两处派上用场：CPU 这边按标签验证（4.3），后端按标签和 program 反射出的类型比较、选上传函数（第 5 节）。
和设计的差别设计 §13 列了 7 种（设计 :834–842），实现有 10 种，多了 int、bool、texture2D。测试注释给了理由：FFT 的开关、stage 和 IBL 的采样次数需要真正的 int 和 bool（Material.test.ts:179）。
对照旧引擎旧引擎的 uniform 也带类型，但标签是 GL 函数名的后缀：'1i'、'3fv'、'matrix3fv'（src/materials/types/Material.ts:25–149），旧 Material 自己 switch 着调 gl.uniform*（src/materials/Material.ts:67–69）——第一层直接知道 gl，这正是第 3 课说的疼。新的标签用 GLSL 的类型名，换成哪个 GL 调用是后端的事。
值的约定数值保留 JavaScript number，不在这里量化成 Float32（materialParameters.ts:28）；mat3、mat4 是平坦的列主序数组；int 是有符号 32 位整数，bool 只收 boolean（:32–33）。

两道防线各挡什么注释原话（materialParameters.ts:57–58）：Record 要求联合的每个分支都登记，配合 hasOwn「拒绝 JavaScript 的非法输入」；default 里的 assertNever「防止维护时漏写新分支」：将来加一种标签却忘了写复制分支，编译不过。
为什么用 hasOwn 而不用 inin 顺着原型链找，'toString' in {} 是 true。用 in 的话，{ type: 'toString' } 会过第一道门，掉进 default，被 assertNever 抛成 ExhaustiveMatchError（卡片 C）。
和第 10 课比Geometry 的 topology 只有后一道：运行时的非法值直接落进 default，抛的是 ExhaustiveMatchError，不在 RenderingError 家族里（第 10 课审查视角 2）。Material 在进 switch 之前先拦下，抛的是 InvalidMaterialError，调用者按错误类型处理时不会漏掉。

function requireCubeTexture(value: unknown, fieldName: string, createError: ParameterErrorFactory): CubeTexture {   // :118–129

function copyNumberArray(value: unknown, length: number, fieldName: string, createError: ParameterErrorFactory): number[] {   // :80–100
  if (!Array.isArray(value) || value.length !== length)                               // TypedArray 不是数组
    throw createError(fieldName, 'must be an array of ' + length + ' numbers')
  const input: readonly unknown[] = value
  const copy: number[] = []
  for (let i = 0; i < length; i++) {                                                 // 按下标读：空洞读出来是 undefined
    const num = requireFiniteNumber(input[i], () =>
      createError(fieldName + '[' + i + ']', 'must be a finite number')
    )
    copy.push(num)
  }
  return copy
}
10 月 10 日、12 日更新（提交 2c8291a、b54b581）：这一节和 4.2、4.4、4.6、4.7 的节选已经换成现在的代码。变了三处：① requireFiniteNumber、requireBoolean 搬进了 core/validation.ts，第二个参数从字段名换成了错误工厂（第 7 课 6.1 节），所以每个调用点都多了一行 () => new InvalidMaterialError(…)；② 本文件原来的 assertObject、assertAlive 删了，对象检查换成 assertNonArrayObject，存活检查改调资源自己的 assertUsable()；③ texture2D 参数的值类型从 Texture2D 换成了 Texture2DSamplingSource：既能放 Texture2D，也能放 RenderTarget 颜色附件的地址，复制规则在 copyTexture2DSamplingSource 里（第 29 课第 7 节）。cubemap 的检查挪进了新函数 requireCubeTexture。
作用验证一个参数，复制出新的包装和新的数组。Material 的构造、setParameter、getParameter、getParameterEntries 共用它，ParameterBlock 的构造、get、set 也用它（materialParameters.ts:131–140）：同一套规则，进来、出去都用。
数值float 要有限；int 是 [−2³¹, 2³¹ − 1] 里的整数；bool 只收 true、false，1 不行，不做「真值」转换（requireBoolean，在 core/validation.ts，第 7 课 6.1 节）。
数组必须是普通数组，长度恰好对，每个元素都有限（卡片 D）。TypedArray 被拒：gl-matrix 的 mat3、mat4 是 Float32Array，要先 Array.from（:77–78）。按下标逐个读，所以空洞也会被查到；换成 forEach，空洞会被跳过，那一格就没人检查了。
纹理cubemap：instanceof 查类型，再调 CubeTexture 自己的 assertUsable 查存活，value 还是同一个对象。二维纹理交给 copyTexture2DSamplingSource：Texture2D 一样原样借用；RenderTarget 附件地址 { target, kind, index } 复制成新的冻结包装，里面的 target 还是原来那个 RenderTarget。两种都不复制像素、不 retain、不 release、不碰 GPU（:137–139，卡片 G）。
为什么出去也要复制getParameter 如果交出内部那个数组，调用者改它就绕过了 setParameter 的验证。测试对每种数组都查三个入口：构造输入、getter 输出、setter 输入（Material.test.ts:195–230）。
为什么不在这里量化成 Float32精度是后端的事：WebGL1 按 Float32 上传，别的后端未必。CPU 层保留 double；Uniforms 量化之后再查一次有限，因为「CPU 中有限的 1e300 转成 Float32 后仍会溢出」（WebGL1Uniforms.ts:27–54，卡片 D）。

4.4 RenderState：一份冻结的期望

function createRenderState(input: RenderStateInput | undefined): RenderState {        // Material.ts:106–140
  const state = defaultIfUndefined(input, {})                                         // 只有 undefined 算「没填」；null 在下一行被拒
  assertNonArrayObject(state, () => new InvalidMaterialError('state', 'must be a non-array object'))
  for (const key of Object.keys(state)) {                                             // 先找不认识的字段
    if (!['depthTest', 'depthWrite', 'depthFunction', 'cullMode', 'dither'].includes(key)) {
      throw new InvalidMaterialError('state.' + key, 'unknown render state field')   // depthtest、transparent 都在这里被拒
    }
  }
  return Object.freeze({                                                              // 五个字段都是原始值，冻结一层就够
    depthTest: requireBoolean(
      defaultIfUndefined(state.depthTest, true),
      () => new InvalidMaterialError('state.depthTest', 'must be a boolean')
    ),
    depthWrite: requireBoolean(
      defaultIfUndefined(state.depthWrite, true),
      () => new InvalidMaterialError('state.depthWrite', 'must be a boolean')
    ),
    depthFunction: requireChoice(defaultIfUndefined(state.depthFunction, 'less-equal'), DEPTH_FUNCTIONS, 'state.depthFunction'),
    cullMode: requireChoice(defaultIfUndefined(state.cullMode, 'back'), CULL_MODES, 'state.cullMode'),
    dither: requireBoolean(                                                           // 10 月 14 日新增
      defaultIfUndefined(state.dither, true),
      () => new InvalidMaterialError('state.dither', 'must be a boolean')
    )
  })
}

五个字段、默认值，以及后端怎样把它们变成 GL 状态（dither 由 WebGL1Backend.ts:332–333 直接设，其余见 WebGL1State.ts:121–169、:291–305）：

字段默认后端怎样设GL 自己的初始值
depthTesttrueenable 或 disable(DEPTH_TEST)关闭
depthWritetruedepthMask(depthWrite)开启
depthFunction'less-equal'depthFunc：less → LESS，less-equal → LEQUAL，always → ALWAYSLESS
cullMode'back'none：disable(CULL_FACE)；back、front：enable 之后 cullFace(BACK 或 FRONT)剔除关闭，cullFace 为 BACK
dithertrueenable 或 disable(DITHER)，每次 draw 都设，不经过 State 缓存开启

GL 的初始值见 OpenGL ES 2.0 规范 4.1.5、4.2.2、3.5.1 节。

作用补齐默认值、验证、冻结。结果是一份「期望的状态」，不是 GL 的当前状态。模块说明把这三层分得很清楚：Material 说「我希望开深度测试」，WebGL1State 记「我上次开过没有」，只有 GL context 知道「现在到底开没开」（模块说明 :33–43）。
只有 undefined 算没填defaultIfUndefined 只替换 undefined（:85–95）：显式的 false 保留，null 被拒，而不是当成「没填」（卡片 H）。注释说了原因：TypeScript 的调用方通常不会传 null，但 JavaScript 和外部数据会。
为什么拒绝不认识的字段拼成 depthtest 如果被悄悄忽略，默认值又恰好是 true，这个错可能永远看不出来。transparent 也在这里被拒：设计明确「初版删除 transparent；将来必须连 blend、depthWrite、排序和 transparent queue 一起实现」（设计 :889）。
dither（10 月 14 日）颜色量化抖动 (dithering)。画普通颜色可以开；把深度编码成 RGBA 写进颜色附件时必须关，否则抖动会改掉编码出来的数（Material.ts:43–52）。阴影 pass 的深度材质就要写 dither: false（第 45 课）。后端每次 draw 都按 Material 设一次，不沿用上一个材质留下的值。
没有检查的组合{ depthTest: false, depthWrite: true } 能通过，但 GL 规定深度测试关闭时，深度缓冲也不会被写入（ES 2.0 规范 4.1.5 节），这个 depthWrite 实际上不起作用。
为什么默认 less-equal代码没写理由，是实施计划 Task 7 直接规定的（计划 :652）。three.js 的默认也是 LessEqualDepth（Material.js:208）；旧引擎每帧全局设 LEQUAL（WebGLRenderer.ts:204）。一个常见的用处：旧天空盒 shader 用 pos.xyww 把深度压到 1.0（skybox/vertex.vert:22），清屏的深度也是 1.0，用 LESS 就过不了，要 LEQUAL。
哪一面是背面GL 按三角形投到屏幕上的绕向判断正反面（ES 2.0 规范 3.5.1 节）。applyDrawState 每次都把 frontFace 设成 CCW（WebGL1Backend.ts:337），所以屏幕上逆时针的是正面，'back' 剔掉顺时针的。镜像变换会把绕向反过来，见审查视角 2。
为什么不是 class它不调 GL，也没有释放流程，冻结的普通对象就够了（模块说明 :37）。getter 每次给出同一个冻结对象，不再复制（:298–302）。

4.5 queue：不是 GPU 状态

queue 只有 'background' 和 'opaque' 两个值，默认 opaque。注释说它是「RenderList/Pass 使用的执行分类，本身不是 GPU 状态」（Material.ts:32）：RenderList 按它分组，ForwardPass 先画 background、再画 opaque（设计 :1606–1627）。Backend 不读它。设计把 queue、state、shaderModule 分成三个字段：queue 决定执行的大类，state 描述每次 draw 的 GPU 状态，shaderModule 描述程序（设计 :891）。

4.6 构造与保留名

constructor(options: MaterialOptions) {                                              // Material.ts:202–269（排版压缩过）
  super()
  assertNonArrayObject(                                                              // ① options 本身是对象
    options,
    () => new InvalidMaterialError('options', 'must be a non-array object')
  )
  const shader = options.shaderModule
  if (!(shader instanceof ShaderModule))                                             // ② 类型
    throw new InvalidMaterialError('shaderModule', 'must reference a ShaderModule resource')
  shader.assertUsable()                                                              // ③ 借来的 shader 还活着
  this.shaderModuleValue = shader                                                     // 借用：不 retain
  this.queueValue = requireChoice(defaultIfUndefined(options.queue, 'opaque'), RENDER_QUEUES, 'queue')   // ④
  this.stateValue = createRenderState(options.state)                                  // ⑤
  if (options.parameters !== undefined) {                                             // ⑥ 逐个参数
    assertNonArrayObject(
      options.parameters,
      () => new InvalidMaterialError('parameters', 'must be a non-array object')
    )
    for (const [name, parameter] of Object.entries(options.parameters)) {
      this.parametersValue.set(name, prepareParameter(shader, name, parameter))
    }
  }
  const blocks = defaultIfUndefined(options.blocks, [])                               // ⑦ 借用的参数块（10 月 19 日）
  if (!Array.isArray(blocks)) throw new InvalidMaterialError('blocks', 'must be an array')
  const seen = new Set<ParameterBlock>()
  const copiedBlocks: ParameterBlock[] = []
  const reserved = new Set(Object.values(shader.builtInUniforms))                     // 内建映射出来的真实名字
  for (const block of blocks) {
    if (!(block instanceof ParameterBlock))
      throw new InvalidMaterialError('blocks', 'must contain ParameterBlock resources')
    block.assertUsable()                                                              // 借来的块也得活着
    if (seen.has(block))                                                              // 同一个块不能借两次
      throw new InvalidMaterialError('blocks', 'duplicate block reference', { label: block.label })
    seen.add(block)
    for (const name of block.names) {                                                 // 一个名字只能有一个来源
      if (reserved.has(name) || this.parametersValue.has(name) || this.blockParameterNames.has(name))
        throw new InvalidMaterialError(name, 'uniform must have exactly one source', { label: block.label })
      this.blockParameterNames.add(name)                                              // 记下来，setParameter 要查
    }
    copiedBlocks.push(block)
  }
  this.blocksValue = Object.freeze(copiedBlocks)                                      // 列表复制并冻结；块本身不复制
}

function prepareParameter(shader: ShaderModule, name: string, parameter: MaterialParameter): MaterialParameter {   // :151–163
  assertValidParameterName(name, materialError)                                       // 非空白字符串，原样保留
  shader.assertUsable()
  if (Object.values(shader.builtInUniforms).includes(name))                           // 映射之后的 GLSL 名是保留名
    throw new InvalidMaterialError(name, 'is reserved by builtInUniforms')
  return copyParameter(parameter, 'parameters.' + name, materialError)               // 4.3 的规则；失败时报 InvalidMaterialError
}
作用借用一个 shader 和一组参数块，建立 queue、state 和参数表，全部验证之后才算建成。
顺序先查 options 和 shader，再查 queue、state，然后逐个参数，最后逐个块。参数要用 shader 的映射查保留名，所以 shader 必须先验；块要和参数比名字，所以排在参数之后。
为什么可以直接写进 Map看起来是边验证边写，但构造函数一抛错，对象就不会交出去，写了一半的 Map 跟着对象一起被丢掉（和第 9 课 Mesh 同一个道理）。setParameter 改的是一个已经交出去的对象，不能这样做，所以它先准备后提交（4.8）。
保留名拒绝的是映射之后真正的 uniform 名（例如 uModel），不是语义名 modelMatrix（:148–149，卡片 E）。这样同一个 uniform 就不会有 Material 和 submission 两个来源（图 2）。
块（10 月 19 日）⑦ 逐个登记块里的名字。块与块、块与本地参数、块与内建映射出来的名字，撞了都抛「uniform must have exactly one source」（:254–264；四种撞法见测试 MaterialBlocks.test.ts:53）。登记下来的名字，之后 setParameter 也不许写（4.8）。块的列表构造后就固定了，块里的值由生产者更新（第 45 课）。所以后端找值时，一个名字最多在一处找到，不用排「谁优先」（第 5 节）。
借用Material 不 retain shader、参数里的纹理，也不 retain 借用的块（:171–173）。建场景时它们要各自 retain（热身第 2 题）。
没有检查的名字前后的空白：' uColor' 会原样存下（Node 实测）。draw 时报的是 uColor「没有值」，不会提到那个带空格的参数。这是有意的：「验证实际 uniform 名，不 trim、不尝试解析 GLSL」（materialParameters.ts:222）。同样，参数名是不是 shader 里真有的 uniform，CPU 层也不知道；多出来的参数 draw 时被忽略（第 5 节）。

作用给后端和调用者读数据的全部入口。
查几层shaderModule 查两层：Material 活着，它借的 shader 也活着。queue 和 state 只查 Material（shader 释放了，state 照样读得到，Node 实测）。getParameter 出去时再跑一遍 copyParameter，所以借来的纹理被别人释放了，会在这里抛 ResourceDisposedError，而不是返回 undefined：测试注释说「错误不能被转换成『没有参数』」（Material.test.ts:375，卡片 G）。
getParameterEntries按首次插入顺序，全部复制一遍（:322）。任何一个纹理已释放，整个调用就抛错。Uniforms.prepare 每次 draw 调用它一次（第 5 节）。它和 getParameter 都只管本地参数，块里的值不在里面（测试 MaterialBlocks.test.ts:29）。
blocks（10 月 19 日）每次读都查 Material 和每个块还活着：块被别人先释放了，draw 时就在这里抛 ResourceDisposedError（测试 MaterialBlocks.test.ts:100）。列表在构造时已经复制并冻结，读的时候不再复制；块对象本身是共享的，借用它的材质看到的是同一个块。
不是整帧快照「它们不是整帧快照协议」（:175–176）：两次读取之间，别人可以 setParameter。要求一帧之内不变，得在帧提取时显式捕获（第 6 课第 2 节）。

  • 三阶换成 mat4。16 个系数装进 mat4（order3/vertex.vert:19–21），标签就得写 'mat4'。写错成 mat3，Material 先按 9 个查长度，16 个会被拒；即使长度碰巧对上，draw 时标签和反射出的 FLOAT_MAT4 对不上，也会被拒（第 5 节）。

10. 架构视角

10.1 对照 three.js 的 ShaderMaterial 与 Material

three.js本项目
拆分ShaderMaterial 一个对象装下源码、uniforms 和状态（ShaderMaterial.js:107–128）拆成 ShaderModule（源码）和 Material（参数、状态）；一个 shader 可以被多个 Material 共用
GLSL 版本glslVersion：null、GLSL1 或 GLSL3，一个材质一种（:249）language 二选一
内建 uniformShaderMaterial 自动在源码前面加上固定名字的声明：modelMatrix、modelViewMatrix、projectionMatrix、viewMatrix、normalMatrix、cameraPosition、isOrthographic（WebGLProgram.js:657–663）；RawShaderMaterial 不加（:500）什么都不加，像 RawShaderMaterial；用 builtInUniforms 把语义映射到 shader 自己的名字
uniform 的值material.uniforms 直接保存你给的对象（setValues 里 this[key] = newValue，Material.js:588），每帧改 .value 就行；值不带类型，上传时按 program 反射出的 GL 类型选上传函数（WebGLUniforms.js:638–651、:969）带 type 标签，写入时复制，只能通过 setParameter 改；draw 时标签要和反射出的类型一致，否则拒绝
深度默认值depthTest true、depthWrite true、depthFunc LessEqualDepth（Material.js:208–228）一样：true、true、less-equal
剔除side：FrontSide 剔背面，BackSide 剔正面（靠翻转 frontFace 实现），DoubleSide 不剔；物体的世界矩阵行列式为负（镜像）时再翻一次（WebGLRenderer.js:1100、WebGLState.js:763–772）cullMode 为 none、back、front；frontFace 固定 CCW，没有镜像处理（审查视角 2）
法线矩阵视图空间，由 modelViewMatrix 求（WebGLRenderer.js:2005–2006）也是视图空间：transpose(inverse(mat3(V · M)))（第 19 课 3.6 节）

three.js 选的是方便：拿到 uniforms 对象直接改，渲染器按 shader 的实际类型去上传。本项目选的是查得清：类型、名字在写入时就验证，改只能走 setParameter，draw 时标签和反射再对一次。代价是换环境光这种操作要写 setParameter，而不是改一个 value。至于 ShaderModule 注释里说的 ShaderFamily（一个材质、多种语言），three.js 新渲染器走得更远：节点材质 (node material) 由 GLSLNodeBuilder 或 WGSLNodeBuilder 按后端生成源码（GLSLNodeBuilder.js:71、WGSLNodeBuilder.js:170），用户写的是 TSL 节点，不直接写 GLSL。

10.2 审查视角：两处值得讨论，一道找茬题

  1. 映射重名在 draw 时才查。{ modelMatrix: 'uM', viewMatrix: 'uM' } 能通过 ShaderModule 的构造（Node 实测），要到第一次 draw，才由 Uniforms 抛 InvalidMaterialError（WebGL1Uniforms.ts:119–126）。可是 InvalidMaterialError 的注释说它表示「Material 的构造描述或参数违反 CPU 侧契约」（InvalidMaterialError.ts:4–8），而这个错出在 ShaderModule 的映射上。想一想：这项检查需要 program 的反射信息吗？按第 10 课「能早查的尽量早查」，它该放在哪个函数、抛什么错？
  2. 镜像变换与剔除。cullMode 属于共享的 Material，frontFace 在 applyDrawState 里固定为 CCW（WebGL1Backend.ts:337）。一个 scale 有一个分量为负的 Mesh（镜像），三角形投到屏幕上的绕向会反过来，默认的 'back' 剔掉的正好是朝着相机的那一面。three.js 按每个物体世界矩阵的行列式决定 frontFace（10.1 节）。想一想：「这次要不要翻转」这个信息应该由谁提供：Material、RenderItem 还是 Backend？（提示：图 2，以及模块说明里「共享外观，不承载某个 Mesh 的临时矩阵」那一节。）
  3. 找茬题：模块说明 shader-and-material.zh-CN.md 里，有一处写到 Material 的一个属性，名字和代码里的对不上。读第 11 节的延伸阅读时找找看，找到了告诉我。
