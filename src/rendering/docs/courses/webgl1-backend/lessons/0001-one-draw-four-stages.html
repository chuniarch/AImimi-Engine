一次 draw 的四段调用

你能写出三角形，只是 API 记不住。这一课把「画一个三角形」切成四段，每段只需要记住调用的名字和先后顺序。你在沙盒里从空白把它敲出来，再让代码扛住三次故障注入。最后看 backend/webgl1/ 怎样把同样这四段分给四个类——这就是整个后端的骨架。

和你的任务的关系 —— Task 15 的 WebGL1Backend.draw() 做的事，就是把这四段按顺序串起来。前三段已经有 Manager 替你做好了；第四段有一半在 WebGL1State 里，另一半（uniform 上传和 drawElements）正是你要写的部分。

1. 四段，按依赖排序

WebGL 是一台状态机 (state machine)：大多数调用不返回结果，而是改写 context 里的某个「当前值」，后面的调用再去读这个值。所以调用顺序不是写法风格问题，而是数据依赖：

段目的调用（只写名字，按顺序）要用到谁的产出
① 程序
program		 把两段 GLSL 编译、链接成 GPU 上能跑的程序 createShader → shaderSource → compileShader → getShaderParameter（×2）
createProgram → attachShader（×2）→ linkProgram → getProgramParameter		 —
② 数据
buffer		 把顶点数组复制进 GPU 内存 createBuffer → bindBuffer → bufferData —
③ 接线
vertex input		 告诉 GPU：shader 里的 position 从哪个 buffer 读、按什么格式读 getAttribLocation → bindBuffer → vertexAttribPointer → enableVertexAttribArray ① 的 location，② 的 buffer
④ 状态 + 绘制 选定输出区域和程序，清屏，发出 draw call viewport → clearColor → clear → useProgram → drawArrays ①②③ 留在状态机里的一切
③ 里的 bindBuffer 必须写在 vertexAttribPointer 前面：pointer 在调用的那一刻，把「当前绑在 ARRAY_BUFFER 上的 buffer」记进这个 location。它读的正是状态机的当前值。④ 的 drawArrays 本身几乎不带参数，它画的就是「此刻」状态机里的 program 和接线。
顺序写反了，也不一定当场报错。我在 Chromium 里实测过：offset 为 0 时，pointer 会安静地记下 null，错误一直拖到 drawArrays 才以 INVALID_OPERATION 出现。沙盒的调用日志会把错误标在 drawArrays 那一行。记住这条：报错的地方不一定是犯错的地方。
卡住了再展开：本课 21 个调用的签名
调用做什么
gl.createShader(gl.VERTEX_SHADER | gl.FRAGMENT_SHADER)创建空 shader 对象；类型签名是 WebGLShader | null，要判 null
gl.shaderSource(shader, source)把 GLSL 字符串交给 shader（不编译）
gl.compileShader(shader)编译；不返回结果，也不抛异常
gl.getShaderParameter(shader, gl.COMPILE_STATUS)问「编译成功了吗」→ true/false
gl.getShaderInfoLog(shader)编译日志（出错的行号和原因）
gl.createProgram()创建空 program（现行规范里不返回 null，见下面的 createBuffer）
gl.attachShader(program, shader)把 shader 挂到 program 上（vertex、fragment 各一次）
gl.linkProgram(program)链接；同样不返回结果
gl.getProgramParameter(program, gl.LINK_STATUS)问「链接成功了吗」
gl.getProgramInfoLog(program)链接日志
gl.createBuffer()创建空 buffer。旧版规范在 context 丢失时返回 null；现行规范和 TypeScript 类型都是非 null，Chromium 丢失时返回一个已经作废的对象
gl.bindBuffer(gl.ARRAY_BUFFER, buffer)让 ARRAY_BUFFER 这个绑定点指向它
gl.bufferData(gl.ARRAY_BUFFER, new Float32Array([...]), gl.STATIC_DRAW)给「绑定点上的那个 buffer」分配存储并写入数据
gl.getAttribLocation(program, 'position')查 attribute 的编号；找不到返回 -1，0 是合法值
gl.vertexAttribPointer(location, 2, gl.FLOAT, false, 0, 0)这个 location 从当前 ARRAY_BUFFER 读：每顶点 2 个 float，不归一化，紧密排列，从第 0 字节开始
gl.enableVertexAttribArray(location)让这个 location 从数组读（不启用就读一个常量值）
gl.viewport(0, 0, gl.drawingBufferWidth, gl.drawingBufferHeight)NDC → 像素的映射区域
gl.clearColor(r, g, b, a)只设置清屏颜色（状态）
gl.clear(gl.COLOR_BUFFER_BIT)真正执行清屏
gl.useProgram(program)设为当前程序
gl.drawArrays(gl.TRIANGLES, 0, 3)从第 0 个顶点起画 3 个顶点，按三角形组装

每个调用的完整说明（失败时怎么报告、要校验什么、项目里在哪用）见 WebGL1 API 速查。

2. 动手：从空白敲出三角形

规则：先只看上面表格里的名字来敲；卡住了再展开签名；参考答案留到最后再看。凭记忆费力地「想起来」，本身就是在加深记忆，这一步不要省。

右边的判分分两组。第一组检查画面和调用本身。第二组是故障注入 (fault injection)：沙盒把你的代码放到新的 context 上再跑三遍，每一遍悄悄把某个 GL 调用改成返回失败值，看你的代码会不会在正确的地方停下。项目的单元测试做的就是这件事——createFakeWebGL1ResourceContext 就是一个可以注入失败的假 context。

我写完了（或者真的卡死了）：参考答案 
function compile(type, source, stage) {
  const shader = gl.createShader(type)
  if (shader === null) throw new Error(`createShader(${stage}) 返回 null`)
  gl.shaderSource(shader, source)
  gl.compileShader(shader)
  if (gl.getShaderParameter(shader, gl.COMPILE_STATUS) !== true) {
    const info = gl.getShaderInfoLog(shader)
    gl.deleteShader(shader)
    throw new Error(`${stage} shader 编译失败：${info}`)
  }
  return shader
}

// ① 程序
const vertex = compile(gl.VERTEX_SHADER, vertexSource, 'vertex')
const fragment = compile(gl.FRAGMENT_SHADER, fragmentSource, 'fragment')
const program = gl.createProgram()
if (program === null) throw new Error('createProgram 返回 null')
gl.attachShader(program, vertex)
gl.attachShader(program, fragment)
gl.linkProgram(program)
if (gl.getProgramParameter(program, gl.LINK_STATUS) !== true) {
  throw new Error('链接失败：' + gl.getProgramInfoLog(program))
}
// 项目的 ProgramManager 在链接成功后还会 detachShader + deleteShader，第 6 课细讲。

// ② 数据
const buffer = gl.createBuffer()
// 现行规范下 createBuffer 不会返回 null（TS 类型也是非 null），这一行防的是旧实现和假 context。
// context 丢失时它返回一个已经作废的对象，要靠 gl.isContextLost() 才能发现——第 2 课讲。
if (buffer === null) throw new Error('createBuffer 返回 null')
gl.bindBuffer(gl.ARRAY_BUFFER, buffer)
gl.bufferData(gl.ARRAY_BUFFER, new Float32Array([0, 0.8, -0.8, -0.8, 0.8, -0.8]), gl.STATIC_DRAW)

// ③ 接线
const location = gl.getAttribLocation(program, 'position')
if (location < 0) throw new Error('attribute position 不存在或没被使用（location = -1）')
gl.bindBuffer(gl.ARRAY_BUFFER, buffer) // 其实已经绑着；写出来是强调 pointer 记下的是「此刻」的绑定
gl.vertexAttribPointer(location, 2, gl.FLOAT, false, 0, 0)
gl.enableVertexAttribArray(location)

// ④ 状态 + 绘制
gl.viewport(0, 0, gl.drawingBufferWidth, gl.drawingBufferHeight)
gl.clearColor(0.1, 0.1, 0.12, 1)
gl.clear(gl.COLOR_BUFFER_BIT)
gl.useProgram(program)
gl.drawArrays(gl.TRIANGLES, 0, 3)

注意几个判断都写成 === null、!== true、< 0，没有用真假值：0 是合法的 location；context 丢失时状态查询返回 null 而不是 false。

三道故障题在考什么

三道题的共同点：WebGL 的失败几乎从不抛 JavaScript 异常。要么返回一个特殊值，要么把结果记在状态里，等你主动去问。所谓校验，就是在每个这种地方主动去问。

注入真实场景GL 怎样报告项目在哪拦住
编译失败 GLSL 拼错一个字 compileShader 照常返回；只有去问 COMPILE_STATUS 才会知道。链接状态也会随之变成 false ProgramManager.compile → ShaderCompilationError(stage, infoLog)
location = -1 attribute 名拼错，或者 shader 没用到它、被编译器优化掉了 返回 -1。拿 -1 去调用 pointer 会记一个 INVALID_VALUE，但 draw 照样执行，画面空白 ProgramManager.ts:156；VertexInputSupport.resolve
createBuffer = null 旧版规范规定 context 丢失时 create* 返回 null。现行规范里只剩 createShader 还可能返回 null；其余的（我在 Chromium 实测过）返回一个已经作废的对象 null：bindBuffer(…, null) 合法，错误拖到 bufferData 才以 INVALID_OPERATION 出现。作废对象：之后的调用全部静默失效，只有 isContextLost() 会告诉你 两道防线：requireNonNull 拦 null，紧接着的 assertAvailable（即 isContextLost）拦作废对象，见 GeometryManager.upload

MDN 的 WebGL best practices 有一句很好的判断标准：「The only errors a well-formed page generates are OUT_OF_MEMORY and CONTEXT_LOST.」凡是出现 INVALID_*，都说明你的代码有 bug。下一课专门讲这五种失败通道。

3. 同样四段，在后端里分给了谁

把你刚写的代码放到项目里，每一段都有一个类负责。区别在于：每个类都在原生调用之外，替你多做了几件事。

段负责的类与入口在原生调用之外多做的事
① WebGL1ProgramManager.get(shader) 以 ShaderModule 对象为 key 缓存（两个 Material 共用一个 shader 时只编译一次）；失败时删掉本次创建的一切；链接后一次性反射所有 attribute、uniform 的 location
② WebGL1GeometryManager.get(geometry) 每个属性一个 buffer，外加可选的索引 buffer；上传前记下原来的绑定，结束后恢复；设备没有 32 位索引扩展时安全地降成 16 位
③ createWebGL1VertexInputManager 选出的策略的 bind(...) 两种策略：有 OES_vertex_array_object 就把接线「录」进 VAO，下次一次 bind 全部恢复；没有就每次重接，并关掉上一个物体遗留的 location
④ WebGL1State.useProgram、bindSurface …
draw call：WebGL1Backend Task 15		 State 记住「上次设成了什么」，值没变就不再发 GL 命令；draw call 本身目前还没有任何代码在发——它在等你写

这些类由 WebGL1ResourceManager 统一组装。完整的依赖关系和所有权，见 架构地图。

4. 为什么要拆成这么多类：三个力

你的沙盒代码只画一个三角形，一个函数就够了。一旦进入真实场景，下面三个力会把这一个函数撕成好几个类：

  1. 共享 (sharing)。两个 Mesh 共用一个 Geometry，照沙盒的写法会 bufferData 两次。要做到只上传一次，就需要一个以 CPU 对象为 key 的缓存——这就是每个 Manager 里的 Map<Geometry, …>、Map<ShaderModule, …>。
  2. 丢失 (context loss)。GPU 重置时，你创建的 buffer 和 program 全部一起作废，但 CPU 上的顶点数组还在。所以 CPU 资源（Geometry、ShaderModule）永远不保存 GPU 句柄 (handle)；句柄只活在「每个 context 一份」的 Manager 里，丢失时整批丢弃，恢复后再新建一批。
  3. 全局状态 (global state)。每次 bindBuffer 都在改写 context 里的全局值。谁改了谁就要负责：要么把原值恢复回去（GeometryManager 就是先保存、后恢复绑定），要么通知状态缓存「我动过了，你记的值不可信了」（hooks.invalidateState）。

之后你在 webgl1/ 里读到的大部分「多出来的代码」，都能归到这三类里；剩下的是校验，也就是本课第二组判分在练的东西。
