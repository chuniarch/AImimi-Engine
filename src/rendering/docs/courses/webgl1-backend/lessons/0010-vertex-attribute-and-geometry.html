resources ①：VertexAttribute 与 Geometry——一份不会被悄悄改掉的顶点数据

一个模型的顶点数据，要从 loader 手里走到 GPU buffer，中间可能隔好几帧，还可能上传到两个 context。这一课逐个函数读 VertexAttribute 和 Geometry，看它们怎样保证三件事：数据一旦交出去就不会再变；不需要设备就能发现的错误，构造时就报出来；和设备有关的决定，留给后端去做。

和你的目标的关系 —— Task 19 的 HW2 场景工厂要把 Mary 的 OBJ 和 PRT 系数装进 Geometry（第 6 节）；第 19 课的 GeometryManager 第一次 draw 时从 Geometry 里读数据上传（第 5 节）。读懂这一层的契约，写 loader 时就知道哪些错会被自动挡住、哪些得自己小心。

1. 设计问题：CPU 几何要保证什么

一份顶点数据从 loader 手里交出去以后，要等第一次 draw 才上传；context 丢失再恢复，还要再上传一次；将来如果有两个 Backend，每个 context 各传一次（第 4 课）。这中间隔了很久，而且读它的人不止一个。所以 CPU 这一层要保证三件事，分别交给不同的地方：

要保证的事由谁负责怎样做到
数据交出去以后不会再变VertexAttribute、Geometry构造时复制一份私有的快照 (snapshot)，之后只通过复制 API 往外给（第 3.3 节）
不需要设备就能发现的错，构造时就报出来VertexAttribute、Geometry 的构造函数分量数、顶点数、索引范围、图元分组全部在构造时验证（第 3.2、4.1 节）
和设备有关的决定，留给知道设备的一层后端的 GeometryManager、VertexInputSupport32 位索引能不能用、每个 attribute 最多几个分量，都等到第一次上传、绑定时才检查（第 5 节）

Geometry 继承 Resource，是被 Scene 登记、被 Manager 按对象身份缓存的单位；VertexAttribute 不是 Resource，它只是 Geometry 里的一个值对象 (value object)，没有自己的生命周期（VertexAttribute.ts:49–51）。

3. VertexAttribute：一个属性的快照

读下面每一节时，先看代码摘录（行尾注释是我加的；「节选」表示省略了一部分），再看表。

3.1 能用哪几种数组

export type VertexAttributeData = Float32Array | Int8Array | Uint8Array | Int16Array | Uint16Array   // VertexAttribute.ts:10

正好是 WebGL1 的 vertexAttribPointer 能直接解释的五种分量类型：FLOAT、BYTE、UNSIGNED_BYTE、SHORT、UNSIGNED_SHORT。没有 Int32Array、Uint32Array（WebGL1 的顶点属性不支持 32 位整数），也没有 Float64Array（GPU 不吃双精度）。Uint32Array 只出现在索引里，能不能用由后端根据扩展决定（:3–9）。后端把这五种类型一一映射成 GL 枚举（WebGL1GeometryManager.ts:339–347）。

3.2 构造：先验证形状，再复制

constructor(options: { readonly data: VertexAttributeData; readonly itemSize: number; readonly normalized?: boolean }) {   // :79–103
  const { data, itemSize, normalized = false } = options
  if (!Number.isInteger(itemSize) || itemSize <= 0) {                   // 每个顶点几个分量：正整数（0、1.5、NaN、Infinity 都不行）
    throw new InvalidVertexAttributeError('attribute', `itemSize must be a positive integer; …`)
  }
  if (data.length % itemSize !== 0) {                                    // 长度必须能整除：不能有「半个顶点」
    throw new InvalidVertexAttributeError('attribute', `data length … is not divisible by itemSize …`)
  }
  this.dataValue = copyVertexAttributeData(data)                         // 复制；类型不在五种之内也在这里抛错
  this.itemSize = itemSize
  this.normalized = normalized
}
作用把一组连续的数字，解释成「每 itemSize 个分量是一个顶点」，并保存一份私有副本。
所在层第一层 resources。调用者是 loader，或者手写几何的代码。
校验itemSize 是正整数；data.length 能被 itemSize 整除；data 是五种 TypedArray 之一（普通数组 [0, 0, 0] 会被拒绝）。长度为 0、布局完整的属性是允许的（测试 VertexAttribute.test.ts:190），要不要至少一个顶点，由 Geometry 决定。
没有检查的itemSize 的上限。WebGL 一个 attribute location 最多 4 个分量，但这是设备的限制，不是数据的限制；由后端在第一次绑定时检查（卡片 F、第 5 节）。另外，没传 data 时 data.length 直接抛 TypeError，而不是 InvalidVertexAttributeError（审查视角 1）。
normalized 是什么只对整数类型有意义：GPU 读取时是否把整数范围映射到 [0, 1] 或 [−1, 1]。例：Uint8Array 存颜色 255，normalized 为 true 时 shader 里读到 1.0，为 false 时读到 255.0。VertexAttribute 自己不调用任何 GL，只记下这个布局信息（:57–63）。
状态、生命周期构造之后没有任何可变状态。不是 Resource：没有 dispose，也不被任何 Manager 缓存；它的寿命跟着引用它的 Geometry（或调用者）走，交给垃圾回收。
它不知道自己的名字「这是 position 还是 normal」由 Geometry 的 Map 键决定，VertexAttribute 本身没有名字。所以它报错时只能用占位名 'attribute'（:12–13），错误信息读起来是「Vertex attribute attribute is invalid」（审查视角 2）。

3.3 copyVertexAttributeData：为什么非复制不可

function copyVertexAttributeData(data: VertexAttributeData): VertexAttributeData {   // :26–37
  if (data instanceof Float32Array) return new Float32Array(data)       // 新数组、新的底层内存 (backing buffer)
  if (data instanceof Int8Array) return new Int8Array(data)
  if (data instanceof Uint8Array) return new Uint8Array(data)
  if (data instanceof Int16Array) return new Int16Array(data)
  if (data instanceof Uint16Array) return new Uint16Array(data)
  throw new InvalidVertexAttributeError('attribute', 'uses an unsupported TypedArray type')
}
作用复制出一个同类型、有独立底层内存的新数组。构造时用一次，copyData 每次也用它。
为什么要复制两个理由（:45–47）。一是调用者交出数组之后还可能继续改它，不复制的话，Geometry 会被悄悄改掉（卡片 A）。二是同一个 Geometry 可能在不同时刻上传到不同 context（恢复后的新一代、将来的第二个 Backend），它们必须看到同一份数据。
为什么不用 Object.freezeJavaScript 不允许冻结有元素的 TypedArray：Object.freeze(new Float32Array([1, 2, 3])) 直接抛 TypeError（卡片 B）。要保证「交出去就不变」，只能自己复制一份私有的，并且永远不把它交出去。
为什么逐个类型写显式列出五种类型，传进来别的 TypedArray（比如 Float64Array）就会明确报错；用一个宽泛的 new (data.constructor)(data) 会把不支持的类型也悄悄复制过去（:21–24）。
代价内存：构造时调用者的数组和快照同时存在，直到调用者的数组被回收；每次 copyData 再多一份临时数组。第 5 节有一个关于它的「想一想」。

3.4 count、copyData 与 copyDataTo：只读，而且只给副本

get count(): number { return this.dataValue.length / this.itemSize }   // :110–112 顶点数；构造时保证是整数

copyData(): VertexAttributeData {                                        // :123–125 每次一个新数组
  return copyVertexAttributeData(this.dataValue)
}

copyDataTo(out: VertexAttributeData): void {                             // :139–155 写进调用者提供的数组
  if (out.constructor !== this.dataValue.constructor) throw …           // 类型必须完全相同：不做隐式数值转换
  if (out.length !== this.dataValue.length) throw …                     // 长度必须完全相同：不截断
  out.set(this.dataValue)                                                // 检查都过了才写，不会只写一半
}
为什么有两个复制 APIcopyData 简单，但每次分配一个新数组；copyDataTo 让调用者复用自己的数组，不分配。两个都不交出内部数组。
为什么 copyDataTo 这么严格如果允许写进 Uint8Array，out.set 会把 0.5 悄悄截成 0；如果允许更短的数组，会抛 RangeError 或写一半。要求类型、长度完全一致，并且先检查、后写入（:135–137）。
状态变化都不改 VertexAttribute。copyDataTo 改调用者的 out。

4. Geometry：把属性组成一个可绘制的整体

4.1 构造：先复制，再按快照验证

constructor(options: { readonly attributes: Readonly<Record<string, VertexAttribute>>; readonly indices?: IndexData; readonly topology?: PrimitiveTopology }) {   // Geometry.ts:188–251
  super()                                                                // Resource：disposed = false，引用数 0
  const { attributes, indices, topology = 'triangles' } = options
  const copiedAttributes = new Map(Object.entries(attributes))          // ① 复制记录（浅复制：VertexAttribute 共用）
  const position = copiedAttributes.get(VertexAttributeSemantic.Position)
  if (position === undefined) throw …('a position attribute is required')     // ② 必须有 position
  const vertexCount = position.count
  if (vertexCount === 0) throw …('the position attribute must contain at least one vertex')
  for (const [attributeName, attribute] of copiedAttributes) {
    if (attribute.count !== vertexCount) throw …(`attribute ${attributeName} has … vertices; expected …`)   // ③ 每个属性的顶点数一致
  }
  const copiedIndices = indices === undefined ? null : copyIndexData(indices)   // ④ 复制索引（只认 Uint8/16/32）
  if (copiedIndices !== null) {
    for (const [indexOffset, vertexIndex] of copiedIndices.entries()) {
      if (vertexIndex >= vertexCount) throw …(`index … at offset … is outside vertex count …`)   // ⑤ 索引不越界
    }
  }
  const drawCount = copiedIndices?.length ?? vertexCount                 // ⑥ 有索引：索引个数；没有：顶点数
  assertValidDrawCount(topology, drawCount)                              // ⑦ 按 topology 检查分组（第 4.2 节）
  this.attributesValue = copiedAttributes                                // ⑧ 全部通过才写字段
  this.indicesValue = copiedIndices
  this.vertexCountValue = vertexCount
  this.drawCountValue = drawCount
  this.topologyValue = topology
}
作用把一组属性、可选的索引和图元类型 (topology) 组成一个可以绘制的整体，并在构造时把能查的错都查完。
所在层第一层 resources。它是 Resource：由 Scene 登记（第 5 课），被每个 context 的 GeometryManager 按对象身份缓存（第 4 课）。
校验必须有 position，而且至少一个顶点；所有属性的顶点数和 position 一致；索引是三种无符号类型之一、不越界；drawCount 满足 topology 的分组要求。名字用的是 VertexAttributeSemantic.Position，免得有人写成 positions。
为什么先复制再验证注释说「先复制 attribute record 和 indices，再根据最终快照完成验证」（:182）。验证的是快照，不是调用者手里的对象：验证完之后调用者再往 record 里加属性、改索引，都影响不到 Geometry（Node 实测：构造之后给 record 加一个 normal，getAttributeNames() 仍然只有 position）。第 9 课 PerspectiveCamera 的快照是同一个道理。
为什么在构造时查索引不查的话，越界要等到 draw 才暴露：WebGL 规范要求 draw 时检查越界，发现了就记一个 INVALID_OPERATION，什么也不画。而 draw 的热路径不调 getError（第 19 课第 3.12 节），这个错会一直憋着，直到下一个冷路径的 preflight 才被取出来，算到一个不相干的资源头上。构造时就抛，是最早、也最说得清的时机（卡片 E）。
状态变化成功时写五个私有字段。任何一步失败都抛错：构造函数一抛错，对象根本不会交到调用者手里，所以也不存在「半个 Geometry」（第 9 课第 3.3 节）。
没有检查的属性值是不是真的 VertexAttribute。构造函数只读 .count，放一个假的 { count: 3 } 也能通过，要到后端上传时才因为没有 copyData 抛 TypeError（卡片 H、审查视角 1）。
和设计文档的差别设计里 topology 是公开只读字段、indices 和 Map 都是 readonly（设计 §10.2）；实现改成私有字段加检查存活的 getter，indices 也去掉了 readonly，为的是释放时能把它断开（第 4.4 节）。

4.2 assertValidDrawCount：多少个元素才能组成完整的图元

function assertValidDrawCount(topology: PrimitiveTopology, drawCount: number): void {   // :58–116（节选）
  switch (topology) {
    case 'triangles':      if (drawCount < 3 || drawCount % 3 !== 0) throw …; break   // 每 3 个一组，互不共享
    case 'lines':          if (drawCount < 2 || drawCount % 2 !== 0) throw …; break   // 每 2 个一组
    case 'line-strip':     if (drawCount < 2) throw …; break                         // 至少 2 个，之后每加 1 个多一段
    case 'triangle-strip': if (drawCount < 3) throw …; break                         // 至少 3 个，之后每加 1 个多一个三角形
    default: assertNever(topology, `[Geometry] unsupported primitive topology: …`)    // 类型之外的值：编译期报错，运行时也抛
  }
}
作用检查 drawCount 个元素能不能按 topology 组成完整的图元。
为什么 CPU 就要查GL 遇到不完整的图元不会报错，只会悄悄丢掉：triangles 画 4 个顶点，第 4 个顶点就被忽略了。这种错在画面上很难看出来（少一个三角形），构造时就拒绝，错误才会被注意到（卡片 D）。
drawCount 用的是哪个数真正交给 draw call 的那个数：有索引时是索引个数，没有索引时是顶点数（:183–186）。4 个顶点、6 个索引的矩形，drawCount 是 6（卡片 C）。
default 分支assertNever 同时管两件事：编译期，将来往 PrimitiveTopology 里加一个成员却忘了加 case，TypeScript 会报错；运行期，JavaScript 调用者传进 'points' 这种类型之外的值，会抛 ExhaustiveMatchError（:44–46、:54–56）。
扩展时要改哪里TODO 说得很清楚：加 points、line-loop、triangle-fan 时，要同时改类型、drawCount 验证、WebGL1 的枚举映射和测试，「不能只扩展此 union」（:16–18）。映射在后端：WebGL1GeometryManager.ts:358–383，它的 default 也调用 assertNever，所以漏改映射同样过不了编译。

4.3 读取：每个 getter 都先查存活

getAttribute(name: string): VertexAttribute | undefined {               // :260–264 借出同一个对象（它不可变）
  this.assertUsable()                                                    // 已释放：抛 ResourceDisposedError
  return this.attributesValue.get(name)
}
getAttributeNames(): readonly string[] { this.assertUsable(); return [...this.attributesValue.keys()] }   // :272–276 新数组
copyIndices(): IndexData | null { this.assertUsable(); return … copyIndexData(this.indicesValue) }       // :284–288 新数组，或 null
get vertexCount / drawCount / indexed / topology                         // :295–335 同样先 assertUsable
作用给后端读数据用的全部入口。没有任何修改方法：初版 Geometry 是完全静态的，没有 revision、usage，也没有 updateAttribute（:135）。
三种给法VertexAttribute 直接借出（它不可变）；名字列表和索引每次给新数组（不暴露内部的 Map 和 TypedArray）；几个数字直接给。
校验每个入口都先 assertUsable()（Resource.ts:77–81）：释放之后再读，一律抛 ResourceDisposedError。
为什么没有 update设计文档要求：动态几何要作为一种完整的新能力单独加入，不能提前把可变的 TypedArray 暴露出去（设计 §10）。一旦能改，第 4 课的「缓存什么时候过期」就要多一种失效：每个 context 的 GPU 副本都得知道数据变了。

4.4 disposeCPUData：释放的最后一步

protected disposeCPUData(): void {                                       // Geometry.ts:345–348
  this.attributesValue.clear()                                           // Map 是 readonly 字段，但内容可以清空
  this.indicesValue = null                                               // 所以这个字段没写 readonly（:150–156）
}
作用断开 Geometry 对属性和索引数据的引用，让可能很大的 TypedArray 能被垃圾回收。
什么时候被调用只有一个时机：Resource 的 finalizeDisposal 先标记 disposed、再逐个通知监听器（各个 GeometryManager 在这时删掉自己的 buffer），最后才调用它（Resource.ts:204–216）。先通知、后断开：监听器执行时，Geometry 的数据还在。
为什么不调 GLGeometry 不知道任何 context（:131–133）。每个 context 的 GPU 副本由各自的 Manager 删；这里只处理 CPU 这一份。
共用的 VertexAttribute 怎么办不受影响。clear 只清掉 Geometry 自己的 Map，里面的 VertexAttribute 对象如果还被别的 Geometry 引用，照样能用（卡片 G）。这就是 VertexAttribute 不做成 Resource 的好处：它不可变，谁用都一样，不需要引用计数。

6. HW2 的例子：Mary 的 Geometry 长什么样

HW2 的 PRT 场景里，每个顶点除了位置，还有预计算的传输系数 (transport SH coefficients)：二阶球谐 9 个数，三阶 16 个。WebGL 一个 attribute 最多 4 个分量，所以 loader 要把它们拆开：9 个拆成 3 个 vec3，16 个拆成 4 个 vec4（旧代码的布局说明：SHAttributeLayout.d.ts:3–20）。按 Task 19 的计划，Mary 的 Geometry 大致是： 

// 示意（课程写的）：二阶 PRT，OBJ 按面展开成不带索引的三角形
new Geometry({
  attributes: {
    position: new VertexAttribute({ data: positions, itemSize: 3 }),      // 内置语义名
    aTransportSH0: new VertexAttribute({ data: sh0, itemSize: 3 }),      // 系数 0、1、2
    aTransportSH1: new VertexAttribute({ data: sh1, itemSize: 3 }),      // 系数 3、4、5
    aTransportSH2: new VertexAttribute({ data: sh2, itemSize: 3 })       // 系数 6、7、8
  }                                                                      // 不带 indices，topology 默认 triangles
})
  • 自定义属性名是允许的。VertexAttributeSemantic 只列出内置的四个名字，「不限制自定义 shader attribute」（VertexAttributeSemantic.ts:8–10）；但名字必须和 shader 里声明的完全一致，后端不猜别名（WebGL1VertexInputSupport.ts:75）。
  • 自动挡住的错。transport 文件的顶点数和 OBJ 对不上，会被第 ③ 步「各属性顶点数一致」拒绝；按面展开之后顶点数一定是 3 的倍数，满足 triangles 的分组要求。
  • 挡不住的错。旧代码拆系数的内层循环写的是 k < shArr.length（组数），而不是这一组的分量数（createSHMesh.ts:62）。二阶是 3 组 × 3 个、三阶是 4 组 × 4 个，组数恰好等于分量数，所以一直没出错；换成 4 + 4 + 1 这样的布局，每个 vec4 的第 4 个系数都会变成 0（我用 Node 实测过）。数组长度、顶点数都对，Geometry 查不出来。计划里专门写了「内层循环使用当前 group itemSize」（Task 19）。数据层能保证结构对，保证不了意思对。

位置复制什么深 / 浅为什么
VertexAttribute 构造data → 新的 TypedArray深调用者之后改原数组，影响不到它
Geometry 构造attributes 记录 → 新 Map浅记录本身复制：调用者之后往 record 里加东西无效；VertexAttribute 不可变，共用安全
Geometry 构造indices → 新的 TypedArray深同 VertexAttribute
copyData()、copyIndices()每次一个新数组深调用者改返回值，影响不到下一次
copyDataTo(out)写进调用者的数组—不分配；要求类型、长度完全相同
getAttributeNames()名字列表 → 新数组—不暴露内部 Map
getAttribute(name)不复制，借出同一个对象—它不可变，借出去也改不了

谁改了什么、怎样结束：

对象或函数改了什么生命周期
new VertexAttribute建立自己的三个字段，之后再也不变不是 Resource；交给垃圾回收
new Geometry建立五个私有字段；Resource 部分 disposed = false、引用数 0Resource：由 Scene 登记，最后一份引用交还时释放
Geometry 的所有 getter无释放之后一律抛 ResourceDisposedError
disposeCPUData清空 Map、断开 indices只在 finalizeDisposal 的最后一步被调用；VertexAttribute 本身不受影响

10. 架构视角

10.1 对照 three.js 的 BufferAttribute 与 BufferGeometry

three.js本项目
数组直接保存调用者的数组（BufferAttribute.js:68），可以随时改，改完设 needsUpdate = true，版本号加一（:152–154）构造时复制，之后改不了；初版没有动态更新
用途提示usage，默认 StaticDrawUsage（:108）没有：初版全是静态几何
组装先 new BufferGeometry，再逐个 setAttribute、setIndex（BufferGeometry.js:268、:207），只是存进去构造时一次给全，并且当场验证顶点数、索引和分组
绘制范围drawRange 可以只画一部分（:178）没有：drawCount 固定
数据在哪BufferAttribute 本身就是 GPU 上传的单位Geometry 是缓存单位；VertexAttribute 只是值

three.js 选的是灵活：数组共享、随时可改、靠版本号通知渲染器重新上传。本项目初版选的是简单可靠：数据不变，GPU 副本就永远不会过期。想做每帧都变的几何（比如你将来 FLIP 项目的水面），要按设计文档的要求，作为一种完整的新能力单独加入，而不是在 Geometry 上补一个 setter。

10.2 审查视角：两处值得讨论，一道找茬题

  1. 运行时类型检查不全。Geometry 不检查属性值是不是 VertexAttribute：假对象 { count: 3 } 能通过构造，要到后端上传时才抛 TypeError（卡片 H）。VertexAttribute 漏传 data 时，抛的是 data.length 的 TypeError，而不是 InvalidVertexAttributeError（我用 Node 实测过）。对照 Mesh 的 instanceof（Mesh.ts:38–39）和第 9 课 PerspectiveCamera 的运行时检查，这里松了。想一想：这两处各该加什么检查、抛什么错？加在哪一行之前？
  2. 错误的名字和分类。VertexAttribute 不知道自己叫什么，报错信息是「Vertex attribute attribute is invalid: …」（占位名 VertexAttribute.ts:13 加上错误类的前缀 RenderingError.ts:151）。另外，运行时传进不支持的 topology，抛的是 ExhaustiveMatchError，它直接继承 Error（ExhaustiveMatchError.ts:1），不在 RenderingError 家族里；按第 6 课的分类，它其实属于「调用者用错了」。想一想：能不能让 Geometry 在错误信息里补上属性名？（提示：VertexAttribute 的错误在它自己构造时就抛了，那时还没有 Geometry。）
  3. 找茬题：模块自己的说明 static-geometry.zh-CN.md 里，有一处示例和真实的构造函数对不上。读第 11 节的延伸阅读时找找看，找到了告诉我。
