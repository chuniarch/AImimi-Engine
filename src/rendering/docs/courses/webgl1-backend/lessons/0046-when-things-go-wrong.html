1. 三层检查，在小引擎的哪一行

一条主线：谁能知道，谁就检查（校验地图第一节）。同一个错越早发现越好，可很多事早的时候还不知道——建材质时不知道 shader 里有没有这个 uniform，建场景时不知道这一帧相机放在哪。所以分三层，每层只查它那一刻能知道的事：

层小引擎里的检查通过以后可以放心
① 构造、修改时Geometry 的长度（第 42 课）、RenderTarget.requireSize、Material.setParameter 的有限数、ParameterBlock.set 的名字和种类、材质的「一个名字一个来源」、setBias 非负（第 45 课）；Engine.setScene 的 passes（第 44 课）每个对象自己是对的；值已经复制、冻结，外面再改影响不到
② 每帧提取时snapshotMatrix：16 个有限数（第 43 课）；snapshotLight：投影的灯必须有阴影设置（第 45 课）交给 Pass 的这一帧数据冻结、有限、组合合法
③ 上 GPU 时编译链接（makeProgram）；每个 active uniform 都有值（setUniforms）；draw 在某扇门里、不采样正在写的目标（Backend.draw）；用到的资源没释放（各 Manager 的 get）这次 draw 的输入完整；出门一定换回

还有一种失败不报错，而是故意做成看得见、无害的样子：阴影块的全零矩阵。没装 ShadowMapPass，或这盏灯这一帧没画，画面就是「没有阴影」（卡片 H）。

第 ③ 层是唯一会「画一半」的地方：GPU 命令发出去就收不回来。所以它只保证状态换回来，不保证像素回滚。真实代码的 SurfaceScope 也只承诺这一点（WebGL1SurfaceScope.ts:156–163：「scope 退出不 dispose RenderTarget，也不回滚已写入的像素」）。

4. 设备丢了：context 丢失与恢复

4.1 丢了什么，还剩什么

显卡驱动重启、系统休眠、GPU 被别的页面占满，浏览器都可能收走一个 WebGL context。规范规定（WebGL 1.0 规范「The Context Lost Event」）：

  • 这个 context 建过的每一个 WebGL 对象（program、buffer、纹理、framebuffer）都被标记作废；之后的 GL 调用什么都不做，查询返回默认值（getParameter 返回 null）。
  • getError 第一次返回 CONTEXT_LOST_WEBGL（37442），之后返回 0。
  • canvas 收到 webglcontextlost 事件。处理函数必须调用 preventDefault，否则恢复的步骤直接中止，这个 context 再也不会回来（卡片 I）。
  • 恢复时收到 webglcontextrestored。丢失前建的对象仍然作废，要用新建的（卡片 K）。

对照这套结构：

东西丢失后怎样回来
Manager 表里的 GPU 对象全部作废表清空；恢复后第一次用到时，照 CPU 资源重建
阴影图里的像素没了ShadowMapPass 每帧在 ForwardPass 之前重画，恢复后第一帧就有
Geometry、ShaderModule、Material、RenderTarget（描述）都在：它们是 CPU 对象不用回来
参数块在：WebGL1 下没有 GPU 部分不用回来；下一帧照常发布
场景、Pass、Pipeline都在不用回来

第 42 课把「画什么」写成 CPU 数据，第 41 课让 GPU 对象按需从这些数据建出来——到这里才看出这两步的另一半用处：GPU 上的一切都可以扔掉重来，因为它们都是 CPU 数据的副本。

4.2 小引擎：忘掉、跳过、换一套新表

  • 丢失时只忘掉，不删除（forgetAll）：旧句柄已经作废，gl.delete* 也没用；但要取消对 CPU 资源的订阅，否则以后释放资源时，旧表里的回调还会去删一个作废的句柄。真实代码一样：WebGL1ProgramManager.invalidateForContextLoss（:244–251）先逐个取消订阅，再清空表，不调用 deleteProgram。
  • 没准备好就整帧跳过：不读场景、不碰 GL、不抛错。注意判断里有两项：丢失事件是异步来的，loseContext() 之后、事件到达之前，isContextLost() 已经是 true（实测）。真实代码的 Backend.ready 也是两项一起看（WebGL1Backend.ts:114–120，注释写着「物理 lost 可能早于事件」），Renderer 开头 if (!this.backend.ready) return（Renderer.ts:51）。
  • 恢复时换一套全新的表，而不是接着用清空的旧表。小引擎里两者效果一样；真实代码这样做是为了让「旧一代」的调用栈即使还拿着旧 Manager，也碰不到新一代的东西（WebGL1Backend.ts:82–95 的 restore 建新的 generation）。
  • restoring 期间也不许画：重建完才回到 ready。
35° （丢失期间也能拖：改的是 CPU 上的场景）

试试：先「画一帧」；「丢失」以后连点几次「画一帧」，再把灯拖到别的角度；最后「恢复」。备课时实测：丢失以后表变成 0 / 0 / 0，跳过的帧里 GL 命令、查询都是 0 次，getError 先给 37442、之后 0；恢复以后的第一帧新建 program 2、shader 4、buffer 2、阴影图一套（纹理、深度缓冲、framebuffer），一共 103 条命令、33 次查询——和第 44 课第一次安装时一样多；画面和丢失期间拖到的那个角度的正确画面逐像素相同。
