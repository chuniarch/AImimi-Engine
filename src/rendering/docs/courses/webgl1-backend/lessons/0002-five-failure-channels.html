GL 怎样告诉你失败了：五条失败通道

第 1 课的三道故障题只是三个例子。这一课把 WebGL 报告失败的所有方式归成五条通道：每条通道「GL 怎么说、你怎么问、项目在哪拦」。然后你亲手写出项目里那几个校验原语——requireNonNull、checkError、状态检查——沙盒会像项目的单元测试一样，用真实的、已丢失的和伪造的 context 去测它们。

和你的任务的关系 —— Task 15 的 draw() 要在十几个 GL 调用之间决定「在哪查、查什么」。查多了会拖慢每一帧（getError 会同步等待 GPU），查少了错误就会在别处以奇怪的样子冒出来。这一课给你一张地图；你说自己「校验考虑不全」，这张地图就是用来补这一块的。

1. 一张地图：五条通道

WebGL 几乎从不抛 JavaScript 异常。能抛的只有参数类型错误（例如 bindBuffer 收到的不是 WebGLBuffer，会抛 TypeError）。其余所有失败，都从下面五条通道之一报出来：

通道GL 怎么说你怎么问项目里的原语
① 特殊返回值返回 null 或 -1：createShader、getAttribLocation、getUniformLocation、getExtension判 === null、< 0，不用真假值requireNonNull
② 状态查询什么都不说，把结果存在对象的状态里：COMPILE_STATUS、LINK_STATUS、framebuffer 完整性主动查，不查就永远不知道compile 与 link 检查、checkFramebufferStatus
③ 错误标志参数取值或当前状态不合法：把 INVALID_ENUM、INVALID_VALUE、INVALID_OPERATION、OUT_OF_MEMORY 记进错误标志 (error flag)getError()，只在冷路径调用checkError、assertTextureOperation
④ context 丢失任何时刻都可能发生：之后所有调用变成空操作，返回默认值isContextLost()；入口查一次，跨过查询、创建或回调之后再查一次assertAvailable
⑤ 静默失败什么都不报，只是结果不对：纹理不完整采样出黑色、attribute 没 enable、uniform 名字拼错只能靠事前校验和最终的像素验收validateStorage、resolve

于是，每写下一个 GL 调用，都可以按顺序问自己四个问题。这就是「校验考虑全面」的具体做法：

  1. 它的返回值能不能是失败值（null、-1）？能就判 === null 或 < 0。
  2. 它有没有对应的状态可查（编译、链接、framebuffer）？有就主动查。
  3. 它会不会把错误记进错误标志？会的话，在这一段冷路径结束时 checkError。
  4. context 还活着吗？入口查一次；跨过一次 GL 查询、创建或外部回调之后再查一次。

四个问题都答完了还是可能出错——那就是第 ⑤ 条通道。它没有「查询」可用，只能在调用之前把参数组合校验好，在调用之后用像素去验收。

2. 语法：先读懂项目里的四个原语

下面每段都是项目的原样代码，注释是我逐行加的。先读懂，第 3 节你要自己写出同样职责的版本。

2.1 getError：每次只取出一个标志

规则（ES 2.0 参考页，并在 Chromium 152 里实测过）：

  • 每一种错误各有一个标志；同一种错误重复发生，只记一次。
  • 每调用一次 getError，取出并清除其中一个。同时有好几个时，返回哪一个不保证——实测我依次制造了 ENUM、VALUE、OPERATION，取出的顺序却是 ENUM、OPERATION、VALUE。要全部取干净，只能循环调用直到 NO_ERROR。
  • context 丢失后，第一次调用返回 CONTEXT_LOST_WEBGL，之后一直是 NO_ERROR；丢失之前还没取走的错误被一并丢弃。
  • 它会同步等待 GPU（MDN：一次 flush 加一次到 GPU 进程的往返）。所以只放在创建、上传这种只发生一次的冷路径 (cold path) 上，不放进每帧的热路径 (hot path)。
  • 错误会一直攒着，直到有人来取。所以在做一件事之前先取一次，叫 preflight：把前面别人留下的错误先报出来，免得算到自己头上。
// WebGL1ProgramManager.ts 的 checkError：10 月 12 日之前的版本（提交 137d9de 的 :323-334），
// 现在的写法见本节末尾的更新
/** 错误检查仅出现在创建冷路径；cache hit 不执行 getError。 */
private checkError(operation: string, label: string): void {
  this.assertAvailable(operation)     // ① 先确认 context 活着：丢失后 getError 会返回 CONTEXT_LOST_WEBGL，不能当普通错误
  const code = this.gl.getError()     // ② 取出一个标志（同步等待 GPU）
  this.assertAvailable(operation)     // ③ 查询期间可能刚好丢失：结果不可信时，按丢失处理
  if (code !== this.gl.NO_ERROR) {    // ④ 有错：包成带 operation 和 label 的领域错误，调用方知道是哪一步、哪个资源
    throw new WebGLOperationError(operation, label, `GL error ${code}`)
  }
}

调用点：ProgramManager.ts:99（preflight：「发现既有 GL 错误时停止，不把它伪装成本次编译产生的错误」）、:318（每个 shader 编译后）、:139（链接后）；GeometryManager 的 :124（preflight）和 :333（每次上传后）。

项目的每个检查点只取一次，没有循环排空。只取一次，足以回答「现在干不干净」：只有所有标志都清空时，getError 才返回 NO_ERROR，所以没有错误时，一次调用就能确认。它做不到的是「有错时一次取完」：同时有两种错误时，只报出其中一种，另一种留给下一个检查点——通常是下一个操作开头的 preflight，于是一个无辜的操作也跟着失败，而第一份报告里只看得到一种错误。循环排空并不更贵：没有错误时，它同样只调用一次；多出来的调用只发生在已经出错的冷路径上。所以改成循环，是一个值得在 code review 里提出的改进——本课沙盒的选做题就是它。
10 月 12 日更新：你已经在工作区把 ProgramManager 和 GeometryManager 的 checkError 改成了循环（WebGL1ProgramManager.ts:354–382、WebGL1GeometryManager.ts:416–444）。和选做题的「排空」相比多了两样：读的次数有上限，32 次还没见到 NO_ERROR 就报「收集未完成」，免得一个坏掉的 context 让循环停不下来；每读一次，前后都检查 context 有没有丢。信息里列出全部错误码，例如「GL errors: 1280, 1281」。顶点输入（WebGL1VertexInputSupport.ts:168）和纹理上传（WebGL1TextureUploadSupport.ts:27）的检查还是只读一次。 
// src/rendering/backend/webgl1/WebGL1ProgramManager.ts:354–382（工作区版本）
// 原注释块在 :323–353，这里换成了课程的注释
private checkError(operation: string, label: string): void {
  const maxErrorReads = 32            // 上限：包括最后那次用来确认的 NO_ERROR
  const errorCodes: number[] = []

  for (let readIndex = 0; readIndex < maxErrorReads; readIndex += 1) {
    this.assertAvailable(operation)   // 读之前：context 还活着
    const code = this.gl.getError()
    this.assertAvailable(operation)   // 读之后：读的期间没有丢

    if (code === this.gl.NO_ERROR) {
      if (errorCodes.length === 0) {
        return                        // 一个错误都没有：和旧版一样，只读了一次
      }
      throw new WebGLOperationError(operation, label, `GL errors: ${errorCodes.join(', ')}`)
    }

    errorCodes.push(code)             // 记下来，接着读
  }

  // 读满 32 次还没见到 NO_ERROR：不假装已经读干净
  throw new WebGLOperationError(
    operation,
    label,
    `GL error collection incomplete after ${maxErrorReads} reads: …`
  )
}

2.2 状态查询：先排除丢失，再解读结果

// src/rendering/backend/webgl1/WebGL1ProgramManager.ts:307-318（compile 的后半段）
gl.shaderSource(compiled, stage === 'vertex' ? source.vertexSource : source.fragmentSource)
gl.compileShader(compiled)                        // 不返回结果、不抛异常，getError 也还是 NO_ERROR
const success: unknown = gl.getShaderParameter(compiled, gl.COMPILE_STATUS)
                                                  // 返回类型是 any：先收进 unknown，逼自己在下面做判断
this.assertAvailable('compile shader')            // 丢失时 success 是 null——那不是编译失败，必须先排除
if (success !== true) {                           // 用 !== true，不用 !success：只有明确的 true 才算成功
  throw new ShaderCompilationError(source.name, stage, gl.getShaderInfoLog(compiled) ?? '')
}                                                 // 错误对象里带上 stage 和 info log，失败时知道是哪个 shader、第几行
this.checkError('compile shader', source.name)    // 顺手把这一段的错误标志也清一遍

顺序是关键：查询 → 确认 context 还活着 → 才解读结果。反过来写，丢失时的 null 就会被当成「编译失败」，报出一个误导人的 ShaderCompilationError。链接用 LINK_STATUS 和 getProgramInfoLog，写法一样（:120–125）。

2.3 requireNonNull：只判 null，而且拦不住丢失

// src/rendering/core/requireNonNull.ts:15-21
export function requireNonNull<T>(value: T | null, errorFactory: () => Error): T {
  if (value === null) {      // 只判 null：0、false、'' 都是合法值，不能用 !value
    throw errorFactory()     // 惰性工厂：只有真的失败时才构造错误对象，成功路径零开销
  }
  return value               // 原样返回，TypeScript 把类型从 T | null 收窄成 T
}

第 1 课备课时我实测发现：现行规范里，createBuffer、createProgram、createTexture 等不再返回 null（TypeScript 5.8 的类型也是非 null），context 丢失时返回的是一个已经作废的对象；只有 createShader 的签名还是 WebGLShader | null。所以光判 null 拦不住丢失。项目的写法是三步连用： 

// src/rendering/backend/webgl1/WebGL1ProgramManager.ts:296-305
const candidate = gl.createShader(type)       // ① 创建
this.assertAvailable('create shader')         // ② 先查丢失：作废对象判 null 判不出来，要靠 isContextLost
const compiled = requireNonNull(candidate, () => new WebGLResourceCreationError('shader', `${source.name}:${stage}`))
                                              // ③ 再判 null：旧实现、测试替身，以及规范仍允许的 createShader 失败
owned.push(compiled)                          // ④ 立刻登记，后面任何一步失败都能找到它、把它删掉

2.4 assertAvailable：入口查一次，跨过查询之后再查一次

// src/rendering/backend/webgl1/WebGL1ProgramManager.ts:384-392
/** 物理 lost 可以早于 DOM 事件，因此不能只依赖 onLost 回调。 */
private assertAvailable(operation: string): void {
  if (this.disposedValue) throw new WebGLBackendDisposedError(operation)   // 我们自己关掉的：生命周期错误
  if (this.lostValue || this.gl.isContextLost()) {                        // 之前记下的丢失，或者浏览器此刻报告丢失
    this.invalidateForContextLoss()                                        // 整批丢弃这一代的记录（不对失效的 context 发 delete）
    throw new WebGLContextLostError(operation)
  }
}

为什么不能只靠 webglcontextlost 事件？事件是异步派发的：GPU 已经丢了，事件可能还没到，这期间 isContextLost() 已经返回 true。所以每个入口直接问浏览器。「跨过一次查询之后再查一次」的例子：Capabilities.ts:41 和 :53 在探测前后各查一次，避免把丢失期间 getExtension 返回的 null 误判成「不支持」。

3. 动手：写出你自己的校验原语

模板里给了四种错误类型（对应项目的错误类）。你要补完五个函数。这一课不画图，沙盒会像单元测试一样调用你的函数：有时传真实的 context，有时传已经丢失的 context，有时传一个在 getError 之后才「丢失」的伪造 context。第一次运行全红是正常的——先红后绿，和项目的 TDD 流程一样。

我写完了（或者真的卡住了）：参考答案 
function requireNonNull(value, what) {
  if (value === null) throw new NullHandleError(`${what} 返回了 null`)
  return value
}

function assertAlive(gl, operation) {
  if (gl.isContextLost()) throw new ContextLostError(`${operation}：context 已丢失`)
}

function checkError(gl, operation) {
  assertAlive(gl, operation)            // 丢失后 getError 会返回 CONTEXT_LOST_WEBGL，不能当普通错误
  const code = gl.getError()
  assertAlive(gl, operation)            // 查询期间可能刚好丢失：先确认结果还可信
  if (code !== gl.NO_ERROR) {
    throw new GLCallError(`${operation}：${ERROR_NAMES[code] ?? '0x' + code.toString(16)}`)
  }
}

function checkCompiled(gl, shader, stage) {
  const ok = gl.getShaderParameter(shader, gl.COMPILE_STATUS)
  assertAlive(gl, `compile ${stage}`)   // 丢失时 ok 是 null，不是编译失败
  if (ok !== true) {
    throw new CompileError(`${stage} shader 编译失败：${gl.getShaderInfoLog(shader) ?? ''}`)
  }
}

function checkLinked(gl, program) {
  const ok = gl.getProgramParameter(program, gl.LINK_STATUS)
  assertAlive(gl, 'link program')
  if (ok !== true) {
    throw new CompileError(`链接失败：${gl.getProgramInfoLog(program) ?? ''}`)
  }
}

// 选做：一次排空所有错误标志
function checkErrorDrained(gl, operation) {
  const names = []
  for (let guard = 0; guard < 16; guard++) {   // 上限防止实现异常时死循环
    assertAlive(gl, operation)
    const code = gl.getError()
    assertAlive(gl, operation)
    if (code === gl.NO_ERROR) break
    names.push(ERROR_NAMES[code] ?? '0x' + code.toString(16))
  }
  if (names.length > 0) throw new GLCallError(`${operation}：${names.join(', ')}`)
}

选做题要让沙盒测到它，把 checkErrorDrained 的函数体直接写进 checkError（或者在 return 里写 checkError: checkErrorDrained）。

5. 在项目里：通道 → 错误类型 → 上层怎么处理

项目为每种失败准备了不同的错误类（都继承自 RenderingError）。分这么多类，不是为了好看，而是让上层可以分别处理：有的该报告给开发者，有的该暂停绘制等待恢复，有的该换一种方案重试。

通道项目原语抛出的错误类上层该怎么办
① null / -1requireNonNull、location < 0WebGLResourceCreationError、WebGLOperationError中止这次构建，清理已经创建的对象
② 编译、链接compile 与 link 的状态检查ShaderCompilationError、ProgramLinkError（带 infoLog）报告给开发者：这是 shader 写错了，重试没有用
② framebuffercheckFramebufferStatusIncompleteFramebufferError换一种附件格式，或者关掉这个功能
③ 错误标志checkError、assertTextureOperationWebGLOperationErrorINVALID_* 是代码 bug，要修；OUT_OF_MEMORY 可以考虑降低分辨率
④ 丢失assertAvailableWebGLContextLostError停止绘制，等 restored 事件后重建（第 5 课）
⑤ 静默validateStorage、resolve 等事前校验UnsupportedRenderFeatureError、InvalidTextureSourceError在上传之前就拒绝，并说明原因

另外还有一类不是 GL 给的失败：我们自己的生命周期。Manager 已经 dispose 之后又被调用，抛 WebGLBackendDisposedError；CPU 资源已经释放之后又被使用，抛 ResourceDisposedError。它们和 context 丢失是两回事：前者是调用方的 bug，后者是设备那边发生的事。
