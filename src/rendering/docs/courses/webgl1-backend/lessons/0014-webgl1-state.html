backend ②：什么时候可以不发 GL 命令

GL 是状态机：useProgram、bindBuffer、enable 设下去的值会一直留着，直到下一次改它。连着画几个用同一个材质的物体，同样的命令就会一遍遍重发。WebGL1State 记住上一次设的值，相同就不发。这一课从「画三次同一个模型」出发，一版一版写出这个缓存，看清它在什么时候会骗人；再看同一个类里为什么偏偏不缓存输出目标，每次都去问 GL，以及这样做每帧要问多少次。

和你的目标的关系 —— 每次 draw，Backend 都经过 State 设 program、深度和剔除（WebGL1Backend.ts:214、:308–329）；每进入一次 surface scope，都经过 State 记下、切换、恢复输出目标（WebGL1SurfaceScope.ts:208、218、306）；每个 Manager 绕过 State 改了 GL 以后，都通过钩子让 State 作废（WebGL1Backend.ts:264–266）。FFT 迁移计划的「决定 4」问的就是这一课第 3 节的事。
默认你已经会的：GL 是状态机，useProgram、bindBuffer、enable 的作用（第 1 课）；「缓存什么时候过期」（第 4 课第 5 节）；surface scope 的骨架：先记下、再切换、finally 里恢复（第 6 课卡片 D）；Backend.draw 的顺序和卡片 H（第 19 课）；context 丢失（第 13 课）。VAO 在第 1 课出现过，这一课只用到一条事实：每个 VAO 各自记着一份索引 buffer（EBO）绑定，卡片会在你的浏览器里验证。
这一课从零讲的：缓存里 undefined 和 null 为什么不能混用；invalidate 为什么只「忘记」、不「重置」；切换 VAO 以后为什么只作废 EBO；深度状态为什么信缓存、输出目标为什么每次查询，以及每帧要查多少次。
页面会用到你的显卡：标着「真实 WebGL」的三张卡片和第 3.4 节的计时实验，会在你的浏览器里创建 WebGL context，用完释放。其余卡片用一个会记账的假 GL：它不画像素，只记下每一条命令、每一次查询，并跟踪 GL 里真实的绑定。

1. 需求

1.1 先看原始输入：一次 draw 之前发哪些状态命令

这是 Backend.draw 里设状态的几行，和它调用的 applyDrawState：

// WebGL1Backend.ts:214–217、:308–329（节选，注释是课程加的）
generation.state.useProgram(program.program)      // 经过 State：可以去重
this.applyDrawState(material, generation.state)   // 见下面
generation.uniforms.upload(commands)
// 顶点输入：自己绑 VAO 和 buffer，不经过 State
generation.resources.vertexInputs.bind(geometry, buffers, program)

private applyDrawState(material: Material, state: WebGL1State): void {
  const gl = this.gl
  // 还不支持的功能：每次 draw 都无条件关掉，不经过 State（6 条命令）
  for (const capability of [gl.BLEND, gl.STENCIL_TEST, gl.SCISSOR_TEST,
    gl.POLYGON_OFFSET_FILL, gl.SAMPLE_ALPHA_TO_COVERAGE, gl.SAMPLE_COVERAGE]) {
    gl.disable(capability)
  }
  gl.colorMask(true, true, true, true) // 这 4 条也是每次都发
  gl.depthRange(0, 1)
  gl.frontFace(gl.CCW)
  gl.lineWidth(1)

  // 经过 State：深度测试、深度写入、深度比较，最多 3 条；剔除，最多 2 条
  state.setDepthState(material.state)
  state.setCullMode(material.state.cullMode)
}

HW2 每帧画两样东西。先画背景立方体：深度测试开、深度写入关、比较函数 less-equal、剔除正面（createHW2Scene.ts:357–362）。再画 Mary：用 Material 的默认值，深度测试开、深度写入开、less-equal、剔除背面（Material.ts:116–139）。经过 State 的那部分，每次 draw 最多 1 + 3 + 2 = 6 条命令。State 要做的，就是把其中和上一次相同的省掉。

为了先看清楚缓存本身，第 2 节的前几版只管四样东西：program、顶点 buffer、索引 buffer、深度测试开关。深度的另外两项和剔除，到 2.5 节的真实代码里再补全，做法完全一样。

1.2 需求：要应付哪些情况

  1. 重复的值不发。同一个模型画三次（比如场景里三棵一样的树），每次 draw 前都要设 program P、顶点 buffer B、索引 buffer I、打开深度测试。第二、三次和第一次完全一样，不该再发。
  2. 一开始什么都不知道。State 刚建好时，GL 里绑着什么，它并不知道。同一个 canvas 上的旧渲染器可能刚画完，留下了它的 program：对同一个 canvas 再调一次 getContext，拿到的就是同一个 context（第 19 课卡片 E）。所以每样东西第一次都必须发。
  3. null 也是要发的值。useProgram(null) 是「解绑」，删除 program 之前常常要先这样做。它不能被当成「已经是这样了」跳过。
  4. 有人绕过 State 改了 GL，要能作废。上传模型、创建离屏目标的代码会直接调用 bindBuffer、bindFramebuffer。改完以后，State 记的就不对了。
  5. 切换 VAO 会顺带换掉索引绑定。只作废受影响的那一项，program 和深度照常去重。
  6. context 丢了，就不再发命令。丢失期间发的命令，浏览器会默默丢掉。
  7. 临时换输出目标，结束后换回来。进入一段离屏绘制前记下当前的 framebuffer 和 viewport，结束时（正常结束或抛错）恢复；嵌套时，每一层恢复到自己的入口（第 6 课卡片 D）。

2. 一版一版写

2.1 第 0 版：不缓存

// 第 0 版：不缓存。每次调用都原样发给 GL
class StateV0 {
  constructor(private readonly gl: WebGLRenderingContext) {}

  useProgram(program: WebGLProgram | null): void {
    this.gl.useProgram(program) // 不管 GL 里是不是已经是它，照发
  }

  bindArrayBuffer(buffer: WebGLBuffer | null): void {
    this.gl.bindBuffer(this.gl.ARRAY_BUFFER, buffer) // 顶点数据从哪个 buffer 读
  }

  bindElementArrayBuffer(buffer: WebGLBuffer | null): void {
    this.gl.bindBuffer(this.gl.ELEMENT_ARRAY_BUFFER, buffer) // 索引从哪个 buffer 读
  }

  setDepthTest(enabled: boolean): void {
    if (enabled) this.gl.enable(this.gl.DEPTH_TEST)
    else this.gl.disable(this.gl.DEPTH_TEST)
  }
}

2.2 第 1 版：记住上一次的值，初值用 null

最直接的想法：每样东西记一个字段，设之前先比较，相同就 return。字段总得有个初值，最顺手的是 null，意思是「什么也没绑」。three.js 就是这样写的（第 4 节）。

// 第 1 版：记住上一次设的值，相同就不发。初值用 null
class StateV1 {
  private programValue: WebGLProgram | null = null // 初值 null：当作「现在什么也没绑」
  private arrayBufferValue: WebGLBuffer | null = null
  private elementArrayBufferValue: WebGLBuffer | null = null
  // 深度测试只会是 true / false，null 表示还没设过
  private depthTestValue: boolean | null = null

  constructor(private readonly gl: WebGLRenderingContext) {}

  useProgram(program: WebGLProgram | null): void {
    if (this.programValue === program) return // 和记住的一样：认为 GL 里已经是它，不发
    this.gl.useProgram(program)
    this.programValue = program // 发完再记，记的就是 GL 里现在的值
  }

  bindArrayBuffer(buffer: WebGLBuffer | null): void {
    if (this.arrayBufferValue === buffer) return
    this.gl.bindBuffer(this.gl.ARRAY_BUFFER, buffer)
    this.arrayBufferValue = buffer
  }

  bindElementArrayBuffer(buffer: WebGLBuffer | null): void {
    if (this.elementArrayBufferValue === buffer) return
    this.gl.bindBuffer(this.gl.ELEMENT_ARRAY_BUFFER, buffer)
    this.elementArrayBufferValue = buffer
  }

  setDepthTest(enabled: boolean): void {
    if (this.depthTestValue === enabled) return
    if (enabled) this.gl.enable(this.gl.DEPTH_TEST)
    else this.gl.disable(this.gl.DEPTH_TEST)
    this.depthTestValue = enabled
  }
}

问题出在初值。null 在这里身兼两职：既表示「我还不知道」，又是 useProgram 的一个合法参数「解绑」。两件事撞在一起，第一次 useProgram(null) 就被跳过了。下面这张卡片在你的浏览器里看看跳过的后果。

2.3 第 2 版：初值改成 undefined，并加上 invalidate

第一处改动：「不知道」换一个 null 以外的值来表示。字段不写初值就是 undefined，它不等于任何 program，也不等于 null，所以每样东西第一次一定会发。这就是真实代码类注释里那句「undefined 表示缓存未知，null 表示已知没有绑定对象」（WebGL1State.ts:24–25），测试的第一条守的就是它（WebGL1State.test.ts:25–41）。

第二处改动是为了第 4 条需求。先看没有它会怎样，再看加上以后：

// 第 2 版：初值改成 undefined（「不知道」），并加上 invalidate
class StateV2 {
  // 不写初值，就是 undefined：「不知道 GL 里现在是什么」
  // null 留给「确实没绑」：useProgram(null) 是一条真实的解绑命令，不能和「不知道」混用
  private programValue: WebGLProgram | null | undefined
  private arrayBufferValue: WebGLBuffer | null | undefined
  private elementArrayBufferValue: WebGLBuffer | null | undefined
  private depthTestValue: boolean | undefined

  constructor(private readonly gl: WebGLRenderingContext) {}

  useProgram(program: WebGLProgram | null): void {
    // undefined 不等于任何 program，也不等于 null：第一次一定发
    if (this.programValue === program) return
    this.gl.useProgram(program)
    this.programValue = program
  }

  bindArrayBuffer(buffer: WebGLBuffer | null): void {
    if (this.arrayBufferValue === buffer) return
    this.gl.bindBuffer(this.gl.ARRAY_BUFFER, buffer)
    this.arrayBufferValue = buffer
  }

  bindElementArrayBuffer(buffer: WebGLBuffer | null): void {
    if (this.elementArrayBufferValue === buffer) return
    this.gl.bindBuffer(this.gl.ELEMENT_ARRAY_BUFFER, buffer)
    this.elementArrayBufferValue = buffer
  }

  setDepthTest(enabled: boolean): void {
    if (this.depthTestValue === enabled) return
    if (enabled) this.gl.enable(this.gl.DEPTH_TEST)
    else this.gl.disable(this.gl.DEPTH_TEST)
    this.depthTestValue = enabled
  }

  /**
   * 有人绕过我直接改了 GL（比如上传新 buffer 时直接 bindBuffer）：把记住的全部忘掉。
   * 只改 JS 里的记录，不发任何 GL 命令；下次设置时，不管值是什么都重新发。
   */
  invalidate(): void {
    this.programValue = undefined
    this.arrayBufferValue = undefined
    this.elementArrayBufferValue = undefined
    this.depthTestValue = undefined
  }
}

invalidate 只做一件事：把记住的值全部改回「不知道」。它不发任何 GL 命令，也不把 GL 改回什么默认值；GL 里现在是什么，就还是什么。下一次设置时，因为「不知道」不等于任何值，命令照常发出，缓存和 GL 重新对上。真实代码的注释管这叫「遗忘全部已缓存状态，但不把 GPU 重置成任何默认值」（WebGL1State.ts:265–280）。第 4 节会和 three.js 的 reset 对比：那边是发 31 条命令，把 GL 改成一组已知的默认值。

2.4 第 3 版：切换 VAO 以后，只作废 EBO

先在你的浏览器里确认一条事实：哪些绑定跟着 VAO 走，哪些不跟。

OES_vertex_array_object 规范把 ELEMENT_ARRAY_BUFFER_BINDING 列为 VAO 状态的一部分，并特意写明 ARRAY_BUFFER_BINDING 除外（顶点数据来自哪个 buffer，是在 vertexAttribPointer 那一刻记进 VAO 的）。所以切换 VAO 以后，State 记的 EBO 就不可信了，其余几项照样可信。第 2 版只有「全部忘掉」一种失效，用在这里太粗了：program 和深度也会跟着重发。第 3 版加一个只管 EBO 的失效： 

// 第 3 版：第 2 版的类原样保留，只多一个方法
class StateV3 {
  // ……第 2 版的四个字段、四个设置方法、invalidate，一行不改……

  /**
   * EBO（ELEMENT_ARRAY_BUFFER）的绑定存在 VAO 里，每个 VAO 各有一份。
   * 切到另一个 VAO，GL 里的 EBO 就变成那个 VAO 自己的，我记住的那个已经不对了。
   * program、ARRAY_BUFFER、深度测试都不属于 VAO，切换 VAO 不影响它们，用不着全部忘掉。
   */
  invalidateVertexInputState(): void {
    this.elementArrayBufferValue = undefined
  }
}

2.5 真实代码：比第 3 版多了什么

第 3 版已经满足了前五条需求。真实代码再做三件事：每个设置方法先检查 context 有没有丢（第 6 条）；深度拆成测试、写入、比较三项分别缓存，再加上剔除；另外三个方法管输出目标（第 7 条，放到第 3 节）。每一代 Manager 配一个新的 State（WebGL1Backend.ts:259–267），所以恢复以后，旧缓存不会混进新的一代。 

// 项目里的真实代码（WebGL1State.ts:30–169、:265–306，节选，注释是课程加的）
export class WebGL1State {
  private readonly gl: WebGLRenderingContext

  // 和第 3 版一样：不写初值 = undefined = 不知道；null = 确实没绑
  private programValue: WebGLProgram | null | undefined
  private arrayBufferValue: WebGLBuffer | null | undefined
  private elementArrayBufferValue: WebGLBuffer | null | undefined
  // 第 3 版只有一个深度开关；真实代码把 Material 的 RenderState 拆成四个字段，各记各的
  private depthTestValue: boolean | undefined
  private depthWriteValue: boolean | undefined
  private depthFunctionValue: DepthFunction | undefined
  private cullModeValue: CullMode | undefined

  // 构造时不去问 GL，也不发命令：一律从「不知道」开始
  constructor(gl: WebGLRenderingContext) {
    this.gl = gl
  }

  useProgram(program: WebGLProgram | null): void {
    this.assertContextAvailable('use program') // 新增：丢了就别发（见下面）
    if (this.programValue === program) return
    this.gl.useProgram(program)
    this.programValue = program
  }

  // bindArrayBuffer、bindElementArrayBuffer、invalidateVertexInputState 和第 3 版相同，略

  setDepthState(state: RenderState): void {
    this.assertContextAvailable('set depth state')
    // 'less-equal' → gl.LEQUAL
    const depthFunction = this.toDepthFunction(state.depthFunction)

    // 三个字段分开比较：只有变了的那一项才发命令
    if (this.depthTestValue !== state.depthTest) {
      if (state.depthTest) this.gl.enable(this.gl.DEPTH_TEST)
      else this.gl.disable(this.gl.DEPTH_TEST)
      this.depthTestValue = state.depthTest
    }
    if (this.depthWriteValue !== state.depthWrite) {
      this.gl.depthMask(state.depthWrite)
      this.depthWriteValue = state.depthWrite
    }
    // 缓存里存的是 'less-equal' 这样的字符串，比较的也是字符串；
    // 只有发命令时才换成 GL 的数字
    if (this.depthFunctionValue !== state.depthFunction) {
      this.gl.depthFunc(depthFunction)
      this.depthFunctionValue = state.depthFunction
    }
  }

  setCullMode(mode: CullMode): void {
    this.assertContextAvailable('set cull mode')
    if (this.cullModeValue === mode) return
    switch (mode) {
      case 'none': // 不剔除：关掉 CULL_FACE 就够了
        this.gl.disable(this.gl.CULL_FACE)
        break
      case 'front': // 剔除正面：打开 CULL_FACE，再指定剔除哪一面
        this.gl.enable(this.gl.CULL_FACE)
        this.gl.cullFace(this.gl.FRONT)
        break
      case 'back':
        this.gl.enable(this.gl.CULL_FACE)
        this.gl.cullFace(this.gl.BACK)
        break
      default:
        // 以后加了新的剔除模式，这里会编译不过
        assertNever(mode, 'Unsupported WebGL1 cull mode')
    }
    this.cullModeValue = mode
  }

  // 和第 2 版一样：只忘，不发命令，也不把 GL 改回任何默认值
  invalidate(): void {
    this.programValue = undefined
    this.arrayBufferValue = undefined
    this.elementArrayBufferValue = undefined
    this.depthTestValue = undefined
    this.depthWriteValue = undefined
    this.depthFunctionValue = undefined
    this.cullModeValue = undefined
  }

  // 每个设置方法第一行都调用它
  private assertContextAvailable(operation: string): void {
    if (this.gl.isContextLost()) {
      this.invalidate() // GL 里的东西已经全没了，记住的值都作废
      // 丢失期间的命令浏览器会默默丢掉，不如直接告诉调用者
      throw new WebGLContextLostError(operation)
    }
  }
}

第二张卡片的结果和第 19 课卡片 H 是同一件事，这里换成数命令：顶点输入的 bind 每次都在 finally 里调用钩子（WebGL1OESVertexInputManager.ts:136–138），而钩子接的是整份 state.invalidate()（WebGL1Backend.ts:264–266）。2.4 节专门为切换 VAO 写的 invalidateVertexInputState，在正式代码里没有人调用（第 5 节）。

2.6 和 Lifecycle 的关系

第 13 课第 2 节说过，context 丢了以后 Backend 要做两件事：把旧的一代作废，再建新的一代。State 在这两件事里的位置，可以归成四点：

  1. 一代一个 State。createGeneration 每次都 new WebGL1State(this.gl)（WebGL1Backend.ts:261）。恢复时整个换成新的，旧的不再被引用，所以 State 不需要「重置」方法。
  2. lost 事件到达：只忘，不发命令。onLost → invalidateGeneration → state.invalidate()（:331–336）。context 已经丢了，命令发出去也会被浏览器丢掉，所以这里和 2.3 节的 invalidate 一样，只把缓存改回「不知道」。
  3. 事件还在排队、context 已经丢了：先发现，再抛错。第 13 课的卡片测到，loseContext() 返回时 isContextLost 已经是 true，lost 事件却还没派发。这段空隙里有人调用 State，每个方法第一行的 assertContextAvailable 会先发现：作废缓存，抛出 WebGLContextLostError（WebGL1State.ts:283–288）；2.5 节最后一张卡片演示过。出门恢复输出目标时也一样，只作废、不发命令（:255–259）。
  4. 新的一代从「全都不知道」开始。新 context 里的状态是 GL 的默认值，和旧缓存毫无关系。新 State 的七个字段全是 undefined，所以恢复后的第一次 draw，program、深度、剔除都会发一遍。这是 2.3 节选 undefined 而不选 null 的又一个好处：不用为恢复写特殊代码。

下面用假 GL 和项目真实的 State 走一遍：画一次 Mary，然后浏览器收走 GPU、事件还在排队，接着 lost 事件到达，最后恢复、建第 2 代。

3. 信缓存，还是每次问 GL

3.1 深度：信缓存

上面几版有一个共同前提：缓存记的值就是 GL 里的值。还有一种做法不需要这个前提：每次设置之前，先问 GL 现在是什么。

// 另一种做法（课程自写，用来对比）：不信缓存，每次先问 GL 现在是什么
class QueriedDepthState {
  constructor(private readonly gl: WebGLRenderingContext) {}

  setDepthState(state: RenderState): void {
    const gl = this.gl
    // 三次查询：不管值有没有变，每次调用都要问
    const testNow = gl.isEnabled(gl.DEPTH_TEST)
    const writeNow = gl.getParameter(gl.DEPTH_WRITEMASK) as boolean
    const funcNow = gl.getParameter(gl.DEPTH_FUNC) as number

    if (testNow !== state.depthTest) {
      if (state.depthTest) gl.enable(gl.DEPTH_TEST)
      else gl.disable(gl.DEPTH_TEST)
    }
    if (writeNow !== state.depthWrite) gl.depthMask(state.depthWrite)
    // DEPTH_FUNC 查回来是 GL 的数字（比如 515），要先把 'less-equal' 换成数字再比
    const wanted = toGLDepthFunction(gl, state.depthFunction)
    if (funcNow !== wanted) gl.depthFunc(wanted)
  }
}

真实代码选了信缓存，并在 setDepthState 的注释里把账算清楚了（WebGL1State.ts:88–117）：每次查询，一帧调用 1000 次就多出 3000 次查询；查询有调用成本，还可能要等 GPU 进程回话。省掉查询的代价是一条规矩：受管理的状态必须经过 State 修改；谁绕过它，谁就得调用 invalidate。所以 invalidate 不是可有可无的补丁，而是「信缓存」这个选择的另一半。

3.2 输出目标：每次都问

同一个类里，管输出目标的三个方法却反过来：一律不缓存，进入时问 GL，切换时照发，退出时按问到的值恢复。

// 项目里的真实代码（WebGL1State.ts:180–263，注释是课程加的）

// 进入一段临时绘制之前调用：把 GL 里现在的输出目标问出来，记下来
captureSurfaceState(): SurfaceStateSnapshot {
  this.assertContextAvailable('capture surface')
  // 两次查询。这里不用缓存，每次都问 GL 真实的值
  const framebuffer = this.gl.getParameter(this.gl.FRAMEBUFFER_BINDING) as
    WebGLFramebuffer | null
  const viewport = this.gl.getParameter(this.gl.VIEWPORT) as Int32Array
  this.assertContextAvailable('capture surface') // 查询途中丢了：查到的是 null，不能用
  // viewport 复制成冻结的四个数：GL 交回的 Int32Array 不能被别人改掉
  const copiedViewport: readonly [number, number, number, number] = Object.freeze([
    viewport[0]!, viewport[1]!, viewport[2]!, viewport[3]!
  ])
  return Object.freeze({ framebuffer, viewport: copiedViewport })
}

// 切到这次要画的目标。null 表示画到屏幕（默认 framebuffer）
bindSurface(resource: WebGL1SurfaceResource | null): void {
  this.assertContextAvailable('bind surface')
  // 不比较、不跳过：创建 RenderTarget 时 Manager 会直接绑定新的 FBO，GL 里现在是什么说不准
  this.gl.bindFramebuffer(
    this.gl.FRAMEBUFFER,
    resource === null ? null : resource.framebuffer
  )
  // 屏幕用 drawing buffer 的像素尺寸，离屏目标用它自己的尺寸
  this.gl.viewport(
    0,
    0,
    resource === null ? this.gl.drawingBufferWidth : resource.width,
    resource === null ? this.gl.drawingBufferHeight : resource.height
  )
}

// 临时绘制结束（正常或抛错，都在 finally 里调用）：回到进入之前记下的目标
restoreSurfaceState(snapshot: SurfaceStateSnapshot): void {
  if (this.gl.isContextLost()) {
    this.invalidate() // 丢了：旧 framebuffer 已经失效，绑回去也没用。只忘记缓存
    return // 不抛错：外层可能正在抛 draw 的原始错误，这里再抛会把它盖住
  }
  this.gl.bindFramebuffer(this.gl.FRAMEBUFFER, snapshot.framebuffer)
  this.gl.viewport(...snapshot.viewport)
}

为什么这里不信缓存？

  • 迁移期，同一个 context 上还有旧代码。旧引擎的渲染路径不经过 State，它绑过什么 framebuffer、设过什么 viewport，State 不可能知道。State 的注释写明，查询真实 framebuffer 和 viewport 是「记录作用域入口」，和逐 draw 设深度「不是同一种使用频率和职责」（WebGL1State.ts:112–114）。
  • 创建离屏目标时，Manager 会直接绑定新的 FBO。RenderTargetManager 先查出原来的 framebuffer，绑定新的 FBO 配置附件，最后再绑回原来那个（WebGL1RenderTargetManager.ts:246、:262、:350）。它用的也是查询到的真实值。所以 scope 必须在解析目标之前先记下入口（WebGL1SurfaceScope.ts:184）。
  • 恢复错了，后面的绘制就画到别处。入口可能是屏幕，也可能是外层 scope 的离屏目标。记错一次，外层剩下的 draw 就全画错了地方（第 6 课卡片 D）。

3.3 每帧要问几次

代价是：每进入一次 scope，至少查询 2 次。scope 带清屏时，清屏代码还要再查几项，因为 WebGL 的 clear 受写掩码和 scissor 影响，要先查出来、临时改掉、清完再改回去（WebGL1SurfaceScope.ts:359–382）。下面两张卡片用项目的真实 WebGL1SurfaceScope 和 WebGL1State，在假 GL 上数查询次数。

FFT 的数字来自迁移计划的默认配置：4 层海浪，每层 N = 512，log₂N = 9；每层每帧 74 次 draw（频谱 1 次、IFFT 4 × 2 × 9 = 72 次、组装 1 次），每次 draw 换一个目标，所以每次 draw 一个 scope，4 层共 296 个。旧的 FFT 代码（v3）是一整块，自己知道绘制顺序，只在 pass 入口查询一次，共 7 次。新代码由通用的积木拼成，每块积木不知道外面是什么，只好每次进门都问一遍。下面可以自己组合：

3.4 次数不等于耗时

592 次查询要多久，取决于浏览器怎样回答它。MDN 的 WebGL 最佳实践说，get*Parameter() 一般来说「可能要 flush 再往返一次」，有些情况浏览器会缓存答案，免去往返，但不要依赖这一点（MDN · Avoid blocking API calls in production）。Chrome 的 WebGL 跑在独立的 GPU 进程里，需要往返的查询要同步等对方回答；具体哪些查询需要往返，我没有查证 Chrome 的源码。所以用你的浏览器量一量：

我备课时用无界面 Chrome（Chrome 的软件渲染 SwiftShader）量到的数：

                         每次      每帧 592 次（FFT）
getParameter 这两项      0.2–0.6 μs   约 0.14 ms   ← 不到一帧预算 16.7 ms 的 1%
读 JS 缓存               几乎为 0     约 0.003 ms
getError（对照）          37–62 μs     约 23 ms     ← 超过一整帧

（两次运行，每种组合各跑 60 帧取平均；表里是两次运行的范围。）

同样是「问 GL」，getError 每次要等 GPU 进程回话，比这两项 getParameter 慢一百倍以上。这两项这么快，看起来 Chrome 没有为它们跨进程，在本进程就答了。至少在这台机器的 Chrome 上，FFT 每帧 592 次这两项查询不是瓶颈；查询前先排 300 次 draw，结果也差不多。这只是一种浏览器的结果：Firefox、Safari 怎样回答这两项查询，我没有测；MDN 也提醒不要依赖浏览器的这种缓存。所以请在你的浏览器里跑一遍，把数字告诉我。迁移计划定的原则是「先测量再优化」，这组数字就是测量的第一步。

3.5 如果要省，有两种改法

  • 嵌套的 scope 从外层推导入口。内层 scope 的入口，就是外层 scope 刚刚绑定的那个目标和 viewport。scope 自己有一个栈（WebGL1SurfaceScope.ts:212），只要在栈里多记一项「这一层绑定了什么」，内层就不用问 GL，只有最外层查询。FFT 每层套一个外层 scope，每帧大约 8 次查询。改动只在 WebGL1SurfaceScope 内部，需要信任的范围也最小：只信「scope 嵌套期间没有别人改输出目标」。上面的自由组合里，「每层套一个外层 scope」那一项按现在的代码是 896 次，反而更多：外层自己查 2 次，内层每个照样查 2 次，退出时还要用 isFramebuffer 确认外层的 FBO 还活着（:302）。
  • State 记住 framebuffer 和 viewport。和 three.js 一样，平时一次都不查。前提有两个：一是 Backend 独占 context，旧代码不再碰它；二是失效要先拆细，否则就会像 2.5 节第二张卡片那样，每次 draw 都被清空。

迁移计划写于测量之前，建议是 FFT 接入时做第一种，第二种等实测确认是瓶颈再做。有了 3.4 节的数字，这条建议可以重新掂量：如果你常用的浏览器也这样快，保持现状、不改也说得过去。计划文件在工作区 claude-workspace/fft-ocean-migration/2026-10-02-fft-ocean-migration-plan.zh-CN.md 的决定 4 和风险 6.2。

4. 架构视角：对照 three.js r177

  • 缓存的范围：three.js 几乎什么都缓存，包括输出目标。bindFramebuffer 和 viewport 都先比较缓存，相同就不发（WebGLState.js:492–520、:1132–1141）。它只在构造时问一次 VIEWPORT 和 SCISSOR_BOX（:414–418），之后每帧一次都不查。前提是 three.js 独占这个 context。
  • 「不知道」怎么表示：两种写法都有。开关用一个空对象记录，没设过的开关读出来是 undefined，第一次 enable 一定会发（:365、:470–490），和本项目一样。program 的初值却是 null（:371），也就是第 1 版的写法。它不出问题，是因为 three.js 平时的流程从不调用 useProgram(null)。本项目真正需要解绑的地方在 ProgramManager：它直接问 GL 当前的 program，是要删的那个才调用 gl.useProgram(null)，然后调用钩子让 State 作废（WebGL1ProgramManager.ts:232–237）。
  • 和别人共用 context：reset 对 invalidate。three.js 给混用多个库的应用准备了 renderer.resetState()（WebGLRenderer.js:3355–3366），它调用的 state.reset 发出 31 条 GL 命令，把混合、剔除、深度、模板、framebuffer、program、viewport 等等全部设成已知的默认值，再把缓存也设成这些值（WebGLState.js:1185–1273）。本项目的 invalidate 一条命令也不发，只把缓存改成「不知道」，下次用到哪项再发哪项。代价是 GL 里可能还留着别人开的混合或 scissor，所以 Backend 每次 draw 都把还不支持的功能无条件关掉（1.1 节 applyDrawState 的前 10 条命令）。
  • 取舍：three.js 是一个独占 context 的完整引擎，缓存一切、出事时整体 reset，简单而且快。本项目正处在新旧两条渲染路径共用一个 context 的迁移期：program、深度、剔除这些只有新路径会碰的状态信缓存；输出目标这种旧代码和资源创建都会碰的状态，每次问 GL。等旧路径退出，这一侧也可以向 three.js 靠拢（3.5 节的第二种改法）。

5. 审查视角

  1. 三个方法只有测试在调用。全仓库搜 bindArrayBuffer、bindElementArrayBuffer、invalidateVertexInputState，除了定义，只出现在 WebGL1State.test.ts 里。两种顶点输入策略都自己直接绑定 VAO 和 buffer，然后调用整份 invalidate（OES :136–138、Manual :101–103），它们的接口注释也要求接完整的 invalidate（WebGL1VertexInputManager.ts:43–53）。第 19 课 10.2 节问过「失效拆细，还是删掉缓存」；这里补上一个事实：拆细所需的那个方法其实已经写好了，只是没有接上。想一想：是删掉这三个方法，还是让顶点输入改走 State 的 bindArrayBuffer、bindElementArrayBuffer？各要改哪几处？
  2. State 的前提，现在由 Engine 来保证。「信缓存」要求受管理的状态都经过 State（WebGL1State.ts:102–106）。新的 Engine 让新旧两条路径互斥：HW2 期间旧路径不画（engine.ts:55–58）；离开 HW2 时先释放整个 Backend，再动 GL（engine.ts:241–251）；下次进入 HW2 又是一个新的 State。想一想：有了这个保证，输出目标还需要每次查询吗？如果改成 State 记住 framebuffer 和 viewport，哪些地方必须调用 invalidate？（提示：RenderTargetManager 创建 FBO 的那条路径。）
  3. 找茬题：WebGL1State.ts 第 230–240 行的注释里，有一句话已经不符合现在的代码了。找出来，并说出是哪一处代码让它过时的。
