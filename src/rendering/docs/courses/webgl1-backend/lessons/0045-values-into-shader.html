阴影值怎样送进 shader：四种办法，为什么选参数块

第 44 课的 ForwardPass 里还剩三行：阴影图、灯的矩阵、bias。画屏幕的那一遍本不该懂阴影，可这三个值总得有人交给 shader。这一课在同一个小引擎里把四种交法各写一遍——A「draw 时带上」、B「后端认识灯光」、three.js「引擎数灯、替 shader 拼代码」、C「参数块」——用同一组需求去试，看 HW1 设计为什么选 C。

和你的目标的关系 —— 这就是 HW1 设计的第 2 项决定（设计 §0）：阴影参数用参数块按引用送到 shader。10 月 19 日你已经把第 2 批录完了：ParameterBlock.ts、共用模块 materialParameters.ts、Material 的 blocks、后端的第三处取值都在工作区里。这一课先在小引擎里把它们跑一遍，第 9 节再逐行对照真实代码。
默认你已经会的：① 第 42 课的 Resource、Material（参数每次 draw 现读）、RenderTarget；② 第 43 课的快照：数值抄一份，资源只借用；③ 第 44 课的 Backend、ShadowMapPass、ForwardPass、RenderPipeline。
这一课讲的：五条需求；第 0 种「抄进材质」为什么不行；A、B、three.js、C 各自的写法和代价；并排跑一遍；C 的合同；对照 src/rendering 和 three.js。
在一帧里的位置和寿命：值由 ShadowMapPass 在第一遍里产生，ForwardPass 每画一个物体时读一次。灯的矩阵只活一帧；阴影图活得和灯的阴影设置一样长；bias 是设置，GUI 随时改。

1. 那三行，和五条需求

第 44 课 ForwardPass 的这几行：

const light = frame.lights[0]
// 和阴影有关的三项：第 45 课要处理的就是这几行
const shadowValues = light.shadow === null ? {} : {
  uLightVP: lightViewProjection(light),
  uShadowBias: light.shadow.bias,
  uShadowMap: light.shadow.target
}

三个值的性质各不相同：阴影图是一张 GPU 纹理，内容由 ShadowMapPass 每帧重画；灯的矩阵（视图 × 正交投影，16 个数）灯一动就变；bias 是一个设置，GUI 随时可能改。怎样交给 shader，用下面五条需求去试。每一条都有一个能跑的场景：

需求具体场景做对了是什么样
R1 灯会动灯从 35° 转到 −30°影子从 (200, 150) 一带挪到 (270, 150) 一带，和第 40 课同角度的画面逐像素相同
R2 关掉投影light.castShadow = false画面变成「没有阴影」：和不带阴影的正确画面逐像素相同；不报错、不变黑
R3 作业往后走PCF、PCSS 要多送几项（阴影图尺寸、光源大小……）改动只落在阴影自己的代码和 shader 里
R4 一个名字一个来源有人也给材质设了 uShadowBias当场报错，不能悄悄「谁压过谁」
R5 别人不认识阴影HW2、FFT 也用同一个 ForwardPass 和后端ForwardPass、后端里没有阴影的词

先说不比的一项：速度。备课时实测，五种写法每帧都是 58 条 GL 命令、4 次查询（和第 44 课一样）。在 WebGL1 上，值最后都是一条条 uniform* 命令传上去，差别全在「谁知道什么、改一处要动几处」。

2. 第 0 种：建场景时抄进材质

最直接的想法：Material 本来就有参数，建场景时把三个值写进接收者（地面、三角形）的材质，ForwardPass 就一行阴影都不用写了（这一课的 ForwardPass 只给相机、物体位置和灯的方向，见第 6 节）。

阴影图和矩阵是一件产品的两半：深度图，加上「怎样在深度图上找到自己」的那个矩阵。材质对阴影图存的是引用（ShadowMapPass 重画，材质自动看到新像素），对矩阵存的是建场景那一刻的 16 个数的副本。灯一动，两半对不上。HW1 设计写下的第一个原型就是这样失败的（设计 §1.1）。

出路只有两条：要么每帧重新送一次矩阵（A、B、three.js 的表面做法），要么让材质对矩阵也存引用，由产生它的人原地更新（three.js 的底层、C）。

3. A：draw 时带上

第 44 课其实已经是 A：ForwardPass 每帧算出三个值，跟相机、物体位置一起放进 draw 的 uniforms。codex 2026-10-15 的方案 A 是同一个形状，只是起了名字：DrawSubmission.parameterOverrides（codex-workspace/…/2026-10-15-hw1-draw-parameters-vs-lighting-semantics.zh-CN.md 第 4 节）。

  • R1 ✓：每帧现算现送。
  • R2 ✗：castShadow = false 时快照里的 shadow 是 null，shadowValues 是空对象，带阴影的 shader 缺了三个值，第一次 draw 就抛「uniform uLightVP 没有值」（第 7 节可以试）。要不抛错，ForwardPass 还得知道「没有阴影时每一项填什么」。
  • R3 ✗：PCSS 多一项光源大小，就要改 ForwardPass。下一项效果（雾、SSAO）再改一次。
  • R4 ✗：两个来源同名时，后展开的赢，没有任何提示。下面的卡片就是这件事。
  • R5 ✗：ForwardPass 认识阴影，而且只认 lights[0]。

4. B：后端认识灯光

B 把「灯光」做成后端认识的词：draw 多收一个 lighting，后端知道其中每一项该叫哪个 uniform。这是 codex 文档的方案 B（第 5 节的 LightingFrameData），小引擎照它的原形写：四项都是必填。

  • R1 ✓：每帧现算现送。
  • R2 ✗：没有阴影时 lighting 缺三项，后端抛「lighting.shadowMap 必须有」。codex 文档自己也写了：lighting? 只能整块可选，表达不了「有光照、没有阴影」（第 5.3 节第 1 条）。
  • R3 ✗：多一项光源大小，要改后端的字段表和名字映射，还要改 ForwardPass 的翻译。
  • R5 ✗：后端认识了灯光、阴影。HW2 的 PRT、FFT 海面都不用它；以后来个 ocean?、ssr?，后端的词越来越多（第 5.3 节第 3 条）。

5. three.js：引擎数灯、替 shader 拼代码

three.js r177 把灯光做成一整套协议，分三层：

  1. 引擎每帧数灯。WebGLLights.setup 把每盏投影子的方向光的 shadowBias 等设置、阴影图、light.shadow.matrix 放进几个数组（WebGLLights.js:266–280）。
  2. 材质的 uniform 指向这些数组。需要灯光的材质第一次编译时，渲染器把它的 directionalShadowMap.value、directionalShadowMatrix.value 直接设成那几个数组本身（WebGLRenderer.js:2110–2126）——这是按引用：之后数组里的值变了，材质不用动。
  3. shader 由引擎拼。材质的 shader 里只写 #include <shadowmap_pars_fragment>，引擎把片段换进去，再把 NUM_DIR_LIGHT_SHADOWS 换成灯数（WebGLProgram.js:242；片段见 shadowmap_pars_fragment.glsl.js:16–29）。灯数是 program 参数之一（WebGLPrograms.js:326）；灯数一变，灯光状态的版本号加 1（WebGLLights.js:425–468），用灯的材质就要换 program（WebGLRenderer.js:2236）。

小引擎按这三层写了一个缩小版：LightsState 是第 1 层，ThreeBackend 每次 draw 接上数组是第 2 层，expandShader 和 variantOf 是第 3 层。ForwardPass 用的是 C 的那一个（一行阴影都没有）。

  • R1 ✓、R2 ✓：关掉投影，灯数从 1 变 0，引擎拼出一份不含阴影代码的 shader，画面和不带阴影的正确画面逐像素相同。代价是多编译一个 program（第 7 节实测 2 → 3）；再打开时用缓存里的那份，不再编译。
  • R3 ✗：shader 里的阴影代码属于引擎，结构体里只有 bias、半径、阴影图尺寸这几项。PCSS 要的光源大小不在里面。three.js 官方的 PCSS 示例是用字符串替换改写 THREE.ShaderChunk.shadowmap_pars_fragment，再用 #define LIGHT_WORLD_SIZE 等把光源参数写死进 shader（r177 的 webgl_shadowmap_pcss.html）。GAMES202 的 HW1 正好要从硬阴影走到 PCF、PCSS。
  • R4 ✓：名字由引擎定，材质不会去设这几个名字。
  • R5 ✗：引擎、后端都认识灯光；要照搬，还得先让后端支持 uniform 数组（真实代码现在明确拒绝，WebGL1Uniforms.ts:235–237）和 shader 变体系统。

它的长处是灯数变了、材质和 shader 一个字不用改。可 GAMES202 里 HW1、HW3 都只有一盏灯，HW2 不用实时灯光。值得拿走的是第 2 层：按引用接线。

6. C：参数块

C 只拿 three.js 的第 2 层，做成一个和阴影无关的通用零件：参数块（ParameterBlock）——一组有名字的值，名字和种类构造时定死，之后只能原地改值。它和 Texture、RenderTarget 是同一种模式：CPU 资源有身份，材质借用，拥有者更新，后端读取。

6.1 块和借用它的材质

  • 块的 set：名字必须已有、种类必须相同，先检查、复制，再替换，失败时旧值不变（实测：往 uLightVP 里塞 3 个数，抛「uLightVP 必须是 mat4，收到 vec3」，块还是全零矩阵、version 没变）。
  • 材质构造时查一遍名字：块与块之间、块与材质自己的参数之间不能同名；之后 setParameter 也不能设块已经提供的名字。
  • copyValue 和 kindOf 是材质和块共用的一套规则，不写两份。真实代码的共用模块是 materialParameters.ts：copyParameter（:141）和 assertValidParameterName（:227）已经从 Material.ts 搬到这里。Material 和 ParameterBlock 都调用它们，各自传一个 createError，所以同一条规则失败时，一个报 InvalidMaterialError，一个报 InvalidParameterBlockError。

6.2 后端多找一处，ForwardPass 少三行

后端给一个 uniform 找值，按顺序看三处：Pass 给的（相机、物体位置）、材质自己的参数、材质借用的块。因为构造时保证了一个名字只有一个来源，这里是查找，不是「谁压过谁」——Pass 给的名字和材质撞了，draw 时直接抛错。材质参数也改由后端去材质里取（第 44 课是 ForwardPass 自己展开），真实代码本来就是这样，现在也多了块这一处：WebGL1Uniforms.prepare 对每个 active uniform，内建语义取内建值，否则先找 Material 自己的参数，再找借用的块（:149–154；块的查找在 blockParameter，:252–270）。块的值每次 draw 重新读，不按 program 缓存。

6.3 谁写块：只有 ShadowMapPass

  • DirectionalLightShadow 拥有阴影图和块，块里的 uShadowMap 构造时就指向阴影图，之后不变。改尺寸（第 42 课的 resize）不换身份，借用它的材质不用动。
  • setBias 只改设置，不碰块。块里的值只由 ShadowMapPass 按这一帧的快照写（publish）。这样 GUI 在两遍之间改 bias，同一帧的两遍也不会读到不同的值（卡片 E）。
  • 没有阴影 = 全零矩阵。块的初值、castShadow = false、灯被移出场景，ShadowMapPass 都发布全零矩阵（publishNoShadow）。接收者 shader 里点乘全零矩阵得到 w = 0，if (vLightClip.w > 0.0) 不成立，visible 保持 1：画面是「没有阴影」，不是全黑，也不是除以 0 得到的不确定值。这是接收者 shader 和第 42 课唯一的差别。

    

    

      这里的检查（第 ① 层，构造和 set 时）：块的名字和种类固定，set 先检查后替换；材质构造时一个名字只有一个来源。之后可以放心：后端找值时最多找到一个，不需要优先级；块里的值永远是合法的、完整的一组。shader 里有没有这些名字，仍然要等第一次 draw 才知道（第 ③ 层）。见 校验地图。

C 的代价也写清楚：

    
    
      
  • 材质多了一个借用列表，构造时多查一轮名字。列表构造后不能改，要换就建新材质（设计 D3）。

架构视角：three.js 的灯光协议、本项目的参数块，底下都是同一件事——材质对会变的值存引用，产生值的人原地更新。区别在于引用指向谁：three.js 指向引擎的全局灯光状态，名字和结构由引擎定；C 指向场景里一个普通资源，名字由定义它的模块定，后端只负责按名字查。
