backend ③：把 shader 源码变成可以 draw 的 program

ShaderModule 里只有两段 GLSL 文本。要用它 draw，得先编译、链接成 GPU 上的 program，再查出每个顶点输入和 uniform 的位置。教程里这只是十来行代码；可一旦源码写错、重试很多次、多个材质共用一份源码，或者 program 正在被使用时要删掉它，十来行就不够了。这一课从教程写法出发，一版一版补上缺的东西，最后对照项目的 WebGL1ProgramManager。

和你的目标的关系 —— 每次 draw，Backend 的第一件事就是向 ProgramManager 要 program（WebGL1Backend.ts:208）；它交回的反射结果，一份给顶点输入按名字找 location，一份给 Uniforms 上传参数（WebGL1Uniforms.ts:213–250）。HW2 的 Mary 只有一份 PRT shader，可它被 Scene 持有、被 Material 借用，什么时候编译、什么时候删除，都由这个类决定。
默认你已经会的：createShader、compileShader、linkProgram 这一串调用（第 1 课）；GL 出错时不抛异常，只留下错误标志，要用 getError 去取（第 2 课）；Resource 的 onDispose 订阅（第 4、5 课）；ShaderModule 的字段（第 11 课）；第 14 课 2.2 节「正在用的 program 删不掉」的实验。
这一课从零讲的：编译和链接失败时浏览器交回什么；为什么失败也要删干净、怎样做到；为什么要先 detach 再 delete；反射拿到的是什么，location 0 和数组名字的坑；缓存的 key 为什么是对象本身；删除之前怎样通知还在用它的顶点输入（beforeDelete 钩子），为什么要在删除之前；删除 program 的顺序。
页面会用到你的显卡：除了一张说明了的，所有卡片都在你的浏览器里创建真实的 WebGL context，真的编译、链接、删除，用完释放。第 5 节有一个编译计时实验。

1. 需求

1.1 先看原始输入：一段 shader 和三个使用者

这是 HW2 的 PRT vertex shader 的接口部分（order2/vertex.vert:12–28，原文的注释换成了课程的注释）：

attribute vec3 position;        // 顶点位置
attribute vec3 aTransportSH0;   // 每个顶点的 9 个传输系数，分三组
attribute vec3 aTransportSH1;
attribute vec3 aTransportSH2;

uniform mat4 uModelMatrix;      // 三个矩阵：Engine 每次 draw 自动填（builtInUniforms）
uniform mat4 uViewMatrix;
uniform mat4 uProjectionMatrix;
uniform mat3 uLightSH_R;        // 环境光的 9 个系数，R、G、B 各一份：来自 Material 参数
uniform mat3 uLightSH_G;
uniform mat3 uLightSH_B;

varying vec3 vColor;            // 交给 fragment shader 的颜色

这段源码装在 ShaderModule 里（createHW2Scene.ts:295–303）。拿到它以后，有三方要用编译的结果：

  • Backend 的 draw：要一个 WebGLProgram，交给 useProgram。
  • 顶点输入：要知道「position 在第几号 location」，才能把 buffer 接到正确的位置上（第 16 课）。location 是链接时由 GPU 驱动分配的数字，源码里看不出来。
  • Uniforms：要每个 uniform 的 location，才能 uniformMatrix4fv 上传（WebGL1Uniforms.ts:239 从这张表里取 location，这一课不展开）。

所以 ProgramManager 的输入是一个 ShaderModule，输出是 { program, attributes: 名字 → location, uniforms: 名字 → location }（WebGL1ProgramManager.ts:22–26）。

1.2 需求：要应付哪些情况

  1. 写错了要说清楚。GLSL 少一个分号，要报出「哪个模块、哪一段、驱动日志原文」，而不是让画面悄悄变黑。
  2. 两段都对、合起来错，也要说清楚。vertex 输出的 varying 是 vec3，fragment 却当成 vec4 来读：各自都能编译，链接时才出错。
  3. 失败不留垃圾。编译到一半失败，已经建好的 shader、program 都要删掉。用户改一次源码重试一次，重试多少次都不能越积越多。
  4. 成功后只留 program。链接完成以后，两段 shader 就用不着了，要真正释放。
  5. 交出反射结果。location 0 是有效位置；数组、没用到的变量，要按 GL 的规矩处理。
  6. 同一份源码只编译一次。多个 Material 共用一个 ShaderModule 时，只建一个 program。同名不等于同一份源码。
  7. 半成品不进缓存。只要有一步失败，缓存里就不能出现这个 ShaderModule。
  8. 源码释放了，program 也要删。先让依赖它的顶点输入收拾，正在用的先换下来，再删。
  9. 别人的错误不算到自己头上；context 丢了不乱发命令。

2. 一版一版写

2.1 第 1 版：照教程写

// 第 1 版：照教程写。编译两段，链接，交回 program
function createProgramV1(
  gl: WebGLRenderingContext,
  vertexSource: string,
  fragmentSource: string
): WebGLProgram {
  const vertex = gl.createShader(gl.VERTEX_SHADER)! // 新建一个空的 shader 对象
  gl.shaderSource(vertex, vertexSource) // 交给它源码
  gl.compileShader(vertex) // 编译
  const fragment = gl.createShader(gl.FRAGMENT_SHADER)!
  gl.shaderSource(fragment, fragmentSource)
  gl.compileShader(fragment)

  const program = gl.createProgram() // 新建 program，把两段装进去
  gl.attachShader(program, vertex)
  gl.attachShader(program, fragment)
  gl.linkProgram(program) // 链接：检查两段的接口对不对得上（varying 的名字和类型）
  return program
}

2.2 第 2 版：编译、链接之后都问一次

GL 不会因为源码写错就抛异常，结果记在 COMPILE_STATUS、LINK_STATUS 里，日志要用 getShaderInfoLog、getProgramInfoLog 去取。第 2 版把这两步补上：

// 第 2 版：编译、链接之后都问一次结果，失败就带着驱动的日志抛错
function compileV2(
  gl: WebGLRenderingContext,
  type: number,
  source: string,
  stage: 'vertex' | 'fragment'
): WebGLShader {
  const shader = gl.createShader(type)!
  gl.shaderSource(shader, source)
  gl.compileShader(shader)
  // GL 不抛异常，失败只记在 COMPILE_STATUS 里，要自己问
  if (gl.getShaderParameter(shader, gl.COMPILE_STATUS) !== true) {
    // 日志是驱动写的原文，比如「ERROR: 0:3: '}' : syntax error」
    throw new Error(`${stage} shader 编译失败：${gl.getShaderInfoLog(shader) ?? ''}`)
  }
  return shader
}

function createProgramV2(
  gl: WebGLRenderingContext,
  vertexSource: string,
  fragmentSource: string
): WebGLProgram {
  const vertex = compileV2(gl, gl.VERTEX_SHADER, vertexSource, 'vertex')
  const fragment = compileV2(gl, gl.FRAGMENT_SHADER, fragmentSource, 'fragment')
  const program = gl.createProgram()
  gl.attachShader(program, vertex)
  gl.attachShader(program, fragment)
  gl.linkProgram(program)
  // 两段各自编译成功，链接仍可能失败：比如同一个 varying 两边的类型不一样
  if (gl.getProgramParameter(program, gl.LINK_STATUS) !== true) {
    throw new Error(`链接失败：${gl.getProgramInfoLog(program) ?? ''}`)
  }
  return program
}

2.3 第 3 版：失败也要收拾，成功后只留 program

第 2 版每失败一次，就在 GPU 上留下一两个 shader，链接失败时还多一个 program。这些对象没有任何 JS 变量指着它们，再也删不掉了。第 3 版用一张清单记下这次新建的 shader，finally 里统一删除；失败时连 program 一起删。 

// 第 3 版：失败也要收拾。这次新建的东西记在清单上，最后统一删
function compileV3(
  gl: WebGLRenderingContext,
  type: number,
  source: string,
  stage: 'vertex' | 'fragment',
  owned: WebGLShader[]
): WebGLShader {
  const shader = gl.createShader(type)!
  owned.push(shader) // 先登记，再编译：编译失败时 finally 也找得到它
  gl.shaderSource(shader, source)
  gl.compileShader(shader)
  if (gl.getShaderParameter(shader, gl.COMPILE_STATUS) !== true) {
    throw new Error(`${stage} shader 编译失败：${gl.getShaderInfoLog(shader) ?? ''}`)
  }
  return shader
}

function createProgramV3(
  gl: WebGLRenderingContext,
  vertexSource: string,
  fragmentSource: string
): WebGLProgram {
  const owned: WebGLShader[] = [] // 本次新建的 shader，不管成败都要删
  let program: WebGLProgram | null = null
  try {
    const vertex = compileV3(gl, gl.VERTEX_SHADER, vertexSource, 'vertex', owned)
    const fragment = compileV3(
      gl,
      gl.FRAGMENT_SHADER,
      fragmentSource,
      'fragment',
      owned
    )
    program = gl.createProgram()
    gl.attachShader(program, vertex)
    gl.attachShader(program, fragment)
    gl.linkProgram(program)
    if (gl.getProgramParameter(program, gl.LINK_STATUS) !== true) {
      throw new Error(`链接失败：${gl.getProgramInfoLog(program) ?? ''}`)
    }
    // 链接好的 program 自己保存了编译结果，用不着这两段了。
    // 先拆开：还装在 program 上的 shader，deleteShader 只会给它做个记号，并不真的释放
    gl.detachShader(program, vertex)
    gl.detachShader(program, fragment)
    return program
  } catch (error) {
    if (program !== null) gl.deleteProgram(program) // 失败：半成品 program 也删掉
    throw error
  } finally {
    for (const shader of owned) gl.deleteShader(shader) // 成功、失败都删 shader
  }
}

这里还有第二个细节：成功的时候为什么要先 detachShader？OpenGL ES 2.0 规定，还装在 program 上的 shader 被 delete 时只会被标记为「待删除」，等它从所有 program 上拆下来才真正释放。所以只 delete 不 detach，两段 shader 会一直活到 program 被删除为止。上面第二张卡片就是在你的浏览器里看这件事。three.js 选择了不 detach，原因见第 4 节。

2.4 第 4 版：反射，以及缓存

反射 (reflection) 指链接之后问 GL「这个 program 实际用到了哪些输入，各在哪个位置」。只有 active 的才会被列出：链接器发现某个 uniform 声明了却没被用到，会把它优化掉，它就不在列表里。缓存的 key 用 ShaderModule 对象本身，第 6 条需求说过，同名不等于同一份源码。 

// 第 4 版：再加两件事。查出每个输入的位置（反射），同一份源码只建一次（缓存）
interface ShaderSource {
  readonly name: string
  readonly vertexSource: string
  readonly fragmentSource: string
}

interface ProgramInfo {
  readonly program: WebGLProgram
  // 顶点输入名 → location，给顶点输入用
  readonly attributes: ReadonlyMap<string, number>
  // uniform 名 → location，给 uniform 上传用
  readonly uniforms: ReadonlyMap<string, WebGLUniformLocation>
}

class ProgramCacheV4 {
  // key 是源码对象本身：两个对象哪怕 name 相同，也是两份不同的东西
  private readonly entries = new Map<ShaderSource, ProgramInfo>()

  constructor(private readonly gl: WebGLRenderingContext) {}

  get(source: ShaderSource): ProgramInfo {
    const cached = this.entries.get(source)
    if (cached !== undefined) return cached // 第二次起直接交回，不再编译

    const gl = this.gl
    const program = createProgramV3(gl, source.vertexSource, source.fragmentSource)
    try {
      const info: ProgramInfo = {
        program,
        attributes: reflectAttributes(gl, program),
        uniforms: reflectUniforms(gl, program)
      }
      this.entries.set(source, info) // 全部成功才登记，缓存里不会出现半成品
      return info
    } catch (error) {
      gl.deleteProgram(program) // 反射失败：program 也不要了
      throw error
    }
  }
}

function reflectAttributes(
  gl: WebGLRenderingContext,
  program: WebGLProgram
): Map<string, number> {
  const result = new Map<string, number>()
  // ACTIVE：链接器认为 shader 真正用到的那些；声明了却没用的，不在里面
  const count = gl.getProgramParameter(program, gl.ACTIVE_ATTRIBUTES) as number
  for (let index = 0; index < count; index++) {
    const info = gl.getActiveAttrib(program, index)!
    const location = gl.getAttribLocation(program, info.name)
    // 0 是有效位置，不能写 if (!location)；只有 -1 表示「没有」
    if (location < 0) throw new Error(`attribute ${info.name} 没有位置`)
    result.set(info.name, location)
  }
  return result
}

function reflectUniforms(
  gl: WebGLRenderingContext,
  program: WebGLProgram
): Map<string, WebGLUniformLocation> {
  const result = new Map<string, WebGLUniformLocation>()
  const count = gl.getProgramParameter(program, gl.ACTIVE_UNIFORMS) as number
  for (let index = 0; index < count; index++) {
    // 数组只占一项，名字带 [0]，比如 uTint[0]
    const info = gl.getActiveUniform(program, index)!
    const location = gl.getUniformLocation(program, info.name)
    if (location !== null) result.set(info.name, location)
  }
  return result
}

2.5 真实代码：比第 4 版多了什么

第 4 版已经满足前七条需求的大意。真实的 get 多做了几件事：错误换成专用的类（ShaderCompilationError 带上 stage，ProgramLinkError 带上日志）；只接受 GLSL ES 1.00；进门先清点已有的 GL 错误；每次查询以后检查 context 是否丢失；把订阅 ShaderModule 的释放放在登记缓存之前的最后一步。 

// 项目里的真实代码（WebGL1ProgramManager.ts:80–198，节选，注释是课程加的）
get(shader: ShaderModule): WebGL1ProgramResource {
  this.assertAvailable('get program') // Manager 已关闭或 context 已丢：不再服务
  // 已释放的源码不能再编译
  if (shader.disposed) throw new ResourceDisposedError('ShaderModule')
  if (this.releasing.has(shader)) {
    // 正在删它的 program（beforeDelete 回调里又来要）：不能一边删一边建
    throw new WebGLOperationError('get program', shader.name, 'release is in progress')
  }

  const cached = this.entries.get(shader) // 和第 4 版一样：按对象身份缓存
  if (cached !== undefined) return cached.resource

  // WebGL1 只认 GLSL ES 1.00；3.00 的源码在动用 GPU 之前就拒绝
  if (shader.language !== 'glsl-es-100') {
    throw new UnsupportedShaderLanguageError(shader.name, shader.language, 'webgl1')
  }

  const gl = this.gl
  // 进门先清点：别人留下的 GL 错误，不能算成这次编译的
  this.checkError('preflight', shader.name)

  const shaders: WebGLShader[] = [] // 第 3 版的清单
  let program: WebGLProgram | null = null
  try {
    const vertex = this.compile(shader, 'vertex', gl.VERTEX_SHADER, shaders)
    const fragment = this.compile(shader, 'fragment', gl.FRAGMENT_SHADER, shaders)
    // createProgram 可能交回 null（比如正好丢了 context），所以先问一次再用
    const candidate = gl.createProgram()
    this.assertAvailable('create program')
    program = requireNonNull(
      candidate,
      () => new WebGLResourceCreationError('program', shader.name)
    )

    gl.attachShader(program, vertex)
    gl.attachShader(program, fragment)
    gl.linkProgram(program)
    const linked: unknown = gl.getProgramParameter(program, gl.LINK_STATUS)
    this.assertAvailable('link program') // 丢失期间查询会交回 null，先排除「丢了」
    if (linked !== true) {
      // 专用错误类，带日志
      throw new ProgramLinkError(shader.name, gl.getProgramInfoLog(program) ?? '')
    }

    gl.detachShader(program, vertex) // 第 3 版的 detach
    gl.detachShader(program, fragment)
    this.checkError('link program', shader.name)

    // ……反射 attributes 和 uniforms，和第 4 版相同，多了计数校验和丢失检查（:141–172）……

    const resource: WebGL1ProgramResource = Object.freeze({
      program,
      attributes,
      uniforms
    })
    // 订阅：ShaderModule 被释放时，自动删掉这个 program
    const unsubscribe = shader.onDispose(() => this.release(shader))
    this.entries.set(shader, { resource, unsubscribe }) // 最后一步才登记
    return resource
  } catch (error) {
    if (gl.isContextLost() || this.lostValue) {
      // 丢了：旧句柄全部失效，不去 delete，整个 Manager 作废
      this.invalidateForContextLoss()
      throw new WebGLContextLostError('create program')
    }
    if (program !== null) gl.deleteProgram(program)
    throw error
  } finally {
    if (!gl.isContextLost() && !this.lostValue) {
      for (const compiled of shaders) gl.deleteShader(compiled)
    }
  }
}
10 月 12 日更新：上面调用的 checkError（进门 preflight、每个 shader 编译后、链接后各一次）以前每次只读一个错误码。你在工作区把它改成了有界循环（WebGL1ProgramManager.ts:354–382）：一直读到 NO_ERROR 为止，最多读 32 次，读到的码一次报出，信息是「GL errors: 1280, 1281」；32 次还没见到 NO_ERROR，就报「收集未完成」。每读一次，前后都 assertAvailable，丢失时照旧按丢失处理。下面「别人留下的 GL 错误」这张卡片已经换成新代码跑。GeometryManager 的同名方法做了同样的修改（第 16 课）；顶点输入和纹理上传的检查（WebGL1VertexInputSupport.ts:168、WebGL1TextureUploadSupport.ts:27）还是只读一次。

2.6 删除之前：还有谁在用这个 program

先看一个具体场景。Mary 的 Geometry 一直留着，材质却换了 shader：比如调试时把 PRT shader 换成一个只画法线的 shader，或者改了 GLSL 重新加载。旧的 ShaderModule 被释放，ProgramManager 就要删掉它的 program。问题是：除了 ProgramManager，还有谁记着这个 program？

答案是顶点输入（第 16 课细讲）。它要告诉 GPU：「第 0 号 attribute 从 Mary 的 position buffer 读，每个顶点 3 个 float；第 1 号从 aTransportSH0 的 buffer 读……」。这里的 0、1 号是 2.4 节反射出来的 location，由 program 决定：PRT program 里 position 在 0 号，另一个 shader 链接出来 position 可能在 2 号。所以这份「谁接到哪个 location」的配置只对一个 program 有效。有 VAO 扩展时，顶点输入把这份配置录进一个 VAO，按「Geometry、program」两层缓存起来（WebGL1OESVertexInputManager.ts:30）： 

// 顶点输入的缓存：Map<Geometry, Map<WebGLProgram, { vao, … }>>
// 换了三次 shader 以后，如果从来没人通知它：
//   Mary ─┬─ program#1（已经删了） → VAO#1   ← 再也不会有人拿 program#1 来查
//         ├─ program#2（已经删了） → VAO#2   ← 同上
//         └─ program#3（正在用）   → VAO#3
// VAO 是 GPU 对象，不调用 deleteVertexArrayOES 就一直占着。

这张图出现在讲 VAO 之前，不好懂。第 16 课 4.4 节讲完 VAO 以后，用一张五步表、一张图和两张跑真实代码的卡片把它重讲了一遍（第 16 课 4.4 节）。

所以删 program 之前，要先让顶点输入把「按这个 program 建的 VAO」删掉。ProgramManager 自己不认识顶点输入（它不 import 顶点输入的任何代码），于是用一个钩子 (hook)：构造 ProgramManager 时，从外面递进来一个函数；ProgramManager 在固定的时刻调用它，并不关心函数里做什么。 

// ① 声明：ProgramManager 说「删除之前，我会调用这个函数，
//    参数是要删的 program」
//    WebGL1ProgramManager.ts:34–44（节选，去掉了原注释）
export interface WebGL1ProgramManagerHooks {
  readonly invalidateState: () => undefined // 删完后让 State 忘掉缓存（第 14 课）
  readonly beforeDelete?: (program: WebGLProgram) => undefined // 删之前调用
}

// ② 接线：负责把各个 Manager 组装起来的 ResourceManager，递进去的函数是
//    「请顶点输入放掉这个 program 的 VAO」    WebGL1ResourceManager.ts:100–105
this.programsValue = new WebGL1ProgramManager(gl, {
  invalidateState: hooks.invalidateState,
  beforeDelete: (program) => {
    this.vertexInputsValue.releaseProgram(program) // 删掉 Map 里这个 program 对应的 VAO
  }
})

// ③ 调用：release 删除之前先调它（下一节的真实代码 ①）
this.hooks.beforeDelete?.(entry.resource.program)

为什么不让顶点输入自己订阅 ShaderModule 的 onDispose？有三个原因：

  • 顶点输入手里只有 WebGLProgram，不知道它来自哪个 ShaderModule。
  • 就算知道，订阅的通知按注册顺序执行：ProgramManager 在 get 时就订阅了（WebGL1ProgramManager.ts:180），比顶点输入早，program 会先被删掉，顺序正好反了。
  • 整个 Backend 关闭时，ShaderModule 并没有被释放，不会有 onDispose；ProgramManager.dispose 是自己逐个 release 的（:260–273）。

为什么一定在删除之前，而不是之后？因为收拾可能失败（比如顶点输入那边抛错）。在之前调用：失败了就停下，program 没删，缓存记录还在，以后可以再 release 一次。如果先删 program、把记录从缓存里拿掉，再去通知，通知失败时就再也没有人记得「还有 VAO 没删」，只能一直漏下去。下面两张卡片在你的浏览器里用真实代码演示这两件事。

2.7 删除的顺序：真实的 release

ShaderModule 被释放时，订阅触发 release。删除 program 之前要处理两类依赖它的东西：上一节的 VAO（beforeDelete），以及「它正是当前 program」这件事（第 14 课 2.2 节：正在用的 program，delete 只会被推迟）。 

// 项目里的真实代码（WebGL1ProgramManager.ts:209–241，注释是课程加的）
release(shader: ShaderModule): void {
  const entry = this.entries.get(shader)
  // 没建过，或者正在删（回调里又调了 release）：什么也不做
  if (entry === undefined || this.releasing.has(shader)) return

  if (this.gl.isContextLost() || this.lostValue) {
    this.invalidateForContextLoss() // 丢了：不发 delete，只丢记录
    return
  }

  this.releasing.add(shader) // 标记「正在删」，挡住重入
  try {
    // ① 先让依赖它的一方收拾：顶点输入里按这个 program 建的 VAO（2.6 节）
    //    抛错就停在这里：entry 还在，program 也没删，以后可以重试
    this.hooks.beforeDelete?.(entry.resource.program)

    if (this.gl.isContextLost() || this.lostValue) {
      this.invalidateForContextLoss() // 回调期间丢了
      return
    }

    // ② 退订、移出缓存
    entry.unsubscribe()
    this.entries.delete(shader)

    // ③ 正在用的 program，先换下来再删；否则删除会被推迟（第 14 课 2.2 节的实验）
    if (this.gl.getParameter(this.gl.CURRENT_PROGRAM) === entry.resource.program) {
      this.gl.useProgram(null)
    }

    // ④ 删除，并让 State 忘掉缓存的 program
    this.gl.deleteProgram(entry.resource.program)
    this.hooks.invalidateState()
  } finally {
    this.releasing.delete(shader)
  }
}

顺序上的每一步都有测试守着：CPU dispose 先触发依赖清理，再解绑当前 program 并删除、依赖清理失败不删除 program，dispose 可以重试、lost 丢弃记录并取消订阅。

2.8 和 Lifecycle 的关系

第 13 课第 2 节说，context 丢了以后 Backend 要把旧的一代作废、再建新的一代。ProgramManager 在这两件事里做的事：

  1. 一代一个 ProgramManager。createGeneration 新建 ResourceManager（WebGL1Backend.ts:263–267），它再新建 ProgramManager（WebGL1ResourceManager.ts:100–105）。缓存跟着 Manager 走，所以缓存也是一代一份。
  2. lost 事件到达：丢记录、退订，不 delete。onLost → invalidateGeneration → resources.invalidateForContextLoss()，它依次通知每个 Manager（WebGL1ResourceManager.ts:171–179）。ProgramManager 这一步（WebGL1ProgramManager.ts:244–251）记下 lostValue，退订所有 ShaderModule，清空缓存，再通知 State 作废。它不调用 deleteProgram：program 的 handle 已经随 context 一起失效了。
    为什么要退订：订阅的回调引用着这个旧 Manager，而 ShaderModule 还活在 Scene 里。不退订的话，旧的一整代 Manager 连同缓存会一直被引用着，回收不掉，每丢一次就多留下一代；以后 ShaderModule 被释放时，还会去叫醒这个早就不用的 Manager。
  3. 事件还在排队、context 已经丢了：先发现，不乱删。get 开头的 assertAvailable 会先发现（:385–392），作废并抛 WebGLContextLostError。编译到一半丢了，get 的 catch 和 finally 也先问 isContextLost，不去 delete 已经失效的 shader 和 program（:184–197）；release 同理（:214–217）。
  4. 恢复以后：新 Manager，空缓存，重新编译。第 2 代的 ProgramManager 什么都没有。同一个 ShaderModule 第一次 draw 时，get 重新编译、链接、反射，得到一个新的 program。ShaderModule 本身没有变，它就是重建的原料（第 4 课）。

3. 反射结果交给谁

  • attributes：顶点输入按 Geometry 的属性名（position、aTransportSH0……）去这张表里找 location，再调用 vertexAttribPointer。找不到的属性不接；shader 要的属性 Geometry 没有，就报错（第 16 课）。
  • uniforms：Uniforms 拿名字去配 Material 参数和内建矩阵。但它没有只用这张表，而是自己又反射了一遍，为的是拿到每个 uniform 的类型和 size（WebGL1Uniforms.ts:205–250）：类型用来核对「Material 给的是 mat3，shader 要的也是 mat3」；size 用来拒绝数组，因为 Material 还没有数组参数。ProgramManager 交出的表里只有 location，没有类型，注释说这是为了不改动 Task 11 已经定下的接口。第 5 节回到这一点。

4. 架构视角：对照 three.js r177

  • 缓存的 key：按内容，不按对象。three.js 把材质类型、宏定义、灯光数量等拼成一个字符串 cacheKey（WebGLPrograms.js:377），key 相同就复用同一个 program，并用 usedTimes 计数；计数归零才 destroy（:591–631）。它的 shader 是由引擎根据材质生成的，内容相同就一定可以共用。本项目的 ShaderModule 是用户手写的源码，引擎没法判断「两份内容一样」；按对象身份缓存，加上 Resource 的引用计数（第 5 课）决定什么时候删。
  • 错误检查：推迟到第一次使用。three.js 在构造时就 compileShader、linkProgram（WebGLProgram.js:895–913），但不立刻查结果，等第一次用到这个 program 时才查 LINK_STATUS 和日志（:916）。中间的时间里，浏览器可以在后台并行编译。它还支持 KHR_parallel_shader_compile，用不阻塞的 COMPLETION_STATUS_KHR 查询「编完了没有」（:1046–1056）。本项目每编译一段就立刻查结果，第 5 节讨论这个取舍。
  • detach：three.js 故意不做。它在链接后直接 deleteShader，detachShader 那两行被注释掉了，注释说 iOS 9、iOS 10 上会崩溃（:995–1000，issue #18402）。代价就是 2.3 节卡片看到的：两段 shader 活到 program 被删除为止。本项目选择 detach，换来及时释放；如果将来要支持很老的 iOS，这里要重新评估。
  • 反射：three.js 一次拿全。它的 fetchAttributeLocations 同时记下类型、location，以及矩阵属性占几个 location（:194–222）；uniform 由 WebGLUniforms 一次性解析成可以直接上传的结构，数组和 struct 都支持。本项目把 location 和类型分在了两个类里反射。

5. 审查视角

  1. 每编译一段就查 COMPILE_STATUS。真实代码在 compileShader 之后立刻查结果（WebGL1ProgramManager.ts:310）。MDN 的 WebGL 最佳实践建议：除非链接失败，否则不要查编译状态，因为这个查询是同步的，会打断流水线；先把所有 shader 都编译、所有 program 都链接，最后再查（MDN · Don't check shader compile status unless linking fails）。HW2 只有两三个 program，影响很小；FFT 有十几个。下面的实验在你的浏览器里比较两种顺序。我在无界面 Chrome（软件渲染，没有 KHR_parallel_shader_compile）里跑了两次，两种顺序互有快慢，看不出稳定的差别；在有后台编译能力的真实显卡上可能不一样，所以请你自己跑：
