一个函数画完：地面上一个带阴影的三角形

这个系列只用一个场景：地面上悬着一个三角形，一盏方向光，三角形在地面上投下影子。这一课用最直接的写法把它画出来——一个函数，从拿 context 到最后一次 draw，没有任何工程结构。后面六课每课只改一处：先找出这一版在某个需求下哪里疼，再把那一处拆出去，直到拆出来的样子就是 src/rendering。走到第 45 课，阴影参数为什么用参数块（C）而不照搬 three.js，会在这个小场景里自己显出来。

和你的目标的关系 —— HW1 就是阴影。你说现在看不清 src/rendering 里谁调用谁，这个系列从反方向走：先看没有结构时代码长什么样、哪里疼，再看每一个目录是为了治哪一种疼才长出来的。
默认你已经会的：① 第 1、2 课手写过的那些 GL 调用：createBuffer、bufferData、vertexAttribPointer、useProgram、uniform*、drawArrays；② 第 27 课：framebuffer、颜色附件、深度附件、checkFramebufferStatus，以及把深度打包进 RGBA 的原因；③ 第 25、32 课：视图矩阵和投影矩阵是什么（这一课只调用，不推导）。如果其中哪一条其实没懂，告诉我，我先补那一块。
这一课讲的：阴影图的两遍绘制；不分层的完整写法；拖动滑块时它在做什么；这段代码混着哪六种东西；改需求时要动哪几行；系列路线图。
校验怎么讲：这个系列不讲校验规则的细节，只说「这里要检查、检查完可以放心什么」。全部位置汇总在 校验地图。

1. 阴影图：画两遍

判断地面上一个点在不在阴影里，问的是：从这个点往灯的方向看，中间有没有别的东西挡着？GPU 不能沿光线一路检查，所以分两遍画：

  1. 第一遍，站在灯的位置看。把整个场景画一次，但不画颜色，只记下每个方向上离灯最近的东西有多远（深度）。这张「深度照片」叫阴影图 (shadow map)。
  2. 第二遍，站在相机的位置看，正常画到屏幕上。每个像素多做一件事：算出自己在灯眼里的位置和深度，去阴影图同一位置查「离灯最近的是多远」。自己比那个更远，说明中间有东西挡着——在阴影里。

七段各做什么：

  1. ① 场景数据：地面两个三角形、悬空的三角形、两种颜色、灯的方向、相机的位置、bias。
  2. ② 编译 program：深度 program 只输出打包后的深度；主 program 算光照，再去阴影图里查自己有没有被挡。
  3. ③ 建阴影图：一张 512 × 512 的颜色纹理、一个深度缓冲、一个把它们挂在一起的 framebuffer。
  4. ④ 上传顶点：两个物体各一个 buffer。
  5. ⑤ 算矩阵：灯的「视图 × 正交投影」、相机的「视图 × 透视投影」。
  6. ⑥ 第一遍：绑阴影图的 framebuffer，清成白色（白 = 最远），用深度 program 把两个物体各画一次。
  7. ⑦ 第二遍：绑回屏幕，用主 program 设好矩阵、灯、bias、阴影图，再把两个物体各画一次。
这一版的检查（点「检查」按钮）：只有两处——② 里 shader 编译、program 链接成功没有；③ 里 framebuffer 完整没有。检查完可以放心：program 能用、往阴影图里画不会报错。其余都没检查：名字对不对得上、矩阵是不是有限的数、两遍的顺序对不对，全靠写的人自己小心。真实代码里这些检查分别在哪，见 校验地图。

3. 拖一拖滑块：每次都从头建一遍

拖动上面的滑块，灯会转，影子跟着动。再看画布下面的计数：函数每调用一次，就新建 2 个 program、4 个 shader、1 张纹理、1 个深度缓冲、1 个 framebuffer、2 个 buffer，一个都不删。备课时在无界面 Chrome 里调用 10 次，数到的是 20 个 program、40 个 shader、10 张纹理、10 个 framebuffer、20 个 buffer，删除 0 个。

点「连续调用 60 次」看看显存估计：每张 512 × 512 的 RGBA 纹理 1 MiB，每个 16 位深度缓冲 0.5 MiB，拖 1 秒就多占 90 MiB，而且永远不还。

可是灯转的时候，真正需要重新做的只有 ⑤⑥⑦：矩阵变了，两遍要重画。① 的数据、② 的 program、③ 的阴影图、④ 的顶点一样都没变。这就是第 41 课要拆的第一刀：只做一次的事和每帧做的事分开。

4. 名字拼错一个字母

点「uniform 名字」按钮，看 uLightVP 出现在哪：深度 program 的 GLSL 里声明一次，主 program 的 GLSL 里声明一次，⑥ 和 ⑦ 里各用字符串 'uLightVP' 查一次位置，一共四处。四处必须一字不差，可是没有任何东西帮你核对。

下面这块画布运行的是同一个函数，只改了一处：⑦ 里 getUniformLocation(mainProgram, 'uLightVP') 写成了 'uLigthVP'（h 和 t 换了位置）。课程用 new Function 把函数源码里这一处替换掉再运行，别的一个字都没动。

拼错的名字查不到位置，getUniformLocation 返回 null；给 null 设值，WebGL 规定什么也不做、也不报错。于是主 program 里的 uLightVP 一直是链接时的初值——全零矩阵，每个像素在灯眼里的坐标都成了 0 除以 0。备课时在无界面 Chrome（软件渲染 SwiftShader）里，这些比较全判成「被挡住」，整个画面变暗，亮处的地面从 159 变成 48。GLSL ES 1.00 没有规定 0 除以 0 得什么，换一块显卡也可能是阴影整个消失；上面的读数是你这台机器的结果。无论哪种，画面都错了，而 getError 照样是 0。

名字的约定分散在 GLSL 和 JS 两边，这是第 45 课的主题：哪些值由谁提供、名字由谁定、在哪里核对。three.js 的灯光协议和我们选的参数块，对这个问题给出了不同的答案。
