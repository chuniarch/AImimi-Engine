1. 设计问题：Backend 要回答四个问题

上层（将来的 ForwardPass）只说一句话：「把这个物体，用这个视角，画到这里」。要把它变成 gl 调用，得回答四个问题，每个问题交给一个专门的类：

问题负责的类它做什么拥有什么
画到哪里WebGL1SurfaceScope绑定输出目标、入口清除、退出时恢复只拥有一个作用域栈；目标是借来的
用什么画WebGL1ResourceManager 和它组装的五个 Manager把 CPU 资源变成这个 context 里的 GPU 对象GPU 对象归各个 Manager
带什么参数WebGL1Uniforms验证并上传这一次 draw 的全部 uniform只缓存反射（reflection）得到的元数据
设备出事了怎么办WebGL1Backend把上面几样和 State 打包成「一代」；丢失时整代作废，恢复时换上新的一代context、生命周期、当前这一代

Backend 的类注释把分工说得很清楚：「上层决定画什么、画到哪里、先后顺序；本类负责如何执行 gl.*」（WebGL1Backend.ts:38–40）。所以 draw 里没有这些事：遍历场景；计算世界矩阵（worldMatrix 由上层算好，放在 item 里）；绑定输出目标（作用域的事）；清除（作用域入口的事）。

3. 逐行精读 draw

先看完整的方法（WebGL1Backend.ts:192–231）。行尾的编号对应下面的小节：

draw(submission: DrawSubmission): void {
  const generation = this.requireGeneration('draw')                         // ① 这一代能用吗
  generation.scope.assertDrawable()                                         // ② 在某个作用域里吗
  if (!(submission?.item?.geometry instanceof Geometry) || …)              // ③ 输入的形状对吗
    throw new InvalidMaterialError('submission', 'invalid draw submission')
  const { geometry, material } = submission.item
  const program = generation.resources.programs.get(material.shaderModule)  // ④ 取 program
  const buffers = generation.resources.geometries.get(geometry)             // ⑤ 取 buffer
  const commands = generation.uniforms.prepare(program, submission)         // ⑥ uniform 预检
  this.assertCurrentDraw(generation)                                        // ⑦ 检查点
  generation.state.useProgram(program.program)                              // ⑧ 选用 program
  this.applyDrawState(material, generation.state)                           // ⑨ 渲染状态
  generation.uniforms.upload(commands)                                      // ⑩ 上传 uniform
  generation.resources.vertexInputs.bind(geometry, buffers, program)        // ⑪ 顶点输入
  this.assertCurrentDraw(generation)                                        // ⑫ 检查点
  if (buffers.indexBuffer === null) this.gl.drawArrays(…)                  // ⑬ 发出 draw
  else this.gl.drawElements(…)
  this.assertCurrentDraw(generation)                                        // ⑭ 检查点
}

读下面每一节时，先看代码摘录（逐行注释；「节选」表示省略了一部分，中文伪代码行是我的概括），再看表。表的行固定为：作用、所在层、为什么需要它、校验、状态变化、生命周期、和谁有关、如果挪位置。有两个词会反复出现：冷路径（cold path）指第一次用到某个资源、要真正创建 GPU 对象的那条路；热路径（hot path）指缓存命中、直接返回的那条路。

3.1 ① requireGeneration：这一代能用吗

private requireGeneration(operation: string): Generation {                  // WebGL1Backend.ts:319–336
  if (this.disposedValue) throw new WebGLBackendDisposedError(operation)    // Backend 已关闭
  if (this.gl.isContextLost()) {                                            // 物理丢失：可能早于 DOM 事件
    this.invalidateGeneration()                                             //   立刻作废这一代（有副作用）
    throw new WebGLContextLostError(operation)
  }
  if (this.lifecycle.state === 'restoring' || this.lifecycle.state === 'restore-failed') {
    throw new WebGLOperationError(operation, 'WebGL1Backend', this.lifecycle.state)
  }
  if (!this.generation.valid || !this.lifecycle.isReady) {
    throw new WebGLContextLostError(operation)                              // 这一代已作废
  }
  return this.generation                                                    // 交出这一次 draw 要用的一代
}
作用确认 Backend 现在能画，并交出「这一次 draw 用哪一代的对象」。
所在层第三层 Backend 自己。会碰 GL 的三个公开方法，第一行都是它：draw、withRenderSurface（:180）、resizeDrawingBuffer（:140）。dispose 不经过它，因为关闭必须在任何状态下都能做。
为什么需要它后面每一步用的 State、Manager、Uniforms、Scope 都属于某一代。context 一丢，这一代的所有句柄一起作废（第 4 课第 6 节），必须在碰它们之前拦住。
校验四种情况、三类错误：已关闭 → WebGLBackendDisposedError（调用者用错了）；context 丢失、或这一代已作废 → WebGLContextLostError（设备暂时不可用）；正在恢复、恢复失败 → WebGLOperationError，附上生命周期状态。错误里的操作名就是参数 'draw'。
状态变化正常时什么都不改。发现物理丢失时有副作用：invalidateGeneration 换一个新的 epoch、把这一代标成 valid = false、清空 State 缓存，并让每个 Manager 丢掉记录、撤销它们在 CPU 资源上的订阅（WebGL1ResourceManager.ts:158–166）。这一路不发任何 GL 命令：句柄已经没用了。
生命周期「一代」的入口检查（第 6 节）。返回的那个对象会在 ⑦⑫⑭ 被拿来比较身份。
和谁有关后面每一步都用它返回的 generation：这是数据依赖（data dependency）。② 的 Scope 还会通过 assertReady 钩子再调它一次（:275–277）。
如果挪位置挪不动：它返回的一代是后面每一步的输入。它做的检查其实不止做一次：② 会再做一遍；ResourceManager 的 getter、每个 Manager、State、Uniforms 也各自检查 context。这叫逐层防御（defense in depth）：每个零件单独拿出来用（比如卡片里、测试里）也得安全，而且 context 可能在任意两次 GL 调用之间丢失。放在第一行的意义是：一进门就用 'draw' 这个操作名报错，并把这一次 draw 钉在同一代上。

3.2 ② scope.assertDrawable：在某个作用域里吗

}
作用确认现在处在某个作用域里，而且从进入作用域到现在，目标和画布都没被动过。
所在层第三层 backend 的 WebGL1SurfaceScope，每一代一个。
为什么需要它draw 自己从不绑定输出目标：「画到哪里」完全由外面的 withRenderSurface 决定（第 6 课第 3 节：用作用域，不用全局开关）。不在作用域里就 draw，只能画到上一个人留下的目标上。
校验三层：生命周期（:282–288）；栈不空（:257）；assertUnchanged 逐层比较进入时记下的画布尺寸、目标的 revision 和 disposed。它检查的是所有活动的祖先，不只是最内层。
状态变化无，只读。
生命周期RenderTarget 是借来的：在使用时检查它还活着、没有被 resize（第 5 课第 5 节「借用方不拥有，但在使用时检查」）。注释写得很老实：它只能发现违规的 resize 或 dispose，拦不住，也撤销不了（:252）。
和谁有关Scope 不认识 Backend 这个类，只拿到三个函数（:24–28）：assertReady、isCurrent、resolveTarget。所以它可以单独构造：第 8 节卡片的准备代码就是用三个假钩子造出来的，单元测试也一样。
如果挪位置挪到后面，结果仍然正确，因为 ⑦ 还会再查一次。但失败得晚：可能先编译了 shader、上传了 buffer，才发现这次根本不该画；报出来的还可能是别的错误（比如 shader 编译失败），把真正的原因「不在作用域里」盖住。便宜的检查放在最前，失败又早又准。

3.4 ④ programs.get：取 program（第一次会编译）

// 先经过 Material 的 getter（Material.ts:376–381）：取 shader 的同时做借用检查

get(shader: ShaderModule): WebGL1ProgramResource {                        // WebGL1ProgramManager.ts:80–198（节选）
  this.assertAvailable('get program')                                     // Manager 没关闭、context 没丢
  if (shader.disposed) throw new ResourceDisposedError('ShaderModule')
  if (this.releasing.has(shader)) throw new WebGLOperationError(…)       // 正在释放时不许再取
  const cached = this.entries.get(shader)
  if (cached !== undefined) return cached.resource                        // 热路径：一次 Map 查找就返回
  if (shader.language !== 'glsl-es-100') throw new UnsupportedShaderLanguageError(…)
  this.checkError('preflight', shader.name)                               // 冷路径：先确认没有别人留下的 GL 错误
  … 编译两个 shader → createProgram → attach → link → 查 LINK_STATUS → detach
  … 反射：每个 active attribute 的 location、每个 active uniform 的 location
  const resource = Object.freeze({ program, attributes, uniforms })
  const unsubscribe = shader.onDispose(() => this.release(shader))        // 订阅 CPU 资源的释放
  this.entries.set(shader, { resource, unsubscribe })                     // 全部成功才发布
  return resource
  // catch：context 丢了 → 丢掉记录、抛 ContextLost；否则删掉建了一半的 program，原错误抛出
  // finally：context 还在就删掉两个临时 shader
}
作用把 CPU 的 ShaderModule 变成这个 context 里能用的 program，附带 attribute 和 uniform 的 location 表。
所在层第三层 backend 的 WebGL1ProgramManager。ResourceManager 组装它，Backend 通过 getter 借用它（WebGL1ResourceManager.ts:118–122）。
为什么需要它编译和链接很贵，所以按 ShaderModule 的对象身份缓存（:59）：同一个 shader 在一个 context 里只编译一次，而且第一次用到时才编译（懒创建，第 4 课）。
校验Material 和 shader 都活着；Manager 可用；不在释放中；只接受 GLSL ES 1.00；preflight 查旧错误（第 2 课：把别人留下的错误先报出来，免得算到自己头上）；编译状态、链接状态；反射出的每一项都有效。
状态变化热路径：无。冷路径：新建一个 program（两个临时 shader 用完即删）；entries 多一条；ShaderModule 上多一个订阅。它不绑定任何东西，也不调用 useProgram，所以不需要清空 State 缓存。
生命周期订阅把「这个 GPU program」和「CPU ShaderModule 的寿命」绑在一起：shader 释放 → release → 先通过 beforeDelete 让 VertexInputManager 删掉关联的 VAO，再删 program；如果它正是当前 program，先 useProgram(null)（:232–234）。
和谁有关结果被三步用到：⑥ prepare（uniform location）、⑧ useProgram（program 句柄）、⑪ bind（attribute location）。三条都是数据依赖，所以它必须排在这三步之前。

所在层第三层 backend 的 WebGL1GeometryManager。

状态变化冷路径：新建 buffer；上传时临时改 ARRAY_BUFFER 和 ELEMENT_ARRAY_BUFFER 的绑定，结束时恢复；然后清空 State 缓存。失败时删掉本次建的 buffer，同样清空 State 缓存。

作用给 program 的每个 active uniform 找到这一次 draw 的值、检查类型，生成一组上传命令（闭包，closure），但一条都不执行。
所在层第三层 backend 的 WebGL1Uniforms（每一代一个，Backend 独占）。它不拥有 program，也不拥有 Material。
为什么需要它这叫「先准备、后提交」（prepare / commit）：把所有可能因为数据出错的检查放在前面，全部通过才动 GL（:60–62）。好处是失败语义简单：一次因为数据问题抛错的 draw，一个 uniform 都没写（卡片 C），正是第 6 课第 4 节说的「要么完整、要么不变」。要说清一点：即使边验证边上传、中途失败留下半套值，在这个项目里也不会被画出来，因为每一次成功的 draw 都会写全部 active uniform（缺一个就拒绝，:62）。所以拆开换来的是清楚的契约，而不是修掉一个看得见的 bug。
校验context；内建映射不重名（:119–126）；sampler 数量（:134–143）；每个 active uniform 都有值（:156–158）、类型匹配（:160–162）；二维纹理和附件交给 resolve2D（10 月 12 日接通，:175–184）；uniform 数组不支持（:235–237），不会只上传第一个元素；数值数组长度对、量化成 Float32 之后仍是有限数（:35–54）；normalMatrix 可逆（:307–309）；借来的纹理还活着（getParameterEntries 里的 copyParameter 调纹理自己的 assertUsable，materialParameters.ts:126、Texture2DSamplingSource.ts:59；块里用到的项也一样，:261–270）。
状态变化不写任何 uniform。可能的副作用只在冷路径：反射缓存加一项；cubemap 第一次用到时由 CubeTextureManager 上传——临时改当前纹理单元上的 cubemap 绑定和四个 UNPACK 参数，结束时恢复（withTextureUploadState），然后清空 State 缓存。注释对此很诚实：这不是「GPU 状态完全不变」的事务，保证的只是不会写一半 uniform（:102–104）。
生命周期命令是一次性的：只能在本次 draw 里执行，不能跨 draw、跨 program、跨代复用（:194）。反射缓存用 WeakMap（:79）：program 对象被回收后，缓存项自动消失。
和谁有关需要 ④ 的 program（反射信息、location），结果交给 ⑩ upload。它不需要 program 已被选用，所以可以放在 ⑧ 之前。

每个 uniform 的值从哪来：

  • 内建值来自这一次的 DrawSubmission，不来自 Material（:272–319）：模型矩阵取自 item.worldMatrix（第 8 课讲它从哪来），视图矩阵、投影矩阵和相机位置取自 view。这就是第 3 课说的「Material 不知道 Camera」。
  • 其余的来自 Material 的参数；10 月 19 日起，本地参数里没有的，再去 Material 借用的参数块里找（WebGL1Uniforms.ts:149–154）。active uniform 找不到值就拒绝这次 draw，类型对不上也拒绝。Material 里那个待办——「缺失的 active uniform 必须有明确策略，不能沿用上一个 Material 留在 Program 中的值」（Material.ts:178–179）——在这里有了答案。
  • cubemap 按顺序分配纹理单元，通过 CubeTextureManager 取得 GPU 纹理（:164–173）。

法线矩阵。先把记号说清：M 是模型矩阵（local → world），V 是视图矩阵（world → view），都是 4×4、列主序；mat3(X) 表示取 X 左上角的 3×3；nlocal 是模型空间里的法线，nview 是视图空间里的法线。代码算的是（:293–298 的注释）： 

n_view = transpose(inverse(mat3(V · M))) · n_local     （shader 里还要再 normalize）

为什么要逆转置，而不是直接用 M？举个例子：M 把 x 方向拉长 2 倍，V 取单位矩阵。平面 x + y = 0 的法线是 (1, 1, 0)；拉长之后平面变成 x/2 + y = 0，真正的法线是 (0.5, 1, 0)。逆转置 diag(0.5, 1, 1) 乘 (1, 1, 0) 正好得到它；直接用 M 会得到 (2, 1, 0)，方向错了（卡片 D）。投影矩阵 P 不参与，相机的旋转必须参与，所以用的是 V · M 而不是 M（:296）。只有 shader 真的用到法线矩阵时才计算它，遇到不可逆的矩阵就报错（:307–309）。

3.7 ⑦⑫⑭ assertCurrentDraw：三个检查点

private assertCurrentDraw(generation: Generation): void {                 // WebGL1Backend.ts:338–344
  if (this.requireGeneration('continue draw') !== generation) {           // 还能用、而且还是同一代吗
    throw new WebGLContextLostError('continue draw from an old generation')
  }
  generation.scope.assertDrawable()                                       // 作用域还有效吗
}
作用在三个关口确认：这一次 draw 手里的对象仍属于当前可用的那一代，作用域也还有效。
为什么在这三处⑦ 在冷路径之后、提交状态之前：④⑤⑥ 可能发出了几十个 GL 调用，context 可能在其中任何一个之后丢失，冷路径内部的检查也不一定覆盖到最后一个调用；⑫ 在真正 draw 之前，最后确认一次；⑭ 在 draw 之后：如果 context 恰好在 draw 期间丢失，要报告 ContextLost，而不是假装画成功了。
「换了一代」会发生吗恢复发生在 DOM 事件里，插不进一次同步执行的 draw 中间，所以「身份变了」这条主要是防御。真正会发生的是物理丢失：requireGeneration 查到 isContextLost，作废这一代并抛错。
状态变化和 ① 一样：只有发现丢失时，才有作废这一代的副作用。

3.8 ⑧ state.useProgram：选用 program

useProgram(program: WebGLProgram | null): void {                          // WebGL1State.ts:47–54
  this.assertContextAvailable('use program')    // 丢失：清空缓存并抛错
  if (this.programValue === program) return      // 缓存说已经是它：不发 GL 命令
  this.gl.useProgram(program)
  this.programValue = program
}
作用让 GL 的「当前 program」变成这一个。缓存说已经是它，就不发命令。
所在层第三层 backend 的 WebGL1State（每一代一个，Backend 独占）。
为什么走 State连续画很多用同一个 program 的物体时，可以省掉重复的 useProgram，这叫去重（deduplication）。缓存用 undefined 表示「不知道」、null 表示「确实没绑」，只在「明确等于」时才跳过（:24–25；第 4 课第 5 节「缓存什么时候过期」）。不过在现在的代码里，这个去重在连续的 draw 之间从不生效，见 3.11 和卡片 H。
状态变化GL 的 CURRENT_PROGRAM；State 的 programValue。
和谁有关⑩ upload 用的 uniform location 属于 ④ 的 program。WebGL 规定：uniform* 调用的 location 必须来自当前 program，否则产生 INVALID_OPERATION、这次调用什么也不做。所以 ⑧ 必须在 ⑩ 之前。这是整个 draw 里最硬的一条状态依赖（state dependency）。
如果挪到 ⑩ 之后upload 执行时，当前 program 还是上一次 draw 留下的那个（第一次 draw 时是 null）。每一条 uniform 调用都因为「location 不属于当前 program」报 INVALID_OPERATION，什么也没写进去（卡片 G 在真实 GPU 上验证过）。接着 ⑧ 选用正确的 program，⑬ 用它上一次被使用时留下的 uniform 值去画——比如上一个物体的模型矩阵，物体就画到了别处。不会抛任何异常：draw 的热路径不调 getError，这个错误一直留在 GL 的错误标志里，直到下一个冷路径的 preflight 把它取出来，算到一个不相干的资源头上（WebGL1ProgramManager.ts:98–99）。
更正：我整理笔记时一度以为「顺序反了，uniform 会写进上一个 program」。那是桌面 OpenGL 的行为：那里的 location 只是一个整数，按当前 program 解释，可能悄悄写进别人的 program。WebGL 把 location 做成属于某个 program 的对象，并且会检查这一点。卡片 G 的实测：A 是当前 program 时用 B 的 location 上传，A、B 的值都没变，调用日志里记着 INVALID_OPERATION。

3.9 ⑨ applyDrawState：渲染状态

private applyDrawState(material: Material, state: WebGL1State): void {    // WebGL1Backend.ts:289–310
  for (const capability of [gl.BLEND, gl.STENCIL_TEST, gl.SCISSOR_TEST,
    gl.POLYGON_OFFSET_FILL, gl.SAMPLE_ALPHA_TO_COVERAGE, gl.SAMPLE_COVERAGE]) {
    gl.disable(capability)                       // 还没支持的功能：一律关掉，不继承别人留下的
  }

  gl.lineWidth(1)
  state.setDepthState(material.state)            // Material 控制的：深度测试、深度写入、深度函数（经过 State 缓存）
  state.setCullMode(material.state.cullMode)     // 剔除（经过 State 缓存）
}
作用把这次 draw 需要的固定功能状态设好。
所在层Backend 的私有方法，深度和剔除交给 State。
为什么分两类Material 能控制的只有深度和剔除（Material 的 RenderState），这两样经过 State 缓存（State.ts:121–169）。其余还不支持的功能，不能靠「希望没人开过」：对同一个 canvas 再调一次 getContext('webgl')，拿到的就是同一个 context（卡片 E 就是这样读像素的），任何拿到它的代码都可能留下 blend 或 scissor。类注释要求 context 由 Backend 独占（:40），这里等于不完全相信这个约定，每次都关掉。
校验material.state 的 getter 检查 Material 还活着（Material.ts:298–302）；State 的方法检查 context 没丢。RenderState 本身在 Material 构造时就验证并冻结了，这里不再验证。
状态变化blend、stencil、scissor、polygon offset、两种 sample coverage 关闭；颜色掩码全开；深度范围 [0, 1]；逆时针为正面；线宽 1；深度测试、深度写入、深度函数和剔除按 Material 设置。
和谁有关⑬ draw 用这些状态。它和 ⑧⑩⑪ 之间没有依赖，四者的先后可以随意换，只要都在 ⑬ 之前（⑧ 和 ⑩ 之间那条除外）。

3.11 ⑪ vertexInputs.bind：顶点输入

上次答疑细讲过两种策略（OES VAO、手动绑定）。放到 draw 里看，它做的是：先检查 Geometry 还活着（assertBindable）；按「(Geometry, 真实的 WebGLProgram)」查 VAO 缓存，命中就绑定一次（OES :66–73）；没命中就先验证布局、再新建并配置 VAO，全部成功才缓存，失败就回滚。最后在 finally 里清空 State 缓存（:136–138），理由是「VAO 切换改变 EBO；配置过程还会临时改变全局 ARRAY_BUFFER」。

注意两点：finally 在命中缓存时也会执行（try 里的 return 同样要经过 finally）；而这个钩子接的是整份 state.invalidate()，program、深度、剔除的缓存一起清掉。于是每一次 draw 结束前，State 缓存都被清空，下一次 draw 的 ⑧⑨ 一定重发全部命令（卡片 H 在真实 GPU 上数过）。

状态变化OES 策略：VAO 绑定（其中带着 EBO）；配置新 VAO 时临时改 ARRAY_BUFFER，完成后恢复。手动策略：默认 VAO 上的 attribute 指针和启用状态、EBO；ARRAY_BUFFER 停在最后一个 attribute 的 buffer 上。两种策略都在 finally 里清空整份 State 缓存。
生命周期VAO 归 VertexInputManager 所有，buffer 和 program 都是借来的；Geometry 或 program 释放时，由 beforeDelete 先删 VAO。
和谁有关要用 ④ 的 attribute location 和 ⑤ 的 buffer（数据依赖）；⑬ 要用它绑好的输入。它清空的缓存影响的是下一次 draw 的 ⑧⑨：这是一条跨 draw 的关系。
如果挪位置它只需要在 ⑤ 之后（数据依赖）、⑬ 之前；和 ⑧⑨⑩ 之间没有依赖。代码注释说「最后绑定 VAO/EBO，避免先前的 buffer 上传扰乱索引来源」（WebGL1Backend.ts:190）。⑤ 的冷路径确实会临时改 EBO，但它会恢复，所以这更像一条保险：离 draw 越近，中间被别的代码改掉的机会越少。

3.12 ⑬ 发出 draw

if (buffers.indexBuffer === null) {                                       // WebGL1Backend.ts:220–228
  this.gl.drawArrays(buffers.primitiveMode, 0, buffers.drawCount)
} else {
  if (buffers.indexType === null) throw new WebGLOperationError('draw', 'Geometry', 'index buffer has no index type')
  this.gl.drawElements(buffers.primitiveMode, buffers.drawCount, buffers.indexType, 0)

参数全部来自 ⑤ 冻结的 GeometryResource，这里不做任何换算。draw 之后不调 getError：第 2 课讲过，getError 要同步等待 GPU，只能放在冷路径上。这一次 draw 如果产生了 GL 错误，会被下一个冷路径的 preflight 取出来，以 WebGLOperationError 抛出（WebGL1ProgramManager.ts:324–334）。之后 ⑭ 再确认 context 没在 draw 期间丢失。draw 正常返回也不代表 GPU 已经执行完（RenderBackend.ts:39）：它只是把命令交给了浏览器。

4. 顺序：哪些能换，哪些不能

把 ④ 到 ⑪ 分成两组，顺序约束就清楚了：

调换硬 / 软换了会怎样
① 挪到后面硬挪不动：后面每一步用的都是它返回的那一代。它的检查在 ② 里还会再做一次（3.1）。
② 挪到后面软⑦ 还会再查，结果仍然正确；只是失败得晚，报出来的还可能是别的错误（3.2）。
④ 挪到 ⑥⑧⑪ 之后硬不可能：这三步都要用 ④ 的结果。
⑤ 挪到 ⑪⑬ 之后硬不可能：bind 要 buffers，draw 要 mode、count、indexType。
⑥ 挪到 ⑩ 之后硬不可能：upload 执行的就是 prepare 生成的命令。
⑧ 挪到 ⑩ 之后硬每条 uniform 调用都报 INVALID_OPERATION、什么也没写；这次 draw 带着这个 program 上一次留下的值去画，而且不抛异常（3.8、卡片 G）。
④⑤⑥ 挪到 ⑧⑨ 之后软冷路径会恢复自己改过的绑定，所以仍然能画对。代价有两个：一是冷路径失败时（编译错误、上传失败），这次失败的 draw 已经改掉了 program 和深度状态——下一次 draw 会重新设置，不会画错，但「抛错的 draw 什么也没改」这条性质没了；二是冷路径会清空 State 缓存，刚设好的状态没用上就作废了。代码注释写的是「必须」（WebGL1Backend.ts:189、WebGL1Uniforms.ts:104），严格说是「应该」。而且在现在的代码里，⑪ 每次都会清空缓存（卡片 H），第二个代价其实不存在。
⑨ 和 ⑧、⑩、⑪ 互换自由它们之间没有依赖，只要都在 ⑬ 之前。
⑪ 挪到 ⑩ 之前自由upload 不碰 VAO 和 buffer，结果相同。
⑧⑨⑩⑪ 挪到 ⑬ 之后硬draw 发出时状态还没设好，用的是上一次 draw 留下的状态。

6. 一代：丢失与恢复的时间线

interface Generation {                         // WebGL1Backend.ts:24–31
  readonly token: object                       // 这一代的身份
  readonly state: WebGL1State
  readonly resources: WebGL1ResourceManager
  readonly uniforms: WebGL1Uniforms
  readonly scope: WebGL1SurfaceScope
  valid: boolean                               // 丢失后变成 false，再也不会变回 true

createGeneration 一次性创建这四样，并且每一代都重新探测一次能力（:259）：恢复后的 context 可能落在另一块 GPU 上（比如笔记本切换了显卡），能力未必和原来相同。新一代的 Manager 都是空的，不会立刻把全部 CPU 资源重新上传，下一次 draw 用到什么才上传什么（:257）。

为什么要比较「代」，而不是只看 gl.isContextLost()？恢复之后，context 又好了，isContextLost 变回 false，但旧一代对象手里的句柄已经全部作废。所以 Scope 的 isCurrent 钩子比较的是「创建我的那一代，还是不是当前代」（WebGL1SurfaceScope.ts:21、WebGL1Backend.ts:279–280）。下面这张图把三样东西分开画：Backend 对外报告的 ready、lifecycle 的状态机、以及「当前这一代」：

图 3 最下面那条时间线，现在有真实浏览器的测试。WebGLContextLifecycle.test.ts（2026-09-28 新增）用 WEBGL_lose_context 让 context 真的丢失、再恢复，等浏览器真正派发 lost、restored 事件，不用 dispatchEvent 伪造（:5–11）；它记下每个回调被调用时的状态：onLost 时已经是 lost、isReady 为 false；restore 和 onReady 执行时都还是 restoring；全部跑完才回到 ready（:91–104）。它只验证 lifecycle 这一条线：测试不创建 Backend，也不证明 GPU 资源已经重建，那部分仍归 WebGL1Backend 的浏览器测试（:36–38）。

epoch 为什么是对象？注释写着「对象身份令牌，不是会不断增长的计数器」（:51–52）。每次状态变化就换一个新的 {}，比较时只看是不是同一个对象：不用考虑溢出，也不会和别处的数字碰巧相等。第 8 课的版本号碰撞，就是两个来源的数字碰巧相等。每一代的 token 也是同样的身份令牌（identity token）。

7. 作用域的栈：嵌套时每一帧记下了什么

withRenderSurface 把工作交给 WebGL1SurfaceScope.run（:191–244），顺序是：

  1. 先确认可用、外层作用域都没被动过（:192–193）；
  2. 验证并复制描述（snapshot），检查回调是函数；
  3. 记下这一层：目标、目标的 revision、drawing buffer 的尺寸（:201–206）；
  4. 用 getParameter 读出真实的 FRAMEBUFFER_BINDING 和 VIEWPORT（:208）；
  5. 入栈（:212）；
  6. try：解析目标（第一次会创建 FBO，而创建 FBO 会改变当前绑定，所以第 4 步必须在它之前，:184）→ 检查 → 绑定 → 入口清除 → 检查 → 执行回调 → 检查回调返回 undefined → 再检查（:215–226）；
  7. finally：出栈，恢复第 4 步读到的状态（:230–241）。

嵌套两层时，栈里是这样的：

校验描述只认 surface、clear 两个字段，多一个字段也报错；数值必须是有限的 Float32，深度在 [0, 1]，stencil 是 32 位有符号整数；目标没被释放；回调是函数，同步返回 undefined（不能是 async 函数）；目标确实有深度、stencil 附件，才能清它们（:331–337）。
状态变化进入：FRAMEBUFFER 绑定和 viewport（bindSurface，每次都发命令，不走缓存）；清除时临时打开写掩码、关闭 scissor 和 dithering，清完恢复（clearAttachments，卡片 B）；目标里的像素被清掉。退出：恢复进入前的 FRAMEBUFFER 和 viewport；不回滚像素。
生命周期目标是借来的：不 retain，也不 dispose。退出时如果这一代已经不是当前代，或者 context 丢了，只清空 State 缓存，不拿旧快照去绑（:266–279）；进入前的 framebuffer 已被删除，就报错，而不是悄悄换成画布。
错误操作失败、恢复成功：原错误原样抛出；操作成功、恢复失败：抛恢复错误；两者都失败：AggregateError 里依次放操作错误和恢复错误（:236–238）。

10. 架构视角

10.1 对照 three.js 的新渲染器

  • 入口清除是同一种形状。three.js 新渲染器的 WebGL 后端在 beginRender 里先设 viewport、再绑定 framebuffer，然后按 renderContext 里的清除值清一次（:478–479）。本项目把清除并进作用域入口，走的是同一条路；WebGPU 的 render pass 也是在开始时指定清除。
  • 收尾不在 finally 里。它的 Renderer 先调 backend.beginRender（Renderer.js:1472），中间画完再调 finishRender（:1490），两者之间没有 try/finally：中间有代码抛错，收尾就不会执行。本项目的作用域用 finally 保证恢复（图 4），这是第 6 课「用作用域，不用全局开关」的延续。

10.2 审查视角：三处值得讨论，一处已经修好

  1. 每次 draw 都无条件设十个状态。applyDrawState 每次都 disable 六个功能，再设颜色掩码、深度范围、正面方向和线宽，不走缓存。好处是绝不继承别人留下的状态；代价是每次 draw 多十次 gl 调用。想一想：要不要把它们也挪进 State、只在变化时才设？要承担什么风险（提示：如果有人绕过 State 改了状态呢）？
  2. 失效钩子只有一种粒度，State 的去重在 draw 路径上从不生效。⑪ 每次都调用整份 state.invalidate()（卡片 H），所以 ⑧ 的 useProgram、⑨ 的深度和剔除每次都重发。命中 VAO 缓存时真正需要作废的只有 EBO，State 为此留了 invalidateVertexInputState；可是 VertexInputManager 只拿到一个钩子，而它的注释要求接完整的 invalidate（WebGL1VertexInputManager.ts:43–53），因为冷路径还改了 ARRAY_BUFFER。HW2 每帧只有几次 draw，性能上无所谓；问题在于一段看起来在工作的缓存，实际上从不命中。想一想：是给钩子分出两种粒度，还是干脆承认 State 在 draw 路径上不需要缓存、删掉它？各自的风险在哪？
  3. submission 形状不对，报的是 InvalidMaterialError。:196–203：geometry 不是 Geometry、view 不是对象，都抛 InvalidMaterialError('submission', …)，消息是「Material field submission is invalid: invalid draw submission」。按第 6 课的分类，它确实属于「调用者用错了」；但类名和消息都指向 Material，排查的人会先去查材质。想一想：该换成哪种错误，还是新加一个？
  4. 已经修好（2026-09-28）：ResourceManager 的空 catch 删掉了。改之前是 try { … } catch (error) {} finally { … }：清理错误被吞掉，和上方注释「本方法不吞错」（WebGL1ResourceManager.ts:181）矛盾。某个 Manager 清理失败时，Backend.dispose 照常返回、把 cleanupComplete 设成 true，之后再调 dispose 直接 return，失败那一步之后的 Manager 永远不会被清理。现在只剩 try { … } finally { this.disposing = false }（:190–201）：错误一路传到 Backend.dispose，cleanupComplete 保持 false；再调一次 dispose，ResourceManager 从 disposalIndex 记住的那一步接着清，已经完成的步骤不重复（WebGL1Backend.ts:241–255；测试 WebGL1ResourceManager.test.ts:314，原来失败，现在通过）。留在这里作对照：多一个空的 catch，失败就再也没法重试。
