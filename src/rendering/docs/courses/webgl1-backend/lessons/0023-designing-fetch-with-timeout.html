从零设计一个能取消、会超时的请求函数

这一课不看现成的答案。我们从「调用者需要什么」出发，一版一版地写。每写完一版，就在实验台上跑几个真实场景：先猜它会怎样，再看它实际做了什么。哪里不够，下一版就改哪里。写到第 6 版，就是你要敲进 src/network/http.ts 的代码。

和你的目标的关系 —— HW2 每次构建场景，createHW2Scene 都要下载 7 个文本文件：OBJ、light、transport 和 4 个 shader。它们全都经过 fetchTextWithTimeout。用户切换场景、服务器卡住、文件丢了，这个函数都要给出正确的结果，上层才知道该安静地丢掉、提示重试，还是报错。

0. 先认识两个对象：controller 和 signal

把 AbortController 想成一个开关，它出生时自带一盏灯，也就是 controller.signal。只有开关能把灯按亮；拿到灯的人只能看它亮没亮，或者登记「灯亮时叫我」。 

const controller = new AbortController() // 新建一个开关，它自带一盏灯
const signal = controller.signal         // 拿到这盏灯。取多少次都是同一个对象

signal.aborted   // false：灯还没亮
signal.reason    // undefined：还没写原因

// 登记：灯亮的那一刻，执行这个函数
signal.addEventListener('abort', () => console.log('灯亮了，原因：', signal.reason.message))

controller.abort(new Error('用户切换了场景')) // 按开关：灯亮，原因记成这个 Error 对象，
                                             // 并且当场执行上面登记的函数，打印「灯亮了，原因：用户切换了场景」

signal.aborted           // true
signal.throwIfAborted()  // 灯亮着：把原因当作错误抛出；灯没亮：什么也不做

controller.abort(new Error('再按一次')) // 没有任何效果：灯只能亮一次，原因还是「用户切换了场景」
signal.abort             // undefined：灯上没有开关，拿到灯的人按不了

addEventListener 的第三个参数 { once: true } 表示「这个监听最多执行一次，执行完自动摘掉」。手动摘的时候写 removeEventListener('abort', 同一个函数)：必须传登记时的同一个函数对象，所以要先把函数存进一个常量。

下面的实验台用的是模拟服务器：课程页用 file:// 打开，发不了真请求。模拟的 fetch 按 Fetch 规范的取消规则来写，我已经在 Node 里用真实的 fetch 和本地服务器逐个场景对照过，结果一致。每次实验里，「你的 controller」代表调用者，比如 HW2SceneController；「你传的原因」就是 new Error('用户切换了场景') 这个对象。为了不让每次实验都等 6 秒，超时缩短成 500 ms。

1. 需求：调用者到底要什么

先别想代码。站在调用者的位置，把要遇到的情况一条条写下来，每条都写清楚「期望得到什么」：

  1. 正常：服务器 100 ms 回响应头，正文再传 100 ms。期望：拿到文本。（响应头和正文为什么能分开到，见第 24 课。）
  2. 等响应头时换场景：服务器要 300 ms 才回应，你在 100 ms 时点了 CornellBox。期望：立刻停下，而且抛出的就是你写在 abort(原因) 里的那个对象，这样上层能认出「这是我自己取消的」，安静地丢掉，不弹错误。
  3. 读正文时换场景：响应头 50 ms 就到了，正文要传 400 ms，你在 200 ms 时取消。期望同上。
  4. 服务器卡住：一直不回应。期望：到时间抛出 NetworkTimeoutError，界面可以提示「网络慢，请重试」。
  5. 调用前就取消了：你按了取消，之后才轮到这个函数被调用。期望：不发请求，直接抛出你的原因。
  6. 文件不存在：服务器回 404。期望：抛出 HttpError，重试也没用。
  7. 断网：连不上服务器。期望：抛出 NetworkError，可以重试。
  8. 大文件下载慢：响应头 100 ms 就到了，正文要传 900 ms。服务器在正常工作，期望：照常拿到文本，不能被超时误杀。

这张清单就是验收标准。下面每写一版，都拿其中几条来试。

2. 第 1 版：能用就行

// 第 1 版：能用就行
async function fetchText(url: string): Promise<string> {
  const response = await fetch(url) // 发出请求，等服务器回「响应头」（状态码、类型这些）
  return await response.text() // 再等「正文」全部传完，变成一个字符串
}

3. 第 2 版：让调用者能取消

要取消，先得有个入口接收取消。fetch 本来就接受一个 signal 选项，那就让调用者把他的 signal 传进来，原样交给 fetch： 

// 第 2 版：让调用者能取消
async function fetchText(url: string, signal?: AbortSignal): Promise<string> {
  // ← 新增：把调用者的 signal 原样交给 fetch。fetch 自己就会盯着它：
  //   signal 一亮，fetch 立刻中止网络请求，并让这次 await 失败，
  //   失败值就是调用者写在 abort(原因) 里的那个「原因」；
  //   如果调用之前 signal 就已经亮了，fetch 根本不发请求，直接失败。
  const response = await fetch(url, { signal })
  // 读正文的时候，fetch 也一直盯着同一个 signal，所以这里同样能被取消
  return await response.text()
}

工程上的第一个判断：如果需求只有「能取消」，写到这里就该停手了。fetch 已经把取消的事全做对了：调用前就亮了不发请求，等响应头时能停，读正文时也能停，抛出的还是调用者自己的原因。平台已经做好的事，不要再写一遍。可是清单里还有「服务器卡住」这一条，fetch 本身没有超时参数。

4. 第 3 版：加上超时

「到点就停」意味着要有人在到点时按灯。能让 fetch 停下的，只有它盯着的那盏灯；而灯只能由它的开关来按。调用者的开关在调用者手里，函数里拿到的只是那盏灯，按不了。所以函数只能自己建一个开关： 

// 第 3 版：加上超时（先只管超时）
async function fetchText(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<string> {
  const { timeout = 6000 } = options
  // ← 新增：超时要做到「到点就让 fetch 停下」。能让 fetch 停下的只有它盯着的 signal，
  //   而 signal 只能由创建它的 controller 来按。调用者的 signal 我们按不了
  //   （signal 上没有 abort 方法），所以自己建一个 controller，自己当那个按开关的人。
  const controller = new AbortController()
  // ← 新增：到点就按下自己的开关，并把「为什么按」写成一个超时错误。
  //   以后 fetch 因此失败，带出来的失败值就是这个超时错误。
  setTimeout(() => controller.abort(new NetworkTimeoutError(url, timeout)), timeout)
  // ← 改动：fetch 只有一个 signal 的位置，现在给了自己的开关。
  //   调用者传进来的 options.signal 没地方放了：取消功能被弄丢了（下一版解决）。
  const response = await fetch(url, { signal: controller.signal })
  return await response.text()
}

5. 第 4 版：两个理由，一个开关

现在的处境是：「该停了」有两个理由，调用者取消、超时；可 fetch 只有一个 signal 的位置。解决办法是让两个理由都去按同一个开关，fetch 只盯这一个。超时已经在按它了；还差一件事：调用者的灯一亮，我们就替他按一下自己的开关，这叫转发。按的时候把调用者写的原因抄过去，开关上写的原因就能说明是哪一种情况。 

// 第 4 版：两个「该停了」的理由，汇到一个开关上
async function fetchText(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<string> {
  // 把调用者的 signal 取出来，改名 callerSignal，免得和自己开关的 signal 混在一起
  const { timeout = 6000, signal: callerSignal } = options
  const controller = new AbortController()
  setTimeout(() => controller.abort(new NetworkTimeoutError(url, timeout)), timeout)
  // ← 新增：转发。调用者的 signal 一亮，就按下我们自己的开关，并把调用者写下的原因原样抄过去。
  //   这样「调用者要停」和「超时要停」都汇到同一个开关上，fetch 只要盯这一个；
  //   开关上写的原因，说明了到底是哪一种。
  //   先把函数存进常量：以后要摘掉这个监听，removeEventListener 必须拿到同一个函数对象。
  const forwardAbort = (): void => controller.abort(callerSignal?.reason)
  // { once: true }：这个监听最多执行一次，执行完自动摘掉
  callerSignal?.addEventListener('abort', forwardAbort, { once: true })
  try {
    const response = await fetch(url, { signal: controller.signal })
    return await response.text()
  } catch (error) {
    // ← 新增：开关被按过，说明是「有人要停」，不是出错。
    //   这时不管 error 是什么，一律以开关上写的原因为准：
    //   要么是调用者的原因，要么是超时错误，原样抛给调用者。
    if (controller.signal.aborted) throw controller.signal.reason
    // 开关没被按过却失败了：连不上服务器或传输中断，浏览器给的是 TypeError。
    // 换成项目自己的 NetworkError，调用者用 instanceof NetworkError 就能认出「网络问题」。
    if (error instanceof TypeError) {
      throw new NetworkError(url, `Network error: ${error.message}`, { cause: error })
    }
    throw error // 其他意料之外的错误：原样往上抛
  }
}

这一招你已经在项目里见过：loadHW2CubeImages.ts:122–124 和 createHW2Scene.ts:251–253 都是「自己建开关，再把调用者的取消转发进来」。它们也有自己要停的理由：某一张图失败了，要停掉其余几张。

6. 第 5 版：进门先看一眼

清单第 5 条还没试过：调用之前就已经取消了。先看第 4 版会怎样：

// 第 5 版：进门先看一眼
async function fetchText(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<string> {
  const { timeout = 6000, signal: callerSignal } = options
  // ← 新增：调用者的 signal 如果在调用之前就亮了，abort 事件已经发生过，
  //   下面再挂的监听永远等不到它，我们的开关也就永远不会被按——请求会照常发出去。
  //   所以一进门先查：亮着就把原因当作错误抛出去；没亮就什么也不做。
  callerSignal?.throwIfAborted()
  const controller = new AbortController()
  setTimeout(() => controller.abort(new NetworkTimeoutError(url, timeout)), timeout)
  const forwardAbort = (): void => controller.abort(callerSignal?.reason)
  callerSignal?.addEventListener('abort', forwardAbort, { once: true })
  try {
    const response = await fetch(url, { signal: controller.signal })
    return await response.text()
  } catch (error) {
    if (controller.signal.aborted) throw controller.signal.reason
    if (error instanceof TypeError) {
      throw new NetworkError(url, `Network error: ${error.message}`, { cause: error })
    }
    throw error
  }
}

7. 第 6 版：用完要收拾，难的是什么时候收拾

第 5 版把清单上大部分情况都处理对了，但它从不收拾：挂上去的监听没摘，计时器没停。先看看这会带来什么：

要收拾的东西有两样：挂在调用者 signal 上的转发监听，和计时器。用 finally 收拾最自然，因为成功、失败都会经过它。MDN 讲「怎样实现一个可取消的 API」时，也要求操作正常结束后把 abort 监听摘掉，免得长期存在的 signal 一直抓着它（见第 11 节）。最直接的写法，是把超时和取消放进一个返回 Response 的 fetchWithTimeout，在它的 finally 里收拾： 

// 第 6 版（错误示范）：知道要收拾，但收拾得太早
async function fetchWithTimeout(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<Response> {
  const { timeout = 6000, signal: callerSignal } = options
  callerSignal?.throwIfAborted()
  const controller = new AbortController()
  // ← 改动：记下计时器的编号，收拾时要用它把计时器停掉
  const timerId = setTimeout(() => controller.abort(new NetworkTimeoutError(url, timeout)), timeout)
  const forwardAbort = (): void => controller.abort(callerSignal?.reason)
  callerSignal?.addEventListener('abort', forwardAbort, { once: true })
  try {
    return await fetch(url, { signal: controller.signal })
  } catch (error) {
    if (controller.signal.aborted) throw controller.signal.reason
    if (error instanceof TypeError) {
      throw new NetworkError(url, `Network error: ${error.message}`, { cause: error })
    }
    throw error
  } finally {
    // ← 新增：不管成功失败，都停掉计时器、摘掉监听。
    //   问题在于时机：fetch 在「响应头到了」时就返回，finally 也就在这时执行了。
    clearTimeout(timerId)
    callerSignal?.removeEventListener('abort', forwardAbort)
  }
}

async function fetchText(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<string> {
  const response = await fetchWithTimeout(url, options)
  // 读正文时，上面的 finally 早就执行完了：转发监听已经摘掉，调用者再取消也传不进来
  return await response.text()
}

问题在于「整件事」什么时候结束：fetch 在响应头到达时就返回了，但正文还没读。收拾必须等到正文读完。办法是把「读正文」也搬进 fetchWithTimeout 里，让调用者用一个 read 函数告诉它怎么读。顺便做一个设计决定：超时只管「服务器多久开始回应」，响应头一到就停掉计时器。 

// 第 6 版：让「收拾」等到正文读完
async function fetchWithTimeout<T>(
  url: string,
  options: { timeout?: number; signal?: AbortSignal },
  // ← 新增：调用者告诉我们「拿到响应以后怎么读」（读成文本、二进制……）。
  //   读正文这件事因此发生在本函数里面，下面的 finally 会等它读完才执行。
  read: (response: Response) => Promise<T>
): Promise<T> {
  const { timeout = 6000, signal: callerSignal } = options
  callerSignal?.throwIfAborted()
  const controller = new AbortController()
  const timerId = setTimeout(() => controller.abort(new NetworkTimeoutError(url, timeout)), timeout)
  const forwardAbort = (): void => controller.abort(callerSignal?.reason)
  callerSignal?.addEventListener('abort', forwardAbort, { once: true })
  try {
    const response = await fetch(url, { signal: controller.signal })
    // ← 新增：响应头到了，就停掉计时器。这是一个设计决定：超时只管「服务器多久开始回应」，
    //   不管「正文要传多久」，否则一个几十 MB 的文件在慢网络上会被超时误杀。
    clearTimeout(timerId)
    // ← 新增：在 try 里面读正文。读的期间转发监听一直挂着，调用者取消照样能传进来。
    return await read(response)
  } catch (error) {
    if (controller.signal.aborted) throw controller.signal.reason
    if (error instanceof TypeError) {
      throw new NetworkError(url, `Network error: ${error.message}`, { cause: error })
    }
    throw error // read 里自己抛的错误（比如下面的 HttpError）走这里，原样抛出
  } finally {
    clearTimeout(timerId) // 没等到响应头就失败时，计时器还在跑，这里停掉
    callerSignal?.removeEventListener('abort', forwardAbort) // 整件事结束了，摘掉挂在调用者 signal 上的监听
  }
}

function fetchText(
  url: string,
  options: { timeout?: number; signal?: AbortSignal } = {}
): Promise<string> {
  return fetchWithTimeout(url, options, async (response) => {
    // 404 之类：服务器回应了，但给的不是我们要的文件。重试没用，换成 HttpError
    if (!response.ok) throw new HttpError(url, response.status, response.statusText)
    return await response.text()
  })
}

8. 最终代码：敲进 src

和第 6 版相比只多了两处：选项类型换成项目里的 FetchOptions（继承自 fetch 的 RequestInit，多一个 timeout），并且把 method、headers 等其余选项原样交给 fetch。注释写的是每一行存在的理由，可以照抄，也可以精简。

src/network/http.ts（整个文件替换）：

import { NetworkError } from '@/errors/EngineError/NetworkError/BaseError'
import { NetworkTimeoutError } from '@/errors/EngineError/NetworkError/NetworkTimeoutError'
import { FetchOptions } from './types/fetch-options'

/**
 * 发一次请求，并在同一个范围里把响应读完。
 *
 * - 调用者取消：抛出调用者写在 abort(原因) 里的那个原因；
 * - 超时：抛出 NetworkTimeoutError，只计算到响应头到达为止；
 * - 连不上、传输中断：抛出 NetworkError；
 * - read 里抛出的错误（比如 HttpError）：原样抛出。
 *
 * 浏览器基线 2022：用到 AbortSignal.throwIfAborted 和 abort(reason)，
 * Chrome 100、Firefox 97、Safari 15.4 起支持。
 */
export async function fetchWithTimeout<T>(
  url: string,
  options: FetchOptions,
  read: (response: Response) => Promise<T>
): Promise<T> {
  // 取出超时时间和调用者的 signal；剩下的 method、headers 等原样交给 fetch
  const { timeout = 6000, signal: callerSignal, ...fetchOptions } = options

  // 调用之前就取消了：abort 事件已经发生过，后面挂的监听等不到它，所以进门先查
  callerSignal?.throwIfAborted()

  // fetch 只认一个 signal，而「该停了」有两个理由：调用者取消、超时。
  // 调用者的 signal 我们按不了，所以自己建一个开关，两个理由都来按它，按的时候把原因写在上面
  const controller = new AbortController()

  // 理由一：超时。到点就按开关，原因写成超时错误
  const timerId = setTimeout(() => {
    controller.abort(new NetworkTimeoutError(url, timeout))
  }, timeout)

  // 理由二：调用者取消。调用者的 signal 一亮就按开关，原因照抄调用者的。
  // 存成常量，是为了在 finally 里用同一个函数对象摘掉这个监听
  const forwardAbort = (): void => controller.abort(callerSignal?.reason)
  callerSignal?.addEventListener('abort', forwardAbort, { once: true })

  try {
    const response = await fetch(url, { ...fetchOptions, signal: controller.signal })
    // 响应头到了：超时只管「服务器多久开始回应」，不管正文要传多久
    clearTimeout(timerId)
    // 在 try 里面读正文：读的期间转发监听还挂着，调用者取消照样有效
    return await read(response)
  } catch (error) {
    // 开关被按过：是有人要停，不是出错。以开关上写的原因为准
    if (controller.signal.aborted) throw controller.signal.reason
    // 连不上或传输中断：浏览器给 TypeError，换成项目的 NetworkError
    if (error instanceof TypeError) {
      throw new NetworkError(url, `Network error: ${error.message}`, { cause: error })
    }
    // read 里抛出的错误（比如 HttpError）：原样抛出
    throw error
  } finally {
    // 整件事结束了（正文已读完，或已经失败）：停掉计时器，摘掉挂在调用者 signal 上的监听
    clearTimeout(timerId)
    callerSignal?.removeEventListener('abort', forwardAbort)
  }
}

import { HttpError } from '@/errors/EngineError/NetworkError/HTTPError'
import { fetchWithTimeout } from './http'
import { FetchOptions } from './types/fetch-options'

/**
 * 获取文本内容：检查 HTTP 状态，再读出全文。
 * 取消、超时、网络错误都由 fetchWithTimeout 统一处理，这里不需要 try/catch。
 */
export function fetchTextWithTimeout(url: string, options: FetchOptions = {}): Promise<string> {
  return fetchWithTimeout(url, options, async (response) => {
    // 服务器回应了，但给的不是我们要的文件（404 等）：重试没用
    if (!response.ok) {
      throw new HttpError(url, response.status, response.statusText)
    }

    // 开发服务器对不存在的路径常常回 index.html（SPA fallback），状态码却是 200
    const contentType = response.headers.get('content-type') ?? ''
    if (contentType.includes('text/html')) {
      throw new HttpError(
        url,
        404,
        'Expected text file but got HTML (likely SPA fallback — file does not exist)'
      )
    }

    return await response.text()
  })
}
  • 全仓库只有 fetchText.ts 调用 fetchWithTimeout，改签名不影响别处。fetchTextWithTimeout 的签名没变，loadHW2OBJ、loadPRTSHTxt、createHW2Scene、Shader.ts 都不用改。
  • loadHW2OBJ 等处自己写的 signal.throwIfAborted() 保留：入口那几处变成了双保险；await 之后那几处管的是另一件事（响应在取消之前就到了，但还没轮到它们处理），仍然必需。
  • 这两份代码我在副本里验证过：tsc 严格模式、生产模式 ESLint、Prettier 都通过；用本地服务器跑了 10 个场景（先取消、等响应头时取消、读正文时取消、超时、404、HTML、不带原因的取消、正常、慢正文、连不上），全部符合清单，结束时调用者 signal 上的监听都是 0。

9. 这段代码有多通用

能直接搬到别的项目吗？能，条件是：

  • 项目用 fetch 发请求；
  • 浏览器基线 2022 年起：throwIfAborted 从 Chrome 100、Firefox 97、Safari 15.4 开始支持；abort(原因) 和 signal.reason 是 Chrome 98、Firefox 97、Safari 15.4（MDN 兼容数据）。Node 18 起也都有；
  • 换掉三个项目自己的错误类（NetworkError、NetworkTimeoutError、HttpError）和 FetchOptions 类型。fetchText.ts 里「拿到 HTML 就当 404」那条是针对开发服务器的，别的项目按自己的情况决定要不要。

比代码更通用的，是推出它的那几步。任何一个「可以取消的异步操作」，都可以照这个顺序问自己：

  1. 平台自己认 signal 吗？认的话，直接把调用者的 signal 交给它（第 2 版），到此为止。
  2. 有没有第二个「该停了」的理由（超时、兄弟任务失败）？有，就自己建一个开关，两个理由都来按它，按的时候写清原因（第 3、4 版）。
  3. 进门先 throwIfAborted()（第 5 版）。
  4. 失败时以开关上写的原因为准，不去猜错误的名字（第 4 版的 catch）。
  5. 等整件事结束了再收拾：摘监听、停计时器（第 6 版）。

图片加载就是一个平台不认 signal 的例子：Image 没有 signal 选项，所以 loadFace（loadHW2CubeImages.ts:19–79）要在灯亮时自己停下工作（去掉 src），其余几步完全一样。

什么时候不该用它：只要能取消、不要超时，就用第 2 版那一行。等基线升到 2024 年（AbortSignal.any 从 Chrome 116、Firefox 124、Safari 17.4 开始支持），可以用它把两盏灯合成一盏，省掉转发和摘监听。不过「超时只管响应头」这个决定仍然要自己写，因为 AbortSignal.timeout() 会把读正文的时间也算进去。
