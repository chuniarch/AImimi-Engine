每帧先抄一份：两遍必须看同一个场景

第 44 课要把两遍拆成两个独立的 Pass。这一课先在第 42 课的 drawScene 上试着切开：切开以后，每一半只能自己去读场景，于是两遍读到的可能不是同一个场景——影子和物体对不上，而且不报错。办法是每帧开始时把要用的东西抄一份：物体列表、相机矩阵、灯的快照；两遍只读这一份。这就是 frame/ 里 RenderListBuilder 做的事。

和你的目标的关系 —— 阴影是「两遍必须看同一个场景」最直接的例子：阴影图照第一遍看到的场景画，第二遍拿它来比。两遍看到的物体位置或灯的方向不一样，影子就错位。HW1 阴影设计文档里的 DirectionalLightSnapshot，就是这一课的「灯的快照」。
默认你已经会的：① 第 42 课的 drawScene、Mesh、Scene、灯和阴影设置；② Object.freeze（第 42 课用过）。第 31 课第 6、7 节从真实代码讲过「拍一张照」和复制、冻结两条规则；这一课换成阴影场景，看不这样做时画面怎样错。
这一课讲的：把 drawScene 切成两半；谁能在两遍之间改场景；先抄一份；抄什么、借什么；冻结；只在开头检查一次；代价；对照 src/rendering。
在一帧里的位置和寿命：快照在每帧开头建一次，所有 Pass 用完就扔，下一帧重新建；它不拥有任何资源，只借用。
页面会用到你的显卡：一块 480 × 300 的画布，外加检查卡片里临时建的几块。

1. 把 drawScene 切成两半

第 42 课的 drawScene 在开头算好灯和相机的矩阵，然后两遍都用它们。第 44 课要把第一遍、第二遍拆成两个独立的对象，各自的 execute 被依次调用。拆开以后，开头那几行算给谁？只能每一半自己算。先不加任何新东西，原样切开：

点「读场景」：两半一共有 15 行去读 scene、light、mesh、camera。前一半在一个时刻读，后一半在稍后的另一个时刻读。只要这两个时刻之间场景没变，结果就和第 42 课一样——备课时实测，切开后的画面和第 40 课逐像素相同。

2. 两遍之间有人改了场景

两遍之间谁能改场景？不会是浏览器事件。JavaScript 的一段同步代码一旦开始，就会一直跑完，中途不会被别的代码打断（MDN · JavaScript execution model · Run-to-completion）；拖动滑块、移动鼠标的回调，只能在这一帧跑完之后才运行（显示器的刷新、浏览器和 rAF 怎样配合，为什么事件插不进来，见第 48 课）。能插进两遍之间的，只有这一帧里自己运行的代码：

  • 其他 Pass。第 44 课以后，场景会把自己要的 Pass 交给引擎（HW2 的 PRT、FFT 的十几步计算）。哪个 Pass 顺手改了场景——比如 HW1 想让三角形随时间移动，有人把这一步写进了排在中间的某个 Pass——排在它后面的 Pass 就看到另一个场景。
  • 回调。three.js 在画每个物体之前调用 object.onBeforeRender（WebGLRenderer.js:2003），在阴影那一遍里调用的是另一个 onBeforeShadow（WebGLShadowMap.js:360）。在其中一个回调里挪动物体，只有那一遍看得到。

  • 灯的矩阵不放进快照，而是由 lightViewProjection(light) 从灯的快照算出来：输入是冻结的快照，所以同一帧里两遍各算一次，得到的 16 个数完全相同（实测两次结果逐项相等）。HW1 设计文档里的 createDirectionalShadowView 就是这样一个纯函数（设计 §3.7）。第 45 课会看到：真正需要它的只有阴影那一遍，第二遍会从别处拿到它。

  • 两遍的参数只剩 frame（加上画图要的 gl 和 Manager）。它们不知道场景是什么形状——有没有父子层级、哪些物体不可见、灯挂在哪里——这些都由 buildFrame 处理完，交出来的是一张平的列表。

  • 每帧 GL 命令数没变：仍是 48 条、0 次查询。抄一份只花 CPU 时间，不多发任何 GL 命令。

快照不是把场景整个深拷贝一遍。规则是：值抄下来，资源借用。

    

      

        
东西快照里放什么为什么

        
物体的位置（model 矩阵）、相机的 视图×投影复制 16 个数，冻结每帧都可能变；16 个数，复制很便宜

        
灯的方向、bias、正交范围复制数值，冻结同上。设计文档的 DirectionalShadowSnapshot 也是复制数值（设计 §3.6）

        
Geometry、Material、阴影图（RenderTarget）借用同一个对象Manager 按对象身份查表：要是每帧复制出新对象，表里每帧多一条（第 41 课第 5 节的「每帧新建描述对象」）。借用不要求对象不会变：三样里只有 Geometry 不能变（第 42 课），另外两样哪些部分会变、怎么处理，见表下面

        
材质参数（uColor）不抄，第二遍现读 getParameters()小引擎和真实代码都没有给材质拍快照。所以「Pass 执行期间不要调 setParameter」只是约定，没有东西强制（真实代码的注释写明了这一点：RenderItem.ts:11–12、RenderList.ts:20）。阴影参数要被好几个材质读，不能只靠约定——这是第 45 课的事

改尺寸的时机要紧。备课时用真实代码量过（4×4 的目标，第一遍清成 1，第二遍读一个像素，第 2 帧改成 8×8）：两帧之间改，第二遍读到 1，正确；两遍之间改，第二遍读到 0，不报错——第二遍查表时 Manager 重建出一张全是 0 的新纹理，第一遍画的那张已经删了，下一帧恢复；在第一遍写它的作用域里改，出作用域时抛 RenderTargetUnavailableError「target was disposed or resized」（WebGL1SurfaceScope.ts:318–333），整帧作废。所以规矩和材质参数一样：设置在帧外改，帧内只读。GUI 的回调本来就只能在两帧之间运行，为什么，见第 48 课。


    
5. 冻结：别让一个 Pass 改掉下一个 Pass 的输入

    
快照只有一份，所有 Pass 共用。如果某个 Pass 改了它，排在后面的 Pass 就拿到被改过的输入。比如写第一遍的人想「地面不投影子，第一遍跳过它」，图省事直接从 frame.items 里把地面删掉。下面的卡片 A 用一份不冻结的副本跑这段代码，卡片 B 用真正冻结的 frame：

    

    

    
正确写法是 frame.items.filter(…)：得到一个新数组，只给自己用。HW1 的设计里，RenderItem 会多一个从 Mesh 抄来的 castShadow，ShadowMapPass 按它过滤（设计 §2 每帧数据流）。第 31 课第 7.3 节用「按离灯远近排序」演示过同一件事。

    
还有一个细节：矩阵为什么抄成普通数组，而不是 Float32Array？因为带元素的 TypedArray 冻结不了——Object.freeze(new Float32Array(16)) 直接抛 TypeError: Cannot freeze array buffer views with elements（实测）。所以 snapshotMatrix 用 Array.from 复制成普通数组再冻结；之后谁写 modelMatrix[12] = 5，都会抛 Cannot assign to read only property '12'。真实代码的 copyMat4Snapshot 也是这样做的。

7. 代价

    
抄一份要时间。备课时在无界面 Chrome 里量 buildFrame：这个场景（2 个物体、1 盏灯）每次约 0.003 毫秒；1000 个物体每次约 0.70 毫秒（100 次的平均）。一帧的预算是 16.7 毫秒。第 31 课第 7.7 节在真实的 RenderListBuilder 上量过 1000 个 Mesh，多花约 0.4 毫秒。场景大到几万个物体时才需要考虑别的做法（例如跨帧复用数组），真实代码现在明确不这样做（RenderList.ts:14「不会跨帧复用内部数组」）。

架构视角：three.js 靠约定，本项目靠快照。three.js r177 的 render 开头也只更新一次世界矩阵（WebGLRenderer.js:1537），再遍历一次场景生成渲染列表（:1582）。但列表里的项引用的是活的物体，不是矩阵的副本；阴影图那一遍（:1607）不读这张列表，而是自己从场景根节点再递归一遍（WebGLShadowMap.js:390），现读 object.matrixWorld（:342）。所以只要没人在 onBeforeRender、onBeforeShadow 里改物体，两遍看到的就是同一个场景——这是约定，不是保证。本项目把它变成了保证：Pass 根本拿不到场景。
