core：Resource、错误体系与 requireNonNull

从这一课起逐个模块精读。第一站是 core：所有包都依赖它，它自己不依赖 rendering 里的任何包。里面只有几样东西——一份生命周期协议（Resource）、一套描述失败的词汇（错误类）、一个收窄 null 的小工具（requireNonNull），以及上周搬进来的纯数学类型。这一课逐行读前三样，重点看一条还没定下来的规则：释放时 listener 抛错怎么办。

和你的目标的关系 —— Task 15 的 Backend 抛出的每个错误都来自这里的类，Renderer 要按类别决定怎么办；Resource 的通知是 Backend 删除 GPU 副本的唯一入口。你正在重写的 ResourceManager 里，beforeDelete 故意用抛错做屏障——这个错误会一路冒到本课第 4 节的那个循环里。

0. 热身：前几课还记得吗

1. 设计问题：core 里该放什么？

core 在依赖图的最底部：scene、resources、frame、backend 都 import 它，它不 import 其中任何一个。所以放进 core 的东西要同时满足三条：被好几个包需要；不知道 GL、也不知道 Scene；是协议或词汇，而不是某种具体资源。现在的 core 正好是这几样：

文件它是什么谁在用
Resource.tsCPU 资源的生命周期协议：计数、释放、通知Geometry、Material、ShaderModule、纹理、RenderTarget 继承它；四个 Manager 订阅它
errors/描述失败的词汇：RenderingError 和它的 26 个子类所有包
requireNonNull.ts把 T | null 收窄成 T各个 Manager 创建 GL 对象时
validation.ts（10 月 10 日新增，6.1 节）「是不是对象、boolean、有限数」的共用规则，报什么错由调用方给Material、Texture2DSamplingSource、PerspectiveCamera
math/tuples.ts跨包传值的纯类型Transform、Material、ViewState、RenderItem

想一想（先不用回答）：WebGLContextLostError、WebGLOperationError 也住在 core/errors 里，名字里却带着 WebGL。它们没有 import 任何 GL 类型，但「WebGL」这个知识已经进了 core 的名字。将来加 WebGL2 后端时它们还适用吗？加一个独立的 WebGPU 模块呢？这个问题留到本课最后。

2. 精读 ①：Resource 的状态与两个抽象成员

export abstract class Resource {
  private disposedValue: boolean = false        // :29  单向：只能从 false 变成 true
  private sceneReferenceCountValue = 0          // :38  持有它的 Scene 数，不是 JS 引用数
  private readonly disposeListeners = new Set<DisposeListener>()  // :43  按注册顺序

  protected abstract readonly resourceType: string   // :50  稳定的诊断名，不用 constructor.name
  protected abstract disposeCPUData(): void          // :59  子类释放自己的 CPU 数据
  • 三个字段都是 private。子类（比如 Geometry）碰不到 disposedValue，也就没法把一个已经释放的对象改回可用（Resource.ts:24–25）。要用这个状态，只能读公开的 disposed，或者调用 assertUsable()（:77–81）。
  • readonly 管的是「能不能换掉这个 Set」，不是「能不能往里加」。注释写得很直白（:41）：禁止替换 Set，但允许增删其中的 listener。
  • resourceType 为什么要子类自己写一个字符串？因为生产构建会压缩类名，constructor.name 靠不住（:47–50）。错误消息里的「Geometry has been disposed」用的就是它，还有专门的测试钉住（Resource.test.ts:338）。记住这一条——第 9.2 节会看到，错误类自己没有做到同样的事。
10 月 10 日更新（提交 2c8291a）：assertUsable() 从 protected 改成了 public（Resource.ts:63–81），注释换成「供子类与外部借用者在使用本资源前统一验证生命周期」。改它是为了借用方：Mesh 构造时要确认 Geometry、Material 还活着，以前只能自己写 if (geometry.disposed) throw new ResourceDisposedError('Geometry')，资源名要再手写一遍；现在写 geometry.assertUsable()，错误里的名字由资源自己的 resourceType 给出，和 onDispose 用的是同一条检查（3.1 节）。src/rendering 里现在有 40 多处这样的调用：Mesh、Material、Texture2DSamplingSource、各个资源自己的 getter，还有 RenderTargetManager 和 Texture2DManager。新注释也写明了它保证不了什么：成功只说明「这一刻 CPU 资源还活着」，不保证 GPU 上传成功或 context 可用；跨过 await 以后要在用的地方重新检查。同一个提交还给 core 加了一个模块 validation.ts，见 6.1 节。

3. 精读 ②：订阅与通知

3.1 onDispose：已经释放就拒绝，返回一个取消函数

onDispose(listener: DisposeListener): () => void {
  this.assertUsable()      // :105  已经释放就抛 ResourceDisposedError
                           //       「避免创建永远不会触发的订阅」（:102）
  this.disposeListeners.add(listener)
  return () => {
    this.disposeListeners.delete(listener)               // :110  Set.delete 天然幂等
  }
}
// 10 月 10 日以前，第一行写的是
// if (this.disposedValue) { throw new ResourceDisposedError(…) }，行为一样
  • 为什么拒绝，而不是悄悄返回一个什么也不做的取消函数？悄悄接受的话，调用方会以为自己将来能收到通知，它的 GPU 副本就永远等不到删除（:102）。大声拒绝，错误就出现在订阅的那一行。
  • 为什么返回一个函数，而不是提供 removeListener(listener)？调用方只要保存这一个闭包，不必再留着 listener 的引用；Manager 的 entry 里存的正是它（第 4 课的 { resource, unsubscribe }）。three.js 用的是另一种写法：removeEventListener(type, listener)，调用方必须拿着同一个函数对象。

3.2 finalizeDisposal：唯一真正的清理路径

private finalizeDisposal(): void {
  if (this.disposedValue) return          // :205  重入时直接返回
  this.disposedValue = true               // :207  ① 先标记
  for (const listener of this.disposeListeners) {
    listener()                            // :210  ② 按注册顺序通知
  }
  this.disposeListeners.clear()           // :213  ③ 清空
  this.disposeCPUData()                   // :215  ④ 最后释放 CPU 数据
}

第 5 课讲过，只有两个入口能到达这里：没有 Scene 引用时的 dispose() / tryDispose()，以及引用数从 1 减到 0 的那一次 releaseSceneReference()（:192–203）。这一课看顺序本身：

  • 先标记。listener 里如果又调了 dispose()，:205 直接返回，不会重复通知；想再订阅，:105 拒绝；想读数据，公开 getter 会因 assertUsable 抛错。所以 Manager 的 listener 只按对象身份查自己的表，不再读 CPU 数据——OES 顶点输入管理器的注释写明了这一点（WebGL1OESVertexInputManager.ts:160）。
  • 先通知，后释放 CPU 数据。Manager 删 GPU 副本时要用 CPU 对象当 key；CPU 数据最后才清，保证通知期间对象身份和它的记录都还在（项目文档「监听者为何先于 CPU 清理」一节专门讲这个）。
  • 在遍历中退订自己，安全吗？GeometryManager 的 listener 会调用 release，而 release 里要执行 entry.unsubscribe()（GeometryManager.ts:232）——也就是在 for-of 遍历这个 Set 的途中，把当前这一项删掉。JavaScript 的 Set 按插入顺序遍历，删除当前项或已访问过的项不影响后面的项；只有删掉还没访问到的项，它才会被跳过。卡片 A 会验证。three.js 的做法不同：派发前先复制一份监听器数组（EventDispatcher.js:113–114），因为从数组里删元素会让后面的下标前移。

4. 一条还没定下来的规则：listener 抛错怎么办

上面那个循环没有 try/catch。第一个 listener 一抛错，后面三步都不再执行：disposed 已经是 true，但后面的 listener 收不到通知，Set 没清空，CPU 数据也没释放。这是项目有意留下、写进待决清单的一条（TODOList.md:5–36）。它的后果分三层：

  1. 这个资源自己：处在「已标记释放、却没清理完」的半截状态。再调一次 dispose 也救不回来：:183 看到 disposed 为 true 就直接返回（卡片 B）。
  2. 其他 context：后面没收到通知的 listener，往往是另一个 context 的 Manager。它的 GPU 副本和订阅会一直留到那个 Backend 关闭（第 4 课审查视角提过）。
  3. 往上一层的 Scene：Scene.dispose() 先把自己标记为 disposed，再逐个交还引用（Scene.ts:134–140）。其中一个资源的 listener 抛错，循环就断了；此后 release 返回 false，再 dispose 直接返回。剩下的资源再也释放不掉（卡片 C）。一个 listener 的错误，变成了另一个资源的泄漏。

会抛错的 listener 从哪里来？最现实的来源就是 GeometryManager 和 ProgramManager 的 release：它们先调用 beforeDelete，这个钩子一抛错，release 就停在删除之前，把 entry 留下来等重试（GeometryManager.ts:209）。在 Manager 内部，这是故意的屏障；但它是在 Resource 的通知循环里被调用的，所以这个错误会一路冒到这里。

待决清单列出了要回答的几个问题。三种典型做法：

做法怎么做好处代价
① 遇错即停（现状）第一个错误直接冒出去简单；错误不会被吞掉上面三层后果全部存在
② 继续通知，最后汇总每个 listener 各自 try/catch；全部通知完、清空 Set、释放 CPU 数据之后，把收集到的错误用 AggregateError 一次抛出一个 Manager 出错不连累别的；资源一定能完整释放Scene.dispose 也得照样改，否则它仍会中途停下；还要想清楚 disposeCPUData 自己抛错怎么办
③ 规定 listener 不许抛错把「不抛错」写进 onDispose 的契约；Manager 在自己的 listener 里 catch 并记录Resource 保持简单契约靠自觉遵守；要和 Manager「beforeDelete 抛错即屏障」的设计协调
一处小小的文档漂移：待决清单写的是「Resource.dispose() currently: 1. marks the resource as disposed…」。那是引入引用计数之前的写法；现在这个循环在 finalizeDisposal() 里，dispose、tryDispose、releaseSceneReference 三个入口都会走到它，所以同一个问题的影响面比清单里写的更大。

5. 精读 ③：错误体系

5.1 基类 EngineError：旧引擎留下的通用结构

RenderingError 继承的是项目原有的 EngineError，它给所有错误提供同一套字段：code（稳定的错误码）、context（诊断上下文）、recoverable、cause（原始错误）、timestamp，以及给日志用的 toJSON()（:92–102）。构造函数里有三行值得认识：

  • Object.setPrototypeOf(this, new.target.prototype)（:67）：编译到 ES5 时，继承内置的 Error 会丢原型链，instanceof 失灵，这一行把它接回来。编译目标是 ES2015 以上时不需要，但也无害。
  • this.name = this.constructor.name（:69）：错误的名字取自类名。第 9.2 节的发现就从这一行开始。
  • Error.captureStackTrace(this, new.target)（:81–83）：V8 引擎的扩展，让调用栈从「创建错误的那一行」开始，不包含构造函数自己。

5.2 RenderingError：冻结诊断现场

constructor(message: string, code: string, details: RenderingErrorDetails = {}) {
  const frozenDetails = Object.freeze({ ...details })    // :34  复制一层，再冻结最外层
  super(message, code, { context: frozenDetails, recoverable: false })   // :38–41
  this.details = frozenDetails                            // :43  details 与 context 是同一个对象
}
  • 为什么复制再冻结？错误创建之后，调用方可能继续修改自己手里那个对象。复制一层，错误里记下的就是「出错那一刻」的现场（RenderingError.ts:19–23）。
  • 只冻结最外层。details 里嵌套的对象还是调用方原来那个，改它就能从错误里看到（卡片 D）。所以 details 里最好只放字符串、数字这样的值。
  • recoverable: false 是写死的——这是第 6 课 8.2 节的审查发现，这里不再展开。

5.3 26 个子类：每个类固定一个错误码和它最窄的上下文

子类的写法都一样：构造参数只收它能解释的上下文，错误码写死。例如 ResourceDisposedError 只收一个 resourceName，码是 RESOURCE_DISPOSED；ResourceHasSceneReferencesError 多收一个当前引用数。其中 19 个写在 RenderingError.ts 里（Task 1 一次落全），后来的任务又加了 7 个单独的文件，比如 InvalidMeshError.ts。

于是，一个错误有三种「身份」，各有用处：

身份是什么适合用来
instanceof类本身程序分支：「是 context 丢失吗」。压缩改不了它
code写死在子类里的字符串日志聚合、统计、国际化映射
name来自 constructor.name，除非子类自己赋值给人看的调试输出——但见第 9.2 节

6. 精读 ④：requireNonNull

export function requireNonNull<T>(value: T | null, errorFactory: () => Error): T {
  if (value === null) {       // :16  只认 null，不认 falsy
    throw errorFactory()      // :17  惰性：只有失败时才创建错误
  }
  return value                // :20  原样返回，对象身份不变
}
  • === null，不是 !value。0、false、空字符串都可能是合法结果，比如 attribute location 0（requireNonNull.ts:11–12）。
  • 传工厂，不传错误对象。成功路径上不创建错误、不拼诊断字符串；参数类型是 () => Error，传一个普通字符串会编译不过（测试里用 @ts-expect-error 钉住）。
  • 只管「null 表示创建失败」。getUniformLocation 返回 null 是正常结果：这个 uniform 没有被使用。那种地方用 requireNonNull 就错了。

一个实测出来的事实：现行 WebGL 1.0 的接口定义里，createBuffer、createProgram 等都已经不返回 null，只有 createShader 还是可空的；TypeScript 5.8 的类型与此一致（lib.dom.d.ts:26023 的 createBuffer(): WebGLBuffer，:26031 的 createShader(…): WebGLShader | null）。Chromium 在 context 丢失后，create 返回的是一个作废的对象（isBuffer 为 false），而不是 null（见 API 速查的实测清单）。

所以今天真正起作用的，是紧跟在 create 后面的那一次 context 检查。ProgramManager 是这样写的：gl.createProgram() 之后立刻 assertAvailable('create program')，然后才 requireNonNull（ProgramManager.ts:108–114）。OES 顶点输入管理器的注释也说得很老实：requireNonNull「保留对历史实现或异常测试替身的 null 防御」（WebGL1OESVertexInputManager.ts:87–101）。对 createShader，它仍然是真正的类型收窄。

6.1 10 月 10 日新增：validation.ts，规则共用、报什么错由调用方定

需求。Material 要查「float 参数是有限数」「depthTest 是 boolean」「options 是对象」；PerspectiveCamera 要查「fovY 是有限数」「options 是对象」。规则一模一样，要抛的错误却不一样：Material 抛 InvalidMaterialError，字段路径写成 parameters.uRoughness；相机抛 InvalidPerspectiveCameraError，字段是 fovY，还要把收到的原值放进 details。

// Material.ts（提交 77c6e7e）
function requireFiniteNumber(value: unknown, fieldName: string): number {
  if (typeof value !== 'number' || !Number.isFinite(value))
    throw new InvalidMaterialError(fieldName, 'must be a finite number')
  return value
}
// PerspectiveCamera.ts（提交 86036aa）：同名、同规则，只是 throw 的换成
//   new InvalidPerspectiveCameraError(fieldName, 'must be a finite number', { received: value })
// requireBoolean、「是不是非数组对象」也各写了一份

第 1 版的问题：规则有两份，改一份忘了另一份，两边就不一致；想把规则搬进 core 共用，又不能让 core 替调用方决定抛哪个错误、字段路径怎么写。第 2 版就是现在的 validation.ts：函数只管规则，错误由调用方用工厂交进来，写法和上面的 requireNonNull 一样。 

// src/rendering/core/validation.ts:63–69（注释是课程加的）
export function requireFiniteNumber(value: unknown, errorFactory: () => Error): number {
  if (typeof value !== 'number' || !Number.isFinite(value)) {   // '1'、NaN、±Infinity 都不过
    throw errorFactory()     // 失败时才调用工厂；抛的就是工厂交回的那个错误对象
  }
  return value               // 原样返回：-0 还是 -0，1e100 还是 1e100
}

// 调用方一：PerspectiveCamera.ts:45–50
const fovYInput = options.fovY          // 只读一次：options 上的 fovY 可能是 getter，每次读的值都可能不同
const fovY = requireFiniteNumber(
  fovYInput,
  () =>
    new InvalidPerspectiveCameraError('fovY', 'must be a finite number', { received: fovYInput })
)

// 调用方二：materialParameters.ts:159–161（copyParameter 的 float 分支）
requireFiniteNumber(parameter.value, () =>
  createError(fieldName, 'must be a finite number')  // 这个工厂也是调用方交的
)
函数放行拒绝不管的事
assertNonArrayObject任何非 null、非数组的对象，包括 Date、Map、TypedArraynull、数组、数字、字符串字段在不在、字段名对不对、字段值合不合法
requireBooleantrue、false1、'true'、null不做 Boolean(value) 转换，不补默认值

注释给这条设计起的名字是「规则与错误分离」（validation-rule-error-separation）。三个函数都不复制、不冻结输入，成功时也不创建错误对象。现在用它的是 Material、ParameterBlock、Texture2DSamplingSource 和 PerspectiveCamera；第 9 课、第 11 课的节选已经换成了新写法。

10 月 19 日更新：「调用方二」原来在 Material.ts 里，直接写 new InvalidMaterialError(…)。新的参数块 ParameterBlock 也要用同一套复制规则，可它出错时该报 InvalidParameterBlockError，所以 copyParameter 搬进了 materialParameters.ts，又多收一个错误工厂 createError：Material 交进来的造 InvalidMaterialError（Material.ts:21–22），ParameterBlock 交进来的造 InvalidParameterBlockError（ParameterBlock.ts:53–54）。这是本节的思路往上走了一层：validation.ts 不替调用方决定报什么错，materialParameters.ts 也不替 Material 和 ParameterBlock 决定。

9. 架构视角

9.1 对照 three.js

  • 通知机制相同，生命周期不同。three.js 的 BufferGeometry、Material、Texture 都继承 EventDispatcher，dispose() 派发一个 dispose 事件，渲染器内部的模块监听它、删除 GPU 数据——和 Resource 加 Manager 是同一种观察者模式。不同在于：three.js 的 dispose 不是终点，对象之后还能再用、再上传（第 5 课）；这里的 disposed 是单向的。
  • 创建 GL 对象不检查 null。three.js 创建 buffer 就是一行 gl.createBuffer()，紧接着 bind、上传（WebGLAttributes.js:11–14）。context 丢失交给渲染器统一处理，而不是在每个创建点防御。
  • 没有错误类体系。出错时在控制台打印、调用 onShaderError 钩子，然后继续运行（第 6 课 8.1）。

取舍：three.js 代码少，对「用完再用」很宽容；本项目多写了一层协议和一套词汇，换来的是「释放只有一次、失败有名字」。代价也看到了：协议越严格，像第 4 节那样没定下来的角落就越显眼。

9.2 审查视角：生产构建里，错误的 name 是空字符串

第 2 节说过，Resource 特意不用 constructor.name，因为生产构建会压缩类名。可错误类的 name 恰恰来自 this.name = this.constructor.name（BaseError.ts:69）。项目的生产构建用 terser 压缩（vite.config.ts:133），Vite 6.3.5 对 ES 模块产物会打开 terser 的 module 选项，顶层的名字都可以改。我用同样的设置压缩了一段只 new 错误的代码，实测结果： 

未压缩：   ResourceDisposedError   WebGLContextLostError   InvalidMeshError
压缩之后："" （空字符串）          ""                       InvalidMeshError

code 和 instanceof 都不受影响。InvalidMeshError 能保住名字，是因为它在构造函数里自己写了 this.name = 'InvalidMeshError'（InvalidMeshError.ts:15）；单独成文件的 7 个错误类里有 4 个这样做了，写在 RenderingError.ts 里的 19 个都没有。测试也挡不住：RenderingError.test.ts:198 断言的是 error.name === error.constructor.name，压缩之后两边都是空字符串，照样通过——它检查的是「前后一致」，不是「名字稳定」。影响在于日志：toJSON() 输出的 name（BaseError.ts:94）会是空的。

想一想（不用写代码）：你会在哪一层修？每个子类像 InvalidMeshError 那样自己赋值；在 RenderingError 或 EngineError 里想办法；还是在构建配置里让 terser 保留类名？各自的代价是什么？再想一个测试：不跑生产构建，也能挡住这个问题。
